## 0. 定位

**XOps 不是一个开箱可用的 AI 编程运营平台，是一个基础框架。**

它只提供一条核心机制，以及围绕这条机制的最小配套：

> **由 skill 赋能、agent 执行的 task；数据源是 Git 仓；输出落表，可查询、可看板、可驱动流程、可交给插件继续处理。**

> **D44 之后，表只在产出侧与查询侧**：执行读不到表。需要表数据的技能，由调用方经 MCP 查好、作为**任务的输入参数**传进去（§5.4）。

```text
      数据源              执行              产出           消费
  ┌────────────┐    ┌────────────┐   ┌────────┐   ┌──────────────┐
  │ Git 仓(只读)│───►│ task       │──►│ 表的行  │──►│ MCP 查询      │
  │ 输入参数    │    │ = skill    │   │        │   │ 看板          │
  └────────────┘    │ + agent    │   └────────┘   │ 流程流转       │
                    └─────┬──────┘                │ 插件继续处理    │
                          │ onComplete            └──────────────┘
                          └──► 插件 / 另一个任务（深度最多 1 层）
```

**一切业务写入经 MCP，一切围绕项目转。** Web 只读。（两个非 MCP 入口都被削得只剩一件事可做，见 §3）

**可本地部署**（本版新增的定位主张，既有需求包里没有这条）。XOps 不以替代任何现有工具为目标——它和 GitHub Actions、Issues、Projects 这类东西**特性有重叠是正常的**，用户想用哪个用哪个。它的差异不在功能清单上，在三件事：**MCP 是唯一写入面**（为 agent 而不是为人设计）、**执行与数据共用一本账**（跑了什么、读的哪一版、产出什么，在同一处可追溯）、**能力用自然语言扩展**（写技能，不写 YAML）。

### 三个扩展点

框架自己很薄，能力靠这三样长出来：

| 扩展点 | 谁写 | 跑在哪 | 它够得到什么 |
|---|---|---|---|
| **技能** | 任何项目成员，自然语言 | 一次性容器 | 只有声明过的代码与出网。无凭据、无写表路径 |
| **插件** | 由技能生成的 JS 代码 | **QuickJS 载体**，一次调用一个 runtime | **默认为零**；输出插件另有声明出来的三样，见 §6.4 |
| **模板** | 一套表 + 流程 + 插件绑定 | —— | 取决于它带的插件声明了什么 |

**技能和插件不是同一件事的两种写法，是两个位置。** 技能在容器里、费 token、能读代码、产出一份报告；插件在服务端、不费 token、只吃平台喂给它的 JSON、产出一个判断或一次投递。

> 第 10 版在这里写的是"插件与平台同权限，高信任"。**第 11 版不再是这样**：Rust 进程里跑不了 TS，插件改由 QuickJS 载体承载，而那个载体默认不给任何宿主绑定。**能力从"全部"变成"声明出来的那几样"**（D52）。但要注意换掉的是**执行**这一半，**判断**那一半没换——一个能通过任何东西的流转插件，隔离拦不住它。§6.4 把两半分开讲。

### 与 XForge 是配合关系，不是绑定关系

```text
   XForge 单独用  ✅  它的 local 审批在真实终端里完成，不需要任何外部系统
   XOps  单独用   ✅  表、技能、任务、插件、流程，全都不需要 XForge 存在
   两者一起用     ✅  XOps 作为 XForge 的 MCP 审批 provider（§10）
```

XOps 挂了，XForge 侧的表现是"这一轮审批失败、可重试"，不是"变更被卡死"，更不是"变更被放行"。

### 实现基线

前十版刻意不写技术选型。**第 11 版写了**，因为有四处选型已经反过来影响概念本身——尤其是插件：语言一换，"进程内、与平台同权限"这条就不再是默认结果，而是一个要专门去实现的东西，而它并不值得实现。

```text
语言与工程形态   Rust，单 workspace 多 crate；一个需求包对应一组 crate
执行引擎         AttaCore（github.com/openatta/AttaCore）
                 以 attacored 分立进程运行，JSON-RPC 2.0 over Unix socket
一次性容器       由 XOps 实现 AttaCore 的四个执行契约
                 （Process / FileSystem / Network / Sandbox）的容器后端
                 —— 全部工具执行落进容器，模型凭据留在容器外
插件载体         QuickJS：一次调用一个 runtime，默认零宿主绑定
存储             SQLite，经一层只用基本 CRUD 的存储契约（D46 不变）
MCP              XOps 是 MCP **server**（对 agent 而言），Rust 实现
Web              后端 Rust 只读 HTTP；前端 TypeScript + React SPA，
                 构建产物随二进制发行
```

**四条选型各自的射程，写在它们该在的地方**：执行引擎与容器在 §5.5，插件载体在 §6，Web 在 §8，存储在 §4.8。这里只说清楚**哪些是选型、哪些不是**：

| 是选型（可换） | 不是选型（换了就是换设计） |
|---|---|
| Rust · SQLite · React | "一切写入经 MCP"、"Web 只读"、"表级写串行"、"结算只认结算表上的行" |
| AttaCore 这个具体引擎 | "XOps 与执行引擎分立、只有一条执行契约"（`EXE-014`） |
| QuickJS 这个具体载体 | "插件由技能生成、维护者安装、源码必须可读、能力默认为空" |
| 契约文件用什么方言（OpenAPI · JSON Schema · `cargo-public-api` 快照 · SQL DDL） | **"接口有三个契约面，各有一份基线记录，实现引用它而不复述它"**（D57，见 [`docs/contracts/`](contracts/README.md)） |

> ⚠️ **一条要在开工前认下来的跨仓依赖**：AttaCore 的四个执行契约已经完备（全部内建工具都经它们碰机器），并且 `exec.process` / `exec.filesystem` / `exec.network` / `exec.sandbox` **已登记进它的可替换扩展点索引**，信任级别是 **host-only**——`exec.process` 的声明用途原文就是"**which machine the work happens on**"。**缺的只有一样：Builder 上没有 `exec` 这个宿主注入位。** 那类注入位它已经有十六个，加一个是有先例的改动。**这是 XOps 侧的交付责任，不是等来的**——落点见 §5.5 与 RP-07。
>
> ⚠️ **另一条与插件有关的话要说清楚：XOps 的插件不是 AttaCore 的扩展。** 两者只是用同一种载体形态（QuickJS）。AttaCore 的 `script.carrier` 是它自己的钩子点扩展，跑在它的轮次里；XOps 的插件由 XOps 在流程求值与 onComplete 时调用，**与 AttaCore 的生命周期无关**。可以复用它 `script-host` 的做法（每次调用新建 runtime、中断器兜死循环、能力经声明解析），但**不要把两者接成一个东西**。

## 1. 四条设计原则

| # | 原则 | 它在实践中长什么样 |
|---|---|---|
| **P1** | **尽量简单。功能有了就行，不对用户怎么用做过多猜想。** | 只有**一种任务**、**一种数据形状（表）**、**一种流程** |
| **P2** | **规则由用户定，我们只按用户的规则做事。** | 平台不预置任何业务表、任何流程、任何质量标准、任何看板内容 |
| **P3** | **一切经 MCP，一切围绕项目。** | 没有 Web 写入面，没有管理后台，没有流程设计器 |
| **P4** | **扩展点是技能、插件与模板，不是配置项。** | 想要新能力，写一个技能或让 agent 生成一个插件，而不是等平台加一个开关 |

> P1 的反面是这套系统最容易走岔的方向：**只要开始为"缺陷"和"审批"分别建模，平台就会长出两套对象、两套视图、两套权限**，而它们本来是同一件事——一张表，加一条流程。

## 2. 一个项目里有什么

```text
┌──────────────────────────────────────────────────────────────────────┐
│                               项目                                    │
│               唯一的归属边界、权限边界、数据边界                        │
│            有一个不可变的**短名**（模板可用它组合可读标识）              │
└──────────────────────────────────────────────────────────────────────┘

 成员与角色     Git 仓库      技能与任务      表           插件        流程     看板
 ─────────    ────────     ──────────    ────         ────       ────    ────
 所有者        当前绑一个     公共 / 私有    系统表        由技能生成   有序节点  表的
 维护者        只读凭据      自然语言写     用户表        维护者安装   每节点：  一个
 成员          确切修订      订阅事件      受保护表      载体里执行   通过/拒绝 视图
                            可挂 onComplete 对外CRUD                  条件
                                          对内追加                    写入者

                            ↓ 全部经 MCP 读写 ↓

     ┌──────────────────────┐        ┌──────────────────────┐
     │  MCP —— 唯一操作面    │        │  Web —— 只读看板      │
     └──────────────────────┘        └──────────────────────┘
```

**项目是边界，不是团队也不是仓库。**

**非项目成员看不到项目的存在。** 查询一个自己不是成员的项目，得到的响应与查询一个真正不存在的项目**完全一致**——不是"无权限"，是"不存在"。否则错误码本身就成了探测他人项目的工具。

**项目的短名**：全平台唯一、创建后**不可变**、限定为便于手写的字符集（既有 R-01-16a）。平台自己不认识"缺陷 ID"这种概念，但模板会用短名去组合可被手写引用的标识（§9）。**一旦分配就再也改不了**——创建项目时必须让人清楚这一点。

## 3. MCP：唯一操作面

**窄接口纪律**（一条都不能松）：

```text
固定形状 schema                    未在 schema 中声明的字段一律拒绝，不静默丢弃
不提供任何通用透传 tool             没有"把这段上下文一起发过去"这种口子
身份只来自令牌                      参数里的 actor / user / author 一律被静默忽略
写操作幂等                          带幂等键的重复调用不产生第二次副作用
无权限与不存在返回相同错误           否则错误码就是探测工具
```

> **"任意表 CRUD"怎么不违反这条**：每张表建好之后，平台为它**派发一组专属的读写 tool**，各自带由该表 schema 生成的固定形状输入 schema。不存在一个 `{table, values: 任意形状}` 的通用写 tool。列名与类型在协议层是**被声明过的**，不是运行时随便塞的。

### tool 全景

> 这是一张速览表，用来看清操作面的规模。表里的概念在后文各章定义——**第一次读可以先跳过**。

| 域 | 意图 |
|---|---|
| **身份** | 查询当前身份 · 能力发现 · **查询我待处理的流程节点（跨项目聚合）** |
| **项目** | 创建 · 查询我参与的 · 查询详情 · 加成员 / 改角色 / 移除 · 归档 |
| **Git 仓** | 绑定（含只读凭据，绑定前验证确实只读）· 查询绑定与同步状态 · 轮换凭据 · 解绑 |
| **表** | 建表（声明列、**声明保护级别**）· 加列 · 查询表结构 · 列出项目的表 · 删表 · **每张表的专属增删改查 tool** · 查询单行完整历史 |
| **模板** | 列出可用模板 · 查看模板内容 · 在本项目实例化 |
| **技能** | 创建 / 更新（产生新版本）· 发起测试执行 · 发布 / 停用 · 查询内容与版本历史 · 声明归属 · 派生私有副本 |
| **任务** | 创建 / 更新 · 启用 / 停用 · 声明订阅哪些事件、读哪些数据源、写哪张表、**onComplete 挂什么** · 手动触发（非阻塞）· 查询执行历史与触发历史（**含被拒绝与被跳过的**）· **配置单次 token 上限与输出保留期** |
| **调度** | 配置任务的定时调度 · 查询下次触发时间 |
| **执行** | 查询状态 · 取消（产出与过程记录都在 `_runs` 表里查：`output` 与 `trace` 两列） |
| **插件** | 列出已安装插件 · **列出候选插件、查看其源码、能力声明与测试结果**（成员）· **读已安装插件源码与能力声明**（成员）· **安装候选插件（需维护者，安装时逐条披露能力）** · 停用 · 查询版本历史 · **读写插件配置**（需所有者） |
| **流程** | 定义 / 发布新版本 / 停用 · 列出流程定义与各版本 · **校验**（不落库；抓三件事：结算表≠主体表 · 无主体表时不得声明随行发起 · 筛选不得重叠（口径见 §7.1））· 发起实例 · 查询实例状态与卡在哪 · 取消实例 · **为某实例的某节点写入一行** |
| **看板** | 定义 / 查询 / 列出看板 |
| **XForge 登记** | 登记"本项目对应哪个仓" · 登记 "policyId → 哪条流程 + 结果列映射" |
| **通知** | 查询我的未读 · 标记已读（**只有这两个**——`_notices` 不派发通用查询 tool，§4.7） |
| **XForge 适配** | `submit_approval_request` · `poll_approval`（**形状由 XForge 定死，不可改**） |
| **审计** | 查询项目事件流 · 查询某对象完整历史 |

### 两个非 MCP 入口（都不是通用写入面）

| 入口 | 它只能做一件事 |
|---|---|
| OAuth 登录回调 | 完成身份验证、建立会话。**不能创建或修改任何业务对象** |
| Git webhook 端点 | 产生一个 git 事件。**不能创建或修改任何对象**，只能让订阅了它的任务被触发 |

## 4. 表：一切数据的形状

### 4.1 表与行

**项目下可以创建命名的表**，经 MCP 声明它有哪些列，然后对它做增删改查。

平台**一张业务表都不预置**。用户想记缺陷就建一张 `bugs`，想记待办就建 `issues`，想记什么就建什么——或者直接用模板（§9）。

### 4.2 三种表

| | 谁建 | schema | 谁能写 | 举例 |
|---|---|---|---|---|
| **系统表** | 平台自动 | 固定（不受用户列类型集合限制） | 只有平台 | `_runs` · `_flows` · `_flow_nodes` · `_plugins` · `_notices` |
| **用户表** | 用户经 MCP 建 | 用户定义 | 按项目角色 | `bugs` · `issues` · `approvals` |
| **受保护表** | 用户建时声明 | 用户定义 | **只有项目所有者** | 名单表（§7.3） |

保护级别**建表时声明，之后不可降级**。

**五张系统表：**

```text
_runs        每次任务执行一行
  run · task · skill(含版本) · trigger · triggeredBy(触发者身份) · inputs(文本)
  revision(读的哪个代码修订) · startedAt · finishedAt · status · failureKind
  **tokensUsed**(本次实际消耗) · **tokenBudget**(本次的上限)
  **retainUntil**(到期后整行被清理) · **traceRetainUntil**(过程记录先过期，§4.9)
  output(技能产出的 Markdown 正文) · **trace**(过程记录，blob 列)

_flows       每个流程实例一行
  instance · flow(含版本) · subject(主体表与行 ID，或外部主体标识) · subjectRevision
  startedBy(发起者) · state(进行中/已通过/已拒绝/已取消/已过期) · startedAt · endedAt
  —— 没有 currentNode：当前激活的节点可能有多个（并行组），
     权威是 `_flow_nodes` 里 state=激活中的那些行

_flow_nodes  每个实例的每个节点一行
  instance · node · state(未激活/激活中/已通过/已拒绝/已作废) · activatedAt · settledAt
  settledBy(结算它的那些行的 ID)
  —— 实例被拒绝或取消时，其余节点转为"已作废"，不停在"未激活"

_plugins     每个插件的每个版本一行
  plugin · version · state(候选/已安装/已停用) · source(TS 源码) · tests(用例)
  testResult · generatedBy(执行标识 + 技能版本) · installedBy · installedAt

_notices     每条通知一行，属于一个用户。**平台全局表**，因而能跨项目聚合
  notice · user · project · kind · subject(指向哪张表的哪一行 / 哪个实例 / 哪次执行)
  text(确定性代码从事件生成；**不含凭据、令牌或产物原文，只含指针**)
  createdAt · readAt
  · 读写都被平台硬限定为 `user = 令牌持有人`，这是行级可见性的唯一例外（§4.7）
  · `readAt` 是全系统唯一一个**用户可改的系统表列**：只能改自己那一行、
    只能改这一列，由平台专属 tool 代写，照样追加事件（I-N）
```

> `_notices` 是全局表而不是项目表，是为了让"我在 N 个项目里的待办"能在一个地方看到。它不破 §2 的项目数据边界——**边界由那条行级限定守住**：一个人只能读到属于自己的行，而属于他的行只会来自他有权见的项目。

**`_runs` 是默认的任务输出表**——"任务跑完就有记录可查"是开箱就有的，不需要用户先建表。这正是框架该给的；而 `bugs` 长什么样是业务，框架不猜。

`_flows`、`_flow_nodes`、`_plugins` 与 `_notices` 让流程实例、插件与通知这三样**运行时对象**也落在表里，不需要第二套查询机制。其中前三张和别的数据一样**可查询、可看板、可被插件读到**；**`_notices` 是例外**——它只有两个平台专属 tool，见 §4.7。

### 4.3 对外 CRUD，对内追加

用起来就是一张普通的表：增、删、改、查。底层每一次写都**追加一条事件**，删除是软删除，**任何一行都能查出它的完整历史**。

```text
用户看到的      insert / update / delete / select
底层发生的      追加一条事件 → 投影到当前视图
可以回答的      "这一行现在是什么"  也能回答  "它当时是什么样、谁改的"
```

既有 G3（账本追加式）因此一个字都不用改，而用户拿到的是一张能用的表。XOps 底层本来就是事件溯源的，这条几乎不额外花钱。

### 4.4 每一行都自带来源

平台在写入时自动补的字段，任何列声明都不能覆盖它们：

```text
writtenBy    谁写的 —— 四种之一，且**自包含**：
               · 某个人      —— 用户标识
               · 某次执行    —— 执行标识 + **任务标识 + 任务所有者 + 技能版本
                                + 代码修订 + 该执行的最终状态**
               · 某次插件求值 —— 插件标识与版本 + 安装它的人 + 流程实例
               · 平台自身    —— 系统表的行、到期清理、状态迁移这类

           ⚠️ **执行与插件两种必须内联那几项，不能只存一个指针。**
              `_runs` 的行有保留期（§4.9），而结算行没有——一个月后
              还要能回答"这一票是谁的"，靠的就是这里内联的任务所有者。
at           什么时候
revision     若来自读仓的执行，读的哪个修订
_instance    若这张表是某条流程的**结算表**，这一行属于哪个流程实例（见 §7.5）
retainUntil  若这一行由任务写入，它什么时候到期被清理（见 §4.9）
```

> **"不可信内容"标注不再是一个特殊标记，而是 `writtenBy` 的自然结果**：一行是人写的、agent 写的、还是插件写的，看这个字段就知道。责任归属、看板上的来源标识、流程节点的写入者判定，全都读它。

### 4.5 列类型

平台提供一组**穷举的**列类型：

```text
文本 · 长文本(Markdown) · 整数 · 小数 · 布尔 · 时间
枚举(取值集合由用户声明) · 自增序号(项目内、每表独立)
行引用(存另一张表的行 ID，平台不校验、不级联)
二进制(blob，存内容或内容引用 —— 将来若需要独立对象存储再单独扩展)
派生文本(按声明的模板，从**同一行的其它列与项目属性**计算，
         **insert 时生成一次、之后不变，update 写不了它**。例：`{project.slug}-{seq}`)
```

> ⚠️ **不提供 `json` / 任意对象 这种列类型。** 一旦有，窄接口纪律当场破掉——每张表专属 tool 那套派发机制就退化成了通用透传。

### 4.6 schema 变更：加列可以，其余不做迁移

> **删表是软删除（D42）**：表从列出结果中消失、专属 tool 停止派发，**行与事件一律保留、单行历史仍可查**——§4.9 说了，除到期清理外系统内没有任何硬删除路径。**表名不可复用**；被任何流程引用为结算表或主体表的表**不能删**，先停用那条流程。


**可以加列**（新列对历史行为空）。**改列类型、删列、改列名——不做。** 需要就新建一张表，自己把数据搬过去。

> 迁移是一整套东西（版本、回滚、部分失败、历史行怎么办），而 XOps 的用户手边就有 agent：**用 MCP 把旧表读出来、写进新表，比我们做一套迁移框架快得多，也不会出现一个我们维护不动的半成品。**

### 4.7 明确不做的三件

| 不做 | 理由 |
|---|---|
| 表之间的关联 / 外键 / 级联 | 行引用列只是存一个 ID。要关联是用户自己的事 |
| 行级权限 | 表级足够。做行级就要为每张表设计可见性规则，那是猜想。**唯一例外见下** |
| schema 迁移 | §4.6 |

> ⚠️ **`_notices` 是行级可见性的唯一例外。** 它装的是"谁被通知了什么"——谁待办堆积、谁写的行没被采纳，这些不该被同项目的其他人看见。所以它**不派发通用的查询 tool、不允许对它建自由看板**：只有两个平台专属 tool（查我的未读、标记已读），读写都被平台硬限定为 `user = 令牌持有人`。个人看板是平台内建的固定视图，不是用户能配的那种看板（§8）。
>
> 立这个例外而不是做通用行级权限，理由是它**只有一张表、只有一条规则、平台自己写死**——不需要为每张表设计可见性模型，那才是被 §4.7 拦掉的东西。
>
> **插件读不到 `_notices`。** 流转插件根本不读表（输入是平台预先查好、按 JSON 喂进去的，§6.1）；输出插件的读表能力按声明授予，而 `_notices` 不在可声明的表里。**第 10 版这里写的是"ctx 层的收窄、不是隔离"，第 11 版不必再这么写了**——载体不给别的路（D52）。

> ⚠️ **那流程的主体表与结算表算不算关联？** 不算。它们的关系记在**流程定义**与 `_flows.subject` / `_instance` 上，是流程这一层的运行时事实，**不是表 schema 层的外键**——不做级联、不做 join 查询、删一边不影响另一边。

### 4.8 写入的一致性：一张表同时只有一个写

```text
一张表在同一时刻只允许一个写操作（insert / update / delete）在进行。
第二个写排队等待，前一个结束才轮到它。
不同的表互不影响 —— 这是**表级**串行，不是全局锁。
```

**一次"写"的完整边界包含四件事，它们在同一个串行区间内完成：**

```text
① schema 校验 → ② 追加事件 + 投影 → ③ 流程节点求值（含流转插件）→ ④ 插件写回
```

把 ③④ 圈进来，是这条规则的**全部意义**：否则求值读到的表可能已经被另一个写改过，`_flows` 的状态迁移就不是原子的，两条并发的结算行会同时被判为"该节点的最后一票"。

**④ 会写到别的表，所以要说清楚锁怎么取：**

```text
串行区间归属**被写的那张表**（触发这次写的那张）。

**流转插件自己不写任何表**：它是一个纯函数，吃 JSON、吐 JSON，
  吐出来的东西里包含"要写回哪些行"，**由平台在同一区间内代写**（§6.1）。
  平台只肯代写**两张表**：本流程的结算表与主体表。
  · 对主体表**只能 update，不能 insert** —— §7.2 规定"主体表插入新行"
    就是随行发起实例的动作，允许插件 insert 等于让它开出新实例，
    自激回路会从"求值"挪到"实例发起"，I-R 挡不住它
  · 这两张表的锁**一次性按表名全序获取** —— 全序即无循环等待，
    构造不出死锁
  · 写回结算表本身时锁**可重入** —— 它已经在手里
  · `_flows` / `_flow_nodes` 的状态迁移随同一区间落定

第三张表 —— **平台不代写**。真要写，用一个任务。
```

> ⚠️ 把写回目标收窄到两张表，是为了让锁集合**在流程定义时就是已知且有限的**。允许写任意表，就要在运行时动态取任意多把锁，死锁立刻可构造：只要表 A 是流程 F1 的结算表、F2 的主体表，表 B 反过来，两个并发写就会以相反顺序请求 A、B。
>
> **第 11 版这条从"约定"变成了"兑现"**：第 10 版的插件在进程内、绕过 `ctx` 直接写第三张表是平凡的，所以那时这条只防正常代码写出死锁、不防恶意。现在插件根本没有写表的路——它只能把想写的行**交回来**，交给谁写由平台说了算（D52）。

**代价要认清，它是真实的：**

| 代价 | 说明 |
|---|---|
| **热表是瓶颈** | 一张被高频写入的表，写吞吐等于 1 / 单次写的耗时 |
| **插件超时上限直接决定表的最大写吞吐** | 因为插件求值在锁内。一个耗时 2 秒的流转插件，会把它所在的结算表压到每秒 0.5 次写。**QuickJS 载体让这个数字好看得多**（一次求值是毫秒级的纯计算），但**好看不等于可以调大超时**——它仍然是锁内的，默认值要小，容量要在设计阶段算一次（§6.4） |
| **它不是通用事务** | 只有"结算表 + 主体表 + `_flows` / `_flow_nodes`"这一组在同一区间内落定。**其余任何跨表写都没有原子性** |

**三件事明确在锁外**，否则这把锁会锁住整个系统：

```text
· 「节点被激活」事件的派发与任务入队 —— 非阻塞入队，模型调用绝不在锁内
· 通知行的写入 —— 见 §8
· 到期清理 —— 整批离线进行
```

> 这是刻意选的**粗粒度一致性**：它简单、可解释、能防住并发结算这一类真问题，而代价用"把重活放进任务、别放进插件"就能绕开。**不做行级锁、不做多表事务、不做 MVCC**——那是数据库的活。
>
> ⚠️ **而且这把串行是应用层自己的，不是数据库的（D46）。** 存储层只使用基本的增删改查，不依赖触发器、存储过程、行锁、事务隔离级别、MVCC、外键、级联或 JSON 列——**换一个数据库不应该改写入路径**。
>
> **第 11 版把它落成一条 Rust trait**：存储契约是一个只有基本 CRUD 的 trait，SQLite 是它的第一个实现，串行区间在 trait 之上。硬验收跟着这条走——**换一个内存实现进去，写入路径与它上面的一切不改一行**。这条与 `EXE-014`（换引擎不改契约）是同一种验收，放在两个接缝上。
>
> 连带前提要认下来：**应用层的表级串行只在单实例部署下成立**，多实例需要一把进程外的锁，那是另一个决定。（这也是 §0 实现基线里 SQLite 是"可换"那一栏的原因——可换的是库，不可换的是串行这条规则。）
>
> ⚠️ **`_runs` 天然是全系统最热的表**（每次执行至少写一次）。它不被任何流程绑定，所以它的写没有 ③④ 两步——但容量规划时要知道它在这条串行规则下的位置。

### 4.9 保留期与清理

```text
任务声明「输出保留多久」，默认 **1 个月**。
到期后，该任务产出的 `_runs` 行**整行删除**，并留一条清理留痕。
清理整批按时间进行，**不得选择性删除个别行**。
```

**保留期作用于任务的输出**：`_runs` 的行，以及任务写进用户表的那些行。

`retainUntil` 和 `writtenBy` 一样是**平台在写入时自动补的字段**（§4.4）——任务写的每一行都带它，值取自该任务当时声明的保留期。不靠"回查任务再取它的配置"，因为任务的保留期可以随时改，而**已经写下的行不应该因为任务改了配置就提前消失或延后清理**。

**豁免清单（豁免优先于任务保留期）**：

```text
① 任何被 `_flows.subject` 引用过的行，或带 `_instance` 的行
   —— 不管它在结算表还是主体表、不管是谁写的
② `_flows` / `_flow_nodes` / `_plugins`
③ 项目 / 成员 / 技能 / 任务 / 流程 / 表 的定义
④ `_notices` —— 另有自己的保留期，见下
```

理由很直接：**一个还在进行中的流程实例，它的主体行或结算行被清理了就等于实例被腰斩**。治理事实的生命周期跟着它治理的那件事，不跟着任务的保留期。① 之所以要写成"引用过"而不是"结算表的行"，是因为**任务完全可以往主体表写行**（§7.3 ③ 允许私有任务参与流程），那批行两条规则都命中，必须有优先级。

**`_notices` 有自己的保留期**（平台级配置，默认 3 个月），与任务无关——否则通知会无限增长。

> ⚠️ **一处已知的悬空，说明白**：`_plugins.generatedBy` 指向生成它的那次执行，而那条 `_runs` 行会到期被清理。插件的源码、用例、测试结果、安装人都在 `_plugins` 行内（豁免），安装那一刻也有审计事件——所以"这个插件哪来的、谁装的"追得到；**丢的只是那次生成执行的 output 与 trace**。这是可接受的，但不要以为全系统零悬空。

**过程记录另有一个更短的保留期**：任务可以分别声明**输出保留多久**与**过程记录保留多久**（后者默认 7 天）。这承接既有 R-05-38 的判断——"过程用于排查，结论用于回看，价值衰减速度不同"。过程记录存在 `_runs.trace`（blob 列），到期只清这一列、行本身按输出保留期走。

> **这条纪律的来源是既有 R-01-44 的精神**（"到期清理只能整批按时间进行，不得选择性删除个别事件"），但**两者管的不是同一样东西**：R-01-44 管的是**审计事件流**的保留期，它仍然有效、仍然是全局配置；本节管的是**任务输出**，保留期挂在任务上。两条并存，互不取代。
>
> ⚠️ **这与 I-D"事件一经写入即不可变"不冲突。** 不可变说的是"不会被改写"，不是"永久保留"——到期清理删的是行与它的历史事件，删除这件事本身留痕。
>
> 但它确实是本版**唯一一处硬删除**：§4.3"任何一行都能查出完整历史"、G3 追加式、D26"删除是软删除"，三条在这里都有一个例外，理由只有一条——**存储不是无限的**。除到期清理外，系统内不存在任何其它删行路径。

## 5. 技能与任务

### 5.1 任务是什么

```text
任务 = 一个技能 + 订阅哪些事件 + 读哪些数据源 + 写哪些表 + onComplete + 执行策略
       ────────   ──────────────  ─────────────  ──────────  ──────────  ─────────
       做什么      什么时候做       能读到什么      能写到哪    完成后干嘛   见下

执行策略 = 超时 · 重叠策略 · 启停 · **单次 token 上限** · **输出保留多久**
```

**单次 token 上限**（未声明用平台默认值）：一次执行消耗的模型 token 撞上这个数，**强制终止**——销毁容器、中止会话、归入"超出 token 预算"这一类失败。已产生的行仍然写入，但标注**来自未正常完成的执行**，因而不结算任何流程节点（§7.6 ⑥）。实际用量记进 `_runs.tokensUsed`。

**终止的时序是定死的**（超时与被取消走同一条路）：

```text
① 中止模型调用与会话（先停掉烧钱的那一头）
② 收敛并移交容器里已产生的行
③ **先落 `_runs`**（status / failureKind / tokensUsed），**再写产出行**
④ 销毁容器
```

③ 的顺序不是洁癖：§7.6 ⑥ 要读"这次执行是否正常完成"才能判断产出行算不算结算，**`_runs.status` 必须先于产出行可见落定**，否则判定读到的是不确定状态。

> ⚠️ **这是顺序保证，不是跨表事务**（D43）。§4.8 已经说明跨表写没有原子性，这里也不例外：两步之间崩溃会留下"`_runs` 行完整、产出行缺失"，**那是可接受的**；反过来不可接受，顺序就是为了排除它。

> 这与既有 D10 **不冲突**，不是对它的修订：D10 的原文射程只有"**不做项目级额度与限流**"，单次执行的上限从来不在其内。这里补的是执行级的闸门——它防的是一次失控的执行把钱烧光，而这是自动化系统最常见的故障形态。**项目级额度与限流仍然不做**：那需要计费模型、配额分配与超额策略，现在没有支撑它的真实需求。

**平台只有这一种任务**（造插件的任务是它的一个受限特例，见 §6.2）。四种常见用法在平台看来完全一样：

| 用户叫它 | 技能里写的 | 订阅的事件 | 写到哪 |
|---|---|---|---|
| 质量监管 | "检查这个仓的 X 有没有问题" | 定时（夜里）、git push | `_runs` + 一张 `findings` 表 |
| 审批 | "查一下相应文件传上来没有、验证过没有" | 流程节点被激活 | `_runs` + `approvals` 表 |
| CI 触发 | "调用外部 CI 的接口把构建跑起来" | git push（需出网白名单，见下） | `_runs` |
| 代码走读 | "按我们的规范逐文件读一遍" | 手动、定时 | `_runs` |

**平台不认识这四个词。** 它认识的是：某个事件发生了，某个任务订阅了它，于是跑一次技能，往声明的表里写几行。

> ⚠️ CI 触发这一类需要**自定义出网白名单**，而"白名单由谁批准、能不能由技能作者自己填"在既有需求里**明确没有定义**。这条用法的授权路径待定（Q10）。

### 5.2 onComplete：任务完成后的一步后处理

任务可以声明 `onComplete`，在它**正常完成、行已写入之后**执行一步：

```text
onComplete = 一个插件入口   或   另一个任务   或   空
```

- **挂插件**：平台调用该插件的入口，把本次执行的 `_runs` 行交给它。**插件拿去干什么是插件的事**——发邮件、发 IM、推到别的系统，平台不管也不提供这些能力（§6）
- **挂任务**：被挂的那个任务被触发，事件载荷带上本次执行的标识与产出行

> ⚠️ **深度硬限制 1。** 被 `onComplete` 挂上的那个任务，它自己的 `onComplete` **必须为空**——创建时就校验，不满足直接拒绝。
>
> 这条限制是这个功能能存在的全部理由：**一层是"输出后处理"，两层就是任务编排 DAG**，随之而来的是依赖解析、失败传播、循环检测及其可视化。有了硬限制，这三样一个都不需要。
>
> 这**修订了上一版"永不引入执行完成事件"那条绝对禁令**——现在有了，但它只能用一次，用完就到底。

**后处理失败不影响主任务的记录。** `_runs` 那一行已经写好了；onComplete 失败只留自己的痕迹并通知任务所有者。

### 5.3 事件：任务订阅，而不是别人来推

| 事件 | 来源 | 载荷 |
|---|---|---|
| **定时** | 平台调度器 | 触发时刻、时区。配置者可追溯 |
| **Git 事件** | webhook（验签，按事件标识幂等） | **确切的提交标识** · 分支 · 事件类型 |
| **手动触发** | 项目成员经 MCP | 触发者身份 · 可选的目标修订 |
| **流程节点被激活** | 平台内部 | **实例标识** · **流程与版本** · **哪个节点** · **发起者** · **主体标识与修订** |
| **上游任务完成** | 平台内部 | 上游执行标识 · 它写的那些行 ·（**深度限制 1**，§5.2） |

前三类由任务自己声明订阅并按载荷过滤。后两类不同：**「流程节点被激活」的唯一订阅途径是被某个节点指定为写入者；「上游任务完成」的唯一订阅途径是被某个任务挂在 onComplete 上。** 它们不是任务能自己声明订阅的事件。

> ⚠️ **白名单里永远不加"某张表被写入"。** 一旦任务能订阅表的变化，就有了不受深度限制的回路——A 写表触发 B，B 写表触发 A。需要串联，就用 onComplete 那一层，或在**一个技能内部**做完多步。
>
> **注意区分**：一行被写进表时，平台确实会去求值相关流程节点的插件（§7.4）。**那是插件求值，不是触发任务**——插件跑在进程内、毫秒级，不产生执行、不烧模型调用。这两件事必须在实现上分得很开。
>
> 同样地，**容器内不提供任何触发能力**。

三条共同纪律：

```text
非阻塞      触发的产出是"一次执行进了队列"，不是"任务跑完了"
幂等        同一个外部事件最多产生一次执行
留痕        被拒绝的、被重叠策略跳过的触发，同样留痕
            —— 一个静默被跳过的任务，会让人以为它在跑
```

### 5.4 一次执行怎么跑

```text
事件 → 任务被触发
        │
        ▼
   装配派工单（不可变）
     技能内容与版本 · 输入 · 数据源清单 · 写入目标 · 超时
     **触发事件的完整载荷** · 触发者
     **不含任何凭据**；只放技能实际声明的东西，不扩权
        │
        ▼
   容器外准备
     只读工作区（用仓凭据拉到确切修订；凭据不进容器）
        │
        ▼
 ┌─ 容器外 ─────────────────────────────────────────────┐
 │  attacored —— 只做编排与模型调用                       │
 │  持有模型凭据，凭据从结构上进不了容器                    │
 │        │ 文件与进程操作全部经四个执行契约路由进容器 ↓     │
 │        │ Process / FileSystem / Network / Sandbox      │
 └────────┼────────────────────────────────────────────┘
          ▼
   ┌──── 一次性容器（用完完整销毁）────────────────┐
   │  全部工具执行在这里发生                        │
   │  只读工作区                                   │
   │  出网：默认拒绝 + 声明的白名单（模型服务不在此列）│
   │  没有凭据 · 没有触发能力 · **没有任何写表的路径** │
   └──────────────────────────────────────────────┘
          │
          ▼
   移交：待写入的行 + 状态 + **失败分类** + 过程记录（不含任何凭据）
          │
          ▼
   **平台在容器外写入**：校验每一行是否符合目标表的 schema
     → 写进 `_runs` 与任务声明的那些表，补上 writtenBy / at / revision / _instance
          │
          ▼
   若声明了 onComplete → 调用插件，或触发那个任务（§5.2）
```

**容器里没有任何写表的路径。** 任务"写表"的实际含义是：容器产出待写入的行，**平台在容器外按任务的声明写入**。既有 I-02-1（容器不得写确定性平面）一个字都不用改。

**两类数据源，一律显式声明，未声明的不提供**（D44 去掉了原来的第三类"表数据"）：

| 数据源 | 形态 | 关键性质 |
|---|---|---|
| **代码** | 只读挂载项目的 Git 仓，定位到确切修订 | 一次执行只有**一个项目**的代码；写入不回流；随容器销毁 |
| ↑ 确切修订从哪来 | **事件载荷覆盖任务定义**：git 事件带来的提交标识、流程事件带来的主体修订，都覆盖任务定义里写死的目标修订 | 少了这条，执行读的是"仓库现在长什么样"，不是"这次要它看的那一版" |
| **外部网络** | 默认拒绝，只放行声明的地址 | 模型服务不在此列——模型调用发生在容器外 |

> ⚠️ **表数据不是数据源（D44）。** 平台不把表导出成快照，也**不给容器任何到 XOps 的网络路径**——"容器里的 agent 自己调 MCP 读表"这条路不存在，那要往容器里放一个令牌，I-F 与"靠能力封锁而不是内容检查"当场破掉。**代价认下来：技能读不到表。** 需要表数据就由调用方经 MCP 查好放进任务输入，或用 onComplete 挂一个输出插件在进程内读。

### 5.5 执行引擎与它的三笔代价

**XOps 与执行引擎是两个分立的进程，之间只有一条执行契约这一个接缝。** 换掉底层引擎不应改动契约，也不应波及其它任何一块——引擎的概念不得泄漏进契约。这条有硬验收：**把引擎换成一个最简桩实现，契约与其余部分无需修改**。

**这一版的引擎是 AttaCore**（D50）。它以 `attacored` 分立进程运行，两侧走它的 JSON-RPC over Unix socket。选它的理由是它已经有 XOps 需要的三样，且三样都在契约后面：

```text
① 四个执行契约        Process / FileSystem / Network / Sandbox
                     ——"工具怎么真正碰到这台机器"被收进了 trait，
                        所以"碰的是容器而不是这台机器"是换一个实现的事
② 单次预算与停止原因   max_budget_usd / budget_exceeded
                     —— §5.1 的单次 token 上限有落点，不必自己造闸门
③ 会话与场景          一次执行一个会话；场景决定模型能看见哪些工具
                     —— 容器内"不提供触发能力""没有写表路径"因此有第二道
                        （工具压根没注册），而不只靠能力封锁一道
```

> ⚠️ **两条纪律不因为换了具名引擎而松动。** 其一，`EXE-014` 说的是**分立进程 + 一条契约**，不是"用 AttaCore"——XOps 侧仍然要有自己的执行契约，AttaCore 的数据结构**不得直接流进它**；桩实现验收照做。其二，**②③ 是便利，不是隔离**：`EXE-005` 要求边界由能力封锁兑现，场景白名单是**第二道**，不是那一道。

**一次性容器由 XOps 提供。** AttaCore 今天有两组执行契约实现——本机的与进程内的，没有容器的那一组。XOps 要实现的正是第三组：

```text
Process     在容器里 spawn，增量输出必须流式传回（这是契约的硬要求，不是优化）
FileSystem  容器内的整值读写；符号链接由这一侧解析，路径安全策略留在契约之上
Network     容器出网：默认拒绝 + 声明的白名单；模型服务不在此列（那是容器外的事）
Sandbox     容器本身就是约束；策略兑现不了的部分必须逐条如实上报，不得静默降级
```

> **上游的现状，按代码而不是按它的设计文档写**（那份文档写在契约迁移之前，已经落后于代码）：
>
> ```text
> 已经有的   四个契约完备，全部内建工具都经它们碰机器
>            exec.* 登记在可替换扩展点索引里，信任级别 host-only
>            exec.process 的声明用途：**which machine the work happens on**
>            出网统一到一个 egress，模型选的目标与运维配的端点分流
>            切换的写法就是一句赋值：ctx.exec = <一组 providers>
> 还缺的     **Builder 上没有 `exec` 这个宿主注入位**
>            —— 它已有十六个同类注入位（turn_policy / budget_policy /
>               environment / recovery_policy / skill_provider …），就是没有这个
> ```
>
> ⚠️ **一项跨仓交付物，责任在 XOps 侧**：把 `exec` 加进 Builder 的注入位，让宿主能按会话换掉那四个 provider。**它在 AttaCore 仓里改，走 XForge，工期算在 XOps 这边**——"上游还没做"从来不是一个可以等来的状态。
>
> ⚠️ **契约会不会因为接容器而改一轮，按代码重新判一次，不要沿用旧结论。** 那四个契约当初是照着"如果这是远端会怎样"设计的（输出流式是硬要求、符号链接由 provider 解析、沙箱兑现程度要如实上报），所以风险比设计文档写的低。**但仍然不是零**——`Q24` 保留，只是降级为"排期时留出余量"，不再是"预期一定会改"。

"容器一次性 + 编排进程常驻"这个拓扑换来了免冷启动和模型凭据的结构性隔离。代价有三笔，**都必须正面应对，不能因为图上画着"一次性容器"就以为它们不存在**：

| 代价 | 应对 | 为什么容易漏 |
|---|---|---|
| **跨执行的会话隔离**原本由"一次执行一个容器"免费提供，编排进程常驻之后变成它自己的责任 | 一次执行一个会话，用完即销毁；显式实现并**实测**：第一次执行在会话里留下可识别痕迹，第二次读不到 | **失效时通常没有任何报错**，表现只是产出变得莫名其妙——光看代码发现不了。引擎侧还有会话池与空闲淘汰，"看起来干净"更容易骗过人 |
| **编排进程崩溃的影响面**从单次执行扩大到全部在途执行 | 在途执行必须在有限时间内被归入明确的失败分类**并可重跑**，不得无限期挂起 | 常驻进程被全部在途执行共享，一次崩溃就是一批执行同时失败 |
| **引擎不可用时的降级方向**（本版新增） | `attacored` 连不上就是执行失败并如实分类，**绝不在 XOps 进程里就地跑一遍** | 这跟"沙箱不可用就不沙箱"是同一个错误：一个配置成"在别处执行"的部署，如果在别处连不上时悄悄在本地执行了，它的隔离承诺**恰好在最需要的时刻不成立** |

另两条同源要求：**超时强制终止时不得留下孤儿会话继续消耗模型额度**；**失败必须分类**（技能错误 / 凭据错误 / 工作区错误 / 模型服务错误 / 引擎错误 / 超时 / **超出 token 预算** / 资源不足）——"失败了"不是一个可用的结论。

### 5.6 归属：公共的与私有的

```text
项目公共  ── 归项目所有，项目成员都能看、能用、能触发
个人私有  ── 归创建它的人所有，同项目的其他成员看不到、也用不了
           但它**在项目中执行，用项目的数据源**
```

**私有技能能读项目数据，是因为它的所有者是项目成员。** 权限来自人，不来自技能——一个人退出项目，他挂在这个项目里的私有任务立刻失去数据源，不能再执行。

**可以从一份技能派生一份私有副本**（同项目内公共 → 私有，是一次拷贝而不是引用）。

**一条例外**：一旦某个私有技能的某个版本被用于满足某个流程节点，**该版本的内容、以及那个任务的定义（订阅什么、写哪张表）对项目成员转为可读**。私有是为了不打扰别人，不是为了让自动决策不可审查。

> 这打破了既有 I-01-4（"每个业务对象恰好归属一个项目"）与 R-05-01（"技能归属项目"）。新表述：**每个对象恰好有一个归属方（项目或用户），并且恰好在一个项目的上下文中被使用。** 执行产生的行归属**项目**。

## 6. 插件

### 6.1 插件是什么

一段 JS 代码，装在项目里，由平台在**两个位置**调用。**它跑在 QuickJS 载体里：一次调用新建一个 runtime，调用结束整个扔掉。**

```text
流转插件   流程节点求值时被调用
           输入：实例状态 · 刚写入的那一行 · **节点声明的相关行**
                 —— 三样都由平台在调用前查好，按 JSON 喂进去
           输出：这个节点过 / 不过 / 拒绝 · 要写回哪些行
                 （平台只肯代写本流程的结算表与主体表，
                   且主体表只能 update，§4.8）
           能力：**零**。没有文件、没有网络、没有表、没有时钟
                 （除了 `Date`）、没有任何宿主绑定

输出插件   任务 onComplete 时被调用
           输入：本次执行的 `_runs` 行与它写的那些行
           输出：由插件自己决定 —— 发邮件、发 IM、推到别的系统
           能力：**声明出来的三样**，见 §6.4
```

**平台不提供"发消息"这种能力，也不定义"通道"这个概念。** 它只负责在正确的时机调用插件入口，把该给的数据给它，并按它声明过的能力放行它要用的那几样。插件要连什么系统、用什么凭据，是插件自己的事（配置见 §6.5）。

> ⚠️ **"节点声明的相关行"这条是本版新增的、有实现后果的一条。** 第 10 版的流转插件在进程内，想读哪张表读哪张表；现在它读不到任何表，**它需要的行必须在流程定义里声明出来，由平台在求值前查好**。
>
> 这不是限制，是把一件本来就该做的事挑明了：求值发生在**写串行区间内**（§4.8），一个能在锁内自由查表的插件，等于把不确定的查询时延接进了这张表的写吞吐。声明之后，求值的输入是有界的、可预取的、可缓存的，**求值本身退化成一次纯计算**。

### 6.2 插件从哪来：一种特别的任务

插件不是上传的，是**生成的**：

```text
造插件任务（一种受限的任务）
  · **只能手动触发**，不能订阅任何事件
  · 技能产出：插件的 JS 源码 + **一份能力声明** + 一组测试用例（输入 → 期望输出）
  · 平台确定性地做三件事：**编译**（QuickJS 字节码 + 入口导出检查）
                          **跑用例**（在真载体里跑，能力按声明给）
                          **静态检查**（见下）
  · 三样全过 → 产出一个**候选插件**（还没生效）
        │
        ▼
  维护者经 MCP **安装**它 → 它才成为项目的插件，
  安装时**逐条披露它声明了哪些能力**，不可跳过
        │
        ▼
  才能被流程节点或 onComplete 引用
```

| 阶段 | 需要什么权限 |
|---|---|
| 造插件任务的创建与手动触发、看测试结果 | **项目成员** |
| 把候选插件安装进项目（含能力披露） | **维护者及以上** |
| 读写插件的配置 | **所有者** |

**已安装的插件版本不可变**，**能力声明是版本的一部分**。改就是生成一个新候选、再装一次——**改能力也是**；引用它的流程节点用**固定版本**，不跟随最新。

> ⚠️ **"能力声明是版本的一部分"这条不能省。** 否则装的时候披露的是一套、跑的时候用的是另一套，披露就成了摆设。

> **静态检查这件事，第 11 版基本被载体回答掉了**（原 Q16）。第 10 版要纠结"要不要禁某些 import、禁 `process.env`"，是因为那时插件在进程内、什么都够得到，禁多少都是概率问题。现在**够不到的东西不需要禁**：载体不给绑定，脚本就没有那条路。剩下的静态检查只剩两件确定性的事——**入口导出在不在**、**声明的能力与披露的是否一致**。

### 6.3 插件的可审查性是硬要求

```text
已安装插件的源码与它的能力声明，对全体项目成员**必须可读**。
```

不是"可以看"，是"必须可读"。**注意理由变了，而结论一个字没变**：第 10 版的理由是"它有完全权限"；这一版它没有了，但**它的判断仍然能结算流程节点**——一个不可审查的、由模型生成的东西替人做决定，没人能对它负责。隔离管的是它能碰什么，管不到它说什么。

配套：安装是一条审计事件，记下**谁装的、哪个技能的哪个版本生成的、哪次执行产出的、声明了哪些能力、测试用例是什么、结果如何**。

### 6.4 载体给了什么、没给什么

> **第 10 版这一节的标题是"必须说清楚：进程内执行意味着什么"，正文是"安装一个插件 ≈ 授予这个人在服务端执行任意代码的能力"。那条结论已被 D52 取代。** 但取代它的不是"所以现在安全了"——是一次**边界的重新划分**，划完之后两边都要重新说一遍。

**载体给了什么（执行这一半）：**

```text
一次调用一个 runtime      调用之间不共享任何状态，
                         一个项目的插件攒不下东西给另一次调用看
默认零宿主绑定            未声明即没有。不是"调用时检查"，是"那个函数不存在"
字节码级中断              `while(true){}` 也停得下来 —— 光靠 future 超时是停不下它的
内存上限                  一个插件吃不垮它寄生的进程
故障只花一次调用           抛异常/超时 = 这次调用失败，不是平台失败
```

**流转插件的能力是零，没有可声明项。** 它的输入是平台喂的、输出是交回平台的，中间没有任何一条通往外面的路。§4.8 那条"锁集合在流程定义时就是已知的"因此从约定变成兑现。

**输出插件可以声明三样，仅此三样：**

| 能声明 | 边界 |
|---|---|
| **出网** | 一张主机白名单。未声明的主机连不上；重定向**每一跳重新判定**，否则白名单只对第一跳成立 |
| **自己的配置** | 只能读到**它自己**那一份（§6.5），读不到别的插件的、读不到平台的 |
| **读表** | 声明的那几张、**本项目的**。`_notices` 不在可声明之列（§4.7） |

> 「读表」这一项存在的唯一理由是接住 **D44** 的那条出路：技能读不到表，需要表数据就"经 MCP 查好放进任务输入，或用 `onComplete` 挂一个输出插件去读"。后一条路必须还在。

**载体没给什么（判断这一半）：**

```text
它拦不住一个"永远返回通过"的流转插件
它拦不住一个把喂给它的数据发到声明过的白名单主机上的输出插件
```

**所以治理一条都不减**：由技能生成 · 编译与用例 · **维护者安装** · **安装时逐条披露能力** · 源码必须可读 · 每一步留痕。第 10 版这套流水线是"沙箱的替代品"，第 11 版它是"沙箱之外那一半的答案"——**位置变了，内容没变**。

**平台仍然要做的三件（它们防的是故障，不是恶意）：**

```text
超时      插件求值有硬超时，超时视为"节点未通过"，绝不视为通过
错误隔离  插件抛异常不能拖垮平台；异常视为"节点未通过"并留痕
不递归    流转插件写回的行**不再触发插件求值**，避免自激
```

**两条残留风险，写出来而不是假装没有：**

```text
① 载体本身是信任基。QuickJS 是一个 C 实现，它的内存安全是这套隔离的地基。
   这不构成"所以不如不隔离"，但它意味着**载体的版本要跟、CVE 要看**
   —— 它是依赖，不是免死金牌。
② 输出插件有出网与配置，就有外泄面。它拿得到的是喂给它的那份数据，
   能送到的是它声明过的那几台主机 —— 两者都在安装时披露过。
   **这是"可审查的外泄面"，不是"没有外泄面"。**
```

**能用技能解决的，仍然不要用插件。** 理由从"插件不可隔离"换成了更朴素的一条：插件读不到代码、读不到任务的输入、只吃平台喂的那点 JSON，**它能做的事本来就少**。它的正当理由还是那两个——**省 token**（流程流转这种高频、确定性的判断不该每次调模型）和**平台做不到的对接**（把产出送到别的系统）。**"JS 写起来顺手"不是理由。**

### 6.5 插件配置

每个插件有一份自己的配置（键值对），**由项目所有者经 MCP 写入，加密存储，任何接口都读不出原文**，调用时只注入给该插件——**且只在它声明了"读自己的配置"这项能力时注入**。

它存在的理由很实际：一个要发邮件的插件需要 SMTP 凭据，总不能让人去改 XOps 的环境变量。**这是最小配套，不是一个凭据管理系统**——平台不知道那些值是什么意思。

> ⚠️ **配置不落在 `_plugins` 表里。** 那张表和别的表一样可查询，把凭据放进去等于公开。配置单独加密存储、不经任何查询面暴露、只在调用时注入给它自己的插件——**这是全系统唯一一份不以表的形式存在的状态**，例外的理由就是这一条。
>
> **第 11 版这条比上一版硬**：上一版还要补一句"这不构成对插件的隔离，进程内的插件读得到它想读的东西"。现在不用补了——没声明这项能力的插件，那个函数不存在。

## 7. 流程：吃掉审批

### 7.1 流程是什么

```text
流程 = 有序的节点序列（可含并行组）
     + **结算表**：节点的结算行写在这里
     + **主体表**（可选）：流程在治理哪张表的行
     + 何时发起实例

每个节点声明：
  · 通过条件      结算表上出现满足<筛选 A>的行，且数量 ≥ N
  · 拒绝条件      结算表上出现满足<筛选 B>的行（可选）
  · 允许写入者    谁被允许写这样的行
  · 职责分离      是否要求写入者 ≠ 实例发起人
  · 求值方式      默认按筛选判定；也可指定一个**流转插件**来判定
```

**节点结算的形式只有一种：结算表上出现了满足条件、且写入者被允许的行。**

> ⚠️ **"筛选不得重叠"的判定口径（D47）**：把流程展开成一个**激活集合序列**——串行节点各自是一个集合，一个并行组整体是一个集合——则**同一集合内的节点两两之间**、以及**相邻两个集合之间**，筛选都不得重叠。同一集合内同时激活，一行落进来会被多个节点同时求值；相邻集合之间则会在前一个通过的瞬间被同一行结算。**判定取保守口径：只要不能证明两个筛选互斥，就判为重叠并拒绝。宁可误拒**——误放的后果是运行时一行同时结算两个节点，那是事后查不出来的。

> ⚠️ **结算表与主体表不得是同一张。** 校验流程定义时就拒绝。
>
> 这一刀避开了两个死结：① 若同表，人要推进流程就得往主体表插新行，而"插新行"正是随行发起实例的动作，会开出第二个实例；② 若靠 update 主体行来推进，那么"数量 ≥ N"（会签）与"同一写入者只能结算一次"两条都失去意义，因为一个主体只有一行。
>
> 分开之后模型是统一的：**主体表放"这件事本身"，结算表放"谁对它做了什么表态"**。`bugs` 是 `bugs` + `bug_events`，XForge 审批是（无主体表）+ `approvals`。

这一步统一是本版最大的简化。因为"人做决定"本来就是**往那张表里写一行**——于是不需要"审批实例""决策""质量门""代理任务"四个概念。

```text
人写这一行      → 这就是审批
任务写这一行    → 这就是自动化（agent 判断，费 token，能读代码）
插件判定        → 这也是自动化（确定性判断，不费 token，只吃平台喂的 JSON）
```

### 7.2 实例：流程的运行时对象

```text
流程实例 = 一条流程定义的一次运行，绑定一个**主体**
  主体 = (类型, 标识, 修订)   类型开放，平台不解释
  实例落在 `_flows` 表；每个节点在 `_flow_nodes` 表有一行
  实例始终按**发起时**的流程定义版本走完，不受后续版本变更影响
```

**实例怎么发起**（流程定义里声明，二选一）：

| 方式 | 何时发起 | 主体是什么 |
|---|---|---|
| **随行自动发起** | **主体表**插入一条新行时 | 那一行 |
| **显式发起** | 有人经 MCP 调"发起实例" | 调用方给的主体（XForge 链路走这条，主体是 `governingDigest`） |

> `bugs` 模板用第一种：插一条 bug（主体表 `bugs`），它的流转实例就开了，之后的表态写进 `bug_events`（结算表）。XForge 审批用第二种：没有主体表，主体是外部的 `governingDigest`，结算表是 `approvals`。
>
> 因为结算表与主体表不同，**结算行的插入永远不会再开出一个实例**——随行发起只看主体表。
>
> 两种方式都一样：**实例创建的同一步，第一个节点随即激活**并产生「流程节点被激活」事件。

### 7.3 谁被允许写

节点的**允许写入者**是三者的并集：

```text
① 项目角色集合      所有者 / 维护者 / 成员
② 某张名单表里的人  受保护表，**只有项目所有者能写**
③ 某个指定的私有任务  该任务写入的行才算数
```

> **这就是"由创建流程的人决定谁来做"的落法。** 想让只有 a 能批，就建一张只有 a 的名单表；想让任何维护者都能批，就写角色；想让它自动，就指一个任务。三种写法在同一个字段里，不新增概念。名单表可以独立于流程定义变更——**人员变动改名单，不改流程**。

⚠️ 两条必须收死的：

- **名单表的写权限就是审批权的元权限**——谁能改名单，谁就能给自己发审批权。所以它是受保护表，只有所有者能写，且保护级别不可降级。
- **③ 只能指定私有任务。** 项目公共任务没有"所有者这个人"，一旦它写的行被算作节点通过，"每一次通过都归属一个具名的人"当场落空。

### 7.4 一行写入时发生什么

```text
一行被 **insert** 进表
   │
   ├─► 追加事件 → 投影到当前视图        （§4.3，总是发生；update/delete 同样走这一步）
   │
   └─► 若这张表是某条流程的**结算表**，且这一行带 _instance：
         定位该实例当前激活的节点 → 求值
           · 默认：按节点的筛选判定
           · 或：调用节点指定的流转插件（进程内，有超时与错误隔离）
           │
           ├─ 不结算 → 行照常留在表里，留一条"未被采纳"的痕迹 + 通知写入者
           ├─ 通过   → 节点标记已通过，**平台代写**流转插件交回的那些行
           │            · 串行：下一个节点激活
           │            · 并行组：全部通过后才推进
           │            → 产生「流程节点被激活」事件 → 该节点指定的任务被触发
           │            · 若已是最后一个节点 → **实例进入"已通过"终态**
           └─ 拒绝   → **整个实例立即进入拒绝终态**，其余节点转为"已作废"
```

整段发生在**这张表的写入串行区间内**（§4.8）——除了最后的"触发任务"那一步，它在锁外入队。

**只有 insert 参与求值（D45）。** 结算表上的 update 与 delete 不触发求值、不结算、也**不撤销任何已有的结算**——一次表态一旦被采纳就是既成事实。要改变结论，只能在节点仍激活时再写一行，或按 §7.8 发起一个新实例。

**写入触发的是插件求值，不是任务。** 任务只被"节点被激活"这一个事件触发，而且只有被指定为该节点写入者的任务才收得到。这条区分守住了"不做执行编排"那条边界。

**流转插件写回的行不再触发插件求值**（§6.4），避免自激。

> ⚠️ **一个总是失败的流转插件会让实例永久停住。** 超时与异常一律判为"未通过"，而 §7.8 既不做超时自动推进、也不做退回——所以实例就停在那儿。**这是刻意的**：卡死的东西应该被看见，不应该被绕过。出路是**取消实例**，修好插件（生成新候选、重新安装）之后发起一个新实例。
>
> 换成 QuickJS 载体之后，"总是失败"多了一种便宜的形态：**死循环**。载体在字节码层面中断得掉它，所以它表现为"这次求值超时"而不是"一个线程转死了"——**结果仍然是节点未通过**（§6.4）。

### 7.5 一行怎么知道自己属于哪个实例

流程的**结算表**上，平台自动加一个**受保护的系统列 `_instance`**：

```text
人写行       → 用"为某实例的某节点写入一行"这个 tool，实例标识作为参数
任务写行     → 由「节点被激活」事件载荷里的实例标识自动填
流转插件写回 → 由求值上下文自动填
```

**主体行不带 `_instance`**——主体与实例的关联记在 `_flows.subject` 上。主体表的插入只负责开实例，主体行本身**不参与任何节点的求值**。

**输出插件写不了结算表。** 它跑在 onComplete 的上下文里，没有流程求值上下文，`_instance` 无从填；让它写结算表等于开一条绕过 §7.6 的旁路。要在流程里做事，用流转插件。
（它连"写"这个动作都没有：它能声明的三样能力里没有写表，§6.4。**结算表对它是只读的，而且是只读到"声明过才看得见"的程度**。）

**技能与用户都不能自己写这一列。** 没有它，两个并发的流程实例会在同一张表上产生两条同样满足筛选的行，节点判定无从区分——这是整个 §7 的地基。

### 7.6 一行要算数，必须同时满足

> **节点指定了流转插件时**：① 里的"满足筛选"这一半由插件的判定替代，**②～⑦ 一条不减**，且由平台在**调用插件之前**先判完——不满足的行根本不会被交给插件。

```text
① 该行写进了节点的**结算表**，`_instance` 指向本实例，且满足节点的筛选
   （指定了流转插件时，筛选部分由插件判定替代）
② 写入者在节点的允许写入者集合内          ← **写入这一刻**判定，不是事先
③ 若节点要求职责分离：写入者 ≠ 实例发起人
     写入者是任务时，比的是**任务所有者** ≠ 实例发起人
④ 同一写入者在同一节点尚未贡献过结算行
⑤ 该节点此刻处于**激活**状态（实例未终结、未被别处的拒绝终止）
⑥ 若写入来自执行：该执行**正常完成**（非超时/取消/失败）
⑦ 若写入来自执行且该执行声明了代码数据源：其实际读取的修订
   == 事件载荷里的主体修订
   （未声明代码数据源的执行——例如只吃输入参数的——本项不适用）

任一不满足 → 这一行**照常留在表里**（它是一条正常数据），只是不结算该节点
             留一条"未被采纳"的痕迹 + 通知写入者
```

几条值得单说：

- **② 是写入这一刻判定。** 名单表可以随时改：事件发出时 a 在名单里，任务跑了几分钟，期间 a 被移出——② 正好挡住这一情形。
- **③ 挡的是闭环自批**：a 自己发起 → 触发 a 自己的任务 → 记为 a 的通过，**全程一个人**。审批唯一的价值（多一个人）当场归零。写入者是任务时比任务所有者，**因为任务不是责任主体，人才是**。
- **⑥⑦ 挡的是产出异常**：执行超时后部分产出仍被保留（既有 R-05-34），那些残片不能算数；以及"执行读的是仓库当前 HEAD 而不是这次要看的那一版"。
- **两层拒绝要分清**：schema 校验不过 → 整批行**不入表**，执行归为技能错误类失败；schema 过、节点判定不过 → 行**入表**，只是不结算。**两种情况都要通知**——自动化失灵不能是静默的。

### 7.7 状态列的保护

流程可以声明**主体表上的哪些列是状态列**（比如 `bugs.status`）。状态列**只有平台与流转插件能写**，用户的 update 写不了它。

> 不这么做，任何成员都能直接 `update bugs.status = closed` 绕过整条流程——§7.6 那七条判定只管"这行算不算结算"，**从不阻止写入**。既有 R-03-09（非法状态转移被拒绝）在本版由这条承接。
>
> 于是一个 bug 的流转是这样闭环的：**人往 `bug_events` 写一行表态 → 节点结算 → 流转插件把 `bugs.status` 写成新状态**。状态列是插件写的，不是人写的。

### 7.8 流程的三条边界

| 不做 | 替代 |
|---|---|
| **条件分支 / 表达式引擎** | 用"不同流程 + 发起时选择"表达；需要条件逻辑就写进流转插件 |
| **退回 / 驳回循环** | 不提供。被拒绝的实例进入拒绝终态；重走一遍是**发起一个新实例** |
| **超时自动通过 / 自动推进** | 实例可设过期，过期走"已过期"终态。**一个会自动放行的关卡比没有关卡更糟——它看起来像有** |

## 8. 看板

**看板 = 一张表的一个视图**：显示哪张表、按什么筛选、按什么排序、显示哪几列。

平台不内建任何报表——没有燃尽图、没有趋势图、没有跨项目对比。想要趋势，就写一个技能，读历史行、往一张趋势表里写行，然后给那张表建个看板。

> 判断标准很简单：**如果有一天需要在平台代码里写"什么是缺陷密度"，那就越界了。**

**一个主体的"完整时间线"横跨两张表。** 以 bug 为例：状态怎么变的、谁改的、什么时候，在 `bugs` 那一行的**单行历史**里；为什么这么变、谁表的态，在同实例的**全部 `bug_events` 行**里。看板上是两个视图，MCP 上是两次查询——**平台不做 join**（§4.7）。

> 既有 R-03-17 要求缺陷详情含完整时间线（每一次变化、谁、何时、**为什么**）。这条没有丢，只是拆成了两半：模板建议在结算表上加一个行引用列指回主体行，方便人和 agent 各自拼起来。

### 个人看板与通知

**通知不是一条投递管道，是 `_notices` 表上属于我的那些行。** 每个用户有一个**个人看板**，显示的就是这张表按自己过滤后的视图。

```text
通知从**事件派生**，不引入独立的产生路径
       —— 否则会出现"发了通知但账本里没有对应事实"
内容由**确定性代码**从结构化事件生成，不经模型
只发给对该事件所属项目**有可见权限**的用户
```

值得通知的：**有节点在等我处理** · 流程实例已决定 · **我写的行未被采纳** · 执行完成或失败（尤其定时任务）· 表里的某行指派给我。

**通知行在业务写的串行区间之外追加**（§4.8）：写失败只留痕，**绝不回滚业务写**。既有 R-09-02 / I-09-1 那条"通知的失败绝不影响产生该事件的业务操作"因此是结构保证，不是"几乎不会失败"这种概率话术。

这样处理省掉了三样东西：投递渠道、重试策略、聚合窗口。

**既有 RP-09（指 2026-08-20 的九包版，非当前包 ID）的十条里，这几条原样保留**：R-09-01（从事件派生，不引入独立触发路径，即 I-W）· R-09-03（确定性代码生成，不经模型）· R-09-04（自由文本原样引用或截断，不改写、不摘要、不翻译）· R-09-05（只发给对该项目有可见权限的用户）· **R-09-09（不含凭据、令牌或产物原文，只含指针）**。被 D39 取代的是投递侧那几条：R-09-02、06、07、08、10。

> 要把消息送出 XOps（邮件、IM），用**输出插件**（§5.2 的 onComplete）。平台自己不提供这个能力，也不定义"通道"——这保住了既有那条"不做通用的发消息给某人"的边界：平台侧没有任何一条能承载任意内容、发给任意人的通路。

Web 上的看板**没有任何直接写库的按钮**——个人看板上的「标记已读」也是发一次 MCP 调用，走平台专属 tool（§4.2）。看板的定义本身同样经 MCP 改。

**长文本（Markdown）列渲染时必须禁用内联 HTML 与脚本**，只渲染受限标记子集，外部资源不自动加载。绝大多数 Markdown 渲染库**默认开启内联 HTML**，而这些内容部分来自被分析的代码仓——**能往那个仓提交代码的人，就能影响它**。这是渲染这条攻击链上唯一的门。

### Web 这一侧的实现形态

```text
后端   Rust 只读 HTTP 服务。它对外只有一个**读模型**：看板视图、单行历史、
       长文本原文。**没有写路由**——不是"有但不给 Web 用"，是不存在
前端   TypeScript + React SPA，构建产物随二进制发行
接缝   读模型是前后端唯一的契约。前端不直连库、不拼 SQL、不调 MCP
```

**G2「Web 只读」由两道兑现，顺序不能反**：

| 道 | 谁兜 | 强度 |
|---|---|---|
| **① 后端不存在写路由** | 后端 | 结构性的。前端就算想写也没有地方可发 |
| **② 前端不存在调用写接口的代码路径** | 前端 + CI | 纪律性的。用检查兜住"就加一个按钮"这种持续压力 |

> ⚠️ **顺序不能反**：只有 ② 没有 ①，等于把一条安全属性交给前端自觉；有了 ① 之后，② 是为了让越界在**评审阶段**就被看见，而不是等它撞上 404。
>
> ⚠️ **选 React 而不是"把前端也写成 Rust"，代价是引入一条 npm 工具链与一个构建步骤**，这与"可本地部署"（D41）不冲突——**构建产物随二进制发行，部署方不需要 Node**——但它确实让仓库多了一套依赖要跟。这笔账认下来。

## 9. 模板

```text
模板 = 一套表 schema + 可选的流程定义 + 可选的插件

tool: 列出可用模板 → 查看模板内容 → 在本项目实例化（建表、建流程、装插件，一步完成）
```

平台自带三个：

| 模板 | 建什么 |
|---|---|
| **bugs** | `bugs`（主体表：状态列、自增序号列、派生的可读 ID 列）+ `bug_events`（结算表）+ 一条随行自动发起的流程 + `bugs` 流转插件 |
| **issues** | `issues` + `issue_events` + 一条流程 + `issues` 插件 |
| **approvals** | `approvals`（结算表，**无主体表**）+ 一条用于审批的流程骨架 + `approvals` 插件 |

**实例化之后它们就是普通的表、流程和插件**，用户想怎么改就怎么改——加列、改流程、换插件（换插件仍需维护者）。模板是起点，不是约束。

> **关于缺陷 ID**：`<项目短名>-<序号>` 由 bugs 模板声明的一个**派生文本列**生成，模板是 `{project.slug}-{seq}`（§4.5）。平台只提供"自增序号"与"派生文本"两个通用列类型和"项目短名"这个项目属性，**不认识"缺陷 ID"这个概念**。
>
> 用派生列而不是让写入方 agent 自己拼字符串，是因为这个 ID 会被手写进提交历史——**它必须简单到不可能出错**（既有 R-03-01）。派生列由平台在写入时算一次、之后不变，这是确定性的；也**不需要为它开第三个插件调用位置**。

**模板的来源**：首版三个模板随平台发行。用户自己的模板 = 一套表 + 流程 + 由自己的造插件任务产出的插件，导出与提交模板的路径待定（Q15）。

## 10. 与 XForge 的配合

### 10.1 前提：一个项目 + 一次绑仓 + 一条登记 + 两条约定

```text
① 在 XOps 建一个项目
② 绑定 XForge 所在的那个仓库
③ 登记 **policyId → 哪条流程**，并声明**结果列映射**：
     结算表的哪一列是 decision（approve/reject）、哪一列是 reason
     approver 由结算行的 writtenBy 解析：
       writtenBy 是人      → 就是他
       writtenBy 是执行    → 取那个私有任务的所有者
       writtenBy 是插件求值 → 取安装该插件的维护者
       role 取该人在本项目的角色
   —— 没有它，适配层拼不出 poll_approval 的返回值
④ **每个开发者用自己的 XOps 令牌**跑 xforge approve
⑤ 被审对象的 **gitHead 必须已推送到绑定的那个仓**
```

**②③ 任一找不到时明确失败，绝不静默创建。** ③ 挂在 ② 的仓绑定上，不另开一套对象。

**XForge 侧的配套由 XOps 提供并维护**，不是让用户自己去拼：**四样，缺一样门就不存在**：

```text
① 一份 `McpServer` 资源（transport: http · url · authTokenEnv · timeoutSeconds）
② 它在 `manifest.yaml` 的 `scaffold.mcpServers` 里的登记
③ 一条 `approvals.providers[]` 条目（roles 与 XOps 实际返回的角色对齐）
④ 某条 Flow 的 `approvalPolicies[].providers` 里**引用这个 provider id**
```

**①② 缺了会加载失败，③④ 缺了会静默失效**——后者更危险：`xforge doctor` 对未被引用的扩展资源**只警告、从不阻塞**，于是 provider 装好了、连得上、却没有任何一条 Flow 引用它，**这道审批门等于不存在，而一切看起来都正常**。

> **两侧的版本对齐责任在 XOps 这边。** XForge 的两个 tool 名字与参数由它定死，我们只有实现义务；但配套模板跟不跟得上它的版本，是我们的事。这是一个**持续交付物**，不是一次性配置说明。

> ⚠️ **④ 不是运维建议，是一条安全前提。** §7.6 的 ③（职责分离）整个压在"事件载荷里的发起者就是那个真人"上，而发起者 = 调用 `submit_approval_request` 所用令牌的持有人。**一旦团队共用一个令牌，这条会整体失效且无声**：要么所有请求都算那个人发起的（他的任务永远不能结算节点），要么所有请求都不算（自发自批的门形同虚设）。既有 R-01-13 本来就规定"令牌一律按人签发"。
>
> ⚠️ **⑤ 只影响自动化，不影响人。** XForge 是本地优先的，approve 完全可以在 push 之前跑；而 XOps 只能克隆远端。gitHead 还没推上去时，任务的工作区准备会失败 → §7.6 ⑥ 不过 → 不结算、归为工作区错误、通知写入者；**人工写入不受影响**——人看 `revision` 各字段照样能批。调用方那边只会看到 `pending`，所以这条失败必须真的发出通知。

### 10.2 链路

```text
开发者机器
  xforge approve --provider xops        ← XForge CLI 本身就是一个 MCP client
    │
    │  submit_approval_request（名字固定、不协商）
    │    change / flow / stage / transition / policyId
    │    revision{stateRevision, contentRevision, policySnapshotDigest, gitBase, gitHead}
    │    governingDigest / roles / reason
    ▼
  XOps
    ├─ 由仓绑定定位 XOps 项目                    找不到 → 明确失败
    ├─ 由 policyId + roles 映射到本项目的流程     找不到 → 明确失败
    ├─ 按 **governingDigest 幂等**发起流程实例（主体 = governingDigest），
    │  第一个节点激活，**立即返回**
    ├─ 原样保存 revision 各字段（人做决定时要看清"我批的是哪一版"）
    │  其中 gitHead 同时作为事件载荷里的**主体修订**，喂给任务
    └─ 产生「流程节点被激活」事件 → 该节点指定的任务被触发
    │
    ▼
  节点被结算（人往结算表写一行，或某个私有任务写一行，或流转插件判定）
    │
    │  poll_approval（参数只有 governingDigest，**必须立即返回**）
    │    未决        → pending
    │    已决        → decided + decision + approver{id, role} + reason (+ expiresAt)
    │                  ← 取自 ③ 声明的结果列映射
    │    从未提交过  → **明确的未知状态，不是报错**
    │                 XForge 会整轮重试（连接+提交+轮询），必须对重试安全
    ▼
  XForge CLI 自己把回执写进仓里，并在同一次运行里追加一条审计事件
    · XOps 从不写任何仓库
    · 回执不带签名，可信的是"项目自己的审计链里有一条匹配事件"
```

两个 tool 的返回值形状也是定死的：**一个 `text` 类型的 content item，其 `text` 是一段 JSON 字符串，不使用 `structuredContent`。**

`approver.role` 必须是 XForge 侧认得的角色名，且同时在 provider 条目与被满足的 policy 角色列表内。**XOps 侧应当自己先校验**——让角色配错在"告诉人类他的批准生效了"之前就失败。

**理由必填**：既有 R-06-21 要求决策附带理由，空理由被拒。本版由 **approvals 模板的插件**承接——它校验 reason 列非空，空的不结算。平台本身不认识"理由"这个概念。

### 10.3 三条必须记住的边界

| 边界 | 说明 |
|---|---|
| **Gate 拿不到凭据** | XForge 的 Gate 子进程会过滤掉一切凭据形状的环境变量（据 G6）。所以**绝不能**把归档前的校验设计成"Gate 去查 XOps"——它没有能力认证。正确形态是决策先经审批通道落进仓库成为回执，Gate 只读本地文件。**这也是 XOps 挂了不影响开发的原因** |
| **角色以 XOps 为准（D15）** | XOps 返回自己的项目角色名，XForge 侧去对齐。**代价**：XOps 的角色固定为所有者/维护者/成员，若 XForge 侧某条 policy 要求 `verifier`，校验将永远失败且无法绕过。要么约定 XForge 侧只用这三个名字，要么日后在绑定上加一张三五行的映射表——**不要为此把 XOps 改成可配置角色系统** |
| **不可用时可重试，不是放行** | 关停 XOps 之后跑 `xforge approve`，必须报连接失败可重试。任何"连不上就跳过"的降级逻辑都会让变更被静默放行——这条必须**实际断网测一次** |

## 11. 两件必须诚实面对的事

### 11.1 平台知道的是"可追溯"，不是"正确"

**平台不执行任何验证命令**（D18）。所以：

> **XOps 的一切自动判定，可信度上限等于「写这个技能/插件的人 + 那次执行」的可信度。**

```text
平台真的知道的：
  哪个技能的哪个版本 · 哪个插件的哪个版本 · 哪次执行 · 读的哪个代码修订
  什么时候 · 谁授权的 · 被哪个事件触发 · 往哪张表写了几行、什么值

平台不知道的：
  这些行对不对
```

**审批的价值也要说清楚**：

> **审批不保证正确。它保证的是：多了一个具名的人为这件事负责。**

任务或插件代人写结算行之后，这个价值发生了一次**部分让渡**：

```text
保留的  ── 结算仍然归属一个具名的人（任务所有者 / 装插件的维护者）
           而且这个人**不能是发起请求的那个人**（§7.6 ③）
让渡的  ── 那个人不再逐次亲自看内容
```

**这打破了既有的四条**，明说：

| 既有 | 原文 | 本版 |
|---|---|---|
| **R-06-19** | 决策由人做出…不接受任何形式的代批声明 | 人可事先授权自己名下的私有任务、或维护者装的插件代写结算行 |
| **I-06-4** | 不存在任何使实例在无人决策的情况下进入"已通过"的代码路径 | **不存在无归属的结算**——每一次结算都追溯到一个具名的人 |
| **RP-06 核心性质一**（九包版） | Agent 不负责决定通过与否 | Agent 与插件可以结算节点，受 §7.6 七条约束 |
| **既有 G8 后半** | 分析平面不得写入确定性平面的任何数据 | **模型生成的插件，经"生成 + 测试 + 维护者安装"之后在确定性平面运行。** 这仍然是最重的一次让渡；**第 11 版把它的射程收窄了一半**——插件在载体里跑、能力默认为零，让渡掉的不再是"执行任意代码"，而是"由模型写的代码替人做判断"。见 §6.4 与 G11 |

**这是一次真实的取舍，不是一次免费的自动化。** 值得做，因为逐次人工点通过在高频场景下退化成橡皮图章——一个不看内容的人和一个不看内容的技能，可信度差不多，而技能与插件至少是**可复现、可审查、有版本**的（这也是 §5.6 那条例外与 §6.3 那条硬要求存在的原因）。

对策不是加机制，是把它标清楚：

```text
每一行都有 writtenBy —— 人写的、执行写的、插件写的、平台写的，永不混同
用于结算节点的私有技能版本与任务定义，对项目成员转为可读
已安装插件的源码，对项目成员必须可读
未正常完成的执行，其产出的行明确标注来源；且不结算任何节点
产物超过体量上限时截断并明确标注，不静默丢弃
```

**一条硬纪律**：

> **任何自动判定只看结构化列，从不读长文本列。**
> "让它读一下报告里有没有写 PASS"是一个非常自然、且会一次性推翻全部设计的想法。

### 11.2 隔离管得了插件碰什么，管不了插件说什么

第 10 版这一节叫"插件是这套设计里唯一没有隔离的地方"。**那条已经不成立了**（§6.4，D52）：插件跑在 QuickJS 载体里，能力默认为零，输出插件的三样是声明出来、安装时逐条披露的。

**但取代它的不是"所以这块没问题了"。** 边界重新划了一次，划完之后剩下的这条要单独说：

> **载体隔离的是插件能碰到什么，不是插件会说什么。**
> 一个流转插件永远返回"通过"，它没有越任何界——它只是做了一个错误的判断，
> 而那个判断会结算一个流程节点。

所以这一节留下来，内容换成三句：

```text
① 插件的**判断**仍然是治理对象，不是隔离对象
   —— 这就是为什么"维护者安装""源码必须可读"两条一个字没减（§6.3）
② 载体本身是信任基
   —— QuickJS 的内存安全是这套隔离的地基，版本要跟、CVE 要看
③ 输出插件的外泄面是**可审查的**，不是**不存在的**
   —— 它拿得到喂给它的数据，送得到它声明过的主机，两者安装时都披露过
```

**能用技能解决的，不要用插件**——理由见 §6.4 结尾，已经不是"插件不可隔离"，而是"插件本来就做不了多少事"。

## 12. 安全边界

| # | 约束 | 一句话 |
|---|---|---|
| G1 | 所有写操作经 MCP | 两个例外（OAuth 回调、webhook）都被削得只剩一件事可做 |
| G2 | Web 只读 | 前端不存在调用写接口的代码路径，后端不为 Web 暴露写接口 |
| G3 | 账本追加式 | 表对外是 CRUD，对内每次写都追加事件（§4.3） |
| G4 | 权限一律按项目判定 | 无跨项目全局角色，无组织级继承 |
| G5 | 身份来自凭据 | MCP 不认证调用者，只认证令牌 |
| G6 | XOps 不进入开发的关键路径 | XForge 的 Gate 只读仓内文件，不查询 XOps |
| G7 | 所有外部自由文本是不可信输入 | 表里的文本、技能内容、任务输入、webhook 载荷、模型产出。**插件源码是唯一的例外**：安装前它是不可信输入且必须经维护者人工审查（§6.3），安装后它是**被载体约束的**平台扩展（G11） |
| G8 | **确定性平面与分析平面隔离。** 账本、审计、权限判定、节点结算判定、schema 校验都不经模型；Agent 只在容器内工作，**没有任何写表的路径** | **插件是分析平面产物在确定性平面运行的唯一入口**——它本身不经模型，但它是模型写的。它的**执行**被载体约束，它的**判断**不被（§6.4、G11） |
| G9 | **任何自动判定只看结构化列** | 从不读长文本列，从不因自由文本改变控制流 |
| G10 | **每一次节点结算都归属一个具名的人** | 人直接写、他名下的私有任务代写、或维护者装的插件判定 |
| **G11** | **插件的执行由载体隔离，插件的判断由治理兜底** | 载体：一次调用一个 runtime · 能力默认为零 · 字节码级中断 · 故障只花一次调用<br>治理：生成+测试流水线 · **维护者安装并逐条披露能力** · 源码必须可读 · 每一步留痕<br>**两半缺一不可**——载体拦不住"永远返回通过"，治理拦不住"装完之后源码没人看" |
| **G12** | **执行引擎与存储都在契约后面，且各有一次换实现的硬验收** | 引擎换成桩实现、存储换成内存实现，两次都**不改上面的任何代码**（`EXE-014` · D46） |

### 不变量

```text
I-A  令牌原文在系统内任何持久化位置都不存在
     插件配置**经任何 MCP 接口**不可读出；**只注入给声明了这项能力的那个插件自己**
I-B  任何写入的行，其 writtenBy 来自令牌解析、执行标识、插件求值或平台自身，
     **不来自请求体**
I-C  每个对象恰好有一个归属方（项目或用户），且恰好在一个项目的上下文中被使用
I-D  事件一经写入即不可变；表的当前视图是缓存，不是权威；任一行可查完整历史
I-E  **不存在任何从容器内写表、写权限、写流程状态的代码路径**；**插件也没有写表的路径**——
     它只能把要写的行交回平台，由平台在串行区间内代写（§4.8、§6.4）
I-F  容器内不含任何凭据；过程记录中也不出现任何凭据
I-G  XOps 在任何代码路径上都不持有、不请求仓库的写权限
I-H  不存在无归属的节点结算
I-I  一次执行的可见范围完全由其声明的数据源决定，不存在隐式扩权
I-J  执行环境无法触发任务，不存在自触发回路
I-K  已发布的技能版本、已安装的插件版本均不可变
     未经成功测试执行的技能不可发布；未通过编译 + 用例的插件不可安装
I-L  Web 会话凭据与 MCP 令牌互不通用；Web 会话不能用于任何写操作
I-M  常驻编排进程中，两次执行之间不存在可观测的状态泄漏
I-N  不存在只改表的当前视图而不写事件的代码路径
I-O  一次流程实例的发起人，其名下的任务不为该实例结算任何节点
I-P  结算表的 `_instance` 列与主体表的状态列是受保护列：技能、用户、普通写入路径都写不了
I-Q  名单表只有项目所有者能写；保护级别不可降级
I-R  **流转**插件交回的行由平台代写，不再触发插件求值，也不发起新实例
     （对主体表只能 update 不能 insert）；输出插件写不了任何表
I-S  onComplete 的深度硬限制为 1：被挂的任务其 onComplete 必须为空
I-T  已安装插件的源码**与它的能力声明**对项目成员可读；不存在不可审查的已安装插件。
     能力声明是版本的一部分，安装时逐条披露，披露不可跳过
I-U  一张表在同一时刻只有一个写在进行。schema 校验、事件追加、节点求值、
     插件写回四件事在同一串行区间内完成；该区间涉及的表**只有**结算表、
     主体表与 `_flows`/`_flow_nodes`，按表名全序取锁，因而构造不出死锁。
     其余任何跨表写都没有原子性
I-V  每次执行都有 token 上限；撞上即强制终止，绝不放任跑完
I-W  通知只从事件派生，不存在只发通知而没有对应事件的路径；通知行在业务写的
     串行区间**之外**追加，其失败绝不回滚业务写；平台侧不存在任何能承载
     任意内容、发给任意人的通路
I-X  治理事实不受任务保留期约束：被 `_flows.subject` 引用过的行、带 `_instance`
     的行、`_flows`/`_flow_nodes`/`_plugins`、以及各类定义，都不会因到期被清理
I-Y  `_notices` 的读写被平台硬限定为 `user = 令牌持有人`；它不派发通用查询 tool
I-Z  **插件的能力默认为零，未声明即没有**——不是调用时被拒绝，是那条路不存在。
     流转插件没有可声明项；输出插件只能声明出网、读自己的配置、读声明过的表
```

## 13. 明确不做

| 不做 | 替代 / 理由 |
|---|---|
| 不受限的任务编排（A→B→C…） | onComplete 深度硬限制 1 |
| 内部事件里加"某张表被写入" | 那是不受深度限制的回路 |
| 内建报表引擎 / 燃尽图 / 趋势图 / 跨项目对比 / 执行结果对比视图 | 看板 = 表的视图；趋势自己写技能算 |
| 表的 schema 迁移 | 加列可以，其余新建表自己搬（§4.6） |
| 表之间的关联 / 外键 / 级联 | 行引用列只存 ID |
| 行级权限 | 表级足够。**唯一例外是 `_notices`**（§4.7） |
| `json` / 任意对象 列类型 | 有了它窄接口纪律当场破掉 |
| 流程的条件分支 / 表达式引擎 | 不同流程 + 发起时选择；条件逻辑写进流转插件 |
| 流程的退回 / 驳回循环 | 被拒绝的实例进终态；重走一遍是发起新实例 |
| 超时自动通过 / 自动推进 | 走"已过期"终态 |
| **平台提供"发消息 / 发邮件 / 发 IM"的能力** | 平台只调用插件入口，**干什么是插件的事** |
| **项目级额度与限流** | 单次执行有 token 上限就够了（§5.1）。项目级配额需要计费模型、配额分配与超额策略，现在没有支撑它的真实需求 |
| 行级锁 / 多表事务 / MVCC | 表级串行已经防住并发结算这一类真问题（§4.8）。那是数据库的活 |
| 往代码仓写任何东西 | 保持"XOps 不需要任何仓库写权限"这条安全属性 |
| 用模型判断行是否重复 / 技能是否安全 / 产出是否合格 | 判断题属于人 |
| **跨表写的原子性**（D43） | 只有表级串行区间那一组落定；其余用顺序保证就够 |
| **依赖数据库特有能力**（D46） | 只用基本 CRUD，换库不改写入路径 |
| **表数据作为执行的数据源 / 表导出**（D44） | 需要就经 MCP 查好，放进任务输入 |
| **结算的撤销**（update / delete 参与求值）（D45） | 一次表态一旦被采纳就是既成事实 |
| 容器池化 / 复用 | 与"一次执行一个一次性容器"冲突 |
| Web 上的任何写入 | 页面给出"在你的 Agent 里跑这条命令" |
| **引擎不可用时在 XOps 进程里就地跑技能** | 那等于隔离承诺恰好在最需要的时刻不成立（§5.5） |
| **给插件加第三种宿主绑定** | 能力面只有三样，加第四样是一个要单独论证的决定，不是一次顺手的扩展（§6.4） |
| **给流转插件任何 I/O** | 它的输入由平台预取、输出交回平台。求值在写串行区间内，一次自由查询就是一次不确定的写时延（§6.1） |

**一个项目一个仓（暂定）。** 既有 R-04-01 写的是"零个或多个"。多仓会让"一次执行只持有一个项目的代码"细化成"只持有本次声明的那几个仓"，隔离判定复杂一档。**先做单仓**（Q11）。

## 14. 演进

> 里程碑与需求包的对应见 [需求包总览](requirements/README.md)。本节只写"每一步做完之后，这个东西是什么"。

```text
M0  工程地基（第 11 版新增的一步）
    Rust workspace 起架；**存储契约 + SQLite 实现**；**表级写串行的四步区间骨架**

    + 表：建表（含保护级别）、加列、每张表的专属增删改查 tool、查单行历史
    + 平台自动补的列位（writtenBy / at / revision / _instance / retainUntil）
    ★ Agent 经 MCP 建表、写行、查行；Web 上看到表与单行历史
    这本身就是个能用的东西 —— 一个 agent 友好的、可审计的记录系统

M2  技能跑起来
    执行运行时 —— 隔离是这一步的全部难点，五件事一件都不能少：
       ① 容器隔离全部条目（一次性、无凭据、只读挂载、默认拒绝出网、完整销毁）
       ② 分立进程（attacored）+ **XOps 自己的执行契约**这一个接缝

       ③ **容器后端的四个执行契约实现** + 上游那两项（注入点、契约修订，§5.5）
       ④ 跨执行的会话隔离（一次执行一个会话，用完销毁；失效时没有报错）
       ⑤ 崩溃时在途执行不挂起、可重跑；超时不留孤儿会话；失败必须分类；
          **引擎不可用时绝不就地跑**
    + Git 仓绑定（只读）+ 技能（含公共/私有与派生）+ 任务 + 手动触发
    + `_runs` 系统表 + 平台在容器外写入
    + **单次 token 上限与用量记录** + **输出保留期与到期清理**（§4.9）
      ⚠️ 两条都在 M2：
         token 上限 —— M3 一开定时触发，没有它就是无上限烧钱；
         保留期 —— retainUntil 是写入时就要落的列，事后补等于回填全部历史行
    ★ 手动触发 → 容器里读仓跑技能 → 行落进 `_runs` → 看板上看到
    ★ 主动攻击测试：写一个故意越界的技能，每一项越界都必须在**容器与能力层**失败，
      而不是被内容检查拦下

M3  自动跑起来
    + 定时触发 → git webhook 触发（按平台逐个交付）
    ★ 夜里跑，早上看

M4  流程 + 插件 + 通知 + 模板
    + `_flows` / `_flow_nodes` 系统表 · `_instance` 与状态列的保护
    + 流程定义（节点、通过/拒绝条件、允许写入者、职责分离、随行或显式发起）
      · **节点声明它求值时要用到哪些行**（§6.1）
    + **QuickJS 载体**：能力解析、一次调用一个 runtime、字节码级中断、故障隔离
    + 造插件任务（手动触发、生成 + 编译 + 用例 + 能力声明）
      · 插件安装（维护者，**逐条披露能力**）· 插件配置（所有者）
    + 流转插件求值（超时、错误隔离、不递归）+ onComplete（插件 / 任务，深度 1）
    + `_notices` 系统表 + 个人看板
    + bugs / issues / approvals 三套模板与插件
    ★ 一个 bug 按模板给的流程走完全程
    ★ 自发自批测试：a 自己发起，a 名下的任务写的行**不结算**
    ★ 多节点测试：三节点流程，指定在第 2 节点的任务在第 1 节点通过后**确实被触发**
    ★ 修订测试：任务读到的是**请求载荷里那个修订**，不是仓库当前 HEAD
    ★ 名单竞态测试：任务执行期间把人移出名单，写入时被 §7.6 ② 挡下
    ★ 绕过测试：直接 update 状态列被拒绝（§7.7）
    ★ 插件故障测试：插件超时 / 抛异常 / **死循环** → 节点**未通过**并留痕，
      绝不视为通过
    ★ 插件能力测试：**没声明就够不到**——未声明出网的插件发请求、
      未声明读表的插件查表、任何插件读 `_notices`，三项都必须失败在"函数不存在"，
      不是失败在"被拒绝"
    ★ 并发测试：两个人同时往同一个结算表写"最后一票"，只有一票被结算

    ⚠️ 通知在这一步而不是更晚：§7.6 与 §10.1 都写着"必须通知"，
       没有通知，自动化失灵就是静默的
    ⚠️ 模板从 M1 挪到这里：模板要建的是"表 + 流程 + 插件"三样，
       只有表的那半个模板不值得单独交付一次

M5  XForge 适配
    + 两个固定 tool + 一次绑仓 + 一条登记（含结果列映射）+ 两条约定
    + **XForge 侧配套四样的交付与维护**：McpServer 资源 + manifest 登记

    ★ xforge approve --provider xops 真实跑通
    ★ 断网测试：关停 XOps 后 xforge approve 报可重试，**不是放行**

M6  多仓 · 独立对象存储 · 用户自定义模板的导出与提交 · 多实例部署（要一把进程外的锁）
```

**一条不能被时间压力推翻的顺序**：如果 M2 的隔离做不完，正确的做法是**整个推迟 M2、在 M1 停下**，而不是先上一个隔离不全的运行时。先跑起来再补隔离，等于在补上之前一直敞开，而这段时间里跑过的技能、读过的代码、泄过的凭据都追不回来。

**M0 就要定死、事后补等于重写的两件**：存储契约的形状 · 表级写串行的四步区间边界（它决定了流程求值与插件写回将来怎么接进来）。

## 15. 术语

| 术语 | 一句话 |
|---|---|
| **项目** | 唯一的归属、权限与数据边界。有不可变短名，当前绑一个 Git 仓 |
| **表 / 行** | 项目下命名的数据表与其中的记录。对外 CRUD，对内追加 |
| **系统表** | 平台维护、schema 固定：`_runs` · `_flows` · `_flow_nodes` · `_plugins` · `_notices` |
| **受保护表** | 建表时声明、不可降级。名单表是其一，只有所有者能写 |
| **结算表** | 流程节点的结算行写在这里。带受保护的 `_instance` 列 |
| **主体表** | 流程在治理哪张表的行（可选）。**不得与结算表相同**；它的状态列只有平台与流转插件能写 |
| **技能** | 用自然语言写的一份指令 + 几项声明。归属项目（公共）或用户（私有） |
| **任务** | 一个技能 + 订阅哪些事件 + 读哪些数据源 + 写哪些表 + onComplete + 执行策略 |
| **造插件任务** | 一种受限任务：只能手动触发，产出插件源码 + 测试用例 |
| **事件** | 定时 / Git / 手动 / 流程节点被激活 / 上游任务完成（白名单，仅此五类） |
| **执行** | 一次一次性容器的完整生命周期。永不覆盖，重跑产生新的一次 |
| **插件** | 由技能生成、维护者安装、**在 QuickJS 载体里执行**的 JS 代码。流转插件（零能力）/ 输出插件（三样声明出来的能力） |
| **能力声明** | 插件随源码一起产出的一份清单，说明它要用哪几样宿主绑定。**是版本的一部分**，安装时逐条披露，未声明即没有 |
| **载体** | 跑插件的那层东西。它管的是"插件能碰到什么"，管不到"插件会说什么"（§6.4、G11） |
| **执行契约** | XOps 与执行引擎之间唯一的接缝。引擎的概念不得泄漏进它；换成桩实现，契约与其余部分不改（`EXE-014`） |
| **存储契约** | 只有基本 CRUD 的一层 trait。换一个实现进去，写入路径与它上面的一切不改（D46） |
| **流程** | 有序节点序列 + 一张**结算表** + 可选的**主体表**（两者不得相同）+ 何时发起实例 |
| **流程实例** | 一条流程的一次运行，绑一个主体，落在 `_flows` 表 |
| **节点结算** | **结算表**上出现了满足条件、且写入者被允许的行 |
| **名单表** | 一种受保护表，行是人。**只有项目所有者能写**——它是审批权的元权限 |
| **模板** | 一套表 + 可选流程 + 可选插件，可一步实例化到项目里 |
| **看板** | 一张表的一个视图。个人看板 = `_notices` 里属于我的那些行 |
| **token 上限** | 一次执行的模型消耗上限，撞上即强制终止。项目级额度不做 |
| **保留期** | 任务分别声明输出（默认 1 个月）与过程记录（默认 7 天）保留多久，到期删除。治理事实豁免，且豁免优先 |
| **表级写串行** | 一张表同时只有一个写；校验、追加、节点求值、插件写回在同一区间内，锁集合限于结算表与主体表 |

## 17. 十个核心对象

其余概念都是这十个的派生物或属性。

```text
1  项目        边界
2  成员与角色   谁能做什么
3  Git 仓绑定   代码从哪来
4  表（行）     一切数据的形状 —— 缺陷、待办、审批记录、任务输出，全是它
5  技能        自然语言写的指令，跑在容器里
6  任务        技能 + 何时跑 + 读什么 + 写哪 + 完成后干嘛
7  执行        一次实际发生，落进 _runs
8  插件        JS 代码，QuickJS 载体里跑，能力默认为零，由技能生成、维护者安装
9  流程（实例） 有序节点；节点结算 = 表上出现被允许的行
10 看板        表的一个视图
```
