## 1. MVP 要验证什么

一个 MVP 的价值不在于"功能少"，而在于**它能证伪什么**。XOps 有两条核心命题，MVP 存在的意义就是尽早知道它们成不成立：

| # | 命题 | 不做 MVP 就无法知道的事 |
|---|---|---|
| **C1** | **AI 编程工具里的 Skill 愿意、也能够通过 MCP 把缺陷提交到一个云端账本。** | 窄接口（R-02-03）是否窄到让 Skill 写起来别扭；缺陷 ID 的形状在真实提交信息里好不好用；结构化到底该由谁做。 |
| **C2** | **服务端 Agent 读项目代码仓、按用户写的技能产出报告，这件事的产出值得看。** | 服务端执行的隔离代价有多大；技能这个抽象是否够用；一份自动产出的报告有没有人真的去读。 |

**这两条都是"做了才知道"的**，读文档、画架构图都得不到答案。其余一切——通用审批引擎、三种自动触发、通知——都是在这两条成立之后才需要回答的问题。

反过来说：**如果 C1 和 C2 都不成立，后面那些做得再好也没有意义。**

| 执行记录：每次一条永不覆盖、完整元数据、**Markdown 产物**、原始输出作为过程记录 | 多产物、保留期与清理 |
| 视图：技能列表、任务列表、**执行历史列表**、单次执行详情与安全 Markdown 渲染 | — |

## 3. 实施顺序

依赖关系很浅，因此顺序几乎只由价值决定。

```text
第 1 步    RP-01 平台基座
           （XForge 里的一次 Major Change，内部按 WP-A～WP-E 拆工作包）
              │
              ├──────────────────────┬─────────────────────┐
              ▼                      ▼                     ▼
第 2 步    RP-02 缺陷账本        RP-03 代码仓接入      （可并行开工）
              │                      │
              ▼                      │
        ★ 里程碑 M1                  │
   Skill 经 MCP 提交缺陷              │
   → 账本 → Web 时间线可见            │
              │                      │
              └──────────┬───────────┘
                         ▼
第 3 步            RP-04 技能与任务执行
                （Major Change，WP-D 沙箱是关键路径，建议最先开工）
                         │
                         ▼
                   ★ 里程碑 M2
        手动触发任务 → Agent 读仓执行技能
        → Markdown 报告 → Web 上看每次执行
```

**RP-02 与 RP-03 可以并行**，两者之间没有任何依赖。

**RP-04 严格来说也不依赖 RP-03**（技能可声明不需要代码仓），所以如果想更早验证 C2 的一半，可以先做 RP-04、用一个"读缺陷账本生成周报"的技能跑通链路，之后再补 RP-03 让技能能读代码。这条路把 M2 拆成两个更小的里程碑，代价是要多写一个只为验证而存在的技能。**默认按上图走，这条备选留给时间压力大的情况。**

### M1 是一个真实可用的交付物

不是半成品——它本身就是一个能用的缺陷账本。**如果时间压力大，在 M1 停下来是一个合理的选择**，比做一个隔离不全的 M2 好得多。

## 4. MVP 的不可裁剪清单

这些条目在 MVP 就必须做对。共同点是：**事后补的代价远高于当初就做**——要么是数据模型重写，要么是在补上之前系统一直是敞开的。

### 数据模型类（事后补 = 重写）

| 条目 | 内容 |
|---|---|
| R-01-36 / R-01-39 | 事件只追加、状态可从事件流重建 |
| R-01-40 | 业务副作用与审计事件同一原子边界 |
| R-02-07 | 缺陷状态变化追加新记录，**不 UPDATE** |
| R-02-10 | 重开不新建缺陷 |
| R-04-44 / R-04-46 | 执行记录永不覆盖、不随任务变更丢失 |
| R-04-45 | 每次执行记下**实际使用的技能版本**与**确切代码修订** |
| R-03-10 | 每次仓库读取记下确切修订 |

### 接口纪律类（事后补 = 所有 tool 重写）

| 条目 | 内容 |
|---|---|
| R-01-28 | 未声明字段一律拒绝，**不静默丢弃** |
| R-01-29 / R-02-03 | 固定形状的窄接口，**不提供通用透传上下文的 tool** |
| R-01-30 / R-02-05 | 写操作幂等 |
| R-01-32 | 无权限与不存在返回**相同**错误 |
| R-04-23 | 触发非阻塞 |

### 安全边界类（补上之前一直是敞开的）

| 条目 | 内容 |
|---|---|
| R-01-02 | **不开放自注册**，未预置账号登录后不留任何记录 |
| R-01-08 / R-01-11 / R-01-14 | 令牌不可读出、错误不可区分、**不接受自述身份** |
| R-01-26 / R-01-27 | 每次调用认证、身份只来自令牌 |
| R-01-45 / R-01-46 | Web 无写入、会话与 MCP 令牌分离 |
| R-03-03 / R-03-04 / R-03-06 | 只读凭据验证、凭据不可读出、**不进 Agent 上下文** |
| R-03-11 | Agent 对工作区的写入不回流仓库 |
| **R-04-27 ～ R-04-35** | **执行运行时的全部九条隔离需求** |
| R-04-51 | 过程记录不含凭据 |
| **R-04-57** | **Markdown 渲染禁用内联 HTML 与脚本** |
| I-04-5 | 执行环境结束后完整销毁 |

### 两条要特别提醒的

**R-04-57**：绝大多数 Markdown 渲染库**默认开启内联 HTML**。MVP 只有 Markdown 产物，很容易顺手用默认配置就上线。而产物内容部分来自被分析的代码仓——**能往那个仓提交代码的人，就能影响产物内容**。这是产物渲染这条攻击链上唯一的那道门。

**R-04-27～R-04-35**：如果 MVP 的时间压力大到做不完执行隔离，**正确的做法是把 RP-04 整个推迟、在 M1 停下**，而不是先做一个隔离不全的执行运行时。理由很直接——先跑起来再补隔离，等于在补上之前一直敞开，而这段时间里跑过的技能、读过的代码、泄过的凭据都无法追回。

## 6. 明确不在 MVP、也建议长期不做的

这些不是"以后再说"，是**建议写死的边界**。理由都是同一条：每多管一件，XOps 就离"平台"近一步，而一旦长成工单系统 + 看板 + 流水线 + 报表引擎，就把 AI 化之后本已消失的重量级流程重新造了一遍。

- **任务编排**（任务 A 完成触发任务 B）——需要 DAG、依赖解析、失败传播、循环检测及其可视化。需要串联就在一个技能内部完成多步。
- **审批的条件分支**（表达式引擎）——用"不同流程定义 + 发起时选择"表达，把判断留在发起方。
- **审批的驳回循环**——每一轮拉锯都需要新的对象修订才有意义，那本来就该是一次新的审批。
- **超时自动通过审批**——一个会自动放行的关卡比没有关卡更糟，**它看起来像有**。
- **内建报表引擎 / 看板 / 燃尽图 / 执行结果对比视图 / 跨项目横向对比**——想要趋势就写一个读取历史执行结果的技能。平台提供机制，不规定内容。
- **通用的"发消息给某人 / 把这个上下文发过去"的 MCP 工具**——一旦通道能承载任意上下文，信息隔离就从结构保证退化成每个人每次的自觉。
- **缺陷回写代码仓**（D5 已定）——保持 XOps 不需要任何仓库写权限这条安全属性。
- **用模型判断**缺陷是否重复、技能是否安全、产出是否合格——判断题属于人，确定性平面不碰模型（G8）。
- **把 XOps 写成 dsh 的插件**（D8 已定）——XOps 是驱动方，不是附属。
