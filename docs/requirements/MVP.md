## 1. MVP 要验证什么

一个 MVP 的价值不在于"功能少"，而在于**它能证伪什么**。XOps 有两条核心命题：

| # | 命题 | 不做 MVP 就无法知道的事 |
|---|---|---|
| **C1** | **AI 编程工具里的 Skill 愿意、也能够通过 MCP 把缺陷提交到一个云端账本。** | 窄接口（R-03-03）是否窄到让 Skill 写起来别扭；`<项目短名>-<序号>` 在真实提交信息里好不好用；结构化到底该由谁做。 |
| **C2** | **服务端 Agent 在容器里读项目代码仓、按用户写的技能产出报告，这件事的产出值得看。** | 容器隔离与 dsh 桥接的真实代价有多大；技能这个抽象是否够用；一份自动产出的报告有没有人真的去读。 |

**这两条都是"做了才知道"的**，读文档、画架构图都得不到答案。其余一切——通用审批引擎、三种自动触发、通知——都是在这两条成立之后才需要回答的问题。

### 两个包的裁剪明细

**RP-04 代码仓接入**：只做 GitHub（D13）· 单仓绑定 · 全量克隆 · 用完直接删工作区。推迟：Gitea/GitLab、多仓、增量更新、工作区生命周期管理。**但 R-04-02a 的平台适配接口要立住。**

**RP-05 技能与任务**：草稿/已发布两态 · 仅固定版本策略 · 手动触发 · Markdown 产物 · 执行历史列表。推迟：技能停用、跟随最新版本、重试、排队与终止重跑、项目级并发配额、多产物、保留期清理。

**RP-02 完整纳入**，只做四处简化：只支持 Markdown 产出、并发上限用固定小值、外部地址白名单不开放自定义、dsh 单实例常驻。**十二条容器隔离与六条进程边界需求一条都不能少**——尤其是常驻拓扑新增的跨执行会话隔离与崩溃恢复。

## 3. 实施顺序

两个根包可以第一天同时开工，这是本次拆分最大的收益。

```text
第 1 步（并行）
  ┌────────────────────────┐   ┌────────────────────────────┐
  │ RP-01 平台基座          │   │ RP-02 容器化执行运行时       │
  │ Major Change / WP-A～E │   │ Major Change / WP-A～E     │
  │                        │   │ ★ WP-A 执行契约最先定型     │
  └───────────┬────────────┘   └──────────┬─────────────────┘
              │                            │
              ├──────────────┐             │
              ▼              ▼             │
第 2 步   RP-03 缺陷账本   RP-04 代码仓接入 │  （两者可并行）
              │              │             │
              ▼              │             │
        ★ 里程碑 M1          │             │
   Skill 经 MCP 提交缺陷      │             │
   → 账本 → Web 时间线可见    │             │
                             │             │
第 3 步                      └──► RP-05 ◄──┘
                                技能与任务
                          （契约定型后即可并行开工，
                            不必等 RP-02 实现完成）
                                    │
                                    ▼
                              ★ 里程碑 M2
                   手动触发任务 → 容器里跑 dsh 读仓执行技能
                   → Markdown 报告 → Web 上看每次执行
```

**RP-02 的 WP-A（执行契约）是全局的早期关键节点**：它一定型，RP-05 就能对着桩实现并行开工，不必等容器与桥接做完。

**M1 是一个真实可用的交付物**——它本身就是个能用的缺陷账本。时间紧时在 M1 停下是合理选择，比做一个隔离不全的 M2 好得多。

## 4. MVP 的不可裁剪清单

共同点：**事后补的代价远高于当初就做**——要么是数据模型重写，要么是在补上之前系统一直是敞开的。

### 数据模型类（事后补 = 重写）

| 条目 | 内容 |
|---|---|
| R-01-16a | 项目短名唯一且**不可变**（缺陷 ID 的前缀，会被手写进提交历史） |
| R-01-36 / R-01-39 / R-01-40 | 事件只追加、可从事件流重建、与业务副作用同一原子边界 |
| R-03-07 / R-03-10 | 缺陷状态变化追加新记录**不 UPDATE**、重开不新建 |
| R-05-30～R-05-32 | 执行记录永不覆盖、不随任务变更丢失、记下实际技能版本与确切代码修订 |
| R-04-10 | 每次仓库读取记下确切修订 |

### 接口纪律类（事后补 = 所有 tool 重写）

| 条目 | 内容 |
|---|---|
| R-01-28 / R-01-29 | 未声明字段一律拒绝；**不提供通用透传上下文的 tool** |
| R-01-30 / R-03-05 | 写操作幂等 |
| R-01-32 | 无权限与不存在返回**相同**错误 |
| R-02-01 / R-02-05 | 执行契约是唯一接缝；**dsh 概念不得泄漏进契约** |
| R-05-23 | 触发非阻塞 |

### 安全边界类（补上之前一直是敞开的）

| 条目 | 内容 |
|---|---|
| R-01-02 | **不开放自注册**，未预置账号登录后不留任何记录 |
| R-01-08 / R-01-11 / R-01-14 / R-01-26 / R-01-27 | 令牌不可读出、错误不可区分、**只认令牌不认自述身份** |
| R-01-45 / R-01-46 | Web 无写入、会话与 MCP 令牌分离 |
| **R-02-06 ～ R-02-17** | **全部十二条容器隔离**（含 R-02-07 全部文件与进程操作在容器内发生） |
| R-02-18 ～ R-02-23 | 分立进程、桥接唯一接缝、**跨执行会话隔离**、**dsh 崩溃时在途执行不挂起** |
| R-02-28 / R-02-31 / I-02-4 / I-02-7 | 超时终止且不留孤儿会话、过程记录无凭据、容器完整销毁、**两次执行间无状态泄漏** |
| R-04-03 / R-04-04 / R-04-06 / R-04-11 | 只读凭据验证、凭据不可读出、**不进容器上下文**、写入不回流 |
| R-05-28 / R-05-29 | 装配请求时**不扩权、不放凭据** |
| **R-05-43** | **Markdown 渲染禁用内联 HTML 与脚本** |

### 两条要特别提醒的

**R-05-43**：绝大多数 Markdown 渲染库**默认开启内联 HTML**。MVP 只有 Markdown 产物，很容易顺手用默认配置就上线。而产物内容部分来自被分析的代码仓——**能往那个仓提交代码的人，就能影响产物内容**。这是产物渲染这条攻击链上唯一的那道门。

**RP-02 的隔离**：如果时间压力大到做不完，**正确的做法是把 RP-02 与 RP-05 整个推迟、在 M1 停下**，而不是先做一个隔离不全的运行时。先跑起来再补隔离，等于在补上之前一直敞开，而这段时间里跑过的技能、读过的代码、泄过的凭据都无法追回。

**验收上唯一挡得住偷工减料的是主动攻击测试**（RP-02 的 WP-E）：写一个故意越界的技能，尝试写确定性平面、读别的项目工作区、读凭据、访问白名单外地址、逃逸宿主文件系统——每一项都必须在**容器与能力层**失败，而不是被内容检查拦下。建议它与容器沙箱同步推进，不要留到最后补。

**常驻 dsh 新增的两条必须实测**：连续两次执行之间读不到对方留下的会话痕迹；强杀 dsh 进程时三个在途执行都在有限时间内失败可重跑而非挂起。前者失效时**通常没有任何报错**，只是产出变得莫名其妙——光看代码发现不了。

## 5. 进入设计前还需要的答案

**没有阻塞 MVP 的未决问题。** Q2、Q3、Q5 与平台优先级已分别由 D11～D14 解决。

Q4（XForge 角色映射：同名直映 / 绑定时声明映射表 / 项目支持自定义角色名，倾向映射表）随 RP-07 一起解决，不阻塞 MVP。

## 6. 明确不在 MVP、也建议长期不做的

不是"以后再说"，是**建议写死的边界**。理由都是同一条：每多管一件，XOps 就离"平台"近一步，而一旦长成工单系统 + 看板 + 流水线 + 报表引擎，就把 AI 化之后本已消失的重量级流程重新造了一遍。

- **任务编排**（任务 A 完成触发任务 B）——需要 DAG、依赖解析、失败传播、循环检测及其可视化。需要串联就在一个技能内部完成多步。
- **审批的条件分支**（表达式引擎）——用"不同流程定义 + 发起时选择"表达，把判断留在发起方。
- **审批的驳回循环**——每一轮拉锯都需要新的对象修订才有意义，那本就该是一次新的审批。
- **超时自动通过审批**——一个会自动放行的关卡比没有关卡更糟，**它看起来像有**。
- **内建报表引擎 / 看板 / 燃尽图 / 执行结果对比视图 / 跨项目横向对比**——想要趋势就写一个读取历史执行结果的技能。平台提供机制，不规定内容。
- **通用的"发消息给某人 / 把这个上下文发过去"的 MCP 工具**——一旦通道能承载任意上下文，信息隔离就从结构保证退化成每个人每次的自觉。
- **缺陷回写代码仓**（D5）——保持 XOps 不需要任何仓库写权限这条安全属性。
- **用模型判断**缺陷是否重复、技能是否安全、产出是否合格——判断题属于人，确定性平面不碰模型（G8）。
- **把 XOps 写成 dsh 的插件**（D8、D12）——XOps 是驱动方，两者是分立进程。
- **容器池化/复用**——与 R-02-06 冲突。若将来冷启动成为瓶颈，需要重新权衡而不是悄悄放宽。
