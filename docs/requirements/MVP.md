## 1. MVP 要验证什么

一个 MVP 的价值不在于"功能少"，而在于**它能证伪什么**。XOps 有两条核心命题，MVP 存在的意义就是尽早知道它们成不成立：

| # | 命题 | 不做 MVP 就无法知道的事 |
|---|---|---|
| **C1** | **AI 编程工具里的 Skill 愿意、也能够通过 MCP 把缺陷提交到一个云端账本。** | 窄接口（R-05-03）是否窄到让 Skill 写起来别扭；缺陷 ID 的形状在真实提交信息里好不好用；结构化到底该由谁做。 |
| **C2** | **服务端 Agent 读项目代码仓、按用户写的技能产出报告，这件事的产出值得看。** | 服务端执行的隔离代价有多大；技能这个抽象是否够用；一份自动产出的报告有没有人真的去读。 |

**这两条都是"做了才知道"的**，读文档、画架构图都得不到答案。其余一切——通用审批引擎、四种触发、三个 Git 平台、通知——都是在这两条成立之后才需要回答的问题。

反过来说：**如果 C1 和 C2 都不成立，后面那些做得再好也没有意义。**

## 2. MVP 范围

16 个需求包中的 12 个：5 个完整纳入、7 个按裁剪后的子集纳入。

### 完整纳入（5 个）

| ID | 需求包 | 为什么不能裁 |
|---|---|---|
| [RP-01](RP-01-identity-and-tokens.md) | 身份与访问令牌 | 身份是地基。做一半等于没做——一个"谁提交的"不可验证的账本不是账本。 |
| [RP-02](RP-02-projects-and-membership.md) | 项目与成员角色 | 项目是权限判定的唯一边界（G4），所有对象都要归属它。 |

## 3. 为什么审批不在 MVP 里

这是这份 MVP 建议里**唯一与你的决策方向有张力**的地方，所以要说清楚。

你已经明确选了**通用审批引擎**（D1），我按这个拆了包，RP-06/07/08 的需求条目是按通用引擎写完整的，**没有缩水**。这里说的只是**顺序**，不是范围。

不放进 MVP 的理由有三条：

1. **审批不参与 C1 和 C2。** MVP 要证伪的两条命题，审批一条都不碰。
2. **它是三个包里最大的一块。** 流程定义、审批点、串并行、会签、职责分离、实例状态机、幂等——放进 MVP 会让第一个可用版本显著推迟，而推迟期间学到的东西并不来自审批。
3. **通用引擎的复杂度目前没有真实需求支撑。** XForge 侧的审批契约是**固定的两个 tool**，它对 XOps 内部有几个审批点、怎么串并行**一无所知也不关心**——它只问"这个 governingDigest 决定了没有"。通用引擎的全部复杂度，服务的是 XForge 之外的场景（缺陷关闭要不要批、技能发布要不要批、任务发布要不要批），而**这些场景现在一个都还不存在**。等第一批真实场景出现，再决定三种成立条件、并行、职责分离各自值不值得，比现在凭空决定要准。

**如果你希望 XForge 联动尽早可用**，还有一条更短的路：RP-07 只做单审批点最小形态 + RP-08，跳过 RP-06 的流程定义（流程写死为"单点、任一成立、绑定固定角色"）。这样 XForge 的审批闭环能提前，而通用引擎随后再长出来。这条路我不主动推荐（它会产生一次返工），但如果 XForge 联动的时间价值高，它是划算的。

## 4. 实施顺序

依赖关系决定了大致次序，可并行的地方已标出。

```text
第 1 批（无依赖，可并行）
  RP-01 身份与令牌
  RP-04 审计日志

第 2 批
  RP-02 项目与成员      ← RP-01
  RP-03 MCP 基座        ← RP-01

第 3 批 —— 到这里 C1 可验证
  RP-05 缺陷账本        ← RP-02, RP-03, RP-04
  RP-15 只读 Web（缺陷视图部分）← RP-05

  ★ 里程碑 M1：从真实 AI 编程工具提交缺陷 → 账本 → Web 可见

第 4 批（可并行）
  RP-09 代码仓绑定（仅 GitHub）← RP-02
  RP-10 技能                    ← RP-02

第 5 批
  RP-11 任务定义        ← RP-10, RP-09
  RP-14 触发器（仅手动）← RP-11

第 6 批 —— 到这里 C2 可验证
  RP-12 Agent 执行运行时 ← RP-11, RP-09, RP-10
  RP-13 执行记录与产物   ← RP-12
  RP-15 只读 Web（执行视图部分）← RP-13

  ★ 里程碑 M2：手动触发任务 → Agent 读 GitHub 仓执行技能 → Markdown 报告 → Web 可见
```

**M1 是一个真实可用的交付物**，不是半成品——它本身就是一个能用的缺陷账本。如果时间压力大，**在 M1 停下来是一个合理的选择**，比做一个隔离不全的 M2 好得多。

## 5. MVP 的不可裁剪清单

这些条目在 MVP 就必须做对。它们的共同点是：**事后补的代价远高于当初就做**——要么是数据模型重写，要么是在补上之前系统一直是敞开的。

### 数据模型类（事后补 = 重写）

| 条目 | 内容 |
|---|---|
| R-04-01 / R-04-05 | 事件只追加、状态可从事件流重建 |
| R-05-07 | 缺陷状态变化追加新记录，**不 UPDATE** |
| R-05-10 | 重开不新建缺陷 |
| R-13-01 / R-13-03 | 执行记录永不覆盖、不随任务变更丢失 |
| I-11-1 | 每次执行记下实际使用的技能版本 |
| R-09-10 | 每次执行记下确切代码修订 |

### 接口纪律类（事后补 = 所有 tool 重写）

| 条目 | 内容 |
|---|---|
| R-03-04 | 未声明字段一律拒绝，不静默丢弃 |
| R-03-05 / R-05-03 | 固定形状的窄接口，**不提供通用透传上下文的 tool** |
| R-03-06 | 写操作幂等 |
| R-03-08 | 无权限与不存在返回相同错误 |
| I-14-1 | 触发非阻塞 |

### 安全边界类（补上之前一直是敞开的）

| 条目 | 内容 |
|---|---|
| R-01-04 / R-01-07 / R-01-10 | 令牌不可读出、错误不可区分、**不接受自述身份** |
| R-03-02 / R-03-03 | 每次调用认证、身份只来自令牌 |
| R-09-03 / R-09-04 / R-09-06 | 只读凭据验证、凭据不可读出、**不进 Agent 上下文** |
| R-09-11 | Agent 对工作区的写入不回流仓库 |
| **R-12-01 ～ R-12-08** | **执行运行时的全部八条隔离需求** |
| I-12-5 | 执行环境结束后完整销毁 |
| R-13-13 | 过程记录不含凭据 |
| R-15-01 / R-15-03 | Web 无写入、会话与令牌分离 |
| **R-15-13** | **Markdown 渲染禁用内联 HTML 与脚本** |

关于最后一条特别提醒：**绝大多数 Markdown 渲染库默认开启内联 HTML。** MVP 只有 Markdown 产物，很容易顺手用默认配置就上线。而产物内容部分来自被分析的代码仓——**能往那个仓提交代码的人，就能影响产物内容**。这是产物渲染这条攻击链上唯一的那道门。

关于 R-12-01～08：如果 MVP 的时间压力大到做不完执行隔离，**正确的做法是把整个执行域推迟、在 M1 停下**，而不是先做一个隔离不全的执行运行时。理由很直接——先跑起来再补隔离，等于在补上之前一直敞开，而这段时间里跑过的技能、读过的代码、泄过的凭据都无法追回。

## 7. 明确不在 MVP、也建议长期不做的

这些不是"以后再说"，是**建议写死的边界**。理由都是同一条：每多管一件，XOps 就离"平台"近一步，而一旦长成工单系统 + 看板 + 流水线 + 报表引擎，就把 AI 化之后本已消失的重量级流程重新造了一遍。

- **任务编排**（任务 A 完成触发任务 B）——需要 DAG、依赖解析、失败传播、循环检测及其可视化。需要串联就在一个技能内部完成多步。
- **审批的条件分支**（表达式引擎）——用"不同流程定义 + 发起时选择"表达，把判断留在发起方。
- **审批的驳回循环**——每一轮拉锯都需要新的对象修订才有意义，那本来就该是一次新的审批。
- **超时自动通过审批**——一个会自动放行的关卡比没有关卡更糟，它看起来像有。
- **内建报表引擎 / 看板 / 燃尽图 / 跨项目横向对比**——想要趋势就写一个读取历史执行结果的技能。平台提供机制，不规定内容。
- **通用的"发消息给某人 / 把这个上下文发过去"的 MCP 工具**——一旦通道能承载任意上下文，信息隔离就从结构保证退化成每个人每次的自觉。
- **缺陷回写代码仓**（D6 已定）——保持 XOps 不需要任何仓库写权限这条安全属性。
- **用模型判断**缺陷是否重复、技能是否安全、产出是否合格——判断题属于人，确定性平面不碰模型（G8）。
