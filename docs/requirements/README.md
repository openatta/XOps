## 2. 这一版为什么重拆

上一版拆包的第一原则是**纵向切片**：每个包是一条完整的价值链（领域逻辑 + 它的 MCP 接口 + 它的只读视图）。那条原则服务的是"能独立进流程、独立验收"。

**第 11 版换了一条原则：按 crate 分层。** 换的理由不是上一条错了，是它在 Rust 多 crate 工程里会付一笔具体的代价：

```text
纵向切片    一个包要动 领域 + MCP + Web 三层
            → 两个并行的包同时改 xops-mcp 与前端，接缝在评审时才发现对不上
按层切分    一个包对应一组 crate，包与包之间只经**已声明的接口**相见
            → 并行的两个包改的是不同目录，接缝是先定好的 trait
```

**代价也要认下来，不能只说好处：**

| 丢掉的 | 怎么补 |
|---|---|
| **"每个包都是一条完整价值链"** —— RP-01、RP-03、RP-05 这类包做完之后，用户看不到任何新东西 | 验收标准改成**对接缝的验收**（换个实现进去不改上层），不再强求"用户能看到" |
| **上一版 RP-01/RP-02 的实测体量数据**（哪种包多大、返工多少）不再逐包可比 | 可迁移的那一半明确搬过来，见 §3 第 4 条 |
| 包数从 12 涨到 19，Change 的固定开销跟着涨 | 承认这笔开销。换来的是**十六个 crate 各只有一个动刀方**，三个共享 crate 的先后关系写死在 §4 |

## 3. 拆包的四条原则

1. **一个包对应一组 crate。** 包的边界就是目录边界。两个包不同时改同一个 crate——**若不得不改，它们必须是串行的两次 Change，不是并行的两个**（本版有三个 crate 各被两个包动过：`xops-task` · `xops-dispatch` · `xops-web`，见 §4 的说明）。
2. **接缝先于实现。** 一个包依赖另一个包时，依赖的是**已定型的 trait 或读模型**，不是它的内部结构。接缝定型即可并行开工——`RP-07` 与 `RP-11`、`RP-05` 与 `RP-06` 都是这么并行的。
3. **前端 / 后端 / 存储三面各有自己的包。** `RP-01`（存储契约）、`RP-05`（读模型与只读 HTTP）、`RP-06`（前端）三者互不进入对方的目录。这是本版重拆最直接的动机。
4. **按预计交付体量切，不按需求条数切。** 经验上界：单个工作包约 **1,500 行**，单个 Change 约 **8,000 行**或约 **6 个工作包**。超出不是禁止，但要在 Proposal 里显式写明为何不拆。

   **需求条数不是切分判据**，这一条有上一轮的实测依据，且它与拆包方式无关，因此原样搬过来：

   | | 上一版 RP-01（二轮） | 上一版 RP-02 表引擎 |
   |---|---|---|
   | 认领的 Requirement | 52 条 | 42 条 |
   | 代码/测试行数 | 4,306 | **24,858** |
   | 工作包 | 10 个 | **13 个**（7 计划内 + 2 临时插入 + 4 轮返工包） |
   | 墙钟 | 约 16 小时 | 约 **46 小时** |

   需求条数**更少**，代码量却是 5.8 倍、耗时接近 3 倍。原因是前者主要在改造既有代码，后者是从零建一个新包。**一个条数少、但技术栈或模块全新的包，交付体量可以远高于一个条数多、只做改造的包。**

   > ⚠️ **第 11 版让这条更凶了，不是更轻了。** 整个仓要用一门新语言从零建起来——**没有"只做改造"的包了，全部是新建**。上表右列才是本版的基准线，不是左列。特别是 `RP-07`（容器后端 + 跨仓改动）与 `RP-14`（42 条流程条目），估的时候按"新建"算。
   >
   > ⚠️ **这条已经被用过两次了。** 第一稿的「技能与任务」是一个 44 条的包，拆成了 `RP-09`/`RP-10`/`RP-11`；「流程引擎」是一个 42 条的包，拆成了 `RP-14`/`RP-15`。**两次都顺手拆了 crate**——只拆包不拆 crate 的话，拆出来的包会在同一个目录上串成一条链，那只是把一个大包换成几次排队。
   >
   > **现在最大的包是 `RP-02` 身份、项目与审计（37 条）。** 它没有被拆，理由是那 37 条里绝大部分是 CRUD 与审计追加，**行数密度远低于流程与执行那两块**；而且它的四个域（项目 / 身份 / 令牌 / 审计）互为前提，任何一种拆法都会让先做的那个半残（见该包的"背景与价值"）。**但它是下一个该被这条判据量一量的包**——Proposal 阶段估出来超界就拆，不要因为"它看起来只是 CRUD"就跳过。

**几条值得单说的：**

- **RP-01 与 RP-07 是两个根**，第一天可以同时开工。RP-07 不依赖任何包，因为它只接收**一份派工单**并交回一份结果——它不知道什么是项目、什么是表。
- **RP-11 → RP-07 只依赖契约**。契约一定型（RP-07 的 WP-A），两个包就能并行：RP-11 对着桩实现写，RP-07 对着契约实现。
- **RP-06 → RP-05 只依赖读模型**。读模型定型（RP-05 的 WP-A），前端就能对着它开工，不必等后端把查询实现完。**这是本版把前后端拆开的全部收益所在**。
- **RP-09 → RP-10 也只依赖接口**。技能是一份资产，任务引用它——两个 crate，接口一定型就能重叠开工。
- **RP-08 与 RP-09/RP-11 是增强而不是依赖**：技能可以声明自己不需要代码仓、只吃任务的输入参数，那类技能不碰 RP-08 就能完整跑通。
- **RP-15 → RP-14 只依赖状态机接口**。接口定型（RP-14 的 WP-C），两个包就能重叠开工。**RP-15 不得自己去改 `_flows` / `_flow_nodes`**——它经接口驱动迁移，这是这一刀能成立的全部前提。
- **RP-15 → RP-10 / RP-16 是增强**：节点的允许写入者有三种，其中"指定私有任务"需要 RP-10、"流转插件"需要 RP-16；**只用角色与名单表两种写入者、只用默认的筛选判定，RP-15 就能完整验收**。
- **RP-01 为 RP-15 与 RP-16 预留了扩展点位**（写串行区间的 ③④）。如果接进来时需要改动 RP-01 的写入路径，说明点位当初留错了——**回头修 RP-01，不要在下游绕开**。

## 6. 里程碑与实施顺序

```text
M0  RP-01
    ★ 存储契约 + 表级写串行的四步区间骨架（③④ 先留 no-op）
    ★ 硬验收：换一个内存实现进去，写入路径与它上面的一切不改一行

M1  RP-02 + RP-03 + RP-04 + RP-05 + RP-06
    ★ 一个 agent 友好的、可审计的记录系统：经 MCP 建表、写行、查行、查单行历史，
      Web 上看得到。这本身就是个能用的东西，即使一行技能都还没跑过。

M2  RP-07 + RP-08 + RP-09 + RP-10 + RP-11 + RP-12
    ★ 手动触发 → 容器里读仓跑技能 → 行落进 _runs → 看板上看到
    ★ 主动攻击测试：每一项越界都必须在容器与能力层失败

M3  RP-13
    ★ 夜里跑，早上看

M4  RP-14 + RP-15 + RP-16 + RP-17 + RP-18
    ★ 一个 bug 按模板给的流程走完全程
    ★ 八个测试一个都不能少（自发自批 / 多节点 / 修订 / 名单竞态 /
      状态列绕过 / 插件故障含死循环 / 并发最后一票 / **插件能力够不到**）

M5  RP-19
    ★ xforge approve --provider xops 真实跑通
    ★ 断网测试：关停 XOps 后报可重试，不是放行

M6  多仓 · 独立对象存储 · 用户自定义模板的导出与提交 · 多实例部署（要一把进程外的锁）
```

> **M2 现在有六个包，是最重的一个里程碑。** 但它内部有真实的并行度：`RP-07`（`xops-exec`）与 `RP-08`（`xops-repo`）互不相干；`RP-09`（`xops-skill`）在 M1 的 MCP 基座之后就能开；只有 `RP-10 → RP-11 → RP-12` 这一串是顺序的，而它们分属两个 crate。

> **一条不能被时间压力推翻的顺序**：如果 M2 的隔离做不完，正确的做法是**整个推迟 M2、在 M1 停下**，而不是先上一个隔离不全的运行时。先跑起来再补隔离，等于在补上之前一直敞开，而这段时间里跑过的技能、读过的代码、泄过的凭据都追不回来。

**M0/M1 就要定死、事后补等于重写的四件**（各自的包文档里都写了理由）：

| 事 | 落点 | 事后补的代价 |
|---|---|---|
| 存储契约的形状 | RP-01 `CON-012` | 换库时要改写入路径，D46 当场落空 |
| 表级写串行的四步区间 | RP-01 `CON-001`～`CON-011` | 重写整条写入路径 |
| 平台自动补的列位（`writtenBy` / `retainUntil` / `_instance`） | RP-04 `TBL-014` | 回填全部历史行 |
| MCP 的窄接口纪律与表专属 tool 派发 | RP-03 `MCP-004` · RP-04 `MCP-005` 的实现 | 全部 tool 重写 |

**M2 不能再推的两件**：单次 token 上限（RP-10 `TSK-005`——M3 一开定时触发就是无上限烧钱）· 保留期与 `retainUntil` 的取值（RP-12 `RET-002`）。

## 8. 需求包文档约定

每个包文档固定这几节：**归属与依赖 · Crate 归属 · 背景与价值 · 范围（含明确不包含）· 需求条目（索引，正文见基线）· 关键不变量 · 接口面 · 验收标准 · 内部工作包建议 · 风险与待定。**

**「接口面」一节现在多了一块「契约元素」**：本包欠契约基线哪些元素、用什么前缀。
条目正文不在包文档里，元素正文也不在——它们由本包自己的变更写进
[`../contracts/`](../contracts/README.md)，包文档只给前缀与归属。**同一条元素只有一个包能写。**

**「Crate 归属」是本版新增的一节**，它回答的是"实现的时候会不会打架"：本包新建哪些 crate、动哪些已有 crate、对外只经哪个接口被别人用。**两个包不同时改同一个 crate**（§4 的两处例外已单列）。

**大包在 XForge 里的正确形态是一次 Major Change + 内部工作包 DAG**（RP-02、RP-04、RP-07、RP-15、RP-16 五个包给了 DAG 建议）。其余用 Solid 即可。
