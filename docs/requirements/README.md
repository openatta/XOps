# XOps 需求包总览

> 状态：需求阶段（不含技术设计与选型）
>
> 更新日期：2026-08-20

## 1. 产品定位

XOps 是配合 [XForge](https://github.com/openatta/XForge) 使用的**云端缺陷管理、流程与质量监控协同平台**。

XForge 是 Git 原生的**单仓**治理控制面——规格、变更、审批回执、Gate 证据、审计链都以文件形式留在仓库里，离线、可复现、防篡改。它明确不做的事情有三类：

1. **跨仓与跨项目的账本**。缺陷在被修复之前不属于任何一个变更，因而不属于任何一个仓库。
2. **审批的实际承载**。XForge 定义"哪条 transition 需要谁批准"，但决策发生在哪、由谁排队、怎么流转，它不管。
3. **服务端的 Agent 执行**。XForge 不托管模型、不调度执行、不拥有工作流。

**XOps 补的就是这三块，并且只通过 MCP 被使用。**

一句话划界：

> **仓库是事实的家，XOps 是账本、审批的承载方与执行场，Web 只是它的只读观察窗。**

## 2. 已确认的产品决策

| # | 决策 | 说明 |
|---|---|---|
| D1 | **审批做成通用引擎** | 支持流程定义、多审批点、串行/并行/会签、按项目角色绑定。XForge 只是其中一个接入方，通过适配器消费它。 |
| D2 | **无组织层，用户平等** | 不存在组织/租户/分组概念。用户注册后地位平等，自己创建项目、把人拉进项目，**角色一律按项目分配**。 |
| D3 | **Agent 执行引擎集成 deepseek-harness（dsh）** | 已 clone 至 `3rds/deepseek-harness`（v0.1.0-rc.8）。**集成形态（子进程 / 插件嵌入 / ACP 驱动）属于设计选型，另行专项讨论，本需求文档不做决定。** |
| D4 | **技术栈 TypeScript / Node** | 与 XForge（Node 20+）同构，MCP SDK 一等公民。 |
| D5 | **代码仓支持 GitHub、Gitea 自建、GitLab** | 三个平台都要接，包括各自的 webhook 形态。 |
| D6 | **缺陷只存 XOps，追加式账本** | 不回写任何项目仓库，XOps 因此不需要任何仓库的写权限。仓侧只在修复提交里引用缺陷 ID。 |
| D7 | **模型凭据平台级统一** | 沿用 dsh 的凭据方案，一套凭据服务全部项目与仓库。 |

## 3. 全局约束

这些约束横跨所有需求包，任何一个包的实现都不得违反。

| # | 约束 | 理由 |
|---|---|---|
| **G1** | **所有写操作经 MCP。** 创建项目、拉人、定义流程、创建技能与任务、提交缺陷、做出审批决策——全部只有 MCP 这一条写入路径。 | 产品定位就是"给 AI 编程工具用的平台"。多开一条写入路径，就要多维护一套权限与审计。 |
| **G2** | **Web 只读。** 呈现层不提供任何增删改。 | 同 G1。Web 是观察窗，不是控制台。 |
| **G3** | **缺陷账本追加式，不得就地改写。** 状态变化以新记录表达，不是 UPDATE。 | 账本要能回答"当时是什么样"，而不只是"现在是什么样"。 |
| **G4** | **权限一律按项目判定。** 不存在跨项目的全局角色，也不存在组织级继承。 | D2。 |
| **G5** | **身份来自凭据，不来自 Agent 的自述。** MCP 不认证调用者，只认证令牌；令牌解析出的用户就是行为人，Agent 声称的名字一律忽略。 | 否则"谁提交了这个缺陷 / 谁做了这个批准"不可验证，整套协同的责任归属立刻失效。 |
| **G6** | **XOps 不得进入开发的关键路径。** XForge 的 Gate 只读仓内文件做判定，不查询 XOps。XOps 挂了不影响任何项目继续开发与归档。 | XForge 的 Gate 子进程会过滤掉一切凭据形状的环境变量，它**没有能力**认证到 XOps。设计上必须让结论先经审批通道落进仓库。 |
| **G7** | **所有外部自由文本是不可信输入。** 缺陷描述、复现步骤、任务输入等文本会被 Agent 读进上下文，构成真实的提示注入面。确定性逻辑不得因这些文本改变行为。 | 缺陷内容由提交方的 Agent 结构化，XOps 只做 schema 校验与原样记录。 |
| **G8** | **确定性平面与分析平面隔离。** 账本、审批、审计、权限判定一律用确定性代码，不经模型；Agent 只在任务执行平面工作，**不得写入确定性平面的任何数据**。 | 模型带来不可复现，一旦它能写账本与证据，前面所有约束都被绕过。 |

## 6. 需求包文档约定

每个需求包文档包含固定小节：

- **归属与依赖**——上下游，以及"不做这个包会阻塞谁"
- **背景与价值**——为什么这个包必须存在，删掉会失去什么
- **范围**——包含什么、明确不包含什么
- **需求条目**——编号 `R-<包号>-<序号>`，每条可独立验收
- **数据与不变量**——这个包必须守住的性质
- **接口面**——MCP tools 与只读查询面（列意图与形状，不定协议细节）
- **验收标准**——怎么算做完
- **MVP 子集**——如果这个包进 MVP，最小做到哪
- **风险与待定**——需要人来决定的事

## 7. 待人决定的事项

这些问题不阻塞需求拆分，但会在进入设计前需要答案。汇总见各包的"风险与待定"，以下是跨包的：

| # | 问题 | 影响 |
|---|---|---|
| Q1 | **用户注册与登录是否是 G1 的例外？** 没有令牌就无法调 MCP，所以第一个令牌必须有非 MCP 的签发路径。是走 Git 平台 OAuth（GitHub/Gitea/GitLab 三选，与 D5 天然一致），还是自建账号密码？ | RP-01、RP-15 |
| Q2 | **dsh 的集成形态**（子进程 headless / Cordis 插件嵌入 / ACP 驱动常驻进程）。 | RP-12，专项讨论 |
| Q3 | **执行沙箱的隔离强度**。dsh 自带 `sandbox` 与 `e2b` 包，但"服务端跑别人写的技能去读别人的代码仓"这件事的隔离要求需要明确到可验收。 | RP-12 |
| Q4 | **审批与 XForge 角色的映射**。XForge 侧的 `roles` 是仓库层面的概念（owner/maintainer，以及跨仓设计里建议新增的 `verifier`），XOps 侧是项目角色，两者对不齐时以谁为准。 | RP-08 |
| Q5 | **单实例部署还是多实例**。D2 说无组织层，但如果一个实例承载多个互不信任的用户，代码仓凭据与执行沙箱的隔离要求会显著上升。 | RP-09、RP-12 |
