# XOps 需求包总览

> 状态：需求阶段（XForge 流程之外的输入物，不含技术设计与选型）
>
> 更新日期：2026-08-20

## 1. 这份文档怎么用

这里的每个需求包，对应后面 XForge 里的**一次 Change**。

```text
docs/requirements/RP-0X-*.md          ← 你在这里（流程之外）
        │
        │  选定一个包，说"实现 RP-0X"
        ▼
   xforge propose  →  design  →  check  →  apply  →  verify  →  archive
```

因此拆包的第一原则是**可独立实现**：选中任何一个包开工时，不应该被另一个还没做的包卡住。这决定了下面的切法——**纵向切片，不是横向分层**。

每个包都是一条完整的价值链：**领域逻辑 + 它的 MCP 接口 + 它的只读视图**。做完一个包，就有一件事从头到尾能用了，而不是"三个包都做完才看得见东西"。

## 2. 产品定位

XOps 是配合 [XForge](https://github.com/openatta/XForge) 使用的**云端缺陷管理、流程与质量监控协同平台**。

XForge 是 Git 原生的**单仓**治理控制面——规格、变更、审批回执、Gate 证据、审计链都以文件形式留在仓库里，离线、可复现、防篡改。它明确不做三件事：

1. **跨仓与跨项目的账本**。缺陷在被修复之前不属于任何一个变更，因而不属于任何一个仓库。
2. **审批的实际承载**。XForge 定义"哪条 transition 需要谁批准"，但决策发生在哪、由谁排队、怎么流转，它不管。
3. **服务端的 Agent 执行**。XForge 不托管模型、不调度执行、不拥有工作流。

**XOps 补的就是这三块，并且只通过 MCP 被使用。**

> **仓库是事实的家，XOps 是账本、审批的承载方与执行场，Web 只是它的只读观察窗。**

## 3. 已确认的产品决策

| # | 决策 | 说明 |
|---|---|---|
| D1 | **审批做成通用引擎** | 流程定义、多审批点、串行/并行/会签、按项目角色绑定。XForge 只是其中一个接入方，通过适配器消费它。 |
| D2 | **无组织层，用户平等** | 不存在组织/租户/分组。用户地位平等，自己创建项目、把人拉进项目，**角色一律按项目分配**。 |
| D3 | **技术栈 TypeScript / Node** | 与 XForge（Node 20+）同构，MCP SDK 一等公民。 |
| D4 | **代码仓支持 GitHub、Gitea 自建、GitLab** | 三个平台都要接，包括各自的 webhook 形态。 |
| D5 | **缺陷只存 XOps，追加式账本** | 不回写任何项目仓库，XOps 因此**不需要任何仓库的写权限**。仓侧只在修复提交里引用缺陷 ID。 |
| D6 | **模型凭据平台级统一** | 沿用 dsh 的凭据方案，一套凭据服务全部项目与仓库。 |
| D7 | **身份走 OAuth，不开放注册** | 用第三方 Git 平台账号（GitHub / Gitea / GitLab）登录。**自注册功能默认关闭**（保留开关）。自测期使用预置的默认账号。实际部署一定走 Git 系统身份。 |
| D8 | **dsh 是被驱动的独立 Agent，XOps 不是它的附属** | XOps 与 deepseek-harness 之间是**进程/服务边界**，XOps 是驱动方。**明确排除**"把 XOps 写成 dsh 的 Cordis 插件"这条路。具体驱动机制（子进程 headless / ACP 协议）仍是 Q2，专项讨论。 |
| D9 | **HTML 产物先不做** | MVP 与其后一段时间只产出 Markdown。HTML 连同其沙箱化渲染方案后续单独讨论。 |
| D10 | **不做成本约束机制** | 只做用量归集（可选），不做项目级额度与限流。 |

## 4. 全局约束

横跨所有需求包，任何一个包的实现都不得违反。

| # | 约束 | 理由 |
|---|---|---|
| **G1** | **所有写操作经 MCP。** 创建项目、拉人、定义流程、创建技能与任务、提交缺陷、做出审批决策——全部只有 MCP 这一条写入路径。**已知的两个例外**：OAuth 登录回调（RP-01）、Git 平台 webhook 接收（RP-07）。两者都不是通用写入面。 | 产品定位就是"给 AI 编程工具用的平台"。多开一条写入路径，就要多维护一套权限与审计。 |
| **G2** | **Web 只读。** 呈现层不提供任何增删改。 | 同 G1。Web 是观察窗，不是控制台。 |
| **G3** | **账本追加式，不得就地改写。** 状态变化以新记录表达，不是 UPDATE。 | 账本要能回答"当时是什么样"，而不只是"现在是什么样"。 |
| **G4** | **权限一律按项目判定。** 不存在跨项目的全局角色，也不存在组织级继承。 | D2。 |
| **G5** | **身份来自凭据，不来自 Agent 的自述。** MCP 不认证调用者，只认证令牌；令牌解析出的用户就是行为人，Agent 声称的名字一律忽略。 | 否则"谁提交了这个缺陷 / 谁做了这个批准"不可验证，整套协同的责任归属立刻失效。 |
| **G6** | **XOps 不得进入开发的关键路径。** XForge 的 Gate 只读仓内文件做判定，不查询 XOps。XOps 挂了不影响任何项目继续开发与归档。 | XForge 的 Gate 子进程会过滤掉一切凭据形状的环境变量，它**没有能力**认证到 XOps。结论必须先经审批通道落进仓库。 |
| **G7** | **所有外部自由文本是不可信输入。** 缺陷描述、技能内容、任务输入、webhook 载荷、模型产出都会被读进上下文，构成真实的提示注入面。确定性逻辑不得因这些文本改变行为。 | 内容由提交方的 Agent 结构化，XOps 只做 schema 校验与原样记录。 |
| **G8** | **确定性平面与分析平面隔离。** 账本、审批、审计、权限判定一律用确定性代码，不经模型；Agent 只在任务执行平面工作，**不得写入确定性平面的任何数据**。 | 模型带来不可复现，一旦它能写账本与证据，前面所有约束都被绕过。 |

## 6. 依赖关系

```text
                        RP-01 平台基座
                              │
        ┌──────────┬──────────┼──────────┬──────────┐
        ▼          ▼          ▼          ▼          ▼
     RP-02      RP-03      RP-04      RP-05      RP-08
   缺陷账本   代码仓接入  技能与执行  审批引擎     通知
                   ╲          │          │
                    ╲(增强)   │          │
                     ╲────────┤          │
                              ▼          ▼
                           RP-07      RP-06
                         自动触发   XForge 适配
```

**只有两条真实依赖，都是本质性的：**

- **RP-06 → RP-05**：适配器必须有被适配物。XForge 的两个固定 tool 背后总要有一个审批引擎来承载决策。
- **RP-07 → RP-04**：自动触发必须有可触发的东西。任务不存在时，定时与 webhook 无处可去。

**RP-03 与 RP-04 之间是"增强"而不是"依赖"**，这是有意设计的：RP-04 的技能可以声明自己**不需要代码仓**（例如"根据缺陷账本生成周报"），这类技能不碰 RP-03 就能完整跑通。两个包因此可以任意顺序做，先做哪个都不卡另一个。做完 RP-03 之后，RP-04 的技能才多出"能读代码"这项能力。

## 7. 关于包的大小

RP-01 与 RP-04 明显比其它包大。这是刻意的取舍：

> **宁可包大一点，也要让它能独立进流程、独立验收。**

如果把 RP-01 拆成"身份"、"项目"、"MCP 基座"、"审计"四个包，它们互相都用得着对方，谁先做都做不完整——那正是重构前的问题。同理，把 RP-04 拆成"技能"和"执行"，前者做完是个不能跑的空壳，后者没有前者无从下手。

**大包在 XForge 里的正确形态是一次 Major Change + 内部的工作包 DAG**，而不是拆成多个 Change。每个大包的文档里给出了内部工作包的划分建议。

## 8. 需求包文档约定

每个包文档包含固定小节：

- **归属与依赖**——上下游，以及这个包能独立到什么程度
- **背景与价值**——为什么它必须存在，删掉会失去什么
- **范围**——包含什么、明确不包含什么
- **需求条目**——编号 `R-<包号>-<序号>`，每条可独立验收
- **数据与不变量**——这个包必须守住的性质
- **接口面**——MCP tools 与只读视图（列意图与形状，不定协议细节）
- **验收标准**——怎么算做完
- **MVP 子集**——如果进 MVP，最小做到哪
- **内部工作包建议**——仅大包有
- **风险与待定**——需要人来决定的事
