# XOps 需求包总览

> 状态：需求阶段（XForge 流程之外的输入物，不含技术设计与选型）
>
> 更新日期：2026-08-20

## 1. 这份文档怎么用

这里的每个需求包，对应后面 XForge 里的**一次 Change**。

```text
docs/requirements/RP-0X-*.md          ← 你在这里（流程之外）
        │
        │  选定一个包，说"实现 RP-0X"
        ▼
   xforge propose  →  design  →  check  →  apply  →  verify  →  archive
```

因此拆包的第一原则是**可独立实现**：选中任何一个包开工时，不应该被另一个还没做的包卡住。这决定了下面的切法——**纵向切片，不是横向分层**。

每个包都是一条完整的价值链：**领域逻辑 + 它的 MCP 接口 + 它的只读视图**（RP-02 是唯一例外，见 §7）。做完一个包，就有一件事从头到尾能用了。

## 2. 产品定位

XOps 是配合 [XForge](https://github.com/openatta/XForge) 使用的**云端缺陷管理、流程与质量监控协同平台**。

XForge 是 Git 原生的**单仓**治理控制面——规格、变更、审批回执、Gate 证据、审计链都以文件形式留在仓库里，离线、可复现、防篡改。它明确不做三件事：

1. **跨仓与跨项目的账本**。缺陷在被修复之前不属于任何一个变更，因而不属于任何一个仓库。
2. **审批的实际承载**。XForge 定义"哪条 transition 需要谁批准"，但决策发生在哪、由谁排队、怎么流转，它不管。
3. **服务端的 Agent 执行**。XForge 不托管模型、不调度执行、不拥有工作流。

**XOps 补的就是这三块，并且只通过 MCP 被使用。**

> **仓库是事实的家，XOps 是账本、审批的承载方与执行场，Web 只是它的只读观察窗。**

## 3. 已确认的产品决策

| # | 决策 | 说明 |
|---|---|---|
| D1 | **审批做成通用引擎** | 流程定义、多审批点、串行/并行/会签、按项目角色绑定。XForge 只是其中一个接入方。 |
| D2 | **无组织层，用户平等** | 不存在组织/租户/分组。用户创建项目、拉人进项目，**角色一律按项目分配**。 |
| D3 | **技术栈 TypeScript / Node** | 与 XForge（Node 20+）同构，MCP SDK 一等公民。 |
| D4 | **代码仓支持 GitHub、Gitea 自建、GitLab** | 三个平台都要接，包括各自的 webhook 形态。 |
| D5 | **缺陷只存 XOps，追加式账本** | 不回写任何项目仓库，XOps 因此**不需要任何仓库的写权限**。 |
| D6 | **模型凭据平台级统一** | 沿用 dsh 的凭据方案，一套凭据服务全部项目与仓库。 |
| D7 | **身份走 OAuth，不开放注册** | 用第三方 Git 平台账号登录。**自注册功能默认关闭**（保留开关）。自测期使用预置默认账号。实际部署一定走 Git 系统身份。 |
| D8 | **dsh 是被驱动的独立 Agent，XOps 不是它的附属** | 明确排除"把 XOps 写成 dsh 的 Cordis 插件"。 |
| D9 | **HTML 产物先不做** | 只产出 Markdown。HTML 连同其沙箱化渲染方案后续单独讨论。 |
| D10 | **不做成本约束机制** | 不做项目级额度与限流。 |
| **D11** | **容器级隔离** | 服务侧 Agent **只在容器中运行**，一切访问经容器边界隔离。 |
| **D12** | **分立进程 + 桥接插件** | XOps 与 dsh 是**两个分立进程**，中间由我们自己写的桥接插件连接（插件装在 dsh 侧）。 |
| **D13** | **平台优先 GitHub，接口可适配** | 身份提供方与代码仓平台都先做 GitHub，差异收在适配接口后面，新增平台只实现接口。 |
| **D14** | **缺陷 ID = `<项目短名>-<项目内序号>`** | 项目短名全平台唯一且**不可变**。 |

## 4. 全局约束

横跨所有需求包，任何一个包的实现都不得违反。

| # | 约束 | 理由 |
|---|---|---|
| **G1** | **所有写操作经 MCP。** 已知两个例外：OAuth 登录回调（RP-01）、Git webhook 接收（RP-08）。两者都不是通用写入面。 | 产品定位就是"给 AI 编程工具用的平台"。多开一条写入路径，就要多维护一套权限与审计。 |
| **G2** | **Web 只读。** 呈现层不提供任何增删改。 | 同 G1。Web 是观察窗，不是控制台。 |
| **G3** | **账本追加式，不得就地改写。** 状态变化以新记录表达，不是 UPDATE。 | 账本要能回答"当时是什么样"，而不只是"现在是什么样"。 |
| **G4** | **权限一律按项目判定。** 无跨项目全局角色，无组织级继承。 | D2。 |
| **G5** | **身份来自凭据，不来自 Agent 的自述。** MCP 不认证调用者，只认证令牌。 | 否则"谁提交了这个缺陷 / 谁做了这个批准"不可验证，责任归属立刻失效。 |
| **G6** | **XOps 不得进入开发的关键路径。** XForge 的 Gate 只读仓内文件，不查询 XOps。 | Gate 子进程会过滤掉一切凭据形状的环境变量，它**没有能力**认证到 XOps。 |
| **G7** | **所有外部自由文本是不可信输入。** 缺陷描述、技能内容、任务输入、webhook 载荷、模型产出。 | 它们都会被读进上下文，构成真实的提示注入面。 |
| **G8** | **确定性平面与分析平面隔离。** 账本、审批、审计、权限判定不经模型；Agent 只在容器内工作，**不得写入确定性平面的任何数据**。 | 模型带来不可复现，一旦它能写账本与证据，前面所有约束都被绕过。 |

## 6. 依赖关系

```text
   RP-01 平台基座                          RP-02 容器化执行运行时
   （身份/项目/MCP/审计/Web）              （容器沙箱 + dsh 桥接）
         │                                        │
         │                                   执行契约（唯一接缝）
         │                                        │
   ┌─────┼─────┬──────────┬──────────┐            │
   ▼     ▼     ▼          ▼          ▼            │
 RP-03 RP-04 RP-06      RP-09      RP-05 ◄────────┘
 缺陷  代码仓 审批引擎    通知      技能与任务
        ╲                  │          │
         ╲(增强)           ▼          ▼
          ╲──────────► RP-07      RP-08
                     XForge适配   自动触发
```

**两个根，四条依赖：**

- **RP-05 → RP-02**：领域层要有东西真的把 Agent 跑起来。但两者之间**只有一条执行契约**，契约一定型就能**并行开发**——RP-05 对着桩实现写，RP-02 对着契约实现。
- **RP-07 → RP-06**：适配器必须有被适配物。
- **RP-08 → RP-05**：自动触发必须有可触发的东西。
- 其余包只依赖 RP-01，彼此完全独立。

**RP-04 与 RP-05 之间是"增强"而不是依赖**：RP-05 的技能可以声明自己**不需要代码仓**（例如"根据缺陷账本生成周报"），这类技能不碰 RP-04 就能完整跑通。做完 RP-04 之后，技能才多出"能读代码"这项能力。

## 7. 关于包的大小与形态

**RP-01 与 RP-05 明显比其它包大**，这是刻意取舍：**宁可包大一点，也要让它能独立进流程、独立验收。** 如果把 RP-01 拆成"身份"、"项目"、"MCP 基座"、"审计"四个包，它们互相都用得着对方，谁先做都做不完整。大包在 XForge 里的正确形态是**一次 Major Change + 内部工作包 DAG**，各包文档里给了划分建议。

**RP-02 是唯一不含 MCP 接口与视图的包。** 它是纯基础设施——没有面向用户的语义，全部经 RP-05 暴露。它之所以仍是一个独立包，是因为：

1. **它不依赖任何包**，可以和 RP-01 并行、第一天就开工；
2. **它是全项目风险最高的一块**（容器编排、进程桥接、凭据边界、隔离验证），早开工早暴露代价；
3. **它有自己完整的验收方式**——用一个测试调用方就能证明"给定技能内容与输入，在容器里跑起来、拿回产物、且越界尝试全部失败"；
4. **它与领域层的变化速度完全不同**：技能生命周期、任务策略会随产品认知反复调整，而容器隔离与桥接一旦做对就很少动。混在一起，每次调领域都要重新验证隔离。
