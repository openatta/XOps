# RP-01 身份与访问令牌

## 归属与依赖

- **依赖**：无。这是整棵依赖树的根。
- **被依赖**：RP-02（成员归属于用户）、RP-03（令牌解析出调用者）、RP-04（审计事件的行为人）、RP-16（通知投递对象）。
- **不做这个包会阻塞谁**：全部。没有可验证的身份，G5 无从谈起，账本与审批的责任归属全部落空。

## 背景与价值

XOps 的每一条记录都要回答"谁做的"。这个问题必须由**凭据**回答，不能由调用方自述——MCP 协议本身不认证调用者，它只是一条管道，管道那头的 Agent 说自己是谁没有任何约束力。

如果这里松了，后面所有东西都是装饰：一份"谁提交的"不可验证的缺陷、一个"谁批准的"不可验证的决策，都不构成事实。

**这个包的产出只有一件事：把一个令牌确定性地解析成一个真实用户，或者拒绝。**

## 范围

### 包含

- 用户账号的存在性与基本属性
- 访问令牌的签发、撤销、过期
- 令牌 → 用户的解析
- 令牌的使用留痕（最后使用时间、来源）

### 不包含

- **项目内的角色与权限判定**——归 RP-02。本包只回答"你是谁"，不回答"你能干什么"。
- **组织、团队、用户分组**——D2 明确不存在这一层。
- **模型 API 凭据**——那是平台级配置，归 RP-12。本包的令牌只用于"调用者认证到 XOps"。
- **代码仓凭据**——归 RP-09。

## 需求条目

| ID | 需求 |
|---|---|
| R-01-01 | 用户是平台的顶层主体，用户之间地位平等，不存在任何上下级或分组关系。 |
| R-01-02 | 每个用户有稳定的、创建后不可变的用户标识；显示名与邮箱可变，但不得作为关联键使用。 |
| R-01-03 | 用户可以持有多个并存的访问令牌，用于区分不同的使用场景（不同的编程工具、不同的机器、不同的自动化）。 |
| R-01-04 | 令牌在签发时**只呈现一次**，之后系统只保存不可逆的摘要，无法再次读出原文。 |
| R-01-05 | 令牌可以被其所有者随时撤销；撤销后立即失效，不存在生效延迟窗口。 |
| R-01-06 | 令牌可以设置过期时间；已过期的令牌与已撤销的令牌行为完全一致。 |
| R-01-07 | 令牌解析失败（不存在、已撤销、已过期、格式非法）时，返回的错误不得泄露失败的具体原因，也不得泄露该令牌是否曾经存在。 |
| R-01-08 | 每个令牌记录其最后一次成功使用的时间，供所有者识别不再使用的令牌。 |
| R-01-09 | 令牌一律**按人签发**，不存在按服务、按项目或按团队共享的令牌。 |
| R-01-10 | 系统在任何位置都不得接受"调用方声明的身份"作为行为人，包括但不限于 MCP 参数中的 `actor`、`user`、`author` 之类字段。 |

## 数据与不变量

- **I-01-1**：令牌原文在系统内任何持久化位置都不存在。
- **I-01-2**：任何一条产生副作用的记录，其行为人字段必须来自令牌解析结果，不得来自请求体。
- **I-01-3**：用户标识一旦分配，永不复用，即使用户被删除。

## 接口面

**MCP tools**

| 意图 | 说明 |
|---|---|
| 查询当前身份 | 返回令牌对应的用户，供 Agent 确认自己以谁的身份工作。这是排查"提交到了错误账号"最直接的手段。 |

令牌的签发与撤销**不在 MCP 面上**——它是获得 MCP 访问能力的前置条件，鸡生蛋的关系（见 Q1）。

**只读查询面**（供 RP-15）

- 当前用户的基本信息
- 当前用户的令牌列表（不含原文）

## 验收标准

- 用有效令牌调用任意 MCP tool，行为人被正确解析。
- 用已撤销 / 已过期 / 伪造的令牌调用，一律被拒绝，且三种情况的错误响应**不可区分**。
- 在 MCP 请求体里附带 `actor` 之类字段试图冒充他人，该字段被完全忽略，记录中的行为人仍是令牌所有者。
- 令牌签发后无法通过任何接口再次读出原文。
- 同一用户的两个令牌，撤销其一不影响另一个。

## MVP 子集

**完整纳入。** 这个包没有可裁剪的部分——身份是其余一切的地基，做一半等于没做。

唯一可以简化的是令牌的管理体验（列表、命名、过期策略可以先给最朴素的形态），但 R-01-04、R-01-05、R-01-07、R-01-10 必须在 MVP 就位。

## 风险与待定

- **Q1（跨包）**：第一个令牌怎么来？没有令牌就没法调 MCP，所以令牌签发必然存在一条非 MCP 的路径，这是 G1 的唯一已知例外。两个候选：
  - **Git 平台 OAuth**——与 D5 的三个平台天然一致，身份源统一在 Git 平台，跨仓设计里"同一个人在两边就是同一个账号"的好处直接继承；代价是 XOps 不再能独立于 Git 平台工作。
  - **自建账号密码**——独立，但要自己承担密码、找回、二次验证这一整套，且身份与 Git 平台对不齐时，"提交修复的人"和"XOps 里的人"需要额外映射。

  **倾向前者**，理由是身份对齐的价值远大于独立性，而后者引入的映射表是这类系统里最容易长期不一致的一块。**这条需要你定。**
- 用户注销 / 删除的语义未定：账本是追加式的，历史记录里的行为人不能消失，所以"删除用户"实际只能是"停用"。这条在 MVP 不必解决，但不要在数据形状上把路堵死。
