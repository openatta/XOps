# RP-01 平台基座

> 身份与 OAuth · 项目与成员 · MCP 基座 · 审计日志 · Web 外壳

## 归属与依赖

- **依赖**：无。**完全独立，是唯一可以第一个开工的包。**
- **被依赖**：其余全部七个包。
- **独立性**：这个包做完，平台是一个可登录、可建项目、可拉人、可被 MCP 调用、有完整审计的骨架。它本身就能验收，只是还没有业务内容。

## 背景与价值

这个包把**所有不可避免的共享地基**收在一起。其余七个包之所以能互相独立，正是因为它们共同的耦合点全部落在这里。

四块内容为什么必须同包：

- **身份**要用**项目角色**来判断能做什么；
- **项目与成员**的变更本身要经 **MCP** 写入（G1）；
- **MCP 基座**要用身份认证、用角色鉴权、把每次写入交给**审计**；
- **审计**的行为人来自身份解析。

四者互为前提，任何一种拆法都会让先做的那个半残。加上一个只读 **Web 外壳**（登录 + 项目视图），这个包就是一个能立起来的骨架。

守住的核心性质只有一条：

> **每一条记录都能回答"谁做的"，而这个答案由凭据给出，不由调用方自述。**

MCP 协议本身不认证调用者——管道那头的 Agent 说自己是谁没有任何约束力。这里松了，后面所有东西都是装饰。

## 范围

### 包含

- OAuth 登录（第三方 Git 平台身份）、默认账号、自注册开关
- 用户与访问令牌的签发、撤销、过期、解析
- 项目的创建、归档；成员的加入、移除、角色分配；权限判定
- MCP server 的服务形态、认证、tool 注册、schema 校验、幂等、错误契约、限流
- 追加式审计事件日志
- 只读 Web 外壳：登录、导航、项目与成员视图、活动时间线

### 不包含

- **任何业务领域对象**——缺陷、技能、任务、审批各归其包。本包只提供归属、鉴权与留痕的机制。
- **业务 tool 的语义**——本包只提供 tool 注册骨架与纪律。
- **模型凭据与代码仓凭据**——分别归 RP-04 与 RP-03。本包的令牌只用于"调用者认证到 XOps"。

## 需求条目

### 身份与登录

| ID | 需求 |
|---|---|
| R-01-01 | 登录通过 **OAuth** 完成，身份提供方是第三方 Git 平台（GitHub / Gitea 自建 / GitLab），与 D4 的代码仓平台一致。 |
| R-01-02 | **不开放自注册。** 自注册功能存在开关，**默认关闭**。关闭时，未被预置或未被邀请的第三方账号登录后被拒绝，且不创建任何用户记录。 |
| R-01-03 | 支持预置默认账号，供部署自测使用。预置账号与 OAuth 账号在系统内是同一种主体，不构成第二套身份模型。 |
| R-01-04 | 用户是平台的顶层主体，用户之间地位平等，不存在任何上下级或分组关系（D2）。 |
| R-01-05 | 每个用户有稳定的、创建后不可变的用户标识；显示名与邮箱可变，**不得作为关联键使用**。 |
| R-01-06 | 用户记录保存其来源身份提供方与在该平台上的账号标识，使"XOps 里的这个人"与"代码仓里提交的那个人"能够对上。 |

### 访问令牌

| ID | 需求 |
|---|---|
| R-01-07 | 用户可持有多个并存的访问令牌，用于区分不同使用场景（不同的编程工具、机器、自动化）。 |
| R-01-08 | 令牌签发时**只呈现一次**，之后系统只保存不可逆摘要，无法再次读出原文。 |
| R-01-09 | 令牌可被其所有者随时撤销，撤销后立即失效，无生效延迟窗口。 |
| R-01-10 | 令牌可设过期时间；已过期与已撤销的行为完全一致。 |
| R-01-11 | 令牌解析失败（不存在、已撤销、已过期、格式非法）时，错误**不得泄露具体原因**，也不得泄露该令牌是否曾经存在。 |
| R-01-12 | 每个令牌记录最后一次成功使用的时间，供所有者识别不再使用的令牌。 |
| R-01-13 | 令牌一律**按人签发**，不存在按服务、按项目或按团队共享的令牌。 |
| R-01-14 | 系统在任何位置都不得接受"调用方声明的身份"作为行为人，包括 MCP 参数中的 `actor`、`user`、`author` 之类字段。 |

### 项目与成员

| ID | 需求 |
|---|---|
| R-01-15 | 任何用户都可以创建项目，无需申请或审批。创建者自动成为所有者。 |
| R-01-16 | 项目有稳定的、创建后不可变的标识；显示名可变。 |
| R-01-17 | 项目内至少有三个角色：**所有者**（管理成员与项目本身）、**维护者**（管理项目内业务对象）、**成员**（提交缺陷、发起任务、参与审批，不改项目结构）。 |
| R-01-18 | 所有者可把其他用户加入项目并指定角色。由于 D7 不开放注册、用户集合受控，被加入者不需要主动接受即生效。 |
| R-01-19 | 一个项目必须始终至少有一个所有者。移除最后一个所有者被拒绝。 |
| R-01-20 | 同一用户在不同项目中的角色互相独立（G4）。 |
| R-01-21 | 非成员对项目的一切内容不可见——查询返回"不存在"，而不是"无权限"。 |
| R-01-22 | 项目可被归档。归档后转为只读：不再接受任何写操作，历史内容完整保留、可查询。 |
| R-01-23 | 权限判定是确定性纯函数：相同的（用户，项目，动作）在角色未变时永远得到相同结果，不受任何模型或外部服务影响（G8）。 |
| R-01-24 | 项目角色不得由审批流程之外的任何自动化路径变更——**特别地，Agent 执行任务时不得提升自己或他人的角色**。 |

### MCP 基座

| ID | 需求 |
|---|---|
| R-01-25 | XOps 对外暴露 MCP server，任何符合 MCP 的客户端都能接入，不需要 XOps 专属 SDK。 |
| R-01-26 | 每次调用必须携带令牌；无令牌或令牌无效时拒绝，且**不执行任何副作用**。 |
| R-01-27 | 调用者身份一律由令牌解析得出（G5）。参数中任何身份类字段被忽略，且忽略是静默的——不报错，但绝不生效。 |
| R-01-28 | 所有 tool 有明确输入 schema，**未在 schema 中声明的字段一律拒绝**，不静默丢弃。静默丢弃会让调用方以为自己传的东西生效了。 |
| R-01-29 | tool 的输入 schema 必须是**固定形状的窄接口**。**禁止提供接受任意结构、任意上下文或自由指令的通用 tool。** |
| R-01-30 | 产生副作用的 tool 支持幂等：调用方提供幂等键时，重复调用不产生第二次副作用，并返回与首次相同的结果。 |
| R-01-31 | 错误响应使用统一契约：稳定错误码、可读消息、以及"该重试还是该改参数"的明确区分。 |
| R-01-32 | **权限不足与对象不存在返回相同的错误**，避免通过错误码探测他人项目的存在（呼应 R-01-21）。 |
| R-01-33 | 提供按用户与按 tool 的速率限制，超限时返回可重试错误并给出建议等待时间。 |
| R-01-34 | tool 的发现结果按调用者的项目角色裁剪。 |
| R-01-35 | 所有自由文本参数视为不可信输入（G7）：只做 schema 与长度校验并原样存储，不解析、不执行、不依据其内容改变控制流。 |

### 审计日志

| ID | 需求 |
|---|---|
| R-01-36 | 事件日志**只追加**，不提供任何就地修改或删除单条事件的能力。纠正错误的方式是追加一条纠正事件。 |
| R-01-37 | 每条事件至少包含：稳定事件标识、发生时间、行为人、所属项目、事件类型、目标对象标识、结构化载荷。 |
| R-01-38 | 事件按所属项目分区，非成员查询不到该项目的任何事件。 |
| R-01-39 | **对任意给定时刻，可以仅凭事件流重建当时的业务状态快照**，不依赖任何当前视图表。 |
| R-01-40 | 事件写入与其对应的业务副作用在同一次操作中完成——不存在"业务成功但没留痕"或"留了痕但业务没生效"的中间态。 |
| R-01-41 | 事件的写入路径不经过任何模型（G8）。Agent 可读自己有权读的事件，但绝不写入。 |
| R-01-42 | 失败的 MCP 调用也留痕，但与成功事件区分——失败留痕用于排查与滥用检测，不进入业务账本。 |
| R-01-43 | 支持按项目、时间范围、事件类型、行为人、目标对象查询。 |
| R-01-44 | 保留期可配置，但保留期内的事件不可删除。到期清理只能整批按时间进行，**不得选择性删除个别事件**。 |

### Web 外壳（只读）

| ID | 需求 |
|---|---|
| R-01-45 | Web 面**不提供任何写入操作**（G2）。前端不存在调用写接口的代码路径，后端不为 Web 暴露任何写接口。 |
| R-01-46 | Web 登录会话与 MCP 令牌是**不同的凭据，互不通用**。Web 会话不能用于调用 MCP 写操作。 |
| R-01-47 | 页面明确展示当前用户身份，避免"登错账号看错项目"。 |
| R-01-48 | 提供项目视图（我参与的项目、成员与角色）与活动视图（项目审计事件时间线）。 |
| R-01-49 | 可见性完全遵循项目成员边界：非成员看不到项目的存在。 |

## 数据与不变量

- **I-01-1**：令牌原文在系统内任何持久化位置都不存在。
- **I-01-2**：任何产生副作用的记录，其行为人字段必须来自令牌解析结果，不得来自请求体。
- **I-01-3**：用户标识与项目标识一经分配永不复用。
- **I-01-4**：每个业务对象恰好归属一个项目，不存在跨项目共享的对象。
- **I-01-5**：事件一经写入即不可变；任何业务对象的当前状态都可由其事件流完整推导——**当前视图是缓存，不是权威**。
- **I-01-6**：不存在只改当前视图而不写事件的代码路径。
- **I-01-7**：不存在绕过 MCP 基座的业务写入路径（G1 的两个例外除外）。
- **I-01-8**：Web 面不存在写入路径。

## 接口面

**MCP tools**

| 意图 | 说明 |
|---|---|
| 查询当前身份 | 供 Agent 确认自己以谁的身份工作——排查"提交到了错误账号"最直接的手段 |
| 能力发现 | 当前令牌能用哪些 tool、在哪些项目上 |
| 创建项目 | 调用者成为所有者 |
| 查询我参与的项目 | Agent 定位该往哪个项目提交的第一步 |
| 查询项目详情 | 含成员与自己的角色 |
| 添加/移除成员、变更角色 | 需所有者 |
| 归档项目 | 需所有者 |
| 查询项目事件流 | 按时间/类型/对象筛选 |
| 查询某对象的完整历史 | |

**对内提供给其余包的**

- tool 注册（声明 schema、所需权限、是否幂等）
- 已认证的调用上下文（调用者、目标项目、角色）
- 统一错误构造
- 审计事件写入（与业务写入在同一原子边界内）

**非 MCP 入口**（G1 的例外之一）

- OAuth 登录回调。它不是通用写入面：只能完成身份验证与会话建立，不能创建或修改任何业务对象。

## 验收标准

- 配置一个 Git 平台的 OAuth 应用，用第三方账号完成登录。
- 自注册开关关闭时，一个未预置的第三方账号登录被拒绝，**且系统内未留下该用户的任何记录**。
- 用预置默认账号登录并正常使用。
- 用有效令牌调用任意 MCP tool，行为人被正确解析。
- 已撤销 / 已过期 / 伪造的令牌调用一律被拒绝，且三种情况的错误响应**不可区分**。
- 在 MCP 请求体里附带 `actor` 试图冒充他人，该字段被忽略，记录中的行为人仍是令牌所有者。
- 令牌签发后无法通过任何接口再次读出原文。
- 新建项目后创建者是所有者且能立刻加人；非成员查询该项目，得到与查询一个真正不存在的项目**一致**的响应。
- 用户 A 在项目 1 是所有者、在项目 2 是成员时，A 在项目 2 无法加人。
- 移除唯一所有者被拒绝，项目状态未变。
- 归档项目后所有写操作被拒绝，所有读操作正常。
- 传入 schema 未声明的字段，调用被拒绝（**而不是成功但字段被忽略**）。
- 同一幂等键连续调用两次，副作用只发生一次，两次返回一致。
- 任何业务写操作完成后能查到对应事件；写操作失败时查不到任何残留事件。
- 修改或删除单条已写入事件的操作**在接口层不存在**（不是"被拒绝"，是没有这个能力）。
- **断开当前视图表后，仅凭事件流能重建全部业务状态**。
- 用 Web 会话凭据尝试调用 MCP 写操作，被拒绝。
- 全站审查：不存在任何提交表单、编辑控件或写接口调用。

## MVP 子集

**完整纳入。** 这个包没有可裁剪的核心——它就是地基。

可以简化的只有体验层面：
- 令牌管理的界面可以最朴素（列表 + 签发 + 撤销）
- 速率限制（R-01-33）先给粗粒度全局上限，不做按 tool 精细配额
- 能力发现的角色裁剪（R-01-34）可以先返回全量列表、调用时才判权限——**裁剪是体验优化，安全边界是 R-01-32 那条**
- 审计保留期与清理（R-01-44）MVP 不做清理，只做无限保留，但配置位置要预留
- 活动视图（R-01-48 后半）可以推迟

**不可裁剪**：R-01-02（不开放注册）、R-01-08、R-01-11、R-01-14、R-01-26～R-01-30、R-01-32、R-01-36、R-01-39、R-01-40、R-01-45、R-01-46。

## 内部工作包建议

这个包在 XForge 里应当是**一次 Major Change**，内部按下面的 DAG 拆工作包：

```text
WP-A 身份与令牌（OAuth 接入、用户、令牌签发解析）
        │
        ├──► WP-B 项目与成员（含权限判定纯函数）
        │            │
        ├──► WP-C 审计事件日志（追加式写入与重建）
        │            │
        │            ▼
        └──────► WP-D MCP 基座（认证 + 鉴权 + schema + 幂等 + 留痕）
                             │
                             ▼
                     WP-E 只读 Web 外壳
```

WP-B 与 WP-C 可并行。WP-D 是汇聚点，它把前三者接起来并强制那套纪律。WP-E 只消费读模型。

## 风险与待定

- **OAuth 的多提供方支持在 MVP 要不要一次做齐三家？** D7 说实际部署一定走 Git 系统身份，D4 说三个平台都要接。**建议 MVP 先做一家**（与 RP-03 的代码仓平台选同一家，共用一套 OAuth 应用配置），另外两家作为后续增量——它们是适配不是设计。这条不影响架构，只影响交付节奏。

- **R-01-06 的身份对齐是这个包的隐藏价值，容易被当成可有可无的字段跳过。** 记录"这个用户在 Git 平台上是谁"，才能在将来回答"提交这个修复的人和 XOps 里指派的人是不是同一个"。跨仓协作设计里那条最强的不变量校验（同一需求上 SE / 实现 / 验收必须是三个不同的人）就压在这个字段上。**现在不用它，但现在不存就永远补不上历史数据。**

- **用户注销/删除的语义未定**：账本是追加式的，历史记录里的行为人不能消失，所以"删除用户"实际只能是"停用"。MVP 不必解决，但不要在数据形状上把路堵死。

- **R-01-29 的"窄接口"是一条需要持续守住的纪律，不是一次性验收项。** 每新增一个 tool 都可能有人想加一个"扩展字段"或"透传上下文"参数。**建议把这条写成项目的 XForge Rule**，让它在每次变更时被检查，而不是靠记性。

- **事件类型的命名与载荷 schema 需要跨领域统一。** 建议在 WP-C 就定一份事件类型目录并留出扩展方式，而不是让后面七个包各自发明——否则查询面会变成一堆特例。
