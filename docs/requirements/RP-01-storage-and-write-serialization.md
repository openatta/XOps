# RP-01 存储与写串行

> 存储契约 · SQLite 实现 · 表级写串行的四步区间 · ③④ 扩展点位

## 归属与依赖

- **依赖**：无。**根包，可与 RP-07 在第一天同时开工。**
- **被依赖**：其余全部十八个包（间接），直接被依赖的是 RP-04 表引擎与 RP-15 结算判定与保护。
- **里程碑**：**M0**。
- **独立性**：本包不知道什么是项目、什么是表、什么是流程。它只提供两样东西：**一层只有基本 CRUD 的存储契约**，和**一个把"一次写"圈成四步的串行执行器**。用一个假的表定义就能完整验收。

## Crate 归属

| crate | 本包是否新建 | 对外只经什么被用 |
|---|---|---|
| `xops-core` | **新建** | 类型、ID、时间、错误、事件形状、角色判定纯函数 |
| `xops-store` | **新建** | `Store` trait（只基本 CRUD）· `SerialWrite` 执行器（四步区间，③④ 是可注入的 stage） |

**本包不动任何其它 crate。** 后续包对它的使用一律经上面两个接口，**不得直接触碰 SQLite**——这条是 `CON-012` 能不能兑现的全部分界线。

## 背景与价值

这个包被单独立出来，理由只有一条，但它足够硬：

> **存储契约的形状与写串行区间的边界，是全系统唯一两处"事后补等于重写写入路径"的东西，而它们与身份、项目、表都无关。**

上一版把它们塞在表引擎里（**十二包版的 RP-02**，与本版的 RP-02 不是同一个包），代价是它们要等在身份与 MCP 后面——而它们本来第一天就能做。**M0 存在的全部意义就是把这两件事提前。**

两件事各自的分量：

| 事 | 事后补的代价 |
|---|---|
| **存储契约**（`CON-012`） | 一旦有任何一处直接用了 SQLite 的特有能力（触发器、行锁、JSON 列、外键），D46「换库不改写入路径」当场落空，而发现它的时机通常是真要换库的那天 |
| **四步串行区间**（`CON-001`～`CON-011`） | 它规定了"一次写"的边界包含 ① schema 校验 ② 追加事件+投影 ③ 流程节点求值 ④ 插件写回。事后再把 ③④ 圈进来，等于重写整条写入路径 |

**③④ 在本包里是 no-op 的扩展点位。** 本包不知道什么是流程、什么是插件——它只保证：**当 RP-15 与 RP-16 把实现接进来时，不需要改动写入路径**。

> ⚠️ **这条是双向的。** 如果 RP-15/RP-16 接进来时发现必须改写入路径，**说明点位当初留错了，应当回头修本包**，而不是在下游绕开。

## 范围

### 包含

- **存储契约**：一层只有基本增删改查的 trait，不依赖任何数据库特有能力
- **SQLite 实现**：契约的第一个实现
- **内存实现**：契约的第二个实现，**它不是桩，是硬验收的载体**（见验收标准）
- **表级写串行**：一张表同时只有一个写；锁按表名全序获取；写回结算表可重入
- **四步区间**的骨架与它的边界，**③④ 实现为可注入的 no-op stage**
- 明确在锁外的三件事：事件派发与任务入队 · 通知行写入 · 到期清理
- 事件追加的原语（不含"什么是审计事件"，那是 RP-02）
- ID、时间、错误分类等跨包共享的基础类型

### 明确不包含

- **表是什么、列有哪些类型、schema 怎么校验**——归 RP-04。本包的 ① 只是一个可注入的校验回调。
- **流程节点求值与插件写回的实现**——归 RP-15 与 RP-16。本包只留点位。
- **审计事件的语义与查询**——归 RP-02。本包只有"追加"这个动作。
- **任何 MCP tool**——本包不对外暴露任何 tool。
- **多实例部署下的分布式锁**——不做（M6）。

本包认领 [`requirements.md`](requirements.md) 的 **12 条**。**条目正文以 `requirements.md` 为准**，下表只是索引与一句话摘要。

### CON 写入一致性（12 条）

| ID | 摘要 |
|---|---|
| `CON-001` | 一张表在同一时刻只允许一个写操作（insert / update / delete）在进行。 |
| `CON-002` | 一次"写"的边界包含四件事，它们在同一个串行区间内完成：① schema 校验 → ② 追加事件 + 投影 → ③ 流程节点求值（含流转插件）→ ④ 插件写… |
| `CON-003` | 串行区间归属被写的那张表。 |
| `CON-004` | 这两张表的锁一次性按表名全序获取（全序即无循环等待，构造不出死锁）；写回结算表本身时锁可重入；_flows / _flow_nodes 的状态迁移随同一区间… |
| `CON-005` | 第三张表，平台不代写。 |
| `CON-006` | 三件事明确在锁外：「节点被激活」事件的派发与任务入队（非阻塞入队，模型调用绝不在锁内）· 通知行的写入 · 到期清理（整批离线进行）。 |
| `CON-007` | 除该区间外，任何跨表写都没有原子性——这是明确不承诺的事，不得在别处依赖它。 |
| `CON-008` | 不做行级锁、不做多表事务、不做 MVCC。 |
| `CON-009` | 插件求值有硬超时，且该超时上限直接决定它所在结算表的最大写吞吐（求值在锁内）。 |
| `CON-010` | 容量规划必须把 _runs 是全系统最热的表这件事算进去（每次执行至少写一次）。 |
| `CON-011` | 跨表写的原子性不做（D43，CON-007 的直接后果）。 |
| `CON-012` | 存储层只使用基本的增删改查，不依赖任何数据库特有能力（触发器、存储过程、行锁、事务隔离级别、MVCC、外键、级联、JSON 列）。 |

## 关键不变量

`I-U`（一张表同时只有一个写；四件事在同一串行区间内完成；区间只涉及结算表、主体表与 `_flows`/`_flow_nodes`，按表名全序取锁因而无死锁；其余任何跨表写都没有原子性）· `I-D`（事件一经写入即不可变）· `I-N`（不存在只改当前视图而不写事件的代码路径）· `G12`（存储在契约后面，有换实现的硬验收）。

## 接口面

**本包不对外暴露任何 MCP tool。**

**对内提供**：

```text
Store          get / put / delete / scan —— 仅此，不多
SerialWrite    在某张表上执行一次写，四步在同一区间内完成
               ③④ 由调用方注入；未注入时是 no-op
```

**契约元素**（基线在 [`../contracts/`](../contracts/README.md)，正文由本包自己的变更逐条添加）：


## 验收标准

- **换实现验收（本包的核心验收，`CON-012` + G12）**：把存储从 SQLite 换成内存实现，**写入路径与它上面的一切不改一行**，全部测试照过。
- **枚举全仓**：`xops-store` 之外不存在任何一处直接引用 SQLite 的代码；`xops-store` 内部不使用触发器、存储过程、行锁、事务隔离级别、MVCC、外键、级联、JSON 列。
- **并发写同一张表**：两个写并发进入，第二个排队；两者的事件顺序与投影结果确定。
- **并发写不同表**：互不阻塞（证明这是表级而不是全局锁）。
- **锁全序**：构造两个流程互为结算表/主体表的场景，两个并发写**不死锁**。
- **可重入**：区间内写回结算表本身不自锁。
- **③④ 点位**：注入一对会写回的假 stage，验证它们**落在同一区间内**——区间外观察不到中间状态。
- **锁外三件**：事件派发、通知写入、到期清理确实在区间之外，它们失败不回滚业务写。
- **事件不可变**：不存在任何改写已有事件的代码路径；不存在只改投影不写事件的路径（`I-N`）。

## 内部工作包建议

一次 **Solid Change**：

```text
WP-A 存储契约 + SQLite 实现 + 内存实现（三者同批，否则契约会长成 SQLite 的形状）
        │
        ▼
WP-B 表级写串行与四步区间骨架（③④ no-op 点位、锁全序、可重入）
        │
        ▼
WP-C 换实现验收 + 并发与死锁测试
```

**WP-A 必须三者同批。** 只写一个实现的契约会不自觉地长成那个实现的形状——第二个实现不是"以后再说"，它是**契约正确性的证据**。

## 风险与待定

- **最容易破坏本包的，是"就用一下 SQLite 的这个特性会快很多"。** 建议把 `CON-012` 写成项目的 XForge Rule：`xops-store` 之外出现 SQLite 依赖，评审阶段就拦下。
- **③④ 点位的形状是本包最难估的一处**：它要在不知道流程与插件长什么样的前提下，留出一个够用的口子。**缓解办法是照着概念文档 §7.4 的求值链与 §6.1 的插件输入/输出形状去设计**，而不是留一个泛泛的回调。
- **单实例前提要写进文档而不是留在脑子里**：应用层的表级串行只在单实例部署下成立（`CON-012` 的连带前提）。多实例是 M6。
- **本包做完之后用户看不到任何东西。** 这是按层切分的必然代价（README §2），不要因此把它并进别的包——它一旦被并进去，就会被排到身份与 MCP 后面。
