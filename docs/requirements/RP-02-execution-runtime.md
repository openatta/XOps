# RP-02 容器化执行运行时与 dsh 桥接

> 容器沙箱 · 分立进程 · 桥接插件 · 执行契约

## 归属与依赖

- **依赖**：无。**完全独立，可以和 RP-01 平台基座并行、在第一天同时开工。**
- **被依赖**：RP-05 技能与任务。
- **独立性**：它不需要用户、项目、权限或审计——它的输入是一份执行请求，输出是一份执行结果。用一个测试调用方就能完整验收：**给定技能内容与输入，在容器里跑起来，拿回 Markdown 产物、过程记录与状态。**

## 背景与价值

这个包被单独拆出来，是因为 Q2 与 Q3 定下来之后，它变成了一块**边界清晰、可独立验收、且不依赖任何其它包**的基础设施。

它同时是**全项目风险最高的一块**：容器编排、进程桥接、凭据边界、隔离验证，每一项都需要真刀真枪跑起来才知道代价。让它第一天就能开工、和平台基座并行推进，是这个拆法最实际的收益。

它也是 XOps 里**唯一允许模型参与的地方**。G8 把系统劈成两半：

| 平面 | 做什么 | 用什么 |
|---|---|---|
| **确定性平面** | 账本、审批、审计、权限 | 确定性代码，不用模型 |
| **分析平面** | 代码与文档分析、报告生成 | **本包** |

**两个平面之间的隔离是硬要求：分析平面不得写确定性平面的任何数据。** 一个能跑但能越界写账本的运行时，比一个跑不起来的运行时危险得多——**隔离比"能跑"重要**。

### 两条已定的形态决策

**D11 容器级隔离。** 服务侧 Agent 只在容器中运行，一切访问经容器边界隔离。这一条把 Q3 从"待定"变成了明确的验收标准。

**D12 分立进程 + 桥接插件。** XOps 与 dsh 是**两个分立的进程**，中间由**我们自己写的桥接插件**连接——插件装在 dsh 侧，把 XOps 的执行请求接进去、把结果送回来。

这条决策的方向承接 D8：**XOps 是驱动方，不是 dsh 的附属。** 明确排除"把 XOps 写成 dsh 的 Cordis 插件、让 XOps 活在 dsh 的运行时里"——那会让 XOps 的生命周期、构建体系与升级节奏全部绑死在一个仍处于 `0.1.0-rc`、明确预告会有破坏性变更的框架上。

分立进程带来的直接好处：dsh 崩溃或卡死不会拖垮 XOps；超时可以直接杀进程；dsh 升级的影响面被限制在桥接插件这一处。

## 范围

### 包含

- 执行契约的定义（本包对外的唯一接口）
- 容器化执行沙箱：创建、资源限制、网络策略、销毁
- 与 dsh 的进程桥接（桥接插件 + 进程生命周期管理）
- 凭据注入的边界控制
- 只读工作区的挂载（消费 RP-04 提供的工作区）
- 超时、取消、强制终止
- 执行状态、失败分类、过程记录的产生

### 不包含

- **技能与任务的领域模型**——归 RP-05。本包不知道什么是"技能"，只接收一份执行请求。
- **执行记录与产物的存储**——归 RP-05。本包产生它们并移交，不负责持久化与查询。
- **排队与调度策略**——归 RP-05。本包只负责"跑这一个"。
- **代码仓的绑定与拉取**——归 RP-04。本包只负责把已经准备好的只读工作区挂进容器。
- **判断产出质量**——不做。产出好不好由人看（G8）。

## 需求条目

### 执行契约

| ID | 需求 |
|---|---|
| R-02-01 | 本包对外只有**一个执行契约**：输入一份执行请求，输出一份执行结果。这是它与 RP-05 之间唯一的接缝，两个包可以据此并行开发。 |
| R-02-02 | 执行请求包含：技能内容、输入参数、产出格式、超时上限、以及**显式声明的能力清单**（是否需要工作区、需要访问哪些外部地址）。 |
| R-02-03 | 执行结果包含：状态、产物、过程记录、失败分类、实际耗时。 |
| R-02-04 | 执行请求中**不含任何凭据**。凭据由本包在容器边界内按需注入（R-02-14）。 |
| R-02-05 | 执行引擎必须是**可替换的**：更换底层 Agent 引擎不应改变执行契约，也不应改变本包的任何需求条目。**dsh 的概念不得泄漏到契约里。** |

### 容器隔离（最高优先）

| ID | 需求 |
|---|---|
| R-02-06 | 每次执行在**独立容器**中进行（D11）。容器不复用、不共享。 |
| R-02-07 | **容器内不得写入确定性平面的任何数据**（G8）：不得创建/修改项目、成员、角色、技能、任务、缺陷、审批实例与决策、审计事件。 |
| R-02-08 | 这条边界必须由**能力封锁**实现——容器里根本没有通往确定性平面的凭据与网络路径，**不得依赖"技能内容里没有要求做这些事"**。 |
| R-02-09 | 容器内可用的能力由执行请求的能力清单决定，未声明的一律不提供。**未声明需要工作区的执行，容器中不存在任何工作区挂载。** |
| R-02-10 | 一次执行的容器只挂载**一个项目**的工作区。跨项目访问在容器层面不可能，而不是被检查后拒绝。 |
| R-02-11 | 容器之间相互隔离：一次执行不得读取或影响另一次执行的文件系统、进程或网络状态。 |
| R-02-12 | 容器的对外网络**默认拒绝**，只放行模型服务地址与执行请求中声明的外部地址白名单。 |
| R-02-13 | 容器有明确的 CPU、内存、磁盘上限，超限时被终止并归入资源不足类失败。 |
| R-02-14 | 模型凭据与代码仓凭据**不得进入容器内 Agent 可读的上下文、环境变量或日志**。凭据只在确定性代码控制的边界内使用。 |
| R-02-15 | 工作区**只读**挂载。容器内的任何写入不回流仓库，且随容器一并销毁。 |
| R-02-16 | 容器内**不提供触发任务的能力**，防止自触发回路（与 RP-08 的 R-08-21 呼应）。 |
| R-02-17 | 执行结束后容器被**完整销毁**，不留残留进程、文件或网络状态。 |

### 进程桥接

| ID | 需求 |
|---|---|
| R-02-18 | XOps 与 dsh 是**两个分立的进程**（D12）。XOps 不运行在 dsh 的进程内，也不作为其插件被加载。 |
| R-02-19 | 两个进程之间由**桥接插件**连接。桥接插件装在 dsh 侧，负责接收执行请求、驱动 dsh 完成任务、把结果送回 XOps。 |
| R-02-20 | 桥接是两个进程之间**唯一的接缝**。除桥接之外，XOps 不依赖 dsh 的任何内部结构、类型或构建产物。 |
| R-02-21 | dsh 进程崩溃、卡死或异常退出时，XOps 侧必须能检测到并把该次执行归入明确的失败分类，**不得表现为无限期挂起**。 |
| R-02-22 | 桥接的协议与数据形状要能承载过程记录的回传，使失败可排查。 |
| R-02-23 | dsh 的版本升级只应影响桥接插件，**不应波及本包的其它部分，更不应波及其它包**。 |

### 执行控制

| ID | 需求 |
|---|---|
| R-02-24 | 执行是**异步**的：提交后立即返回执行标识，不阻塞等待完成。 |
| R-02-25 | 超过超时上限时**强制终止**（杀容器与进程），状态为已超时，**已产生的部分输出仍被保留**——一份跑了一半的报告通常仍有诊断价值。 |
| R-02-26 | 执行可被外部取消，取消后立即终止，部分输出保留。 |
| R-02-27 | 失败原因被**分类**记录：技能错误、凭据错误、工作区错误、模型服务错误、引擎/桥接错误、超时、资源不足。**"失败了"不是一个可用的结论。** |
| R-02-28 | 保留过程记录，至少包含原始输出流。**过程记录中不得出现任何凭据。** |
| R-02-29 | 产出被标注为**不可信内容**：它由模型生成，可能包含任意文本与标记。这个标注在移交给 RP-05 时不得丢失。 |
| R-02-30 | 模型凭据是**平台级统一配置**（D6），沿用 dsh 的凭据方案。凭据变更不需重启服务，且不影响在途执行。 |

## 数据与不变量

- **I-02-1**：不存在任何从容器内写入确定性平面的代码路径。
- **I-02-2**：容器内的 Agent 上下文中不含任何凭据。
- **I-02-3**：一次执行的可见范围完全由其能力清单决定，不存在隐式扩权路径。
- **I-02-4**：容器在执行结束后被完整销毁。
- **I-02-5**：XOps 进程与 dsh 进程始终分立；除桥接外无其它耦合点。
- **I-02-6**：执行契约中不含 dsh 特有的概念。

## 接口面

**对内提供给 RP-05 的**

- 提交一次执行（返回执行标识，异步）
- 查询执行状态
- 取消执行
- 领取执行结果（产物、过程记录、状态、失败分类）

本包**不对外暴露任何 MCP tool**——它没有面向用户的语义，全部经 RP-05。

## 验收标准

**隔离必须被主动攻击验证，不能只做正向测试。**

- 写一个**故意越界**的技能内容，在真实容器中执行，尝试：写确定性平面数据、读另一个项目的工作区、读环境变量里的凭据、访问白名单外的网络地址、触发另一个任务、逃逸到宿主文件系统。**每一项都必须失败**，且失败发生在**容器与能力层**（路径不存在／网络不通），**不是靠内容检查拦下的**。
- 未声明需要工作区的执行，容器中确实没有任何工作区挂载。
- 检查容器内的完整上下文与过程记录：**不含任何凭据原文**。
- 两次并发执行互相不可见（各自写同名文件互不干扰）。
- 超过 CPU／内存／磁盘上限时被终止并正确分类。
- **执行结束后检查宿主：无残留容器、无残留进程、无残留挂载。**

**桥接与控制**

- XOps 与 dsh 确实是两个进程（可从进程列表核实）。
- **强杀 dsh 进程**，该次执行在有限时间内被归入引擎/桥接错误，**不无限挂起**；XOps 自身不受影响，后续执行正常。
- 超时的执行被强制终止，状态为已超时，部分输出可读。
- 外部取消后立即终止，部分输出可读。
- 七类失败原因各构造一次，分类正确。
- **把执行引擎换成一个最简桩实现，执行契约与本包其余部分无需修改**——这是 R-02-05 的硬验收。

## MVP 子集

**完整纳入。**

MVP 可简化：
- 只支持 Markdown 产出（D9，HTML 推迟）
- 并发上限用一个很小的固定值
- 过程记录只保留原始输出流，不做结构化
- 外部地址白名单可以先只支持"模型服务 + 工作区来源"，不开放自定义

**不可裁剪**：R-02-06～R-02-17 **全部十二条容器隔离**、R-02-18～R-02-21（分立进程与崩溃检测）、R-02-25（超时强制终止）、R-02-28（过程记录无凭据）、R-02-29（不可信标注）、I-02-4（容器销毁）。

**如果时间压力大到做不完隔离，正确的做法是把整个包推迟，而不是先做一个隔离不全的运行时。** 先跑起来再补隔离，等于在补上之前一直敞开，而这段时间里跑过的技能、读过的代码、泄过的凭据都无法追回。

## 内部工作包建议

这个包在 XForge 里应当是**一次 Major Change**：

```text
WP-A 执行契约定义（对外唯一接缝，先定，RP-05 据此并行开工）
        │
        ├──► WP-B 容器沙箱（创建、资源限制、网络策略、挂载、销毁）
        │            │
        ├──► WP-C dsh 桥接插件（进程生命周期、协议、崩溃检测）
        │            │
        │            ▼
        └──────► WP-D 凭据边界与执行控制（注入、超时、取消、失败分类）
                             │
                             ▼
                     WP-E 隔离攻击测试套件
```

**WP-A 必须最先完成**——它一定型，RP-05 就能并行开工。**WP-E 不是可选的收尾工作**，它是本包唯一能证明隔离真的成立的东西，建议与 WP-B 同步推进而不是最后补。

## 风险与待定

- **dsh 处于 `0.1.0-rc`，明确预告会有破坏性变更。** D12 的分立进程 + 单一桥接接缝正是对这条风险的直接对冲，R-02-05（引擎可替换）与 R-02-23（升级只影响桥接）是它在需求层的表达。**实现时最容易破坏这一点的地方，是图省事让 dsh 的数据结构直接流进执行契约。**

- **桥接插件要跟着 dsh 的插件体系走**，而那套体系（Cordis + Typert 代码生成）本身有学习成本与构建耦合。**这部分工作量容易被低估**，建议 WP-C 早做一个最小可跑的桥接原型，再决定完整形态。

- **容器编排的形态未定**（直接调容器运行时、还是走编排系统）。属于设计选型，需求侧只要求 R-02-06 的独立容器与 R-02-17 的完整销毁。

- **R-02-12 的网络默认拒绝会和某些技能的真实需要冲突**——例如"查询依赖库有没有已知漏洞"需要访问外部数据源。执行请求里的外部地址白名单（R-02-02）是留给这类场景的出口，但**白名单由谁批准、能不能由技能作者自己随便填**没有定义。建议 MVP 不开放自定义白名单，等出现真实需求再定审批路径。

- **容器启动开销会直接体现在每次执行的延迟上。** 如果将来出现"每次提交都跑一遍检视"这类高频场景，冷启动可能成为瓶颈。**MVP 不优化**，但不要在设计上把预热或池化的路堵死——注意池化与 R-02-06（容器不复用）是冲突的，届时需要重新权衡而不是悄悄放宽。
