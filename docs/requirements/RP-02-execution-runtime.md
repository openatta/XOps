# RP-02 容器化执行运行时与 dsh 桥接

> 执行契约 · 一次性容器 · 常驻 dsh · seam 路由

## 归属与依赖

- **依赖**：无。**完全独立，可以和 RP-01 平台基座并行、在第一天同时开工。**
- **被依赖**：RP-05 技能与任务。
- **独立性**：它不需要用户、项目、权限或审计——输入一份执行请求，输出一份执行结果。用一个测试调用方就能完整验收：**给定技能内容与输入，跑起来，拿回 Markdown 产物、过程记录与状态，且一切越界尝试失败。**

## 背景与价值

这个包是全项目**风险最高的一块**：容器编排、进程桥接、凭据边界、隔离验证，每一项都要真刀真枪跑起来才知道代价。它不依赖任何包，所以能第一天开工、和平台基座并行——这是把它独立成包最实际的收益。

它也是 XOps 里**唯一允许模型参与的地方**。G8 把系统劈成两半：确定性平面（账本、审批、审计、权限）用确定性代码，分析平面用模型。**两者之间的隔离是硬要求：分析平面不得写确定性平面的任何数据。** 一个能跑但能越界写账本的运行时，比一个跑不起来的运行时危险得多——**隔离比"能跑"重要**。

### 执行拓扑（ARC-002）

```text
  apps/worker（容器外）
        │  提交执行请求
        ▼
  dsh 常驻进程（容器外）───── 只做编排与模型调用
        │                      持有模型凭据，凭据从不进容器
        │  ctx.fs / ctx.subprocess
        ▼
  dsh-bridge 插件 ──── 把全部文件与进程操作路由进 ↓
        │
  ┌──── 一次性容器（每次执行一个，用完销毁）────┐
  │  工具执行环境                                │
  │  只读工作区挂载（若技能声明需要）             │
  │  出站网络：默认拒绝 + 白名单                  │
  └──────────────────────────────────────────────┘
```

这个拓扑来自 dsh 自己的**能力 seam** 设计：`ctx.fs` 与 `ctx.subprocess` 是可替换的提供方，它的 `e2b` 家族就是把这两个 seam 指向远程沙箱的实现。dsh 文档明确写了这条边界**不迁移** harness 进程、模型调用与会话状态——**所以我们的桥接插件就是这两个 seam 的容器适配器**。

它带来一个额外好处：**模型凭据留在容器外的 dsh 进程里，从结构上就进不了容器。**

它也转移了一项责任，必须正视：

> **跨执行的会话隔离，原来由"一次执行一个容器"天然提供；dsh 常驻之后，它变成 dsh 进程自己的责任，容器帮不上忙。**

同理，dsh 崩溃的影响面从"单次执行"扩大到"全部在途执行"。这两条是这个拓扑的代价，R-02-21 与 R-02-23 是对它们的正面应对。

## 范围

### 包含

- 执行契约的定义（本包对外的唯一接口）
- 一次性容器：创建、资源限制、网络策略、挂载、销毁
- 常驻 dsh 进程的生命周期管理与跨执行隔离
- 桥接插件：`ctx.fs` 与 `ctx.subprocess` 的容器适配
- 凭据边界
- 超时、取消、强制终止、崩溃恢复
- 执行状态、失败分类、过程记录的产生

### 不包含

- **技能与任务的领域模型**——归 RP-05。本包不知道什么是"技能"，只接收一份执行请求。
- **执行记录与产物的存储**——归 RP-05。本包产生并移交，不负责持久化与查询。
- **排队与调度策略**——归 RP-05。本包只负责"跑这一个"。
- **代码仓的绑定与拉取**——归 RP-04。本包只把已备好的只读工作区挂进容器。
- **判断产出质量**——不做（G8）。

## 需求条目

### 执行契约

| ID | 需求 |
|---|---|
| R-02-01 | 本包对外只有**一个执行契约**：输入一份执行请求，输出一份执行结果。这是它与 RP-05 之间唯一的接缝，两个包可以据此并行开发。 |
| R-02-02 | 执行请求包含：技能内容、输入参数、产出格式、超时上限、以及**显式声明的能力清单**（是否需要工作区、需要访问哪些外部地址）。 |
| R-02-03 | 执行结果包含：状态、产物、过程记录、失败分类、实际耗时。 |
| R-02-04 | 执行请求中**不含任何凭据**。 |
| R-02-05 | 执行引擎必须是**可替换的**：更换底层 Agent 引擎不应改变执行契约，也不应改变本包的其它需求。**dsh 的概念不得泄漏到契约里。** |

### 容器与工具执行隔离（最高优先）

| ID | 需求 |
|---|---|
| R-02-06 | 每次执行使用**独立的一次性容器**。容器不复用、不共享。 |
| R-02-07 | **全部文件与进程操作都在容器内发生。** 容器外的 dsh 进程只做编排与模型调用，不直接触碰工作区、宿主文件系统或宿主进程。 |
| R-02-08 | **容器内不得写入确定性平面的任何数据**（G8）：不得创建/修改项目、成员、角色、技能、任务、缺陷、审批实例与决策、审计事件。 |
| R-02-09 | 这条边界必须由**能力封锁**实现——容器里根本没有通往确定性平面的凭据与网络路径，**不得依赖"技能内容里没有要求做这些事"**。 |
| R-02-10 | 容器内可用的能力由执行请求的能力清单决定，未声明的一律不提供。**未声明需要工作区的执行，容器中不存在任何工作区挂载。** |
| R-02-11 | 一次执行的容器只挂载**一个项目**的工作区。跨项目访问在容器层面不可能，而不是被检查后拒绝。 |
| R-02-12 | 容器之间相互隔离：一次执行不得读取或影响另一次执行的文件系统、进程或网络状态。 |
| R-02-13 | 容器的对外网络**默认拒绝**，只放行执行请求中声明的外部地址白名单。**模型服务不在此列**——模型调用发生在容器外。 |
| R-02-14 | 容器有明确的 CPU、内存、磁盘上限，超限时被终止并归入资源不足类失败。 |
| R-02-15 | 工作区**只读**挂载。容器内的任何写入不回流仓库，且随容器一并销毁。 |
| R-02-16 | 容器内**不提供触发任务的能力**，防止自触发回路（与 RP-08 的 R-08-21 呼应）。 |
| R-02-17 | 执行结束后容器被**完整销毁**，不留残留进程、文件、挂载或网络状态。 |

### 常驻 dsh 与进程边界

| ID | 需求 |
|---|---|
| R-02-18 | XOps 与 dsh 是**两个分立的进程**。XOps 不运行在 dsh 的进程内，也不作为其插件被加载。 |
| R-02-19 | 桥接插件装在 dsh 侧，实现 `ctx.fs` 与 `ctx.subprocess`，把这两个 seam 指向**本次执行的容器**。 |
| R-02-20 | 桥接是两个进程之间**唯一的接缝**。除桥接之外，XOps 不依赖 dsh 的任何内部结构、类型或构建产物。 |
| R-02-21 | **跨执行的会话隔离由 dsh 进程负责。** 一次执行的会话状态、上下文、临时状态与工具绑定，不得被另一次执行读取、继承或影响。**这条原本由"一次执行一个容器"天然提供，常驻之后必须显式实现并验证。** |
| R-02-22 | **模型凭据只存在于 dsh 进程与 XOps 侧，永不进入容器。** 代码仓凭据只用于容器外的工作区准备，同样不进容器。 |
| R-02-23 | dsh 进程崩溃、卡死或异常退出时，**全部在途执行**必须在有限时间内被归入明确的失败分类并可重跑，**不得表现为无限期挂起**。常驻进程被所有在途执行共享，因此这条的影响面比单次执行大得多。 |
| R-02-24 | dsh 进程重启与恢复不得丢失已经完成并移交的执行结果。 |
| R-02-25 | 桥接的协议与数据形状要能承载过程记录的回传，使失败可排查。 |
| R-02-26 | dsh 的版本升级只应影响桥接插件，**不应波及本包的其它部分，更不应波及其它包**。 |

### 执行控制

| ID | 需求 |
|---|---|
| R-02-27 | 执行是**异步**的：提交后立即返回执行标识，不阻塞等待完成。 |
| R-02-28 | 超过超时上限时**强制终止**：销毁容器，并中止 dsh 侧对应的会话，**不得留下孤儿会话继续消耗模型额度**。状态为已超时，**已产生的部分输出仍被保留**。 |
| R-02-29 | 执行可被外部取消，取消后立即终止，部分输出保留。 |
| R-02-30 | 失败原因被**分类**记录：技能错误、凭据错误、工作区错误、模型服务错误、桥接/引擎错误、超时、资源不足。**"失败了"不是一个可用的结论。** |
| R-02-31 | 保留过程记录，至少包含原始输出流。**过程记录中不得出现任何凭据。** |
| R-02-32 | 产出被标注为**不可信内容**：它由模型生成，可能包含任意文本与标记。这个标注在移交给 RP-05 时不得丢失。 |
| R-02-33 | 模型凭据是**平台级统一配置**（D6），沿用 dsh 的凭据方案。凭据变更不需重启服务，且不影响在途执行。 |

## 数据与不变量

- **I-02-1**：不存在任何从容器内写入确定性平面的代码路径。
- **I-02-2**：容器内不含任何凭据。
- **I-02-3**：一次执行的可见范围完全由其能力清单决定，不存在隐式扩权路径。
- **I-02-4**：容器在执行结束后被完整销毁。
- **I-02-5**：XOps 进程与 dsh 进程始终分立；除桥接外无其它耦合点。
- **I-02-6**：执行契约中不含 dsh 特有的概念。
- **I-02-7**：常驻 dsh 中两次执行之间不存在可观测的状态泄漏。

## 接口面

**对内提供给 RP-05 的**

- 提交一次执行（返回执行标识，异步）
- 查询执行状态
- 取消执行
- 领取执行结果（产物、过程记录、状态、失败分类）

本包**不对外暴露任何 MCP tool**——它没有面向用户的语义，全部经 RP-05。

## 验收标准

**隔离必须被主动攻击验证，不能只做正向测试。**

- 写一个**故意越界**的技能内容，尝试：写确定性平面数据、读另一个项目的工作区、读凭据、访问白名单外的网络地址、触发另一个任务、逃逸到宿主文件系统。**每一项都必须失败**，且失败发生在**容器与能力层**（路径不存在／网络不通），**不是靠内容检查拦下的**。
- **验证工具确实在容器内执行**：让技能写一个文件、跑一个进程，在宿主上确认它们只出现在容器里。
- 未声明需要工作区的执行，容器中确实没有任何工作区挂载。
- **检查容器内的完整环境与过程记录：不含任何凭据原文**；同时确认模型凭据确实只在 dsh 进程侧。
- 两次并发执行互相不可见（各自写同名文件互不干扰）。
- 超过 CPU／内存／磁盘上限时被终止并正确分类。
- **执行结束后检查宿主：无残留容器、无残留进程、无残留挂载。**

**常驻 dsh 的新增验收**

- **跨执行会话隔离**：连续两次执行，第一次在会话里留下可识别的痕迹（上下文、临时状态、工具绑定），第二次**读不到它**（R-02-21）。
- **强杀 dsh 进程**：此时故意保持三个在途执行，三个都必须在有限时间内被归入桥接/引擎错误并可重跑，**不得挂起**；XOps 自身不受影响，重启 dsh 后新执行正常（R-02-23）。
- 超时终止后，dsh 侧不残留孤儿会话（R-02-28）。
- XOps 与 dsh 确实是两个进程（可从进程列表核实）。
- **把执行引擎换成一个最简桩实现，执行契约与本包其余部分无需修改**——这是 R-02-05 的硬验收。

## MVP 子集

**完整纳入。**

MVP 可简化：只支持 Markdown 产出（D9）· 并发上限用固定小值 · 过程记录只保留原始输出流 · 外部地址白名单不开放自定义 · dsh 单实例常驻（不做多实例与负载分配）。

**不可裁剪**：R-02-06～R-02-17 **全部十二条容器隔离**、R-02-18～R-02-23（分立进程、桥接唯一接缝、**跨执行会话隔离**、**崩溃可检测不挂起**）、R-02-28（超时终止且不留孤儿会话）、R-02-31（过程记录无凭据）、R-02-32（不可信标注）、I-02-4、I-02-7。

**如果时间压力大到做不完隔离，正确的做法是把整个包推迟，而不是先做一个隔离不全的运行时。** 先跑起来再补隔离，等于在补上之前一直敞开，而这段时间里跑过的技能、读过的代码、泄过的凭据都无法追回。

## 内部工作包建议

这个包在 XForge 里应当是**一次 Major Change**：

```text
WP-A 执行契约定义（对外唯一接缝，先定，RP-05 据此并行开工）
        │
        ├──► WP-B 一次性容器（创建、资源限制、网络策略、挂载、销毁）
        │            │
        ├──► WP-C dsh 桥接插件（ctx.fs / ctx.subprocess 的容器适配）
        │            │
        │            ▼
        └──────► WP-D 常驻 dsh 生命周期（会话隔离、崩溃检测、超时中止、凭据边界）
                             │
                             ▼
                     WP-E 隔离攻击测试套件
```

**WP-A 必须最先完成**——它一定型，RP-05 就能并行开工。**WP-E 不是收尾工作**，它是唯一能证明隔离真的成立的东西，建议与 WP-B 同步推进。**WP-D 是本拓扑新增的责任所在**，跨执行会话隔离与崩溃恢复都在这里，不要把它当成"接上就行"的胶水层。

## 风险与待定

- **跨执行会话隔离（R-02-21）是这个拓扑最容易被漏掉的一条。** 它原本是免费的——一次执行一个容器，什么都不用做。改成常驻之后它需要被显式实现，而且**失效时通常没有任何报错**：两次执行之间串了状态，表现只是产出变得莫名其妙。验收标准里那条"留痕迹再读"必须实际跑，不能只看代码。

- **dsh 崩溃的影响面扩大了（R-02-23）。** 常驻进程被全部在途执行共享，一次崩溃就是一批执行同时失败。这是选择常驻换取免冷启动的代价。**建议 MVP 就把"在途执行可重跑"做进去**，而不是等真出问题再补。

- **dsh 处于 `0.1.0-rc`，明确预告会有破坏性变更。** 分立进程 + 单一桥接接缝正是对这条风险的对冲，R-02-05 与 R-02-26 是它在需求层的表达。**实现时最容易破坏这一点的，是图省事让 dsh 的数据结构直接流进执行契约。**

- **桥接插件要跟着 dsh 的插件体系走**（Cordis + Typert 代码生成），本身有学习成本与构建耦合。它同时要实现 `ctx.fs` 与 `ctx.subprocess` 两个 seam，工作量容易被低估。**建议 WP-C 早做一个最小可跑原型**——参照 dsh 自己的 `e2b` 家族（`fs-e2b`、`subprocess-e2b`）是同一形态的现成范例——再决定完整形态。

- **容器编排的形态未定**（直接调容器运行时、还是走编排系统）。属于设计选型，需求侧只要求 R-02-06 的一次性与 R-02-17 的完整销毁。

- **R-02-13 的网络默认拒绝会和某些技能的真实需要冲突**（例如查询依赖库漏洞库）。白名单是留给这类场景的出口，但**由谁批准、能不能由技能作者自己填**没有定义。建议 MVP 不开放自定义白名单，等出现真实需求再定审批路径。

- **容器池化/复用与 R-02-06 冲突。** 注意这个拓扑已经用"dsh 常驻"消掉了大部分冷启动开销，容器本身的启动通常不是瓶颈——**不要在没有实测的情况下先去动 R-02-06**。
