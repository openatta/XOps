# RP-02 项目与成员角色

## 归属与依赖

- **依赖**：RP-01（成员是用户）、RP-03（项目的创建与成员变更本身也走 MCP）。
- **被依赖**：RP-05、RP-06、RP-09、RP-10、RP-11——所有领域对象都归属于某个项目。
- **不做这个包会阻塞谁**：除 RP-01/03/04 外的全部。项目是权限判定的唯一边界（G4）。

## 背景与价值

D2 定死了这套系统的组织形态：**没有组织，没有团队，没有分组。用户平等，项目是唯一的容器，角色只在项目内有意义。**

这个决定的好处是模型极简——权限判定永远只是一个二元问题："这个用户在这个项目里是什么角色"，没有继承、没有跨层覆盖、没有"组织管理员可以看所有项目"这类会不断长出例外的规则。

代价也要认清：**没有任何人能俯瞰全平台。** 平台没有超级管理员视角，一个项目的内容只有它的成员看得到。这是有意的，不是缺失。

## 范围

### 包含

- 项目的创建、基本属性、归档
- 成员的加入与移除
- 项目内角色的定义与分配
- 权限判定：给定（用户，项目，动作）→ 允许 / 拒绝

### 不包含

- **组织、团队、用户组**——D2 排除。
- **跨项目的全局角色**——G4 排除。不存在"平台管理员"。
- **项目内的业务对象**——缺陷、流程、技能、任务分别归各自的包，本包只提供归属与权限判定。
- **代码仓绑定**——归 RP-09，虽然它是项目的属性。

## 需求条目

| ID | 需求 |
|---|---|
| R-02-01 | 任何用户都可以创建项目，无需申请或审批。创建者自动成为该项目的所有者。 |
| R-02-02 | 项目有稳定的、创建后不可变的标识；显示名可变。 |
| R-02-03 | 项目所有者可以把其他用户加入项目并指定角色。被加入者不需要主动接受即生效——**这是有意的简化**，因为项目内容对非成员不可见，误加的代价仅是多一个能看见的人。 |
| R-02-04 | 项目内至少有三个角色，语义分别是：**所有者**（可管理成员与项目本身）、**维护者**（可管理项目内的业务对象）、**成员**（可提交缺陷、发起任务、参与审批，但不改项目结构）。 |
| R-02-05 | 一个项目必须始终至少有一个所有者。移除最后一个所有者的操作被拒绝。 |
| R-02-06 | 同一用户在不同项目中的角色互相独立，一个项目的所有者在另一个项目里可能连成员都不是。 |
| R-02-07 | 非成员对项目的一切内容不可见——查询返回"不存在"，而不是"无权限"，避免通过错误码探测项目是否存在。 |
| R-02-08 | 项目可以被归档。归档后项目转为只读：不再接受任何写操作，但历史内容与执行记录完整保留、可查询。 |
| R-02-09 | 权限判定是确定性的纯函数：相同的（用户，项目，动作）在角色未变时永远得到相同结果，不受任何模型或外部服务影响（G8）。 |
| R-02-10 | 成员的加入、移除、角色变更全部产生审计事件（RP-04）。 |
| R-02-11 | 项目角色的分配不得由审批流程之外的任何自动化路径变更——特别地，**Agent 执行任务时不得提升自己或他人的角色**（G8）。 |

## 数据与不变量

- **I-02-1**：每个业务对象恰好归属一个项目，不存在跨项目共享的对象。
- **I-02-2**：项目成员集合的每次变化都留下审计事件，可以重建任意时刻的成员快照。
- **I-02-3**：归档项目的写入路径全部关闭，包括 MCP、触发器与 Agent 执行。

## 接口面

**MCP tools**

| 意图 | 说明 |
|---|---|
| 创建项目 | 调用者成为所有者 |
| 查询我参与的项目 | Agent 定位自己该往哪个项目提交的第一步 |
| 查询项目详情 | 含成员与自己的角色 |
| 添加成员 / 指定角色 | 需所有者 |
| 移除成员 / 变更角色 | 需所有者，受 R-02-05 约束 |
| 归档项目 | 需所有者 |

**只读查询面**（供 RP-15）

- 项目列表（仅当前用户是成员的）
- 项目详情与成员列表
- 成员变更历史

## 验收标准

- 新建项目后，创建者是所有者，且能立刻加人。
- 非成员查询该项目，得到"不存在"，与查询一个真正不存在的项目**响应一致**。
- 用户 A 在项目 1 是所有者、在项目 2 是成员时，A 在项目 2 无法加人。
- 移除唯一所有者被拒绝，且项目状态未变。
- 归档项目后，所有写操作被拒绝，所有读操作仍正常。
- 权限判定函数在相同输入下重复调用结果一致。

## MVP 子集

**完整纳入。** 三个角色、加人移人、归属判定、非成员不可见——都是 MVP 必需的。

可以推迟的：
- 项目归档（R-02-08）可以推迟到 MVP 之后，但**数据形状要预留**，事后加状态字段比事后加不了要好。
- 角色的精细化（比如把"维护者"再拆）不做，三个角色够 MVP 用。

## 风险与待定

- **三个角色够不够**，取决于 RP-06 审批引擎最终要绑定哪些角色。通用审批引擎（D1）可能需要项目内可自定义角色（比如跨仓设计里提到的 `verifier`）。**建议**：MVP 用固定三角色，把"项目内自定义角色"作为 RP-06 的扩展需求，而不是现在就把 RP-02 做成可配置角色系统——后者会在还没有真实审批场景时先付一大笔复杂度。
- **Q5（跨包）**：如果一个实例承载互不信任的用户，"任何人都能创建项目"（R-02-01）会让代码仓凭据与执行沙箱的隔离要求显著上升。这条与 RP-09、RP-12 的风险联动。
- R-02-03 不需要被加入者确认，在互不信任的多用户实例上会变成骚扰面（任何人可以把你加进任何项目）。如果 Q5 的答案是"开放注册"，这条需要改成邀请+接受。
