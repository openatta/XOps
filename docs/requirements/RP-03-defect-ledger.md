# RP-03 缺陷账本

> 提交 · 状态流转 · 修复关联 · 查询 · 缺陷视图

## 归属与依赖

- **依赖**：RP-01 平台基座。**除此之外不依赖任何包。**
- **被依赖**：RP-09 通知（可选）。
- **独立性**：完全独立的纵向切片。做完即可用：AI 编程工具里的 Skill 能提交缺陷、能流转状态，人能在 Web 上看到完整时间线。

## 背景与价值

这是 XOps 存在的第一理由，理由本身很短：

> **缺陷在被修复之前，不属于任何一个变更，因而不属于任何一个仓库。**

XForge 把项目事实留在仓里，但一个刚被发现、还不知道该谁改、改在哪个变更里的缺陷，在仓里没有位置。它需要一个跨仓、跨项目、独立于任何一次变更生命周期的账本。

D5 定死了这个账本的边界：**只存 XOps，追加式，不回写任何仓库。** 直接后果是 **XOps 不需要任何项目仓库的写权限**——这是一个很大的安全收益，值得在实现时反复确认没有被悄悄破坏。

关联方向也因此确定：

> **"仓库 → 服务"靠缺陷 ID 关联（修复提交里引用它），"服务 → 仓库"靠提交与摘要关联。双向可查，但权威只有一个方向。**

## 范围

### 包含

- 缺陷提交、缺陷 ID 分配
- 状态流转（确认、指派、修复、验证、关闭、重开、废弃）
- 结构化内容（复现步骤、期望/实际、影响范围、关联标识）
- 与修复提交的关联（由仓侧引用 ID 建立）
- 缺陷查询
- 缺陷视图：列表与筛选、详情与完整时间线

### 不包含

- **往任何仓库写入**——D5 排除。不生成 XForge Change 骨架，不创建分支，不提 PR。
- **判断缺陷是否成立、是否重复、优先级多高**——判断题属于人或提交方的 Agent，XOps 只记录（G8）。
- **看板、燃尽图、报表引擎**——明确不做。
- **通知投递**——归 RP-09。

## 需求条目

### 提交与标识

| ID | 需求 |
|---|---|
| R-03-01 | 缺陷 ID 由 XOps 在创建时分配，形如 **`<项目短名>-<项目内递增序号>`**（D14）。短名来自 R-01-16a，全平台唯一且不可变。ID 稳定、可读、**可在提交信息里手写引用**。这是唯一一处"服务给出仓库将要引用的标识"的地方，因此**必须简单到不可能出错**。 |
| R-03-01a | 序号在**项目内**递增，不跨项目共享计数器——这样两个项目的编号互不干扰，也不会从 ID 上泄露平台的总缺陷量。 |
| R-03-02 | 缺陷通过 MCP 提交，提交方是 AI 编程工具中的 Skill。提交者身份由令牌解析得出（G5）。 |
| R-03-03 | 提交接口是**固定形状的窄接口**（G7、R-01-29）：目标项目、关联的需求或模块标识、复现步骤、观测到的现象、期望的行为、可选的产物/版本标识。**不提供自由结构的附加字段，也不提供"把这段上下文一起发过去"的能力。** |
| R-03-04 | 缺陷内容的结构化由**提交方的 Agent** 完成——它本来就在上下文里，知道自己跑的是什么、失败在哪一步。XOps 只做 schema 校验与原样写入，**不用模型加工内容**（G8）。 |
| R-03-05 | 提交支持幂等：同一提交方携带相同幂等键重复提交，不产生重复缺陷。 |

### 状态流转

| ID | 需求 |
|---|---|
| R-03-06 | 状态集合至少包含：已提交、已确认、处理中、已修复、已验证、已关闭、已重开、已废弃。 |
| R-03-07 | **状态变化以追加新记录表达，不得就地改写**（G3）。缺陷的"当前状态"是其记录流的推导结果。 |
| R-03-08 | 每次状态变化记录行为人、时间、原因，以及（若有）关联的修复提交或变更标识。 |
| R-03-09 | 允许的状态转移是显式定义的确定性规则，非法转移被拒绝并说明当前状态。 |
| R-03-10 | 缺陷可以被重开。**重开不创建新缺陷**，而是在同一 ID 的记录流上追加——否则"这个问题修了三次还在"这个事实会被拆成三个互不相干的缺陷而消失。 |
| R-03-11 | 缺陷可指派给项目成员，指派本身也是一条追加记录。 |

### 关联与查询

| ID | 需求 |
|---|---|
| R-03-12 | 修复方在变更中引用缺陷 ID 后，可通过 MCP 把该引用登记到缺陷上（提交摘要、分支、变更标识）。XOps **只记录这个引用，不去仓库验证它是否真的存在**——验证需要仓库读权限与在线依赖，而这条关联的价值不依赖于此。 |
| R-03-13 | 支持按项目、状态、指派人、提交人、时间范围、关联标识查询。 |
| R-03-14 | 支持查询单个缺陷的完整历史（全部记录，按时间序）。 |
| R-03-15 | 非项目成员无法查询到该项目的任何缺陷（继承 R-01-21、R-01-32）。 |

### 缺陷视图（只读）

| ID | 需求 |
|---|---|
| R-03-16 | 提供缺陷列表与筛选视图。 |
| R-03-17 | 提供缺陷详情视图，含**完整时间线**：每一次状态变化、谁、何时、为什么。时间线是追加式账本（G3）的直接体现，是这个视图的核心而非附属。 |
| R-03-18 | 视图上不存在任何写入操作（G2）。 |

## 数据与不变量

- **I-03-1**：缺陷记录只追加。当前状态视图是缓存，权威是记录流。
- **I-03-2**：缺陷 ID 一经分配永不复用，即使缺陷被废弃。
- **I-03-3**：**XOps 在任何代码路径上都不持有、不请求项目仓库的写权限。**
- **I-03-4**：缺陷内容中的自由文本从写入到读出保持逐字节一致，中间无任何模型参与。

## 接口面

**MCP tools**（窄接口，固定形状）

| 意图 | 说明 |
|---|---|
| 提交缺陷 | 返回缺陷 ID，幂等 |
| 变更缺陷状态 | 确认/指派/标记修复/验证/关闭/重开/废弃 |
| 登记修复引用 | 把变更标识、提交摘要关联到缺陷 |
| 查询缺陷 | 按条件筛选 |
| 查询缺陷历史 | 单缺陷全部记录 |

**只读视图**

- 项目缺陷列表与筛选
- 单缺陷详情与完整时间线
- 缺陷与修复引用的双向视图

## 验收标准

- 从一个**真实的 AI 编程工具**里，通过 Skill 调 MCP 提交缺陷，拿到可读的缺陷 ID。
- 用同一幂等键重复提交，只产生一个缺陷。
- 缺陷走完"提交 → 确认 → 处理中 → 修复 → 关闭 → 重开"，查询历史能看到全部六条记录，当前状态正确。
- **直接检查存储：状态变化产生的是新记录，没有任何一行被 UPDATE。**
- 发起一个非法状态转移，被拒绝且缺陷状态未变。
- 非成员查询该项目缺陷，返回与项目不存在一致的结果。
- Web 上打开缺陷详情，时间线与 MCP 查询结果一致，且页面无任何写入控件。
- **全程审查代码与配置：不存在任何使用项目仓库写权限的路径。**

## MVP 子集

**完整纳入。这是 MVP 的核心价值闭环之一。**

可裁剪：
- **状态集合（R-03-06）** MVP 可缩到四态：已提交 → 处理中 → 已修复 → 已关闭，外加重开。其余状态事后按同一追加机制加，不改结构。
- **指派（R-03-11）** 可推迟。
- **查询筛选维度（R-03-13）** MVP 给项目 + 状态 + 时间即可。

**不可裁剪**：R-03-01（ID 分配）、R-03-03（窄接口）、R-03-05（幂等）、R-03-07（追加式）、R-03-10（重开不新建）、R-03-12（修复引用）、R-03-17（完整时间线）。这七条构成"缺陷账本"这个概念本身，缺任何一条就变成了一个普通的 issue 表。

## 风险与待定

- **缺陷 ID 形状已定（D14）**：`<项目短名>-<项目内序号>`。**代价要认清**——项目短名因此变成不可变的公开标识（R-01-16a）。项目改名很常见，而短名改不了，时间长了会出现"项目叫 A 但缺陷 ID 前缀是 B"的错配。这是可接受的：ID 已经被手写进了别人的提交历史，**能改的短名比改不了的错配危险得多**。但创建项目时必须把这一点讲清楚，不能让人随手填一个。

- **重复缺陷怎么办**没有定义。R-03-05 的幂等只覆盖"同一提交方重复提交同一次"，覆盖不了"两个人发现同一个问题"。**建议 MVP 不做去重**——判断两个缺陷是否是同一个是判断题，属于人。可以提供"标记为重复于某 ID"作为一条普通的状态记录。

- **附件与截图未纳入范围。** 如果 Skill 提交时想带日志片段或截图，会需要一套附件存储。这会直接冲击 R-03-03 的窄接口纪律——**附件是最容易被用来夹带任意上下文的通道**。建议不进 MVP，需要时单独决定。
