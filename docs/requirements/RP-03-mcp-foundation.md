# RP-03 MCP 服务基座

## 归属与依赖

- **依赖**：RP-01（令牌解析）、RP-02（权限判定）、RP-04（写操作留痕）。
- **被依赖**：RP-05、RP-06、RP-08、RP-10、RP-11、RP-14——所有对外的写入面。
- **不做这个包会阻塞谁**：全部写入路径。G1 规定 MCP 是唯一写入面，那么这个基座就是唯一的门。

## 背景与价值

XOps 是"主要通过 MCP 使用"的平台。这意味着 MCP 面不是一个附加的 API 适配层，**它就是产品本身**。

把它单独成包，是因为每个领域包都需要同一套东西：认证、权限、参数校验、幂等、错误契约、留痕。这些如果由各领域各写一遍，会立刻出现"缺陷的 tool 校验严格、审批的 tool 校验松散"这类不一致——而这类不一致恰恰发生在安全边界上。

**一个更重要的理由：窄接口是这套系统的安全属性，不是风格偏好。**

跨仓协作设计里有一条写得很硬的话：绝不要提供一个通用的"把这个上下文发过去"的工具。一旦通道能承载任意上下文，独立性就不再是结构保证，而是取决于每个人每次的自觉。**这条纪律必须由基座强制，不能靠各领域自觉。**

## 范围

### 包含

- MCP server 的对外服务形态与传输
- 令牌认证与调用者解析（消费 RP-01）
- tool 注册与发现
- 请求参数的 schema 校验（拒绝未声明字段）
- 幂等语义的统一支持
- 统一错误契约
- 每次 tool 调用的留痕（消费 RP-04）
- 速率与配额约束

### 不包含

- **具体业务 tool 的语义**——归各领域包。本包只提供骨架与纪律。
- **XForge 的两个固定审批 tool**——它们形状特殊（由 XForge 定死），归 RP-08。
- **XOps 作为 MCP client 去调别人**——本包只做 server 侧。

## 需求条目

| ID | 需求 |
|---|---|
| R-03-01 | XOps 对外暴露 MCP server，任何符合 MCP 的客户端（AI 编程工具及其 Skill）都能接入，不需要 XOps 专属 SDK。 |
| R-03-02 | 每次调用必须携带令牌；无令牌或令牌无效时拒绝，且不执行任何副作用。 |
| R-03-03 | 调用者身份一律由令牌解析得出（G5）。tool 参数中任何身份类字段被忽略，且这种忽略是静默的——不报错，但也绝不生效。 |
| R-03-04 | 所有 tool 的输入有明确 schema，**未在 schema 中声明的字段一律拒绝**，不静默丢弃。静默丢弃会让调用方以为自己传的东西生效了。 |
| R-03-05 | tool 的输入 schema 必须是**固定形状的窄接口**。禁止提供接受任意结构、任意上下文或自由指令的通用 tool。 |
| R-03-06 | 产生副作用的 tool 支持幂等：调用方提供幂等键时，重复调用不产生第二次副作用，并返回与首次相同的结果。 |
| R-03-07 | 错误响应使用统一契约：稳定的错误码、可读消息、以及"该重试还是该改参数"的明确区分。 |
| R-03-08 | 权限不足与对象不存在返回**相同**的错误，避免通过错误码探测他人项目的存在（呼应 R-02-07）。 |
| R-03-09 | 每次成功的写操作产生一条审计事件，包含行为人、时间、tool、目标对象与幂等键（RP-04）。 |
| R-03-10 | 失败的调用也留痕，但与成功事件区分——失败留痕用于排查与滥用检测，不进入业务账本。 |
| R-03-11 | 提供按用户与按 tool 的速率限制，超限时返回可重试错误并给出建议等待时间。 |
| R-03-12 | tool 的发现结果按调用者的项目角色裁剪：调用者在任何项目都无权使用的 tool 不出现在其可见列表中。 |
| R-03-13 | 所有 tool 的自由文本参数被视为不可信输入（G7）：基座只做 schema 与长度校验并原样存储，不解析、不执行、不依据其内容改变控制流。 |

## 数据与不变量

- **I-03-1**：不存在绕过基座的写入路径。任何领域包新增写操作，必须经由本包注册的 tool。
- **I-03-2**：幂等键在其作用域内唯一，重复提交是空操作而非报错。
- **I-03-3**：一次 tool 调用要么完整产生其副作用与审计事件，要么两者都不产生。

## 接口面

**基座自身对外的 tool**

| 意图 | 说明 |
|---|---|
| 能力发现 | 当前令牌能用哪些 tool、在哪些项目上 |
| 服务健康与版本 | 供客户端确认契约版本 |

**对内提供给领域包的**

- tool 注册（声明 schema、所需权限、是否幂等）
- 已认证的调用上下文（调用者、目标项目、角色）
- 统一的错误构造
- 审计事件写入

## 验收标准

- 用任意标准 MCP 客户端连接并列出 tools，得到按角色裁剪后的列表。
- 无令牌调用被拒绝，且未产生任何数据变化与业务审计事件。
- 传入 schema 未声明的字段，调用被拒绝（而不是成功但字段被忽略）。
- 在参数里塞 `actor: "someone-else"`，记录中的行为人仍是令牌所有者。
- 同一幂等键连续调用两次，副作用只发生一次，两次返回一致。
- 对无权访问的项目和对不存在的项目发起同一 tool，两个错误响应不可区分。
- 超过速率限制后返回可重试错误，且此前的调用未受影响。

## MVP 子集

**完整纳入，但可裁剪两项：**

- **速率限制（R-03-11）** 可以先给一个粗粒度的全局上限，不做按 tool 的精细配额。
- **能力发现的角色裁剪（R-03-12）** 可以先返回全量 tool 列表、在调用时才判权限。裁剪是体验优化，不是安全边界——安全边界是 R-03-08 那条。

**不可裁剪**：R-03-02、R-03-03、R-03-04、R-03-05、R-03-06、R-03-08、R-03-09、R-03-13。这几条是纪律，事后补会变成把所有 tool 重写一遍。

## 风险与待定

- **传输形态未定**（远程 HTTP 还是本地 stdio 代理）。XOps 是云端服务，倾向远程；但用户的编程工具在本机，中间是否需要一个本地桥接取决于各工具对远程 MCP 的支持程度。这属于设计选型，**不在需求阶段决定**。
- **契约版本演进策略未定**：tool 的 schema 改变时，已经写好的 Skill 会不会突然失效。建议在设计阶段就把版本化想清楚——这个平台的调用方是别人写的 Skill，破坏性变更的代价比普通 API 高。
- R-03-05 的"窄接口"是一条**需要持续守住**的纪律，不是一次性验收项。每新增一个 tool 都可能有人想加一个"扩展字段"或"透传上下文"参数。建议把这条写进项目的 XForge Rule，让它在每次变更时被检查，而不是靠记性。
