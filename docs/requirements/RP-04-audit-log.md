# RP-04 审计与追加式事件日志

## 归属与依赖

- **依赖**：RP-01（事件的行为人）。
- **被依赖**：RP-02、RP-03、RP-05、RP-07、RP-09、RP-10、RP-12——所有产生副作用的包。
- **不做这个包会阻塞谁**：RP-05 与 RP-07 直接依赖它的追加式语义（G3），其余包依赖它留痕。

## 背景与价值

XForge 那一侧的可信度来自防篡改的审计哈希链——一份没有对应链上事件的审批回执会被直接拒绝，即使其它字段都对。XOps 这一侧要承载审批与缺陷账本，就必须有可比的性质，否则整条协同链的强度会掉到"我们相信这个数据库"。

但要说清楚一件事：**XOps 的审计日志不是、也不应该是证据链的一环。**

规格、需求、验收证据的家是仓库,那里是追加式、防篡改的。XOps 只记录**仓库里没有的东西**（D6 的同一条道理）。审计日志在这里的职责更朴素：

> **让"谁在什么时候做了什么"这个问题永远有答案，并且这个答案不会被后来的写入抹掉。**

这是账本类系统最容易被偷工减料的地方——直接 UPDATE 一行状态、覆盖一个字段，功能上看不出差别，直到某天需要回答"这个缺陷三天前是什么状态、谁改的"，才发现答案已经不存在了。

## 范围

### 包含

- 追加式事件日志的写入与查询
- 事件的标准字段与因果关联
- 从事件重建任意时刻状态快照的能力
- 事件的完整性保护（不可就地改写、不可删除）
- 保留期与容量策略

### 不包含

- **业务状态的当前视图**——各领域包自己维护读模型，本包只保证事件流是权威来源。
- **XForge 的审计链**——那是仓内文件，XOps 不碰、不复制、不代管。
- **执行日志与产物**——任务每次执行的输出归 RP-13，那是工作数据不是审计数据，两者的保留期和访问控制都不同。

## 需求条目

| ID | 需求 |
|---|---|
| R-04-01 | 事件日志只追加，不提供任何就地修改或删除单条事件的能力。纠正错误的方式是追加一条纠正事件。 |
| R-04-02 | 每条事件至少包含：稳定事件标识、发生时间、行为人（来自令牌解析）、所属项目、事件类型、目标对象标识、以及该类型的结构化载荷。 |
| R-04-03 | 事件按其所属项目分区，非项目成员查询不到该项目的任何事件（呼应 R-02-07）。 |
| R-04-04 | 事件之间可以声明因果关联（"这条状态变更由那次审批决策引起"），使得任意结论都能追到它的来源。 |
| R-04-05 | 对任意给定时刻，可以仅凭事件流重建当时的业务状态快照，不依赖任何当前视图表。 |
| R-04-06 | 事件的写入与其对应的业务副作用在同一次操作中完成——不存在"业务成功但没留痕"或"留了痕但业务没生效"的中间态（呼应 I-03-3）。 |
| R-04-07 | 事件载荷中的自由文本原样保存，不做解析、不做规范化（G7）。 |
| R-04-08 | 事件日志的写入路径不经过任何模型（G8）。Agent 可以读取自己有权读的事件，但绝不写入。 |
| R-04-09 | 提供按项目、时间范围、事件类型、行为人、目标对象的查询。 |
| R-04-10 | 保留期可配置，但一经写入的事件在保留期内不可删除。到期清理只能整批按时间进行，不得选择性删除个别事件。 |

## 数据与不变量

- **I-04-1**：事件一经写入即不可变。
- **I-04-2**：事件的行为人字段永远来自令牌解析，不来自请求体（继承 I-01-2）。
- **I-04-3**：任何业务对象的当前状态，都可以由其事件流完整推导出来——当前视图是缓存，不是权威。
- **I-04-4**：不存在只改当前视图而不写事件的代码路径。

## 接口面

**MCP tools**

| 意图 | 说明 |
|---|---|
| 查询项目事件流 | 按时间/类型/对象筛选，供 Agent 回答"这个缺陷经历了什么" |
| 查询某对象的完整历史 | 单个缺陷、单个审批实例的全部事件 |

**对内提供给领域包的**

- 事件追加（与业务写入在同一原子边界内）
- 事件流读取与重放

**只读查询面**（供 RP-15）

- 项目活动时间线
- 单对象历史视图

## 验收标准

- 任何业务写操作完成后，能查到对应事件；业务写操作失败时，查不到任何残留事件。
- 尝试修改或删除单条已写入事件的操作，在接口层不存在（不是"被拒绝"，是没有这个能力）。
- 对一个经历了多次状态变化的缺陷，能重建其在任意历史时刻的状态，且结果与当时的当前视图一致。
- 非成员查询项目事件，返回与项目不存在一致的结果。
- 断开当前视图表后，仅凭事件流能重建全部业务状态。

## MVP 子集

**完整纳入，但可裁剪两项：**

- **因果关联（R-04-04）** 可以先只记录事件本身，不建立显式的因果边。MVP 阶段缺陷与审批之间的关联还不密集。
- **保留期与清理（R-04-10）** MVP 不做清理，只做无限保留；但配置位置要预留。

**不可裁剪**：R-04-01、R-04-05、R-04-06、R-04-08。特别是 **R-04-05（可重建）**——它是判断"这个包是否真的做对了"的唯一硬标准。一个只是"顺手记了些日志"的实现能通过其它所有条目，但过不了这一条。

## 风险与待定

- **事件类型的命名与载荷 schema 需要跨领域统一。** 建议在设计阶段先定一份事件类型目录，而不是让各领域各自发明——否则查询面会变成一堆特例。
- **性能**：追加式 + 从事件重建，在缺陷与执行记录规模上来后会有压力。这是已知的经典权衡，MVP 规模下不构成问题，但设计时不要把重建路径写成只能全量扫描。
- **与 RP-13 执行记录的边界**要在设计阶段划清楚。执行产物（MD/HTML、日志）体量大、保留期短、访问频率低，塞进审计事件流会把这个包拖垮。**建议**：事件流只记"某次执行发生了、结果是什么状态、产物在哪"，产物本身归 RP-13。
