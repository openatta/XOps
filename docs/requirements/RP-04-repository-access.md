# RP-04 代码仓接入

> 绑定 · 只读凭据 · 服务端受控工作区 · 仓视图

## 归属与依赖

- **依赖**：RP-01 平台基座。**除此之外不依赖任何包。**
- **被依赖**：RP-05（增强其读代码能力）、RP-08（Git Hook 触发需要绑定关系）、RP-07（可复用绑定关系定位项目）。
- **独立性**：完全独立的纵向切片。做完即可验收：绑定一个仓、拉下来、在 Web 上看到同步状态与当前修订。**它与 RP-05 谁先做都不卡对方**——RP-05 的技能可以声明不需要代码仓。

## 背景与价值

核心问题不是"怎么 clone"，而是：

> **让服务端 Agent 能读到代码，同时让源码不落到任何个人的机器上。**

这是一个被低估的收益。一个质量负责人如果按 clone 的方式服务 N 条产品线，他的个人机器上会同时存在 N 个产品的完整源码，并且要把它们发往多个模型引擎——**那台机器会成为整个组织代码资产暴露面最大的一个点**。把分析放到服务端，源码留在受控环境里，个人侧只有报告。

第二个核心问题是**只读**。XOps 在 D5 之后已经不需要任何仓库写权限（缺陷不回写），这个包不应该把它加回来。**只读凭据是这个系统一条重要的安全属性，值得写成不变量。**

## 范围

### 包含

- 项目绑定代码仓（GitHub、Gitea 自建、GitLab）
- 只读凭据的登记、加密存储、轮换、撤销
- 服务端受控工作区：按需拉取、更新、按项目隔离
- 工作区的生命周期与清理
- 仓库访问留痕
- 仓视图：绑定列表与同步状态

### 不包含

- **任何写操作**——不推分支、不提 PR、不打 tag、不改任何仓库内容。
- **构建**——被测产物由现有 CI 产出，服务不碰。
- **Webhook 的接收与触发语义**——归 RP-08。
- **代码的语义分析**——那是技能的事，归 RP-05。

## 需求条目

### 绑定与凭据

| ID | 需求 |
|---|---|
| R-04-01 | 项目可绑定零个或多个代码仓。绑定通过 MCP 建立，需所有者或维护者权限。 |
| R-04-02 | 支持 GitHub、Gitea（自建）、GitLab（自建与 SaaS）三类平台（D4），**先做 GitHub**（D13）。绑定时声明平台类型、仓库地址、默认分支。 |
| R-04-02a | 平台差异必须收在一个**可适配的接口**后面（认证、克隆、权限元数据校验、webhook 签名验证）。新增一个平台只需实现该接口，不改动绑定模型、工作区管理与执行链路。 |
| R-04-03 | 凭据**必须是只读的**。绑定生效前**实际验证一次**它确实能读、且**确实不能写**。 |
| R-04-04 | 凭据加密存储，任何接口都不能读出原文，**包括项目所有者自己**。展示时只给可识别片段与来源说明。 |
| R-04-05 | 凭据可轮换与撤销。撤销后依赖它的执行立即失败，不使用任何缓存凭据。 |
| R-04-06 | 凭据传递给执行环境时，只注入到实际需要它的那一次拉取动作，**不得进入 Agent 可读的上下文、环境变量或日志**。 |
| R-04-07 | 每次使用凭据访问仓库产生审计事件：哪个项目、哪个仓、哪次执行、拉取了什么修订。 |

### 工作区

| ID | 需求 |
|---|---|
| R-04-08 | 服务端维护受控工作区，Agent 执行时在其中读取代码。**源码不发送给任何个人终端。** |
| R-04-09 | 工作区按项目隔离。**一次执行不得同时持有多个项目的代码上下文。** |
| R-04-10 | 工作区可定位到具体修订（分支、标签、提交）。**每次读取必须记下确切修订**——否则"这份代码检视报告针对哪版代码"无法回答。 |
| R-04-11 | 工作区**只读**挂载给 Agent。Agent 在其中的任何写入不得回流到仓库，且执行结束后被丢弃。 |
| R-04-12 | 工作区支持增量更新，不要求每次执行都全量克隆。 |
| R-04-13 | 工作区有明确的生命周期与清理策略；长期不用的可被回收，回收后下次执行自动重建。 |
| R-04-14 | 大仓库的拉取有容量与时间上限，超限时失败并明确报告，**不允许无限制占用**。 |

### 仓视图（只读）

| ID | 需求 |
|---|---|
| R-04-15 | 提供项目的代码仓绑定列表与同步状态（上次拉取时间、当前修订）。 |
| R-04-16 | 视图中**不含凭据任何形式的原文或可恢复片段**。 |

## 数据与不变量

- **I-04-1**：XOps 在任何代码路径上都不持有仓库写权限（与 I-03-3 同源）。
- **I-04-2**：凭据原文不出现在日志、执行输出、Agent 上下文或任何查询结果中。
- **I-04-3**：一次执行的工作区只包含一个项目的代码。
- **I-04-4**：每次读取记录其确切修订标识。

## 验收标准

- 对目标平台绑定一个仓并成功拉取。
- **提供一个具备写权限的凭据时，绑定被拒绝**（R-04-03 的"确实不能写"验证生效）。
- 凭据绑定后，通过任何接口都无法读出原文。
- 撤销凭据后，下一次拉取失败，且失败原因明确指向凭据。
- 检查日志与（若 RP-05 已就位）Agent 上下文：不含凭据原文。
- 一次拉取产生的工作区中不存在其它项目的文件。
- 访问记录中能查到本次读取的确切提交标识。
- 在工作区内写文件后，仓库无变化，且释放后写入内容被清理。
- 超过容量上限的仓库拉取失败并明确报告。
- Web 仓视图不含凭据原文或可恢复片段。

## MVP 子集

**以裁剪后的子集纳入 MVP。**

MVP 做到：
- **只做 GitHub**（D13），与 RP-01 的 OAuth 提供方同一家，共用应用配置；但 R-04-02a 的适配接口要立住
- 单仓绑定（一个项目一个仓）
- 全量克隆即可，不做增量（R-04-12 推迟）
- 工作区清理可以粗暴（每次用完直接删），不做生命周期管理（R-04-13 推迟）

**不可裁剪**：R-04-03（只读验证）、R-04-04（凭据不可读出）、R-04-06（不进 Agent 上下文）、R-04-09（项目隔离）、R-04-10（记录修订）、R-04-11（写入不回流）。这六条是安全属性，事后补等于先裸奔一段时间。

## 风险与待定

- **R-04-03 的"验证确实不能写"实现难度因平台而异。** GitHub 的细粒度 PAT 与 GitHub App 能明确表达只读；Gitea 与 GitLab 的 deploy token / project access token 也有只读档位，但"验证它不能写"本身需要尝试一次写操作或读取权限元数据，两条路都有平台差异。**这条可能需要降级成"读取并校验权限元数据，无法确认时明确告警"**，但不要直接删掉——一个悄悄拿着写权限的服务端是很大的风险。

- **私有网络的自建 Gitea/GitLab 可能不允许 XOps 直接访问。** 这会引出"是否需要一个部署在客户网络内的拉取代理"，那是一整块新东西。**建议 MVP 明确假设 XOps 能直接访问所有绑定的仓库地址**。如果不成立，需要单独讨论。

- **单仓还是多仓**：R-04-01 写的是"零个或多个"，D6 也提到多仓。项目绑定多仓在代码检视场景是合理的（一个产品跨多个仓），但会让 R-04-09 需要细化成"只持有本次任务声明的那些仓"。**MVP 先做单仓**，留到有真实多仓需求时再定。

- **三个平台的适配差异不小**（认证方式、克隆协议、权限元数据接口、webhook 签名算法）。已定先做 GitHub（D13），其余**按平台逐个交付**、单独验收。与 RP-01 的 R-01-01a 同一个风险：**只接了一家时，很容易把 GitHub 特有的概念渗进绑定模型**（比如 installation id、它的 token 前缀约定）。建议在只有一家的阶段就用一个桩平台跑一遍，证明 R-04-02a 的接口是真的。
