# RP-04 技能与任务执行

> 技能资产 · 任务定义 · 手动触发 · Agent 运行时 · 执行记录与产物 · 执行视图

## 归属与依赖

- **依赖**：RP-01 平台基座。**除此之外不依赖任何包。**
- **增强来源**：RP-03 代码仓接入——做完之后，技能才多出"能读代码"这项能力。
- **被依赖**：RP-07 自动触发。
- **独立性**：完全独立的纵向切片。**RP-03 未就位时，本包仍可完整实现与验收**：技能声明自己不需要代码仓（例如"根据缺陷账本生成周报"、"分析这段输入产出结构化报告"），链路一样跑得通。

## 背景与价值

这个包覆盖你的第 3、4 条需求：**项目中创建 SKILLS** → **后台运行 AGENT，根据用户的任务执行，通过 AGENT + SKILLS 输出 MD 数据** → **可以查看任务每次执行的输出**。

四件东西为什么必须同包：技能是"怎么做"，任务是"对什么做、什么时候做"，运行时是"真的去做"，执行记录是"做完了给谁看"。**拆开任何一刀，剩下的半边都无法独立验收**——技能不能跑等于空壳，任务没技能无从下手，运行时没有产物留存等于没做完。

这个包也是 XOps 里**唯一允许模型参与的地方**。G8 把系统劈成两半：

| 平面 | 做什么 | 用什么 |
|---|---|---|
| **确定性平面** | 账本、审批、审计、权限 | 确定性代码，不用模型 |
| **分析平面** | 代码与文档分析、报告生成 | **Agent + 技能（本包）** |

**两个平面之间的隔离是硬要求：分析平面不得写确定性平面的任何数据。** 否则模型就能写证据与缺陷账本，前面所有纪律在服务端被绕过。

**这条隔离是本包最重要的需求，比"能跑起来"重要。** 一个能跑但能越界写账本的运行时，比一个跑不起来的运行时危险得多。

### 关于 dsh 的边界（D8）

> **dsh 是一个被驱动的独立 Agent，XOps 不是它的附属。**

XOps 与 deepseek-harness 之间是**进程／服务边界**，XOps 处在驱动方的位置。**明确排除**"把 XOps 写成 dsh 的 Cordis 插件、让 XOps 活在 dsh 的运行时里"这条路——那会让 XOps 的生命周期、构建体系与升级节奏全部绑死在一个仍处于 `0.1.0-rc`、明确预告会有破坏性变更的框架上。

具体驱动机制（子进程调 headless profile，还是 ACP 协议驱动常驻进程）是 **Q2**，专项讨论。因此下面所有需求条目都写成**对能力的要求**，不对实现形态做任何假设——这也意味着**执行引擎必须是可替换的**：如果哪天 dsh 不合适了，换掉它不应该动本包的任何需求。

## 范围

### 包含

- 技能的创建、版本化、生命周期（上传不执行 → 测试 → 发布 → 停用）
- 任务定义：引用技能、输入参数、目标仓与修订、执行策略
- 手动触发
- Agent 执行运行时：排队、调度、隔离、资源限制、超时、终止
- 模型凭据注入（平台级，D6）
- 执行记录与产物（Markdown）的存储与查询
- 技能视图、任务视图、执行历史与产物视图

### 不包含

- **自动触发**（定时、Git Hook、MCP 触发）——归 RP-07。本包只做手动。
- **代码仓的绑定与工作区实现**——归 RP-03。本包只消费它提供的只读工作区。
- **HTML 产物**——D9 明确推迟。
- **成本约束与额度限制**——D10 明确不做。
- **判断产出质量**——不做。产出好不好由人看（G8）。
- **任务之间的依赖编排**——明确不做，见"风险与待定"。

## 需求条目

### 技能

| ID | 需求 |
|---|---|
| R-04-01 | 技能归属项目，由项目成员通过 MCP 创建（G1）。 |
| R-04-02 | 技能有稳定标识与人类可读名称；名称在项目内唯一。 |
| R-04-03 | 技能内容**版本化且已发布版本不可变**。修改产生新版本。 |
| R-04-04 | 技能声明其**输入契约**：需要哪些参数、类型、是否必填。契约必须是**可机读**的，否则任务无法校验自己提供的输入。 |
| R-04-05 | 技能声明其**产出格式**。MVP 及其后一段时间只支持 Markdown（D9）。 |
| R-04-06 | 技能声明它是否需要**读取代码仓**以及需要哪个绑定。**不声明需要代码仓的技能，执行时不得获得任何工作区访问。** |
| R-04-07 | 技能声明其**预计执行时长上限**；未声明时用平台默认值。 |
| R-04-08 | 技能状态至少包含：草稿、已发布、已停用。 |
| R-04-09 | **上传不执行。** 草稿状态的技能不会被任何自动触发路径执行。这条防的不主要是别人，是作者自己——一份还没试过的技能被自动跑起来，浪费算力，产出没人信的报告。 |
| R-04-10 | 技能必须经过至少一次**成功的测试执行**才能发布。测试执行由作者手动发起，在与正式执行**相同的沙箱**中进行。 |
| R-04-11 | 发布只需项目成员权限，**不经过审批流程**。技能影响的是它自己那份分析与报告，不改变任何团队的 Agent 行为，也不扩大作者本来就有的只读范围。 |
| R-04-12 | 已发布的技能可停用；停用后不再被触发，历史执行记录完整保留。 |
| R-04-13 | 技能内容是**不可信输入**（G7）。平台不解析其语义、不因其内容改变控制流，只负责交给执行环境。 |

### 任务

| ID | 需求 |
|---|---|
| R-04-14 | 任务归属项目，由项目成员通过 MCP 创建。 |
| R-04-15 | 任务引用一个**已发布**的技能。引用草稿技能被拒绝。 |
| R-04-16 | 任务声明技能版本策略：**固定版本**或**跟随最新发布版**。**默认固定版本**——跟随最新意味着技能作者一次发布会改变所有引用它的任务的行为，这应当是明确选择而不是默认。 |
| R-04-17 | 任务提供的输入参数必须满足技能的输入契约（R-04-04）。不满足时创建失败并指明缺哪个参数。 |
| R-04-18 | 若技能声明需要代码仓，任务必须指定使用项目的哪个绑定及目标修订范围。 |
| R-04-19 | 任务可被启用与停用。停用的任务不响应任何触发，包括手动。 |
| R-04-20 | 任务声明**重叠策略**：上次执行未结束时又被触发，是**跳过本次**、**排队等待**、还是**终止上次并重跑**。**默认跳过**——定时任务最常见的故障是执行变慢后堆积成雪崩。 |
| R-04-21 | 任务声明单次执行的**超时上限**；未声明时用平台默认值。 |
| R-04-22 | 任务可声明失败重试次数与间隔。**默认不重试**——一个会读代码、调模型、产出报告的任务，盲目重试的代价不小且很少有用。 |

### 手动触发

| ID | 需求 |
|---|---|
| R-04-23 | 项目成员可通过 MCP 手动触发任务，**立即得到执行标识，不阻塞等待完成**。 |
| R-04-24 | 触发前检查：任务存在、已启用、允许手动触发。任一不满足则拒绝并留痕。 |
| R-04-25 | 触发受重叠策略约束（R-04-20）。**被跳过的触发必须留痕**——一个静默被跳过的任务，会让人以为它在跑。 |
| R-04-26 | 每次触发记录触发方式与触发者身份（G5），传递给执行记录。 |

### 隔离与边界（最高优先）

| ID | 需求 |
|---|---|
| R-04-27 | **执行中的 Agent 不得写入确定性平面的任何数据**（G8）：不得创建/修改项目、成员、角色、技能、任务、审批实例与决策、审计事件。 |
| R-04-28 | 这条边界必须由**能力封锁**实现，**不得依赖技能内容中"没有要求做这些事"**。Agent 手里只有本次执行该有的工具，没有别的。 |
| R-04-29 | Agent 可用的工具集由本次执行的技能声明决定，未声明的能力一律不提供。特别地：未声明需要代码仓的技能，其执行环境中**不存在任何工作区**。 |
| R-04-30 | 一次执行只能触及**一个项目**的资源。跨项目访问在环境层面不可能，而不是被检查后拒绝。 |
| R-04-31 | 执行环境之间相互隔离：一次执行不得读取、影响另一次执行的文件系统、进程或网络状态。 |
| R-04-32 | 模型凭据、代码仓凭据、平台令牌**不得进入 Agent 可读的上下文**。凭据只在确定性代码控制的边界内使用。 |
| R-04-33 | 执行环境的对外网络访问受限。默认只允许访问模型服务与已绑定的代码仓地址，其余出站默认拒绝。 |
| R-04-34 | Agent 对工作区的写入不回流仓库，且执行结束后销毁。 |
| R-04-35 | **执行环境中不提供触发任务的能力**，防止自触发回路（与 RP-07 的 R-07-21 呼应）。 |

### 执行

| ID | 需求 |
|---|---|
| R-04-36 | 执行是**后台异步**的。 |
| R-04-37 | 执行状态至少包含：排队中、执行中、已完成、已失败、已超时、已取消。 |
| R-04-38 | 超过超时上限时强制终止，状态为已超时，**已产生的部分输出仍被保留**——一份跑了一半的报告通常仍有诊断价值。 |
| R-04-39 | 执行可被有权限的人手动取消，部分输出保留。 |
| R-04-40 | 并发执行数有上限，按平台与项目两级控制，防止单个项目耗尽全部算力。 |
| R-04-41 | 失败原因被**分类**记录：技能错误、凭据错误、仓库拉取失败、模型服务错误、超时、资源不足。**"失败了"不是一个可用的结论。** |
| R-04-42 | 执行引擎必须是**可替换的**：更换底层 Agent 引擎不应改变本包的任何需求条目（D8）。 |
| R-04-43 | 模型凭据是**平台级统一配置**（D6），沿用 dsh 的凭据方案，一套配置服务全部项目。凭据变更不需重启服务，且不影响在途执行。 |

### 执行记录与产物

| ID | 需求 |
|---|---|
| R-04-44 | 每次执行产生一条**独立记录，永不被后续执行覆盖**。 |
| R-04-45 | 执行记录包含：执行标识、所属任务、触发方式与触发者、**实际使用的技能版本**、**代码仓与确切修订**、输入参数、开始/结束时间、最终状态、失败分类。 |
| R-04-46 | 执行记录在其任务被修改或停用后仍完整保留。 |
| R-04-47 | 产物内容一经写入不可修改。需要更正就重新执行。 |
| R-04-48 | 部分完成的执行（超时、取消、失败）已产生的产物仍被保留并可读，且**明确标注该产物来自未正常完成的执行**。 |
| R-04-49 | 产物被标注为**不可信内容**：它由模型生成，可能包含任意文本与标记。这个标注从存储到呈现不得丢失。 |
| R-04-50 | 单次执行的产物有体量上限，超限时截断并**明确标注被截断**，不静默丢弃。 |
| R-04-51 | 保留执行的过程记录，至少包含原始输出流，供失败时排查。**过程记录中不得出现任何凭据。** |
| R-04-52 | 执行记录、产物、过程记录三者的保留期可以不同——过程用于排查，结论用于回看，价值衰减速度不同。 |

### 视图（只读）

| ID | 需求 |
|---|---|
| R-04-53 | 技能视图：列表、状态、版本历史与内容。 |
| R-04-54 | 任务视图：列表、状态、配置。 |
| R-04-55 | **执行历史视图：同一任务连续多次执行，按时间倒序，含状态与产物入口。这是"查看任务每次执行的输出"这条需求的直接落点。** |
| R-04-56 | 单次执行详情视图：元数据、产物、过程记录。 |
| R-04-57 | **Markdown 产物渲染时禁用内联 HTML 与脚本**，只渲染受限标记子集；外部资源引用被明确标注为外部且不自动加载。 |
| R-04-58 | 提供产物的原始形式下载，供不信任渲染的人自行查看。 |
| R-04-59 | 视图上不存在任何写入操作（G2）。 |

## 数据与不变量

- **I-04-1**：不存在任何从执行环境写入确定性平面的代码路径。
- **I-04-2**：Agent 上下文中不含任何凭据。
- **I-04-3**：一次执行的资源可见范围完全由其项目归属与技能声明决定，不存在隐式扩权路径。
- **I-04-4**：每次执行都能追溯到确切的技能版本与代码修订。
- **I-04-5**：执行环境在结束后被完整销毁，不留残留状态。
- **I-04-6**：已发布的技能版本不可变；未经测试执行的技能不可发布。
- **I-04-7**：执行记录与产物一经写入不可变，且永不因任务变更而丢失。
- **I-04-8**：产物在系统内始终携带"不可信内容"标记。

## 验收标准

**隔离必须被主动攻击验证，不能只做正向测试。**

- 写一个**故意越界**的技能：尝试创建业务对象、修改项目成员、读另一个项目的资源、读环境变量里的凭据、访问未授权外网地址、触发另一个任务。**每一项都必须失败**，且失败发生在能力层（工具不存在／网络不通），**不是靠内容检查拦下的**。
- 未声明需要代码仓的技能，其执行环境中确实没有任何工作区文件。
- 检查执行的完整上下文与过程记录：**不含任何凭据原文**。
- 两次并发执行互相不可见（各自写同名文件互不干扰）。
- 执行结束后检查宿主：无残留进程、无残留工作区。

**功能验收**

- 创建技能后状态为草稿；草稿技能无法被触发。
- 未经测试执行直接发布被拒绝；完成一次测试执行后发布成功。
- 发布 v1 后修改产生 v2，v1 内容不变，已有执行记录仍指向 v1。
- 引用草稿技能创建任务被拒绝；缺少契约必填参数时创建失败并指明缺哪个。
- 停用任务后手动触发无效。
- 手动触发返回执行标识且**不阻塞**；上次未结束时的触发按重叠策略被跳过且留痕。
- 同一任务连续执行五次，五条记录全部保留，产物互不覆盖。
- 修改任务配置后，此前五条记录的元数据仍是当时的值。
- 超时的执行被终止、状态为已超时、部分产物可读且带"未正常完成"标注。
- 六类失败原因各构造一次，分类正确。
- 产物超过体量上限时被截断并标注。
- **构造一份含恶意内容的 Markdown 产物**（内联脚本、事件处理属性、外部资源引用），在 Web 上打开：**脚本不执行、外部资源不自动加载、会话不泄露**。这条必须实际构造并验证，不能只做代码审查。

## MVP 子集

**以裁剪后的子集纳入 MVP。**

MVP 做到：
- 技能：创建、输入契约、产出格式、是否需代码仓、**草稿/已发布两态**、发布前必须测试执行成功、版本化
- 任务：引用已发布技能（**仅固定版本**）、输入参数、指定仓与修订、启停
- 手动触发（非阻塞 + 重叠策略默认跳过）
- 运行时：低并发、**全部九条隔离需求（R-04-27～R-04-35）**、超时终止、失败**三分类**（技能错误／基础设施错误／超时）
- 执行记录：每次一条永不覆盖、完整元数据、Markdown 产物、原始输出作为过程记录
- 视图：技能列表、任务列表、**执行历史列表**、单次执行详情与安全的 Markdown 渲染

MVP 可推迟：技能停用（R-04-12）、资源预期声明（R-04-07）、跟随最新版本策略、重试（R-04-22）、排队与终止重跑两种重叠策略、项目级并发配额（R-04-40 先做平台级）、结构化过程记录、多产物、保留期与清理（R-04-52）。

**不可裁剪——这是全部需求包里"不可裁剪"最多的一个**：R-04-09（上传不执行）、R-04-10（发布前必须测试过）、R-04-13、R-04-15、R-04-17、R-04-23（非阻塞）、R-04-25（跳过留痕）、**R-04-27～R-04-35 全部九条隔离**、R-04-38（超时终止）、R-04-44、R-04-45、R-04-46、R-04-49、R-04-51（过程记录无凭据）、**R-04-57（禁用内联 HTML）**、I-04-5（环境销毁）。

关于 R-04-57 特别提醒：**绝大多数 Markdown 渲染库默认开启内联 HTML。** MVP 只有 Markdown 产物，很容易顺手用默认配置就上线。而产物内容部分来自被分析的代码仓——**能往那个仓提交代码的人，就能影响产物内容**。这是产物渲染这条攻击链上唯一的那道门。

关于隔离：**如果 MVP 的时间压力大到做不完执行隔离，正确的做法是把整个包推迟、先交付 RP-01 + RP-02，而不是做一个隔离不全的执行运行时。** 先跑起来再补隔离，等于在补上之前一直敞开，而这段时间里跑过的技能、读过的代码、泄过的凭据都无法追回。

## 内部工作包建议

这个包在 XForge 里应当是**一次 Major Change**，内部按下面的 DAG 拆工作包：

```text
WP-A 技能资产（创建、版本化、生命周期状态、声明契约）
        │
        ├──► WP-B 任务定义（引用技能、参数校验、执行策略）
        │            │
        │            ▼
        │       WP-C 手动触发与执行队列（非阻塞、重叠策略、留痕）
        │            │
WP-D 执行沙箱与隔离  │      ← 可与 WP-A/B 并行开工，是本包的关键路径
（能力封锁、网络、凭据边界、环境销毁）
        │            │
        └────────────┴──► WP-E Agent 运行时接入（驱动 dsh，Q2 定形态）
                                 │
                                 ▼
                          WP-F 执行记录与产物存储
                                 │
                                 ▼
                          WP-G 只读视图（含安全 Markdown 渲染）
```

**WP-D 是关键路径，建议最先开工**：它的隔离强度取决于 Q3，而它一旦定型，WP-E 的接入形态才有边界可依。WP-A 与 WP-D 可并行。

## 风险与待定

- **Q2：dsh 的驱动机制。** D8 已排除插件嵌入，剩下两条：**子进程调 headless profile**（`dsh --profile headless "<任务>"`，进程隔离天然、超时可杀、dsh 升级不拖垮 XOps，代价是拿不到细粒度中间事件）与 **ACP 协议驱动常驻进程**（`packages/acp`，有流式事件又保持进程隔离，但 ACP 面的成熟度要先验）。两者都符合 D8。**专项讨论。**

- **Q3：沙箱的隔离强度需要明确到可验收。** R-04-27～R-04-35 说的是"要隔离什么"，没说"隔离到什么强度"——目录级、进程级、容器级还是虚拟机级。D7 的"不开放注册"把威胁模型降低了（用户是受控的、可追责的），但技能仍会读代码仓、调模型、访问网络，误伤与横向影响仍需防。**在 Q3 有答案之前，验收标准里那条"主动攻击验证"是唯一能挡住偷工减料的东西，不要删。**

- **dsh 处于 rc 阶段是真实的时间风险。** README 明确写了"未来将出现破坏兼容性的变更"。D8 的进程/服务边界正是对这条风险的直接对冲，而 R-04-42（引擎可替换）是这条对冲在需求层的表达——**实现时不要让 dsh 的概念泄漏进本包的领域模型**。

- **技能的内容形态未定**（Markdown 提示词、结构化步骤定义、还是 dsh 的某种资产形式）。与 Q2 强耦合，属于设计选型。需求侧唯一的硬约束是 R-04-04：**输入契约必须可机读**。

- **R-04-10 里的"测试执行成功"怎么判定？** 技能执行完成不代表结果有用。建议 MVP 只要求"执行完成且未报错"，由作者自己看产出决定是否发布——**不要试图自动判断产出质量**，那是判断题（G8）。

- **R-04-33 的网络限制与技能的实际需要可能冲突。** 一个"查询依赖库有没有已知漏洞"的技能需要访问外部数据源。**建议在技能声明里增加"需要访问哪些外部地址"走白名单**，而不是放开默认出站。这条等 Q3 定了一起加。

- **任务编排明确不做。** 一旦支持"任务 A 完成后触发任务 B"，就需要 DAG、依赖解析、失败传播、循环检测及其可视化——这正是"不长成平台"那条边界要拦住的东西。需要串联就在一个技能内部完成多步。**建议写死。**

- **执行历史的对比视图不做。** "怎么对比两次报告"依赖产物结构，而产物是自由文本。**想要趋势就写一个读取历史执行结果的技能**，让它自己产出趋势报告。平台提供机制，不规定内容。

- **删除任务的语义**：I-04-7 要求执行记录不丢，所以"删除"实际只能是停用+隐藏。**建议不提供删除，只提供停用**——少一个会让人误以为数据没了的操作。
