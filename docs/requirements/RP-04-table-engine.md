# RP-04 表引擎

> 一切数据落表 · 三种表 · 穷举列类型 · 对外 CRUD 对内追加 · 表专属 tool 派发

## 归属与依赖

- **依赖**：RP-01 存储与写串行（写入路径与四步区间）、RP-03 MCP 基座（注册骨架）。
- **被依赖**：RP-05、RP-10、RP-12、RP-14、RP-15、RP-16、RP-17、RP-18——**几乎所有后续包**。
- **里程碑**：M1。
- **独立性**：做完这个包，XOps 就是一个 **agent 友好的、可审计的记录系统**：经 MCP 建表、写行、查行、查单行历史。**这本身就是个能用的东西**，即使一行技能都还没跑过。

## Crate 归属

| crate | 本包是否新建 | 对外只经什么被用 |
|---|---|---|
| `xops-table` | **新建** | 表定义的读写 · 行的读写（经专属 tool）· 单行历史查询 |

**本包在 `xops-store` 的串行执行器上工作，不自己实现锁；在 `xops-mcp` 的注册骨架上派发 tool，不自己起服务。**

## 背景与价值

**一切数据落表。** 缺陷、待办、审批记录、任务输出，全是表的行。平台一张业务表都不预置——这是 P2 在数据面的兑现。

本包认领一块**事后补等于回填全部历史行**的东西，所以它必须在 M1：

> **平台自动补的列位**（`TBL-014`：`writtenBy` / `at` / `revision` / `_instance` / `retainUntil`）。这些是写入时就要落的列。事后补，等于回填全部历史行——而 `writtenBy` 的"执行"与"插件求值"两种取值**必须自包含**（内联任务所有者、技能版本、代码修订），回填时那些信息可能已经随 `_runs` 到期清理掉了。

还有一条纪律在这里兑现：**`MCP-005` 的表专属 tool 派发**。"任意表 CRUD"看起来像是对窄接口纪律的破例，其实不是——每张表建好后派发一组由它自己的 schema 生成的固定形状 tool，**不存在 `{table, values}` 这种通用写 tool**。这条一松，整个操作面就退化成通用透传。

> ⚠️ **上一版这个包（十二包版的 RP-02「表引擎」）同时包含 CON（写串行）与 TPL（模板机制）两块，42 条、24,858 行、46 小时。本版把 CON 拆去 RP-01、TPL 拆去 RP-18**，本包只剩 TBL 的 26 条。**但不要因此以为它变小了**——那 46 小时里很大一部分是"从零建一个新包"的固定成本，而本版每个包都是从零建的（README §3）。

## 范围

### 包含

- 建表（声明列、**声明保护级别**）、加列、查表结构、列出项目的表、软删表
- **三种表**（系统表 / 用户表 / 受保护表）与**五张系统表的 schema 定义**
- **穷举的列类型**，含派生文本列、自增序号列、行引用列
- 对外 CRUD、对内追加、软删除、**单行完整历史**
- 每张表的**专属增删改查 tool** 的派发（落在 RP-03 的注册骨架上）
- **平台自动补的来源字段**（`writtenBy` 四种取值且自包含 · `at` · `revision` · `_instance` · `retainUntil`）
- 不做的三件：表间关联 / 行级权限 / schema 迁移

### 明确不包含

- **写串行与四步区间**——归 RP-01。本包**使用**它，不实现它。
- **流程节点求值与插件写回**（区间的 ③④）——归 RP-15 与 RP-16。
- **系统表的写入方**——`_runs` 归 RP-12、`_flows`/`_flow_nodes` 归 RP-14、`_plugins` 归 RP-16、`_notices` 归 RP-17。**本包只定义它们的 schema 与"只有平台能写"这条规则。**
- **保留期的取值与清理作业**——归 RP-12。本包只负责 `retainUntil` 这个**列位的存在与写入时的自动补齐**。
- **看板与读模型**——归 RP-05。
- **模板**——归 RP-18。

## 关键不变量

`I-B`（`writtenBy` 不来自请求体）· `I-D`（事件不可变；当前视图是缓存不是权威；任一行可查完整历史）· `I-N`（不存在只改视图不写事件的路径）· `I-P`（`_instance` 与状态列是受保护列——**本包负责"列位受保护"这件事，谁能写它归 RP-15**）· `I-Q`（名单表只有所有者能写；保护级别不可降级）。

## 接口面

**MCP tools**：建表 · 加列 · 查询表结构 · 列出项目的表 · 删表 · **每张表的专属增删改查 tool** · 查询单行完整历史。

**对内提供**：

```text
schema 校验回调  —— 注入给 RP-01 四步区间的 ①
行的读接口       —— 给 RP-05 的读模型、RP-16 的输出插件读表能力
自动补列的写入点 —— 给 RP-12（retainUntil）、RP-15（_instance）
```

**契约元素**（基线在 [`../contracts/`](../contracts/README.md)，正文由本包自己的变更逐条添加）：


## 验收标准

- **不存在通用写 tool**：枚举全部已派发的 tool，**每一个的输入 schema 都是由某张表的 schema 生成的固定形状**；不存在 `{table, values}` 形状的写 tool。
- **建表即派发、删表即停派**：建一张表后它的专属 tool 立刻出现在能力发现里；软删后停止派发，**但行与事件仍在、单行历史仍可查**。
- **表名不可复用**（`TBL-026`）；被流程引用为结算表或主体表的表**不能删**。
- **自动补的列位**：任何写入路径产生的行都带 `writtenBy` / `at`，且 `writtenBy` 的四种取值**都自包含**——特别是"某次执行"要内联任务所有者、技能版本、代码修订，**不能只存一个指向 `_runs` 的指针**（因为那行会到期被清理）。
- **列声明不能覆盖自动补的字段**：建表时声明一个叫 `writtenBy` 的列，被拒绝。
- **没有 json 列类型**：枚举列类型集合，**不含任意对象**。
- **派生文本列**：insert 时生成一次，之后 update 写不了它。
- **自增序号**：项目内、每表独立。
- **单行历史**：任一行都能查出它的完整历史（谁、何时、改了什么）。
- **加列可以，改类型/删列/改列名不做**：三者都被拒绝，且错误信息指向"新建一张表自己搬"。
- **保护级别不可降级**：把受保护表改成普通表，被拒绝。

## 内部工作包建议

一次 **Major Change**：

```text
WP-A 表定义（列类型全集、三种表、保护级别、五张系统表的 schema）
        │
        ├──► WP-B 事件追加与投影、软删除、单行历史（落在 RP-01 的区间上）
        │            │
        ├──► WP-C 表专属 tool 的派发（schema 生成、能力发现、按角色裁剪）
        │            │
        │            ▼
        └──────► WP-D 平台自动补的列位（writtenBy 自包含、at、revision、
                      retainUntil / _instance 的列位）
```

**WP-D 不能后置。** 它是"事后补等于回填全部历史行"的那一块。

## 风险与待定

- **`writtenBy` 的自包含要求是最容易被做浅的一条。** 直觉写法是存一个执行 ID 然后回查——而那条 `_runs` 行会到期清理（RP-12 的 `RET-*`）。**一个月后还要能回答"这一票是谁的"，靠的就是这里内联的任务所有者。**
- **WP-C 与 RP-03 的注册骨架是本包最重的一处接缝**：动态生成的 schema、随建表增减的 tool 集合、跟着变的能力发现。**这三件要在 RP-03 的 WP-B 设计时就问清楚形状**，不要等到这里才发现骨架不够用。
- **`_instance` 与状态列的"受保护"在本包只是列位**：谁能写它、什么时候填，归 RP-15。**两个包对这个列位的理解必须一致**，建议在 RP-04 完成时就把 RP-15 要用的写入路径签名定下来。
