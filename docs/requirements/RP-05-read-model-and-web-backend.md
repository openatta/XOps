# RP-05 读模型与只读 Web 后端

> 读模型是前后端唯一的契约 · 后端不存在写路由 · 可见性遵循项目边界

## 归属与依赖

- **依赖**：RP-04 表引擎（要有表可读）、RP-02 身份与项目（可见性与会话）。
- **被依赖**：RP-06 Web 前端（**只依赖读模型契约**）、RP-17 通知（个人看板长在这套读模型上）、RP-13 自动触发（webhook 端点落在同一个 HTTP crate 里，**但在 M3，不并行**）。
- **里程碑**：M1。
- **独立性**：薄包。做完即可验收——建一张表、写几行、定义一个看板，**用 curl 就能把它读出来**，并且**枚举后端路由，不存在任何写路由**。

## Crate 归属

| crate | 本包是否新建 | 对外只经什么被用 |
|---|---|---|
| `xops-read` | **新建** | **读模型**：看板视图、单行历史、长文本原文。这是 Web 唯一的查询契约 |
| `xops-web` | **新建** | 只读 HTTP 服务 · 会话 · 静态资源托管 |

> ⚠️ **`xops-web` 会被 RP-13 再动一次**（加 webhook 端点）。**两者不并行**：本包在 M1，RP-13 在 M3。这是本版拆分里两处"同目录"风险点之一（README §4）。

## 背景与价值

**Web 是观察窗，不是控制台。** 这个包的全部价值在两条纪律上，而两条都是"很容易顺手破掉"的那种。

**第一条是 G2，本版把它拆成了两道且顺序不能反**（`BRD-005`）：

| 道 | 谁兜 | 强度 |
|---|---|---|
| **① 后端不存在写路由** | **本包** | **结构性的**。前端就算想写也没有地方可发 |
| ② 前端不存在调用写接口的代码路径 | RP-06 | 纪律性的。用 CI 兜住"就加一个按钮"的压力 |

> **只有 ② 没有 ①，等于把一条安全属性交给前端自觉。** 这就是本版把前后端拆成两个包、并把 ① 放在后端包里的原因——上一版它们在同一个包里，两道界限容易糊成一道。

**第二条是本包存在的另一半理由：读模型是前后端唯一的契约。**

```text
前端不直连库、不拼查询、不调 MCP
读模型定型 → 前端就能对着它开工，不必等后端把查询实现完
```

这是把前后端拆开的**全部收益**：上一版它们在同一个包里，前端只能等。

看板本身刻意做得很薄：**一张表的一个视图**（显示哪张表、按什么筛选、按什么排序、显示哪几列）。

## 范围

### 包含

- **读模型的定义**（本包最先要定型的东西）：表视图 · 单行历史 · 长文本原文
- 看板的定义、查询、列出（**定义本身经 MCP**，注册在 RP-03 的骨架上）
- 只读 HTTP 服务：路由、会话、静态资源托管
- Web 的身份展示与**可见性边界**（完全遵循项目成员边界）
- **Web 会话凭据与 MCP 令牌互不通用**（`I-L`）
- `_notices` 不允许建自由看板这条约束（`BRD-004`）

### 明确不包含

- **任何渲染**——归 RP-06。本包交出的是数据，不是 HTML。
- **安全 Markdown 渲染**（`BRD-008`/`009`）——归 RP-06。**本包只保证能拿到长文本的原文**（`BRD-010` 的下载也在 RP-06 的页面上，数据由本包给）。
- **个人看板**——归 RP-17。它是 `_notices` 上属于我的行，且是**平台内建的固定视图**。**本包不得先做一个"简化版通知页"顶上。**
- **任何写入**——包括"标记已读"，那是一次 MCP 调用（`NTF-009`）。
- **webhook 端点**——归 RP-13，虽然它落在同一个 crate 里。
- **任何图表、指标、聚合、跨表 join**。

本包认领 [`requirements.md`](requirements.md) 的 **5 条**。**条目正文以 `requirements.md` 为准**，下表只是索引与一句话摘要。

### BRD 看板与 Web（5 条）

| ID | 摘要 |
|---|---|
| `BRD-001` | 看板 = 一张表的一个视图：显示哪张表、按什么筛选、按什么排序、显示哪几列。 |
| `BRD-004` | _notices 不允许建自由看板（NTF-009）。 |
| `BRD-006` | 一个主体的"完整时间线"横跨两张表：状态怎么变的、谁改的、什么时候，在主体行的单行历史里；为什么这么变、谁表的态，在同实例的全部结算行里。 |
| `BRD-007` | Web 会话凭据与 MCP 令牌互不通用；Web 会话不能用于任何写操作（I-L）。 |
| `BRD-011` | Web 的可见性完全遵循项目成员边界，并明确展示当前用户身份。 |

## 关键不变量

`I-L`（Web 会话凭据与 MCP 令牌互不通用；Web 会话不能用于任何写操作）· `G2`（本包负责它的第①道）· `G4`（可见性按项目判定）。

## 接口面

**MCP tools**：定义看板 · 查询看板 · 列出看板。

**只读 HTTP**：表视图（按看板定义）· 单行历史 · 长文本原文。

**对内提供给 RP-06**：**读模型契约**——这是前端唯一能看见的东西。

## 验收标准

- **枚举后端路由：不存在任何写路由。** 不是"有但不给 Web 用"，是不存在。**这条要用路由表枚举来证明，不是靠代码审查。**
- **拿一个 Web 会话凭据去调 MCP**：不通用。反过来也不通用。
- **Web 会话不能用于任何写操作**：构造一次带会话凭据的写尝试，失败。
- **非成员访问某项目的看板**：与项目不存在时表现一致（承接 RP-02 的同一条纪律）。
- **一个主体的时间线是两个视图**：主体行的单行历史与结算行列表**分别查**，页面上没有把它们 join 起来的后端查询（`BRD-006`）。
- **`_notices` 建不了自由看板**：尝试为它定义看板，被拒绝。
- **读模型的完备性**：RP-06 需要的每一样数据都在读模型里，**前端不需要第二条数据通路**。

## 内部工作包建议

一次 **Solid Change**：

```text
WP-A 读模型定型（本包第一件事，定完 RP-06 即可并行开工）
        │
        ├──► WP-B 看板定义的 MCP tools（落在 RP-03 骨架上）
        │
        └──► WP-C 只读 HTTP：路由、会话、可见性、静态资源托管
```

**WP-A 必须最先完成，并且要与 RP-06 一起评审。** 它一定型，前端就不必等了——**这是本包拆出来的全部收益，做丢了就白拆了**。

## 风险与待定

- **"就加一个写接口"是这个包持续的压力来源。** 建议把"后端无写路由"写成项目的 XForge Rule，并在 CI 里做路由表枚举——**页面上出现任何写操作，应当在评审阶段被拦下**。
- **读模型定得太薄，前端会绕过它**（自己去调 MCP 或直接读表）。定型时要**由 RP-06 的页面清单反推**，不要凭想象定。
- **`xops-web` 会被 RP-13 再动一次。** 本包在设计路由层时就要给"一个非 MCP 的 POST 端点"留出位置，**但不要提前实现它**——留位置和留一个空路由是两件事。
