# RP-06 审批引擎

> 流程定义 · 审批点 · 实例与决策 · 待办视图

## 归属与依赖

- **依赖**：RP-01 平台基座。**除此之外不依赖任何包。**
- **被依赖**：RP-07 XForge 审批 Provider 适配。
- **独立性**：完全独立的纵向切片。做完即可验收：定义一条流程、发起一次审批、有人做决策、在 Web 上看到待办与决策时间线。

## 背景与价值

D1 定了：**审批做成通用引擎**，不是只为 XForge 定制的一根管子。

流程定义与实例决策合在一个包里，是因为它们**无法各自独立验收**——只有定义没有实例，等于产出了一堆没人用的配置；只有实例没有定义，实例不知道该按什么走。

这个包要守住的核心性质有两条。

**第一条，判定权始终在人手上。**

> Agent 负责提交、结构化、通知，**不负责决定通过与否**。模型没有立场也没有记忆，把裁决交给它，等于把这套设计唯一守得住的那个点让出去。

**第二条，审批天然是异步的，因此必须幂等。**

发起方会反复来问"批了没有"，也可能因为网络重试而重复发起。如果重复发起会开出第二个审批单，人就会看到两个一模一样的待办，批了其中一个另一个还挂着，账本立刻失去可信度。XForge 那侧已经把答案给出来了，本包把它一般化：

> **任何审批实例都由一个"治理摘要"标识，重复发起是空操作。**

还有一条边界要记住：**审批点是"谁的判断可以拦住什么"，不是"这个单子流转到哪一步了"。** 这个区别决定了这个包会长成一个治理机制，还是长成一个工单系统。

## 范围

### 包含

- 流程定义：审批点的组成、角色绑定、成立条件、串并行
- 流程定义的版本化与停用
- 审批实例：发起、幂等、审批点激活、成立判定
- 决策：通过／拒绝、责任记录、有效期
- 实例终态与取消
- 待办查询与审批视图

### 不包含

- **XForge 两个固定 tool 的形状与回执语义**——归 RP-07。
- **条件分支与表达式引擎**——明确不做，见"风险与待定"。
- **通知投递**——归 RP-09。本包只产生"有新待办"这个事实。
- **在 Web 上做决策**——G2。页面告诉你该批什么，决策动作走 MCP。
- **代替人做决定**——G8。任何自动通过、超时默认通过的机制都不在范围内。

## 需求条目

### 流程定义

| ID | 需求 |
|---|---|
| R-06-01 | 流程定义归属项目，由所有者或维护者通过 MCP 创建（G1）。**流程的创建本身也是 MCP 操作，不存在流程设计器界面。** |
| R-06-02 | 一条流程由一个或多个**审批点**组成。审批点是流程的最小单元。 |
| R-06-03 | 每个审批点声明：允许决策的**项目角色**集合、需要的**最少决策人数**、是否要求这些人**互不相同**。 |
| R-06-04 | 审批点支持三种成立条件：**全票**、**法定人数**、**任一**。 |
| R-06-05 | 支持串行审批点（前一个成立后才激活下一个）与并行审批点组（同时激活，全部成立后才推进）。 |
| R-06-06 | 任一审批点出现**拒绝**时，整个流程立即终止为拒绝——**不提供"驳回到上一节点重来"的循环**。循环会把审批变成拉锯，而每一轮拉锯都需要新的对象修订才有意义，那本来就应该是一次新的审批。 |
| R-06-07 | 流程定义声明它适用于哪类被审批对象。 |
| R-06-08 | 流程定义**版本化且不可变**。修改产生新版本，不改动已有版本。 |
| R-06-09 | 已在运转中的实例，始终按其**发起时**的流程定义版本执行完毕，不受后续版本变更影响。 |
| R-06-10 | 流程定义可停用；停用后不能发起新实例，在途实例继续执行完。 |
| R-06-11 | 审批点绑定的是**项目角色**，不是具体的人。人员变动时流程定义不需要修改。 |
| R-06-12 | 若某审批点在实例发起时，项目内没有任何成员满足其角色要求，**发起立即失败**并明确指出是哪个审批点无人可批——**不允许创建一个永远不可能推进的实例**。 |
| R-06-13 | 支持声明**职责分离**约束：某审批点的决策人不得是被审批对象的发起人。 |

### 实例与幂等

| ID | 需求 |
|---|---|
| R-06-14 | 实例由发起方通过 MCP 发起，声明：目标项目、流程定义、被审批对象的标识与修订、**治理摘要**。 |
| R-06-15 | **治理摘要是幂等键。** 对同一治理摘要重复发起一律视为空操作，返回与首次相同的实例，**不得开出第二个实例**。 |
| R-06-16 | 治理摘要由发起方计算并提供，XOps **不解释其内容**，只把它当作不透明的唯一键使用。 |
| R-06-17 | 被审批对象的修订变化时，发起方会算出不同的治理摘要，因而自然产生新实例——旧实例**不因此自动失效**，但查询时可以看出它绑定的是旧修订。 |

### 决策

| ID | 需求 |
|---|---|
| R-06-18 | 决策只有两种：**通过**与**拒绝**。不存在"有条件通过"作为系统状态——条件是文字，属于决策附带的理由，不属于状态机。 |
| R-06-19 | 决策由人做出，通过 MCP 提交。决策人身份由令牌解析得出（G5），**不接受任何形式的代批声明**。 |
| R-06-20 | 决策人必须在该审批点绑定的角色内，且满足职责分离约束，否则拒绝该决策且**不产生任何记录**。 |
| R-06-21 | 决策**必须附带理由**。空理由被拒绝——一条没有理由的批准，在事后无法回答"当时基于什么"。 |
| R-06-22 | 决策是追加式记录（G3），已做出的决策不可修改、不可撤回。 |
| R-06-23 | 同一人在同一审批点只能做出一次决策，重复提交被拒绝。 |
| R-06-24 | 一旦任一审批点出现拒绝，整个实例立即进入拒绝终态，其余未激活的审批点不再激活。 |

### 状态与查询

| ID | 需求 |
|---|---|
| R-06-25 | 实例状态至少包含：进行中、已通过、已拒绝、已取消、已过期。 |
| R-06-26 | 实例的**"当前在等谁"必须可查询**——具体到审批点、所需角色、还差几人。这是发起方 Agent 与人共同需要的唯一一条状态信息。 |
| R-06-27 | 提供"该我批的待办列表"，**跨项目聚合**当前用户的全部待决审批点。 |
| R-06-28 | 发起方可取消自己发起的、尚未终结的实例。 |
| R-06-29 | 实例可设过期时间；过期后进入已过期终态，**绝不自动通过**。 |
| R-06-30 | 通过的决策可携带有效期。超过有效期后，该决策在下游消费方不再计入有效批准。 |
| R-06-31 | 全部发起、激活、决策、终态变化产生审计事件，可重建实例的完整过程。 |

### 审批视图（只读）

| ID | 需求 |
|---|---|
| R-06-32 | 提供"我的待办"视图，跨项目聚合。 |
| R-06-33 | 提供实例状态视图，含"当前在等谁"。 |
| R-06-34 | 提供单实例的完整决策时间线。 |
| R-06-35 | **视图上没有"批准/拒绝"按钮**（G2）。页面应当直接给出"在你的 Agent 里跑这条命令"，就像 XForge 的 `nextActions` 那样，而不是让用户自己猜。 |

## 数据与不变量

- **I-06-1**：流程定义版本一经发布即不可变；在途实例引用的版本必须始终可读。
- **I-06-2**：治理摘要在项目内唯一标识一个审批实例。
- **I-06-3**：决策记录只追加，永不改写。
- **I-06-4**：**不存在任何使实例在无人决策的情况下进入"已通过"的代码路径。**
- **I-06-5**：决策人一律来自令牌解析，不来自请求体。
- **I-06-6**：流程定义不含任何用户标识（只含角色）。

## 接口面

**MCP tools**

| 意图 | 说明 |
|---|---|
| 创建流程定义 | 一次性提交完整定义 |
| 发布流程新版本 | |
| 停用流程定义 | 不影响在途实例 |
| 校验流程定义 | 不落库，只回报是否合法、是否存在无人可批的审批点 |
| 查询项目流程定义 | 含各版本 |
| 发起审批实例 | 按治理摘要幂等 |
| 查询实例状态 | 含"当前在等谁" |

| 查询我的待办 | 跨项目聚合 |
| 取消实例 | 仅发起方 |

**只读视图**

- 流程定义列表与版本历史
- 审批实例列表与状态
- 单实例完整决策时间线
- 个人待办

## 验收标准

- 通过 MCP 创建一条含三个串行审批点的流程，查询能拿到完整结构。
- 创建一条绑定了项目内无人担任的角色的流程，发起实例时失败并指明具体审批点。
- 修改流程产生 v2 后，v1 发起的在途实例仍按 v1 走完。
- 停用流程后无法发起新实例，在途实例不受影响。
- 全票/法定人数/任一三种条件各构造一次，成立时机符合定义。
- **用同一治理摘要连续发起十次，只存在一个实例。**
- 三个串行审批点的流程，第一个点未成立时第二个点不接受决策。
- 并行审批点组中任一点被拒绝，整个实例立即终止，其余点不再接受决策。
- 无权角色提交决策被拒绝，且**不留下任何决策记录**。
- 同一人在同一点重复决策被拒绝。
- 空理由的决策被拒绝。
- 声明了职责分离的审批点，被审批对象的发起人无法在该点做出决策。
- **实例过期后状态为"已通过"以外的"已过期"。**
- 从事件流重建实例过程，与实时观察一致。
- Web 待办页面能看到待办，但**页面上没有任何批准/拒绝按钮**，且给出了该在 Agent 里跑的命令。
- **全程代码审查：不存在自动通过路径。**

## MVP 子集

**不纳入 MVP。**

理由：MVP 要证伪的两条命题（Skill 经 MCP 提交缺陷到账本、服务端 Agent 按技能产出报告）**审批一条都不碰**。它是全部包里最大的一块之一，放进 MVP 会让第一个可用版本显著推迟，而推迟期间学到的东西并不来自审批。

更实际的一条：**通用引擎的复杂度目前没有真实需求支撑。** XForge 侧的审批契约是固定的两个 tool，它对 XOps 内部有几个审批点、怎么串并行**一无所知也不关心**——它只问"这个 governingDigest 决定了没有"。通用引擎的全部复杂度，服务的是 XForge 之外的场景（缺陷关闭要不要批、技能发布要不要批），而这些场景现在一个都还不存在。

**若需要提前打通 XForge 联动**，有一条更短的路：本包只做**单审批点 + 任一成立 + 绑定固定角色 + 按治理摘要幂等 + 通过/拒绝含理由 + 待办查询**，跳过版本化、并行、会签、职责分离，然后接 RP-07。这会产生一次返工，但如果 XForge 联动的时间价值高，是划算的。

**即使是这个最小形态，R-06-15（幂等）、R-06-19（身份来自令牌）、R-06-21（必填理由）、R-06-29（过期不自动通过）、I-06-4 也不可省。**

## 风险与待定

- **超时自动通过：明确不做，并且建议永远不做。** 这类功能在传统审批系统里很常见，理由是"防止流程卡死"。但在这套设计里，审批的全部价值就是"有人的判断拦在这里"，**一个会自动放行的关卡等于没有关卡，而且比没有关卡更糟——它看起来像有**。R-06-29 因此规定过期走向"已过期"，卡死的流程应该被看见，不应该被绕过。

- **R-06-06 不做驳回循环**是一条有主张的取舍，值得你确认。传统审批系统普遍有"驳回到某节点"，去掉它会让习惯了传统流程的人不适应。理由写在条目里，但你可能有不同看法。

- **R-06-18 不设"有条件通过"**同样值得确认。跨仓协作设计里的验收判定是四档（通过/有条件通过/不通过/阻塞）。如果希望 XOps 承载那套判定，要么增加状态，要么由 RP-07 在适配层把四档映射成两档 + 理由文本。**倾向后者**：状态机越小越可靠，语义细节放在理由里由人读。

- **条件分支明确不做。** 一旦引入"金额大于 X 走这条、否则走那条"，就需要表达式引擎、求值上下文及其测试面，那是"长成平台"的第一步。将来真需要，用"不同流程定义 + 发起时选择"表达，把判断留在发起方。

- **职责分离（R-06-13）的判定依赖"被审批对象的发起人是谁"。** 对 XForge 的 transition 来说，作者集合在仓里，XOps 拿不到（也不该去拿，那需要仓库读权限与在线依赖）。**建议先只支持"决策人 ≠ 审批实例的发起人"**——这是 XOps 自己知道的事实。完整的作者集合比对留到有真实需求时再说。

- **三个固定角色够不够。** R-06-03 绑定的是 RP-01 的项目角色，而 XForge 侧可能需要 `verifier` 这类角色。这与 Q4 联动，见 RP-07。**建议不要为此把 RP-01 改成可配置角色系统**——在还没有真实审批场景时先付这笔复杂度不划算。
