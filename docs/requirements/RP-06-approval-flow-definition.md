# RP-06 审批流程定义

## 归属与依赖

- **依赖**：RP-02（流程归属项目、审批点绑定项目角色）、RP-03（流程的创建本身也走 MCP）。
- **被依赖**：RP-07（实例按定义运转）、RP-08（XForge 适配需要知道该走哪条流程）。
- **不做这个包会阻塞谁**：整个审批域。

## 背景与价值

D1 定了：**审批做成通用引擎**，不是只为 XForge 定制的一根管子。

这个决定值得把代价说清楚。只做 XForge provider 的话，这一整包不存在——XForge 自己定义"哪条 transition 需要几个什么角色的人批准"，XOps 只负责把请求排到某个人面前。做成通用引擎，意味着 XOps 自己要拥有流程模型：流程定义、审批点、串并行、会签、角色绑定、条件流转。**这是三个包里最大的一块，也是最容易长成"工单系统"的一块。**

守住它的办法是记住这个引擎服务于什么：

> **审批点是"谁的判断可以拦住什么"，不是"这个单子流转到哪一步了"。**

判定权始终在人手上。Agent 负责提交、结构化、通知，**不负责决定通过与否**——模型没有立场也没有记忆，把裁决交给它，等于把这套设计唯一守得住的那个点让出去。

用户还有一条明确要求：**流程的创建本身也通过 MCP 完成**（G1）。也就是说不存在一个"流程设计器"界面，流程由 Agent 按人的意图创建。

## 范围

### 包含

- 流程定义：一条流程由哪些审批点按什么结构组成
- 审批点：绑定哪些项目角色、需要几个人、是否要求不同人
- 流转结构：串行、并行、会签（全票/多数/任一）
- 流程定义的版本化
- 流程与被审批对象类型的绑定

### 不包含

- **具体某次审批的运转**——归 RP-07。本包只产出定义，不产出实例。
- **XForge 两个固定 tool 的形状**——归 RP-08。
- **条件分支与表达式引擎**——见"风险与待定"，MVP 明确不做。
- **看板式的流程可视化编辑**——G2，Web 只读。

## 需求条目

### 定义与结构

| ID | 需求 |
|---|---|
| R-06-01 | 流程定义归属于项目，由项目的所有者或维护者通过 MCP 创建。 |
| R-06-02 | 一条流程由一个或多个**审批点**按顺序组成。审批点是流程的最小单元。 |
| R-06-03 | 每个审批点声明：允许做出决策的**项目角色**集合、需要的**最少决策人数**、以及是否要求这些人**互不相同**。 |
| R-06-04 | 审批点支持三种成立条件：**全票**（所有指定角色的成员都要通过）、**法定人数**（达到最少人数即成立）、**任一**（一人通过即成立）。 |
| R-06-05 | 支持串行审批点（前一个成立后才激活下一个）与并行审批点组（同时激活，全部成立后流程才推进）。 |
| R-06-06 | 任一审批点出现**拒绝**决策时，整个流程立即终止为拒绝——不提供"驳回到上一节点重来"的循环。**这是有意的**：循环会把审批变成拉锯，而每一轮拉锯都需要新的对象修订才有意义，那本来就应该是一次新的审批。 |
| R-06-07 | 流程定义声明它适用于哪类被审批对象（例如：XForge 的 stage transition、缺陷的关闭、任务的发布）。 |

### 版本与生效

| ID | 需求 |
|---|---|
| R-06-08 | 流程定义是**版本化且不可变**的。修改流程产生新版本，不改动已有版本。 |
| R-06-09 | 已经在运转中的审批实例，始终按其**发起时**的流程定义版本执行完毕，不受后续版本变更影响。 |
| R-06-10 | 流程定义可以被停用；停用后不能发起新实例，但在途实例继续按原定义执行完。 |
| R-06-11 | 流程定义的创建、发版、停用全部产生审计事件（RP-04）。 |

### 角色绑定

| ID | 需求 |
|---|---|
| R-06-12 | 审批点绑定的是**项目角色**，不是具体的人。人员变动时流程定义不需要修改。 |
| R-06-13 | 若某审批点在实例发起时，项目内没有任何成员满足其角色要求，发起立即失败并明确指出是哪个审批点无人可批——**不允许创建一个永远不可能推进的实例**。 |
| R-06-14 | 支持声明**职责分离**约束：某审批点的决策人不得是被审批对象的发起人/作者。这是跨仓协作设计里"验收者 ≠ 实现者"那条不变量在 XOps 侧的落点。 |

## 数据与不变量

- **I-06-1**：流程定义版本一经发布即不可变。
- **I-06-2**：在途实例引用的流程定义版本必须始终可读，停用与新版本都不能使其消失。
- **I-06-3**：审批点绑定角色而非人，因此流程定义不含任何用户标识。

## 接口面

**MCP tools**

| 意图 | 说明 |
|---|---|
| 创建流程定义 | 含全部审批点，一次性提交完整定义 |
| 发布流程新版本 | 基于现有定义产生新版本 |
| 停用流程定义 | 不影响在途实例 |
| 查询项目的流程定义 | 含各版本 |
| 校验流程定义 | 不落库，只回报这份定义是否合法、是否存在无人可批的审批点 |

**只读查询面**（供 RP-15）

- 项目的流程定义列表与版本历史
- 单个流程定义的结构展开

## 验收标准

- 通过 MCP 创建一条含三个串行审批点的流程，查询能拿到完整结构。
- 创建一条绑定了项目内无人担任的角色的流程，发起实例时失败并指明具体审批点。
- 修改流程产生 v2 后，v1 发起的在途实例仍按 v1 走完。
- 停用流程后无法发起新实例，在途实例不受影响。
- 声明了职责分离的审批点，被审批对象的发起人无法在该点做出决策。
- 全票/法定人数/任一三种条件各构造一次，成立时机符合定义。

## MVP 子集

**不纳入 MVP。**

理由：审批引擎是三个包里最大的一块，而 MVP 要验证的核心命题——"AI 编程工具通过 MCP 把缺陷提交到平台、平台记账、Web 能看"——不需要审批参与。把这一块放进 MVP 会让第一个可用版本推迟很久，而推迟期间学到的东西并不来自审批。

**如果一定要在 MVP 就有审批**，最小形态是：单审批点、任一成立、绑定固定角色、不支持并行与会签、无版本化。但我建议不做——见下方。

## 风险与待定

- **通用引擎 vs 先做窄的：这是这份需求里我最想请你再确认一次的地方。**

  你已经明确选了通用引擎，我按这个拆了包，不改。但有一个事实值得摆出来：XForge 侧的审批契约是**固定的两个 tool**（`submit_approval_request` / `poll_approval`），它对 XOps 内部有几个审批点、怎么串并行**一无所知也不关心**——它只问"这个 governingDigest 决定了没有"。也就是说，通用引擎的全部复杂度，服务的是 XForge 之外的审批场景（缺陷关闭要不要批、任务发布要不要批、技能发布要不要批）。

  **这些场景现在还没有一个是真实存在的需求。** 我的建议是：包按通用引擎拆（已经拆好了，需求条目完整），但**实现顺序放在 MVP 之后**，等第一批真实审批场景出现，再决定 R-06-04 的三种成立条件、R-06-05 的并行、R-06-14 的职责分离各自值不值得。这不改变你的决策，只是把它排在真实需求之后而不是之前。

- **条件分支明确不做。** 一旦引入"金额大于 X 走这条、否则走那条"这类表达式，就需要一个表达式引擎、一套求值上下文、以及它们的测试面，而这正是"长成平台"的第一步。如果将来真的需要，用"不同的流程定义 + 发起时选择"来表达，把判断留在发起方。
- **R-06-06 不做驳回循环**是一条有主张的取舍，值得你确认。传统审批系统普遍有"驳回到某节点"，去掉它会让习惯了传统流程的人不适应。我的理由写在条目里，但这条你可能有不同看法。
- **职责分离（R-06-14）的判定依赖"被审批对象的发起人是谁"**，而对 XForge 的 transition 来说，这个信息在仓里（变更的作者集合），XOps 拿不到。这条在 XForge 场景下能否成立，取决于 RP-08 的适配设计——见该包的 Q4。
