# RP-06 Web 前端

> TypeScript + React SPA · 安全 Markdown 渲染 · 前端不存在写调用路径

## 归属与依赖

- **依赖**：RP-05 的**读模型契约**（不依赖它的实现——**契约定型即可并行开工**）。
- **被依赖**：RP-17 通知（个人看板是前端上的一个内建固定视图）。
- **里程碑**：M1。
- **独立性**：对着读模型契约的桩数据就能开发与验收大部分内容。**唯一必须联调的是可见性与会话**。

## Crate 归属

| 目录 | 本包是否新建 | 说明 |
|---|---|---|
| `web/` | **新建** | TypeScript + React SPA。**构建产物随二进制发行**（部署方不需要 Node） |

**本包不动任何 Rust crate。** 它与后端之间只有读模型这一条契约——**这是本版把前后端拆成两个包的直接目的**。

## 背景与价值

这个包的价值集中在两条纪律上，两条都很容易被默认配置或"顺手"破掉。

**第一条：`BRD-008` 渲染时禁用内联 HTML 与脚本。**

> **绝大多数 Markdown 渲染库默认开启内联 HTML**，而长文本列的内容部分来自被分析的代码仓——**能往那个仓提交代码的人，就能影响它**。这是渲染这条攻击链上唯一的门。

`BRD-009` 明确要求**实际构造恶意内容验证**，不能只做代码审查。理由就是上面那句"默认开启"——**代码审查看不出一个默认值**。

**第二条：G2 的第②道。**

```text
① 后端不存在写路由      RP-05 兜。结构性的
② 前端不存在调用写接口   本包兜。纪律性的，要用 CI 检查
```

② 的作用不是"防止写成功"（①已经保证了），而是**让越界在评审阶段被看见，而不是等它撞上 404**。

**第三条不是纪律是边界**：平台不内建任何报表（`BRD-002`）。判断标准很简单：

> **如果有一天需要在平台代码里写"什么是缺陷密度"，那就越界了。**

### 技术栈这一笔账

选 React 而不是把前端也写成 Rust（Leptos/Dioxus），代价是**引入一条 npm 工具链与一个构建步骤**。这与"可本地部署"（D41）不冲突——构建产物随二进制发行，部署方不需要 Node——**但它确实让仓库多了一套依赖要跟**。这笔账在 D55 里认过。

## 范围

### 包含

- SPA 的整体外壳、路由、状态、身份展示
- 表视图的渲染：筛选、排序、选列
- 单行完整历史的视图
- **长文本（Markdown）列的安全渲染**与**原始形式下载**
- 前端的**只读纪律**与它的 CI 检查
- 构建产物的产出形态（随二进制发行）

### 明确不包含

- **读模型的定义与实现**——归 RP-05。**前端不直连库、不拼查询、不调 MCP。**
- **看板定义的修改**——那是一次 MCP 调用，页面上给出"在你的 Agent 里跑这条命令"。
- **个人看板**——归 RP-17。**本包不得先做一个"简化版通知页"顶上。**
- **任何图表、指标、聚合、跨表 join**——没有燃尽图、没有趋势图、没有跨项目对比、没有执行结果对比视图。

| `BRD-003` | 判断标准：如果有一天需要在平台代码里写"什么是缺陷密度"，那就越界了。 |

## 关键不变量

`G2`（本包负责它的第②道）· `G9`（看板只呈现，不因长文本内容改变任何控制流）· `I-L`（Web 会话不能用于任何写操作——前端不持有也不使用任何可写凭据）。

## 接口面

**对外**：只读 Web 页面。

**对内**：只消费 RP-05 的读模型，**不存在第二条数据通路**。

## 验收标准

- **构造一份含恶意内容的长文本**（内联脚本、事件处理属性、外部资源引用、`javascript:` 链接、SVG 内嵌脚本），写进一张表，在 Web 上打开：**脚本不执行、外部资源不自动加载、会话不泄露**。**这条必须实际构造并验证，不能只做代码审查**（`BRD-009`）。
- **把这组恶意样本固化进 CI**，并在渲染库升级时重跑——**默认值会随版本变**。
- **枚举前端代码：不存在任何调用写接口的路径。** 这条要有一个 CI 检查，不是靠人看。
- **原始形式下载**：不信任渲染的人能拿到长文本原文（`BRD-010`）。
- **没有报表**：枚举全部视图，不存在任何图表、趋势、聚合或跨项目对比。
- **可见性**：非成员看不到某项目的任何内容，且与"项目不存在"表现一致。
- **身份明确展示**：当前用户是谁，页面上看得见。
- **构建产物**：`cargo build` 之后的二进制**自带前端资源**，部署方不需要 Node。

## 内部工作包建议

一次 **Solid Change**：

```text
WP-A SPA 外壳 + 读模型客户端（对着契约与桩数据开工）
        │
        ├──► WP-B 表视图渲染（筛选/排序/选列）+ 单行历史视图
        │
        └──► WP-C 安全 Markdown 渲染 + 原始下载 + 对抗性测试进 CI
                    ← 与 WP-B 同步做，不要留到最后
```

**WP-C 不是收尾工作。** 把它排到最后的项目，通常是在最后发现渲染库的默认值和自己以为的不一样。

## 风险与待定

- **`BRD-008` 是最容易被默认配置绕过的一条。** 对策已写进验收：对抗性测试进 CI，渲染库升级时重跑。
- **"就加一个按钮"是这个包持续的压力来源。** ① 已经让它写不进去，但**②的意义是让它在评审时就被看见**——建议写成 XForge Rule。
- **npm 依赖面是本包引入的新风险**（供应链、构建可重现）。建议锁版本、限制依赖数量，并把"前端依赖新增"列为需要论证的评审项。
- **前端与读模型的差距要在 WP-A 就暴露**：如果发现读模型缺东西，**回头修 RP-05，不要在前端自己找路**——那条路一旦开了，"前端不直连"就不成立了。
