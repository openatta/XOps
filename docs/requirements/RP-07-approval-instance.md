# RP-07 审批实例与决策

## 归属与依赖

- **依赖**：RP-06（按定义运转）、RP-04（决策是追加式记录）、RP-02（角色判定）、RP-03（写入面）。
- **被依赖**：RP-08（XForge 适配把两个固定 tool 映射到本包）、RP-15、RP-16。
- **不做这个包会阻塞谁**：RP-08。流程定义没有实例就没有任何用处。

## 背景与价值

RP-06 产出的是"应该怎么批"，本包产出的是"这一次批得怎么样了"。

这个包要守住的核心性质只有一条：

> **一个审批实例，从发起到终态，全过程是确定性的、可重放的、责任可追溯的。**

具体到实现上，最容易被做错的是**幂等**。审批天然是异步的——发起方（可能是 XForge 的 CLI、可能是某个 Skill）会反复来问"批了没有"，也可能因为网络重试而重复发起。如果重复发起会开出第二个审批单，人就会看到两个一模一样的待办，批了其中一个另一个还挂着，整个账本立刻失去可信度。

XForge 那侧已经把答案给出来了，而且是**现成的、经过设计的**：

> **按 `governingDigest` 幂等。对同一个 Change/Flow/Stage/policy/revision 重复提交永远安全；平台应该认出这个 digest，不要重复开工单。**

本包把这个性质**一般化**：任何审批实例都由一个"治理摘要"标识，重复发起是空操作。

## 范围

### 包含

- 审批实例的发起、幂等去重
- 审批点的激活、决策收集、成立判定
- 决策的做出（通过 / 拒绝）与责任记录
- 实例的终态（通过 / 拒绝 / 取消 / 过期）
- 待办查询（"该我批的有哪些"）
- 决策的有效期

### 不包含

- **流程定义**——归 RP-06。
- **XForge 的两个固定 tool 形状与回执语义**——归 RP-08。
- **通知投递**——归 RP-16。本包只产生"有新待办"这个事实。
- **代替人做决定**——G8。任何自动通过、超时默认通过的机制都不在范围内，见"风险与待定"。

## 需求条目

### 发起与幂等

| ID | 需求 |
|---|---|
| R-07-01 | 审批实例由发起方通过 MCP 发起，声明：目标项目、流程定义、被审批对象的标识与修订、以及**治理摘要**。 |
| R-07-02 | **治理摘要是幂等键。** 对同一治理摘要重复发起，一律视为空操作，返回与首次相同的实例，**不得开出第二个实例**。 |
| R-07-03 | 治理摘要由发起方计算并提供，XOps 不解释其内容，只把它当作不透明的唯一键使用。 |
| R-07-04 | 被审批对象的修订发生变化时，发起方会算出不同的治理摘要，因而自然产生新实例——**旧实例不因此自动失效**，但查询时可以看出它绑定的是旧修订。 |
| R-07-05 | 发起时按 R-06-13 校验：任何审批点无人可批则发起失败，不创建实例。 |

### 决策

| ID | 需求 |
|---|---|
| R-07-06 | 决策只有两种：**通过**与**拒绝**。不存在"有条件通过"作为系统状态——条件是文字，属于决策附带的理由，不属于状态机。 |
| R-07-07 | 决策由人做出，通过 MCP 提交。决策人身份由令牌解析得出（G5），**不接受任何形式的代批声明**。 |
| R-07-08 | 决策人必须在该审批点绑定的项目角色内，且满足该点声明的职责分离约束（R-06-14），否则拒绝该决策且不产生任何记录。 |
| R-07-09 | 决策必须附带理由。空理由被拒绝——**一条没有理由的批准，在事后无法回答"当时基于什么"**。 |
| R-07-10 | 决策是追加式记录（G3），已做出的决策不可修改、不可撤回。改变主意的方式是在实例仍未终结时由其他有权者做出相反决策，或让实例走向终态后重新发起。 |
| R-07-11 | 同一人在同一审批点只能做出一次决策，重复提交被拒绝。 |
| R-07-12 | 一旦任一审批点出现拒绝，整个实例立即进入拒绝终态，其余未激活的审批点不再激活（R-06-06）。 |

### 状态与查询

| ID | 需求 |
|---|---|
| R-07-13 | 实例状态至少包含：进行中、已通过、已拒绝、已取消、已过期。 |
| R-07-14 | 实例的"当前在等谁"必须可查询——具体到审批点、所需角色、还差几人。**这是发起方 Agent 与人共同需要的唯一一条状态信息。** |
| R-07-15 | 提供"该我批的待办列表"查询，跨项目聚合当前用户的全部待决审批点。 |
| R-07-16 | 发起方可以取消自己发起的、尚未终结的实例。 |
| R-07-17 | 实例可以设置过期时间；过期后进入已过期终态，**绝不自动通过**。 |
| R-07-18 | 通过的决策可以携带有效期。超过有效期后，该决策在下游（RP-08 的回执消费方）不再计入有效批准。 |
| R-07-19 | 全部发起、激活、决策、终态变化产生审计事件（RP-04），可重建实例的完整过程。 |

## 数据与不变量

- **I-07-1**：治理摘要在项目内唯一标识一个审批实例。
- **I-07-2**：决策记录只追加，永不改写。
- **I-07-3**：实例的当前状态可完全由其事件流推导（继承 I-04-3）。
- **I-07-4**：不存在任何使实例在无人决策的情况下进入"已通过"的代码路径。
- **I-07-5**：决策人一律来自令牌解析，不来自请求体。

## 接口面

**MCP tools**

| 意图 | 说明 |
|---|---|
| 发起审批实例 | 按治理摘要幂等 |
| 查询实例状态 | 含"当前在等谁" |
| 做出决策 | 通过/拒绝 + 必填理由 |
| 查询我的待办 | 跨项目聚合 |
| 取消实例 | 仅发起方 |

**只读查询面**（供 RP-15）

- 项目的审批实例列表与状态
- 单实例的完整决策时间线
- 个人待办

## 验收标准

- 用同一治理摘要连续发起十次，只存在一个实例。
- 三个串行审批点的流程，第一个点未成立时第二个点不接受决策。
- 并行审批点组中任一点被拒绝，整个实例立即终止，其余点不再接受决策。
- 无权角色提交决策被拒绝，且不留下任何决策记录。
- 同一人在同一点重复决策被拒绝。
- 空理由的决策被拒绝。
- 实例过期后状态为"已过期"，**不是**"已通过"。
- 从事件流重建实例过程，与实时观察到的一致。
- 全程代码审查：不存在自动通过路径。

## MVP 子集

**不纳入 MVP**（随 RP-06 一起推迟）。

若单独提前实现，最小形态：单审批点、任一成立、按治理摘要幂等、通过/拒绝 + 理由、待办查询。**即使是最小形态，R-07-02（幂等）、R-07-07（身份来自令牌）、R-07-09（必填理由）、R-07-17（过期不自动通过）也不可省。**

## 风险与待定

- **超时自动通过：明确不做，并且建议永远不做。** 这类功能在传统审批系统里很常见，理由是"防止流程卡死"。但在这套设计里，审批的全部价值就是"有人的判断拦在这里"，一个会自动放行的关卡等于没有关卡，而且比没有关卡更糟——它看起来像有。R-07-17 因此规定过期走向"已过期"而不是"已通过"，卡死的流程应该被看见，不应该被绕过。

- **R-07-06 不设"有条件通过"**值得你确认。跨仓协作设计里的验收判定是四档（通过/有条件通过/不通过/阻塞），如果你希望 XOps 承载那套判定，这里要么增加状态，要么由 RP-08 在适配层把四档映射成两档 + 理由文本。**倾向后者**：状态机越小越可靠，语义细节放在理由里由人读。

- **谁能发起审批实例**没有完全定义。对 XForge 场景是 CLI（携带项目令牌），对项目内场景可能是任意成员。建议在设计阶段按"被审批对象类型"分别定，而不是给一条全局规则。

- **R-07-18 的决策有效期**是为对齐 XForge 的 `expiresAt` 而设。它的语义边界要小心：过期的是**下游是否还计入这条批准**，不是"实例回到未决状态"。实例本身仍然是"已通过"，只是这份通过不再新鲜。这两件事混在一起会很难解释。
