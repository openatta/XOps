# RP-07 自动触发

> 定时 · Git Hook · MCP 触发

## 归属与依赖

- **依赖**：RP-04 技能与任务执行。**这是一条本质依赖**——自动触发必须有可触发的东西，任务不存在时定时与 webhook 无处可去。
- **配套**：RP-03 代码仓接入——Git Hook 触发需要仓绑定来定位任务并验证事件来源。
- **被依赖**：无。这是一个入口。
- **独立性**：增量包。RP-04 已经包含手动触发，本包是在其上增加三种自动来源。**三种触发方式之间彼此独立，可以逐个交付。**

## 背景与价值

你的第 6 条需求里除手动之外的三种：**定时、GIT Hook、MCP 触发**。

它们看起来是三个功能，真正的共同点是：**都要把一个外部事件，确定性地变成一次入队的执行请求。**

收在一个包里的理由是共享同一套纪律：

1. **触发不等于执行。** 产出是"一次执行请求进了队列"，不是"任务跑完了"。三种方式都必须**非阻塞**。
2. **触发要携带上下文。** 特别是 Git Hook——它带来的是一个具体的提交，那个提交标识必须原样传到执行，否则"这份报告针对哪版代码"就没有答案。
3. **触发要防重与防洪。** 定时会堆积，webhook 会重投，MCP 触发会被循环调用。三类问题的解法是同一套：幂等 + 重叠策略 + 速率限制。
4. **触发方的身份必须可追溯。**

## 范围

### 包含

- 定时触发（周期性调度）
- Git Hook 触发（GitHub / Gitea / GitLab 的 webhook 接收与验证）
- MCP 触发
- 各自的鉴权、幂等、去重、限流
- 触发上下文到执行的传递
- 触发历史视图

### 不包含

- **手动触发**——已在 RP-04。
- **执行**——归 RP-04。本包只负责把请求放进队列。
- **任务之间的编排**——明确不做（见 RP-04 的风险条）。
- **Git 仓库内容的读取**——归 RP-03。本包只接事件，不拉代码。

## 需求条目

### 通用

| ID | 需求 |
|---|---|
| R-07-01 | 三种触发方式都是**非阻塞**的：产出执行标识后立即返回。 |
| R-07-02 | 触发前检查：任务存在、已启用、**该任务允许这种触发方式**。任一不满足则拒绝并留痕。 |
| R-07-03 | 每次触发记录触发方式与触发者身份，传递给执行记录。 |
| R-07-04 | 触发受任务的重叠策略约束。**被跳过的触发必须留痕**——一个静默被跳过的定时任务，会让人以为它在跑。 |
| R-07-05 | 触发受速率限制。超限的触发被拒绝并留痕，**不排进队列**。 |
| R-07-06 | 触发本身产生审计事件，**包括被拒绝与被跳过的触发**。 |

### 定时触发

| ID | 需求 |
|---|---|
| R-07-07 | 任务可配置周期性调度，支持至少"每天某时"与"每隔 N 小时"两类表达，以及**明确的时区**。 |
| R-07-08 | 定时触发的默认时段建议在业务低谷（夜间）。理由：分析是重活，而**质量结论不需要实时**——质量看的是趋势与系统性偏差，不是某一次提交。 |
| R-07-09 | 服务重启或短暂不可用后恢复时，**错过的定时窗口不补跑**，只按下一个窗口正常触发，并对错过的窗口留痕。补跑会在恢复瞬间产生一批并发执行，风险大于收益。 |
| R-07-10 | 定时触发的触发者记录为系统，但**必须能追溯到配置该调度的人**。 |

### Git Hook 触发

| ID | 需求 |
|---|---|
| R-07-11 | 支持接收 GitHub、Gitea、GitLab 三个平台的 webhook（D4）。 |
| R-07-12 | webhook 必须**验证签名/密钥**。验证失败的请求被拒绝，且**不泄露任何关于任务或项目是否存在的信息**。 |
| R-07-13 | 平台各自的重投机制会导致重复投递，因此必须**按事件标识幂等**：同一事件重复投递不产生第二次执行。 |
| R-07-14 | 触发时把事件携带的**确切提交标识**传给执行，作为本次读取代码的修订。 |
| R-07-15 | 支持按事件类型与分支过滤：任务可声明只对某些分支或某类事件（推送、PR）响应。 |
| R-07-16 | webhook 端点**必须快速返回**，不在请求内做任何拉取或执行——平台的 webhook 都有超时并会因超时重投，从而放大问题。 |
| R-07-17 | webhook 载荷是**不可信输入**（G7）：只从中提取结构化字段（提交标识、分支、事件类型），**不解析其中任何自由文本**，不因其内容改变控制流。 |

### MCP 触发

| ID | 需求 |
|---|---|
| R-07-18 | 任务可通过 MCP tool 触发，供 AI 编程工具中的 Skill 主动发起（例如"帮我对这次改动跑一遍代码检视"）。 |
| R-07-19 | 支持幂等键，重复调用不产生第二次执行。 |
| R-07-20 | 调用方可指定目标修订，但必须在任务绑定的代码仓范围内，越界被拒绝。 |
| R-07-21 | MCP 触发**不得形成回路**：由某次执行产生的动作不得再触发任务。执行环境中不提供触发能力（继承 RP-04 的 R-04-35）。 |

### 触发历史视图（只读）

| ID | 需求 |
|---|---|
| R-07-22 | 提供任务的触发历史，**含被拒绝与被跳过的触发**。 |
| R-07-23 | 提供定时调度配置与下次触发时间。 |

## 数据与不变量

- **I-07-1**：触发永不同步执行任务。
- **I-07-2**：同一外部事件（webhook 事件标识／MCP 幂等键）最多产生一次执行。
- **I-07-3**：每次执行都能追溯到确切的触发方式、触发者与触发上下文。
- **I-07-4**：被拒绝或被跳过的触发同样留痕。
- **I-07-5**：**执行环境无法触发任务，不存在自触发回路。**

## 验收标准

- 三种触发方式各触发一次任务，均返回执行标识且不阻塞。
- 停用的任务，三种方式全部触发失败并留痕。
- 任务只声明允许手动触发时，定时与 webhook 触发被拒绝。
- **同一 webhook 事件重复投递十次，只产生一次执行。**
- **伪造签名的 webhook 被拒绝，且响应不泄露任务/项目是否存在。**
- webhook 触发的执行，其记录中的代码修订与事件携带的提交一致。
- 上次执行未结束时的触发，按重叠策略被跳过，且跳过被留痕可查。
- **服务停机跨过一个定时窗口后重启，不补跑，且错过的窗口有留痕。**
- 在技能里尝试触发任务：**执行环境中不存在该能力**。
- 超过速率限制的触发被拒绝且留痕。

## MVP 子集

**不纳入 MVP。**

理由：MVP 要验证的是"技能能跑通、产出能看"，RP-04 的手动触发已经足够验证这条链路。另外三种触发各自带着独立的复杂度（调度器、三平台 webhook 适配与签名验证、回路防护），它们提升的是**自动化程度，不是可行性**。

**建议的交付顺序**（三种方式彼此独立，可逐个进流程）：

1. **定时触发**——最简单，且最先产生价值（夜间跑质量分析，早上看报告）
2. **Git Hook 触发**——按平台逐个交付，每个平台单独验收
3. **MCP 触发**——最后，因为它需要 R-07-21 的回路防护配套

## 风险与待定

- **webhook 端点是 G1 的例外之一**（另一个是 RP-01 的 OAuth 回调）。这不可避免——Git 平台不讲 MCP。但要守住边界：**webhook 只能触发已配置的任务，绝不能创建或修改任何对象**。建议把这条写成项目的 XForge Rule，因为"顺手让 webhook 也能自动建个缺陷"是一个非常自然、但会打开一个无认证写入面的想法。

- **三个平台的 webhook 差异不小**（签名算法、事件类型命名、载荷结构、重投策略）。需求上是一条，实现上是三份适配。**按平台逐个交付**，不要三个一起做。

- **R-07-09 不补跑是一条有主张的取舍。** 有些场景（每日必须有一份报告）会希望补跑。如果你更倾向补跑，需要同时定义"最多补几次"和"补跑的并发上限"，否则一次长停机后的恢复会打垮执行队列。**这条你可以推翻，但推翻时要连带定这两个数。**

- **R-07-21 的回路防护与 RP-04 的 R-04-35 是同一条边界的两面。** 注意不要在"让技能更强大"的动机下给执行环境开触发能力——**一个能触发自己的任务是无限循环，而它花的是真金白银的模型调用**。D10 说不做成本约束，这条防护因此更重要：没有额度兜底时，回路的代价没有上限。

- **触发时能否覆盖任务的输入参数**没有定义。手动/MCP 触发时想临时改个参数是很自然的需求，但一旦允许覆盖，RP-04 的创建期契约校验就要在触发期再做一遍，且执行记录要记下实际用的参数而非任务定义的参数。**建议不允许覆盖**，需要不同参数就建不同任务。
