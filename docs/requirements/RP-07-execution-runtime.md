# RP-07 执行运行时与引擎集成

> 执行契约 · attacored 分立进程 · 容器 ExecProviders · 隔离与失败分类

## 归属与依赖

- **依赖**：无。**第二个根包，可与 RP-01 在第一天同时开工。**
- **被依赖**：RP-11 事件、触发与派工单（**只依赖契约**，契约一定型即可并行）。
- **里程碑**：M2。
- **独立性**：本包对外只有**一个执行契约**——输入一份派工单，输出一份执行结果。用一个测试调用方就能完整验收：**给定技能内容与输入，在容器里跑起来、拿回产物与过程记录，且一切越界尝试失败。** 它不需要用户、项目、权限、审计或表。

## Crate 归属

| crate | 本包是否新建 | 对外只经什么被用 |
|---|---|---|
| `xops-exec` | **新建** | **执行契约**：提交一次执行 · 查询状态 · 取消 · 领取结果。仅此四件 |

**跨仓**：本包还要在 **AttaCore 仓**里做两处改动（见下）。那两处走 AttaCore 自己的 XForge 流程，**但工期算在本包**。

## 背景与价值

这是全项目**风险最高的一块**，而且第 11 版换了它的形状：

```text
上一版   自建容器编排 + 自建常驻编排进程 + 自建模型调用
本版     引擎是 AttaCore（attacored 分立进程，D50）
         XOps 要建的是**容器后端**：实现引擎四个执行契约的容器实现（D51）
```

**风险没有变小，只是换了地方**：从"造一个 agent 运行时"变成"把一个 agent 运行时的手脚接进容器里，并且证明它伸不出去"。

它也是 XOps 里**唯一允许模型参与的地方**。G8 把系统劈成两半，两者之间的隔离是硬要求：

> **一个能跑但能越界写表的运行时，比一个跑不起来的运行时危险得多。隔离比"能跑"重要。**

### 两条纪律不因为有了具名引擎而松动

| 纪律 | 为什么容易松 |
|---|---|
| **`EXE-014` 说的是"分立进程 + 一条契约"，不是"用 AttaCore"** | XOps 侧仍要有自己的执行契约，**引擎的数据结构不得直接流进它**；桩实现验收照做。**最容易破坏它的，正是图省事让引擎的类型直接穿过去** |
| **`EXE-005` 要求边界由能力封锁兑现** | 引擎的场景机制能让模型看不见某些工具（"没注册"），这是**第二道**，不是那一道。第一道永远是"容器里根本没有那条路" |

### 上游的现状，按代码而不是按它的设计文档

> ⚠️ **AttaCore 的 `EXECUTION_LAYER_DESIGN.md` 写在契约迁移之前，已经落后于代码。开工前按代码重新核一次，不要沿用那份文档的结论。**

```text
已经有的   四个执行契约完备，**全部内建工具都经它们碰机器**
           exec.process / filesystem / network / sandbox
             登记在它的可替换扩展点索引里，信任级别 **host-only**
             （索引由 base::interface::catalog 生成，有测试守住不漂移）
           `exec.process` 的声明用途原文：**which machine the work happens on**
             —— 这正是本包要做的那件事，不是我们把它掰过来用
           出网已统一到一个 egress，模型选的目标与运维配的端点分流
           切换 provider 的写法就是一句赋值

还缺的     **Builder 上没有 `exec` 这个宿主注入位**
           它已有十六个同类注入位：turn_policy · budget_policy · environment
           · recovery_policy · skill_provider · model_interceptor · …
           —— 加一个是有先例的改动，不是重新设计
```

**跨仓交付物只有一项，责任在本包**：给引擎的 Builder 加上 `exec` 宿主注入位，让宿主能按会话换掉那四个 provider。它在 AttaCore 仓里改、走 XForge，**工期算在这边**——"上游还没做"从来不是一个可以等来的状态。

> **`Q24`（接容器要不要改契约）随之降级。** 那四个契约当初是照着"如果这是远端会怎样"设计的——**输出流式是硬要求、符号链接由 provider 解析、沙箱兑现程度要如实上报**——所以风险比设计文档写的低。**但不清零**：排期时留余量，不要当成一定会发生，也不要当成一定不会。

### 引擎侧现成的三样（是便利，不是隔离）

```text
四个执行契约   Process / FileSystem / Network / Sandbox —— 容器后端的挂点
单次预算       单次预算与对应的停止原因 —— TSK-005 的 token 上限有落点
会话与场景     一次执行一个会话；场景决定模型能看见哪些工具 —— 第二道
```

## 范围

### 包含

- **XOps 侧执行契约的定义**（本包对外的唯一接口）
- **容器后端**：四个执行契约的容器实现（`EXE-029`）
- 一次性容器：创建、资源限制、网络策略、挂载、**完整销毁**
- `attacored` 的生命周期管理与**跨执行的会话隔离**
- 凭据边界（模型凭据只在容器外）
- 超时、取消、强制终止、崩溃恢复、**失败分类**
- **引擎不可用时绝不就地跑**（`EXE-030`）
- 过程记录的产生
- **隔离的主动攻击测试套件**
- **跨仓**：给 AttaCore 的 Builder 加上 `exec` 宿主注入位

### 明确不包含

- **技能与任务的领域模型**——归 RP-09 与 RP-10。本包不知道什么是"技能"，只接收一份派工单。
- **派工单的装配**（`EXE-001`）——归 RP-11。本包只校验它收到的东西。
- **数据源的准备**——只读工作区由 RP-08 备好，本包只负责**挂载**。
- **表数据**——`EXE-013`（D44）已经把它从数据源里去掉了。**这也是本包能独立开工的原因**：它不需要表引擎存在。
- **执行记录与产出行的存储**——归 RP-12。本包产生并移交，不负责持久化。
- **排队与调度策略**——归 RP-10 与 RP-11。本包只负责"跑这一个"。
- **判断产出质量**——不做（G8）。

### EXE 执行（22 条）

| ID | 摘要 |
|---|---|
| `EXE-002` | 每次执行使用独立的一次性容器。 |
| `EXE-003` | 全部文件与进程操作都在容器内发生。 |
| `EXE-004` | 容器里没有任何写表的路径。 |
| `EXE-005` | 这条边界必须由能力封锁实现——容器里根本没有通往确定性平面的凭据与网络路径——不得依赖"技能内容里没有要求做这些事"。 |
| `EXE-006` | 容器内可用的能力由派工单的数据源清单决定，未声明的一律不提供。 |
| `EXE-007` | 容器的对外网络默认拒绝，只放行声明的白名单。 |
| `EXE-008` | 容器有明确的 CPU、内存、磁盘上限，超限时被终止并归入资源不足类失败。 |
| `EXE-009` | 容器之间相互隔离：一次执行不得读取或影响另一次执行的文件系统、进程或网络状态。 |
| `EXE-010` | 容器内不含任何凭据，不提供触发能力（I-F、I-J）。 |
| `EXE-011` | 执行结束后容器被完整销毁，不留残留进程、文件、挂载或网络状态。 |
| `EXE-014` | XOps 与执行引擎是两个分立的进程，之间只有一条执行契约这一个接缝。 |
| `EXE-015` | 模型凭据只存在于容器外，从结构上进不了容器。 |
| `EXE-016` | 跨执行的会话隔离由常驻编排进程负责，必须显式实现并实测：一次执行一个会话、用完即销毁；第一次执行在会话里留下可识别痕迹，第二次读不到（I-M）。 |
| `EXE-017` | 编排进程崩溃、卡死或异常退出时，全部在途执行必须在有限时间内被归入明确的失败分类并可重跑，不得无限期挂起。 |
| `EXE-018` | 编排进程重启与恢复不得丢失已经完成并移交的执行结果。 |
| `EXE-019` | 超时强制终止时不得留下孤儿会话继续消耗模型额度。 |
| `EXE-020` | 失败必须分类：技能错误 / 凭据错误 / 工作区错误 / 模型服务错误 / 引擎错误 / 超时 / 超出 token 预算 / 资源不足。 |
| `EXE-021` | 执行是异步的：提交后立即返回执行标识，不阻塞等待完成。 |
| `EXE-022` | 保留过程记录（至少含原始输出流），存 _runs.trace。 |
| `EXE-028` | 隔离必须被主动攻击验证，不能只做正向测试：写一个故意越界的技能，尝试写表、读另一个项目的工作区、读凭据、访问白名单外地址、触发另一个任务、逃逸宿主文件系统—… |
| `EXE-029` | 一次性容器由 XOps 实现引擎的四个执行契约的容器后端提供（Process / FileSystem / Network / Sandbox）（D51）： |
| `EXE-030` | 引擎不可用时，执行失败并如实归入引擎错误类，绝不在 XOps 进程里就地跑一遍。 |

## 关键不变量

`I-E`（不存在从容器内写表的代码路径）· `I-F`（容器内无凭据、过程记录无凭据）· `I-I`（可见范围完全由声明决定）· `I-J`（执行环境无法触发任务）· `I-M`（两次执行之间无可观测的状态泄漏）。

## 接口面

**本包不对外暴露任何 MCP tool**——它没有面向用户的语义，全部经 RP-11。

**对内提供给 RP-11 的执行契约**：提交一次执行（返回执行标识，异步）· 查询执行状态 · 取消执行 · 领取执行结果（待写入的行、状态、失败分类、过程记录）。

> **契约里不出现引擎的任何类型。** 这条有硬验收，见下。

## 验收标准

**隔离必须被主动攻击验证，不能只做正向测试。**

- 写一个**故意越界**的技能内容，尝试：写表、读另一个项目的工作区、读凭据、访问白名单外的网络地址、触发另一个任务、逃逸到宿主文件系统。**每一项都必须失败**，且失败发生在**容器与能力层**（路径不存在／网络不通），**不是靠内容检查拦下的**。
- 验证工具确实在**容器内**执行：让技能写一个文件、跑一个进程，在宿主上确认它们只出现在容器里。
- 未声明需要代码的执行：容器中**确实没有任何工作区挂载**。
- 检查容器内的完整环境与过程记录：**不含任何凭据原文**；同时确认模型凭据确实只在 `attacored` 侧。
- 两次并发执行互相不可见（各自写同名文件互不干扰）。
- 超过 CPU／内存／磁盘上限时被终止并**正确分类**。
- 执行结束后检查宿主：**无残留容器、无残留进程、无残留挂载**。
- **跨执行会话隔离**：连续两次执行，第一次在会话里留下可识别痕迹，第二次**读不到它**（`EXE-016`）。⚠️ 引擎侧有会话池与空闲淘汰，**"看起来干净"更容易骗过人——这条必须实测，不能看代码**。
- **强杀 `attacored`**：此时故意保持三个在途执行，三个都必须在有限时间内被归入引擎错误**并可重跑**，**不得挂起**（`EXE-017`）。
- **停掉 `attacored` 再提交一次执行**：失败并归入引擎错误，**绝不在 XOps 进程里就地跑**（`EXE-030`）。
- 超时终止后**不残留孤儿会话**继续消耗模型额度。
- **把执行引擎换成一个最简桩实现，执行契约与本包其余部分无需修改**——这是 `EXE-014` 的硬验收。
- **沙箱不静默降级**：容器后端兑现不了某条策略时，**逐条如实上报**，绝不当作已兑现（`EXE-029`）。

## 内部工作包建议

一次 **Major Change**：

```text
WP-A XOps 侧执行契约定义（对外唯一接缝，先定，RP-11 据此并行开工）
        │
        ├──► WP-B 跨仓：给 AttaCore 的 Builder 加 `exec` 宿主注入位
        │            │
        │            ▼
        ├──► WP-C 容器后端：四个执行契约的容器实现（EXE-029）
        │            │  ⚠️ Q24 若要发生，会在这里发生 —— 留余量，别当意外
        │            ▼
        ├──► WP-D 一次性容器（创建、资源限制、网络策略、挂载、销毁）
        │            │
        └──────► WP-E attacored 生命周期（会话隔离、崩溃检测、超时中止、
                      凭据边界、不可用时不降级）
                             │
                             ▼
                     WP-F 隔离攻击测试套件
```

**WP-A 必须最先完成**——它一定型，RP-11 就能对着桩实现并行开工，不必等容器做完。

**WP-B 是跨仓工作，排在 WP-C 之前**：没有注入点，容器后端接不进去。**它在 AttaCore 仓里走 XForge，工期算在本包。**

**WP-F 不是收尾工作**，它是唯一能证明隔离真的成立的东西，**建议与 WP-D 同步推进**。

## 风险与待定

- **如果隔离做不完，正确的做法是把整个包推迟、在 M1 停下**，而不是先上一个隔离不全的运行时。先跑起来再补隔离，等于在补上之前一直敞开，而这段时间里跑过的技能、读过的代码、泄过的凭据都追不回来。
- **Q24 是本包最难估的一处，但比第一次评估时轻。** 上游的契约是照着"如果这是远端会怎样"设计的，所以接容器时不一定要改。**排期留余量即可，不必按"一定会改一轮"来算。**
- **本包开工第一件事是按代码核一遍上游现状，而不是读它的设计文档。** 那份文档已经落后；这次估工期用的判断（"只缺一个注入位"）也应当在开工时再核一次——**上游还在动**。
- **`EXE-016` 是这个拓扑最容易被漏掉的一条**，因为它原本是"一次执行一个容器"免费提供的。验收里那条"留痕迹再读"必须实际跑。
- **最容易破坏 `EXE-014` 的，是图省事让引擎的数据结构直接流进执行契约。** 引擎的概念一旦泄漏，换引擎就变成改全系统。**建议把这条写成 XForge Rule**：`xops-exec` 的公开接口里出现引擎类型，评审阶段拦下。
- **Q10 出网白名单由谁批准**未定。本包实现默认拒绝 + 声明白名单的机制，但**自定义白名单在 Q10 定下来之前不开放**。
- **容器池化/复用与 `EXE-002` 冲突。** 这个拓扑已经用"编排进程常驻"消掉了大部分冷启动开销——**不要在没有实测的情况下先去动它**。
