# RP-08 通知

> 从审计事件派生的告知通道

## 归属与依赖

- **依赖**：RP-01 平台基座。**除此之外不依赖任何包。**
- **被依赖**：无。这是一个出口。
- **独立性**：完全独立。它订阅审计事件（RP-01 就有），能通知什么取决于当时已经存在哪些包——RP-02 就位就能通知缺陷，RP-05 就位就能通知待办。**不需要等任何包做完。**

## 背景与价值

这套系统里有一条必须守住的区分，它比通知本身重要：

| 类型 | 内容 | 机制 | 性质 |
|---|---|---|---|
| **拦住** | 审批不通过、关键缺陷否决 | **审批通道**（RP-05 / RP-06） | 治理事实，进审计链，可阻塞归档 |
| **告知** | 缺陷明细、执行完成、待办提醒 | **通知**（本包） | 工作信息，**不构成门禁** |

> **"拦住"与"告知"必须用不同机制。**

一个只能"告知"的结论，等于没有实质否决权——而**没有实质否决权的独立性只是装饰**。反过来，**一个通知工具返回的字符串本身不构成治理事实**：它是外部断言，没有绑定、不可审计。

所以这个包的边界非常清楚：**它只搬运信息，永远不产生任何后果。** 通知发失败了，不影响任何事情的正确性——最多是有人晚知道了一会儿。**这条性质应当被当成设计目标，而不是缺陷。**

## 范围

### 包含

- 通知的产生（订阅审计事件）
- 投递渠道
- 用户的订阅偏好
- 投递结果与重试
- 通知列表视图

### 不包含

- **任何构成门禁的机制**——通知的成功与失败不影响任何业务状态。
- **通知内容的模型加工**——由确定性代码从结构化事件生成（G8）。
- **通用的"发消息给某人"能力**——见"风险与待定"，这一条很重要。

## 需求条目

| ID | 需求 |
|---|---|
| R-08-01 | 通知从审计事件（RP-01）派生，**不引入独立的通知触发路径**——否则会出现"发了通知但账本里没有对应事实"。 |
| R-08-02 | 通知的产生与投递是**异步**的，其失败**绝不**影响产生该事件的业务操作。 |
| R-08-03 | 通知内容由确定性代码从结构化事件生成，**不经模型**（G8）。 |
| R-08-04 | 通知内容中的自由文本**原样引用或截断**，不做改写、摘要或翻译（G7）。 |
| R-08-05 | 通知只发给对该事件所属项目有可见权限的用户。 |
| R-08-06 | 用户可按事件类型配置订阅偏好，包括完全关闭。 |
| R-08-07 | 通知有**去重与聚合**：同一对象短时间内的多次变化合并为一条，避免一次批量操作产生几十条通知。 |
| R-08-08 | 投递失败按有限次数重试后放弃并留痕。**不无限重试。** |
| R-08-09 | 通知中不含任何凭据、令牌或产物原文（只含链接）。 |
| R-08-10 | 至少支持一种投递渠道；渠道可扩展，但每种渠道都受 R-08-05 的可见性约束。 |

### 值得通知的事件

| ID | 需求 |
|---|---|
| R-08-11 | **有新的审批待办**——最有价值的一类，因为审批是唯一会阻塞别人的事。（需 RP-05） |
| R-08-12 | **审批实例已决定**——发起方需要知道该去重跑命令了。（需 RP-05） |
| R-08-13 | **执行完成或失败**——尤其是定时任务，人不会一直盯着。（需 RP-04） |
| R-08-14 | **缺陷被指派给我 / 我提交的缺陷状态变化**。（需 RP-02） |

### 视图（只读）

| ID | 需求 |
|---|---|
| R-08-15 | 提供通知列表与已读状态视图。 |
| R-08-16 | 视图上不存在任何写入操作（G2）。订阅偏好的变更走 MCP。 |

## 数据与不变量

- **I-08-1**：通知失败不改变任何业务状态。
- **I-08-2**：不存在只发通知而没有对应审计事件的路径。
- **I-08-3**：通知不投递给无权看到该事件的用户。
- **I-08-4**：通知内容不含凭据。

## 验收标准

- 产生一个可通知的事件，订阅者收到通知，**非项目成员不收到**。
- **通知渠道完全不可用时，业务操作全部正常完成**，仅通知留痕为失败。
- 一次批量操作产生多个同对象事件时，通知被聚合成一条。
- 关闭某类订阅后不再收到该类通知。
- 检查通知内容：**不含凭据、不含产物原文**。
- 投递失败重试到上限后停止，且留痕可查。

## MVP 子集

**不纳入 MVP。**

理由：通知按定义不产生任何后果，它优化的是及时性。MVP 阶段用户数少、使用频次低，且使用者本来就在 Agent 会话里——直接查询就能拿到全部信息。把通知放进 MVP 会占用本该给隔离（RP-04）和安全渲染的时间，**而那两块是后补代价极高的**。

**MVP 之后的优先级也不高**，建议排在 RP-05 审批引擎之后——因为通知最有价值的场景（R-08-11 待办提醒）要等审批存在才成立。

## 风险与待定

- **绝不要提供一个通用的"发消息给某人"或"把这个上下文发过去"的 MCP 工具。** 这是这个包唯一一条严重风险，值得单独强调。

  一旦这样的工具存在，它就成了一条可以承载任意内容的通道。在这套设计里，这会破坏两件事：

  1. **信息隔离**。如果将来 XOps 承载了开发侧与验证侧的协作，一条通用通道会让"验证侧拿不到实现"这个结构性保证退化成每个人每次的自觉。结论回流只应带结论、复现步骤、观测现象，**不带推导过程与判定逻辑**——否则下一轮实现照着它写，直接退化成对验收集的过拟合，而通过率还会好看起来。
  2. **窄接口纪律**（R-01-29）。通知是最容易被要求"加个自由文本字段"的地方，因为它看起来无害。

  **对策**：本包所有通知都由 R-08-01 从审计事件派生，**不提供任何"主动发送自定义内容"的入口**。建议把这条写进项目的 XForge Rule。

- **渠道选择未定**（站内、邮件、企业 IM、Webhook 出站）。属于设计选型。需求侧唯一的约束是 R-08-05 的可见性与 R-08-09 的不含凭据——**出站 Webhook 尤其要注意，它会把项目内容发到 XOps 控制之外的地方**。

- **R-08-07 的聚合窗口**需要具体数值，等有真实使用频次后再定。先给一个保守值（如 5 分钟）。
