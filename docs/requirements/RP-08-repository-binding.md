# RP-08 Git 仓绑定

> 只读凭据 · 绑定前验证确实只读 · 确切修订 · 只读工作区准备

## 归属与依赖

- **依赖**：RP-02 身份、项目与审计。
- **被依赖**：RP-11 事件、触发与派工单（**是增强而不是依赖**，见下）、RP-19 XForge 适配（登记挂在仓绑定上）。
- **里程碑**：M2。
- **独立性**：绑一个仓、验证凭据只读、按一个确切修订备好一份只读工作区——用一个假的消费方就能完整验收。

## Crate 归属

| crate | 本包是否新建 | 对外只经什么被用 |
|---|---|---|
| `xops-repo` | **新建** | 仓绑定的读写 · **按修订准备一份只读工作区** · 同步状态查询 |

## 背景与价值

这个包守一条**安全属性**，它比它的体量重要得多：

> **`I-G` XOps 在任何代码路径上都不持有、不请求仓库的写权限。**

这条不是"我们目前不写"，是"我们要不到写权限"。它有两个直接后果：绑定时要**验证凭据确实只读**（不是相信用户说它只读），以及 XForge 的回执由 **XForge CLI 自己写进仓里**，XOps 从不写任何仓库（`XFG-017`）。

第二条价值是**确切修订**：

```text
事件载荷覆盖任务定义里写死的目标修订
  git 事件带来的提交标识、流程事件带来的主体修订，都覆盖任务定义
少了这条，执行读的是"仓库现在长什么样"，不是"这次要它看的那一版"
```

> ⚠️ **本包与 RP-09 / RP-11 是增强关系，不是依赖关系。** 技能可以声明自己**不需要代码仓**、只吃任务的输入参数，那类技能不碰本包就能完整跑通（产出行照样落 `_runs` 与声明的表）。做完本包之后，技能才多出"能读代码"这项能力。**这也是 RP-11 能在本包未就位时完整验收的原因。**

## 范围

### 包含

- 绑定一个 Git 仓（含只读凭据），**绑定前验证凭据确实只读**
- 查询绑定与同步状态
- 凭据的轮换与解绑
- **按确切修订准备一份只读工作区**（交给 RP-07 去挂载）
- 凭据的存储与保护（**不进容器**，`I-F`）
- 一个项目当前绑一个仓（多仓是 Q11 / M6）

### 明确不包含

- **容器与挂载**——归 RP-07。本包只把工作区备好，**不负责它怎么被挂进容器**。
- **派工单的装配**——归 RP-11。本包不知道谁要这份工作区。
- **webhook 端点与 git 事件**——归 RP-13。本包不接收事件。
- **往仓里写任何东西**——**永不**（`I-G`、`RPO-013`）。
- **XForge 的登记**（policyId → 流程、结果列映射）——归 RP-19，虽然它挂在本包的仓绑定上。

本包认领 [`requirements.md`](requirements.md) 的 **14 条**。**条目正文以 `requirements.md` 为准**，下表只是索引与一句话摘要。

### RPO Git 仓绑定（14 条）

| ID | 摘要 |
|---|---|
| `RPO-001` | 项目当前绑一个 Git 仓。 |
| `RPO-002` | 凭据必须是只读的。 |
| `RPO-003` | 凭据加密存储，任何接口都不能读出原文，包括项目所有者自己。 |
| `RPO-004` | 凭据可轮换与撤销。 |
| `RPO-005` | 凭据只注入到容器外实际需要它的那一次拉取动作，不进入容器、不进入 agent 可读的上下文、不进入环境变量、不进入过程记录（I-F）。 |
| `RPO-006` | 每次使用凭据访问仓库产生审计事件：哪个项目、哪个仓、哪次执行、拉取了什么修订。 |
| `RPO-007` | 平台差异必须收在一个可适配的接口后面（认证、克隆、权限元数据校验、webhook 签名验证）。 |
| `RPO-008` | 工作区在容器外准备：定位到确切修订，只读挂载进容器，容器内的任何写入不回流仓库，且随容器一并销毁。 |
| `RPO-009` | 一次执行的工作区只包含一个项目的代码。 |
| `RPO-010` | 每次读取记下确切修订——否则"这份报告针对哪版代码"无法回答。 |
| `RPO-011` | 拉取有容量与时间上限，超限时失败并明确报告，不允许无限制占用。 |
| `RPO-012` | 提供绑定与同步状态查询（上次拉取时间、当前修订）、凭据轮换、解绑。 |
| `RPO-013` | XOps 在任何代码路径上都不持有、不请求仓库的写权限：不推分支、不提 PR、不打 tag、不改任何仓库内容（I-G）。 |
| `RPO-014` | XForge 的登记（XFG-002）挂在仓绑定上，不另开一套对象。 |

## 关键不变量

`I-G`（XOps 不持有、不请求仓库写权限）· `I-F`（凭据不进容器）· `I-I`（可见范围完全由声明决定）。

## 接口面

**MCP tools**：绑定仓（含只读凭据，**绑定前验证确实只读**）· 查询绑定与同步状态 · 轮换凭据 · 解绑。

**对内提供给 RP-11 / RP-07**：

```text
prepare_workspace(project, revision) -> 一份只读工作区
    —— 凭据在这一侧用掉，**不随工作区进容器**
```

## 验收标准

- **绑定一个有写权限的凭据：被拒绝。** 这条要实际验证（尝试一次写并期待它失败），不是读凭据的声明。
- **枚举全仓代码路径：不存在任何向仓库写入的调用。**
- **按确切修订备工作区**：给定一个提交标识，备出的工作区**就是那一版**，不是分支当前 HEAD。
- **工作区是只读的**：消费方（容器）对它的写入不回流到仓库。
- **凭据不出现在**：工作区内容、过程记录、日志、错误消息里。
- **轮换凭据**：不影响在途执行；旧凭据立即失效。
- **解绑**：绑定消失；已备好的工作区按各自生命周期结束。
- **修订不存在**（例如 gitHead 还没推上去）：**明确失败并归入工作区错误**，不是静默用 HEAD 顶替。⚠️ 这条是 `XFG` 那条"⑤ gitHead 必须已推送"的落点，**它只影响自动化，不影响人**。

## 内部工作包建议

一次 **Solid Change**：

```text
WP-A 仓绑定与只读凭据（含"验证确实只读"）
        │
        ▼
WP-B 按修订准备只读工作区 + 凭据不外泄
        │
        ▼
WP-C 轮换、解绑、同步状态查询
```

## 风险与待定

- **"验证凭据确实只读"没有一个跨平台的标准做法。** 不同 Git 托管方的能力查询接口不同，最保守的做法是**实际尝试一次无害的写并期待它失败**。这条要在 WP-A 里定下来，不要留到实现时临时决定。
- **Q11 一个项目能否绑多个仓**未定（M6）。多仓会让"一次执行只持有一个项目的代码"细化成"只持有本次声明的那几个仓"，隔离判定复杂一档。**先做单仓**，但接口形状上不要写死成"一个"。
- **"修订不存在时明确失败"必须真的发出通知**（RP-17）。调用方那边只会看到 `pending`，**如果这条失败是静默的，XForge 链路上会出现一个查不出原因的挂起**。
