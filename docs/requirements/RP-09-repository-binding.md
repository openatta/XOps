# RP-09 代码仓绑定与只读工作区

## 归属与依赖

- **依赖**：RP-02（仓绑定是项目的属性）、RP-03（绑定通过 MCP 建立）、RP-04（凭据与访问留痕）。
- **被依赖**：RP-12（Agent 执行时需要代码）、RP-14（Git Hook 触发依赖仓绑定）、RP-08（绑定关系可复用）。
- **不做这个包会阻塞谁**：RP-12 中一切需要读代码的技能（代码检视是你点名的场景）、RP-14 的 Git Hook 触发。

## 背景与价值

你的第 5 条需求：**项目可以配置代码仓，执行 SKILL 时 AGENT 需要读代码仓完成工作，比如检视代码。**

这个包解决的核心问题不是"怎么 clone"，而是：

> **让服务端 Agent 能读到代码，同时让源码不落到任何个人的机器上。**

这是一个真实且被低估的收益。一个质量负责人如果按 clone 的方式服务 N 条产品线，他的个人机器上会同时存在 N 个产品的完整源码，并且要把它们发往多个模型引擎——**那台机器会成为整个组织代码资产暴露面最大的一个点。** 把分析放到服务端，源码留在受控环境里，个人侧只有报告。

第二个核心问题是**只读**。XOps 在 D6 之后已经不需要任何仓库的写权限（缺陷不回写），本包也不应该把它加回来。**只读凭据是这个系统一条重要的安全属性，值得写成不变量。**

## 范围

### 包含

- 项目绑定一个或多个代码仓（GitHub、Gitea 自建、GitLab）
- 只读凭据的登记、加密存储、轮换、撤销
- 服务端受控工作区：按需拉取、更新、按项目隔离
- 工作区的生命周期与清理
- 仓库访问的留痕

### 不包含

- **任何写操作**——不推分支、不提 PR、不打 tag、不改任何仓库内容。
- **构建**——被测产物由现有 CI 产出，服务不碰。
- **Webhook 的接收与触发语义**——归 RP-14，虽然它依赖本包的绑定关系。
- **代码的语义分析**——那是技能的事，归 RP-10/RP-12。

## 需求条目

### 绑定与凭据

| ID | 需求 |
|---|---|
| R-09-01 | 项目可以绑定零个或多个代码仓。绑定通过 MCP 建立，需项目所有者或维护者权限。 |
| R-09-02 | 支持 GitHub、Gitea（自建）、GitLab（自建与 SaaS）三类平台（D5）。绑定时声明平台类型、仓库地址、默认分支。 |
| R-09-03 | 凭据**必须是只读的**。绑定时要求提供只读凭据，并在绑定生效前**实际验证一次**它确实能读、且**确实不能写**。 |
| R-09-04 | 凭据加密存储，任何接口都不能读出原文，包括项目所有者自己。展示时只给可识别的片段与来源说明。 |
| R-09-05 | 凭据可以被轮换与撤销。撤销后依赖该凭据的执行立即失败，不使用任何缓存的凭据。 |
| R-09-06 | 凭据在传递给执行环境时，只注入到实际需要它的那一次拉取动作，**不得进入 Agent 可读的上下文、环境变量或日志**。 |
| R-09-07 | 每次使用凭据访问仓库产生审计事件：哪个项目、哪个仓、哪次执行、拉取了什么修订（RP-04）。 |

### 工作区

| ID | 需求 |
|---|---|
| R-09-08 | 服务端维护受控工作区，Agent 执行时在其中读取代码。**源码不发送给任何个人终端。** |
| R-09-09 | 工作区按项目隔离。**一次执行不得同时持有多个项目的代码上下文。** |
| R-09-10 | 工作区可以定位到具体修订（分支、标签、提交），执行记录必须记下本次读的是哪个修订——否则"这份代码检视报告针对哪版代码"无法回答。 |
| R-09-11 | 工作区是**只读挂载**给 Agent 的。Agent 在工作区内的任何写入不得回流到仓库，且在执行结束后被丢弃。 |
| R-09-12 | 工作区支持增量更新，不要求每次执行都全量克隆。 |
| R-09-13 | 工作区有明确的生命周期与清理策略；长期不用的工作区可被回收，回收后下次执行自动重建。 |
| R-09-14 | 大仓库的拉取有容量与时间上限，超限时执行失败并明确报告，**不允许无限制占用**。 |

## 数据与不变量

- **I-09-1**：XOps 在任何代码路径上都不持有仓库写权限（与 I-05-3 同源）。
- **I-09-2**：凭据原文不出现在日志、执行输出、Agent 上下文或任何查询结果中。
- **I-09-3**：一次执行的工作区只包含一个项目的代码。
- **I-09-4**：每次执行记录其读取的确切修订标识。

## 验收标准

- 分别对 GitHub、Gitea、GitLab 各绑定一个仓并成功拉取。
- 提供一个具备写权限的凭据时，绑定被拒绝（R-09-03 的"确实不能写"验证生效）。
- 凭据绑定后，通过任何接口都无法读出原文。
- 撤销凭据后，正在使用它的下一次执行失败，且失败原因明确指向凭据。
- 检查执行日志与 Agent 上下文：不含凭据原文。
- 一次执行的工作区中不存在其它项目的文件。
- 执行记录中能查到本次读取的确切提交标识。
- Agent 在工作区内写文件后，仓库无变化，且执行结束后写入内容被清理。
- 超过容量上限的仓库拉取失败并明确报告。

## MVP 子集

**以裁剪后的子集纳入 MVP。**

MVP 做到：
- **只支持一个平台先跑通**（建议 GitHub，因为 webhook 与只读 token 的形态最标准，且你上一版就在 GitHub）。另外两个平台在 MVP 之后补，需求条目已经写好，补的是适配不是设计。
- 单仓绑定（一个项目一个仓），不做多仓。
- 全量克隆即可，不做增量（R-09-12 推迟）。
- 工作区清理可以粗暴（每次执行后直接删），不做生命周期管理（R-09-13 推迟）。

**不可裁剪**：R-09-03（只读验证）、R-09-04（凭据不可读出）、R-09-06（不进 Agent 上下文）、R-09-09（项目隔离）、R-09-10（记录修订）、R-09-11（Agent 写入不回流）。这六条是安全属性，事后补等于先裸奔一段时间。

## 风险与待定

- **R-09-03 的"验证确实不能写"实现难度不一。** GitHub 的细粒度 PAT 与 GitHub App 能明确表达只读；Gitea 与 GitLab 的 deploy token / project access token 也有只读档位，但"验证它不能写"这件事本身需要尝试一次写操作或读取权限元数据，两条路都有平台差异。**这条可能需要降级成"读取并校验权限元数据，无法确认时明确告警"**，但不要直接删掉——一个悄悄拿着写权限的服务端是很大的风险。

- **Q5 联动**：如果实例上有互不信任的用户，R-09-09 的项目隔离就从"整洁"变成"安全边界"，隔离强度要求会显著提升（进程/容器级而非目录级）。这条与 RP-12 的沙箱要求是同一个问题的两面。

- **私有网络的自建 Gitea/GitLab** 可能不允许 XOps 直接访问。这会引出"是否需要一个部署在客户网络内的拉取代理"，那是一整块新东西。**建议 MVP 明确假设：XOps 能直接访问所有绑定的仓库地址。** 如果这个假设不成立，需要单独讨论。

- **单仓还是多仓**：R-09-01 写的是"零个或多个"，但 D7 提到"支持多仓"是在模型凭据的语境下。项目绑定多仓在代码检视场景是合理的（一个产品跨多个仓），但会让 R-09-09 的"一次执行只持有一个项目的代码"需要细化成"只持有本次任务声明的那些仓"。**MVP 先做单仓，把这条留到有真实多仓需求时再定。**
