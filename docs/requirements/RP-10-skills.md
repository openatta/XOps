# RP-10 技能资产与生命周期

## 归属与依赖

- **依赖**：RP-02（技能归属项目）、RP-03（创建走 MCP）、RP-04（留痕）。
- **被依赖**：RP-11（任务引用技能）、RP-12（执行技能）。
- **不做这个包会阻塞谁**：整个执行域。没有技能，Agent 不知道该干什么。

## 背景与价值

你的第 3、4 条需求：**项目中可以创建 SKILLS**，然后 **AGENT + SKILLS 执行任务，输出 MD 或 HTML**。

技能是这个平台上**用户自己写的、决定 Agent 干什么的东西**。它同时是产品的核心价值和最大的风险面：

- **价值**：把"我这次是怎么让 AI 做代码检视的"从一次性的对话，固化成可重复、可定时、可分享的资产。有效的经验固化回技能，形成自动化。
- **风险**：技能是**别人写的、会在服务端执行、能读到代码仓**的东西。它比缺陷描述危险得多——缺陷描述只是被读进上下文，技能是主动指挥 Agent 的指令。

有一条设计纪律必须从一开始就在：**上传不执行。**

| 阶段 | 发生什么 |
|---|---|
| **上传** | 只存放，**不执行** |
| **测试执行** | 在受控范围内试跑，作者看结果、改了再试 |
| **发布** | 通过测试后发布，进入可被自动触发的池子 |
| **执行** | 定时、手动、事件触发（归 RP-14） |

这条防的**不主要是别人，是作者自己**：一份还没试过的技能被自动跑起来，浪费的是服务端算力，产出的是没人信的报告。分阶段让作者先看清它干了什么。

关于**发布是否需要审批**，跨仓协作设计里有一条明确判断，值得直接采纳：

> **技能是每个人自己的副本，因此发布不需要批准。** 一个人发布自己的技能，影响的只有他自己那份分析与他自己的报告——它不改变任何团队的 Agent 行为，也不扩大他本来就有的只读范围。

这条在 XOps 里要稍作调整：技能归属项目而非个人，所以"发布"影响的是项目内的自动执行。但结论方向不变——**不为技能发布造一套审批流程**，权限用项目角色控制即可。

## 范围

### 包含

- 技能的创建、更新、版本化
- 技能的生命周期状态：草稿 → 测试通过 → 已发布 → 已停用
- 技能声明它需要什么（是否需要读代码仓、期望的输入、产出格式）
- 技能的测试执行入口
- 技能查询

### 不包含

- **技能的实际执行**——归 RP-12。
- **技能的调度与触发**——归 RP-14。
- **执行产物**——归 RP-13。
- **跨项目的技能市场/共享**——明确不做。要让一份技能成为共享资产，走的是把它合入代码仓主线，那是 Git 侧的事。
- **技能内容的自动审查**——不用模型判断技能是否安全（G8）。安全性靠 RP-12 的沙箱边界保证，不靠内容审查。

## 需求条目

### 定义与版本

| ID | 需求 |
|---|---|
| R-10-01 | 技能归属项目，由项目成员通过 MCP 创建（G1）。 |
| R-10-02 | 技能有稳定标识与人类可读名称；名称在项目内唯一。 |
| R-10-03 | 技能内容**版本化且已发布版本不可变**。修改产生新版本。 |
| R-10-04 | 技能声明其**输入契约**：需要哪些参数、各自的类型与是否必填。任务（RP-11）按此契约提供输入。 |
| R-10-05 | 技能声明其**产出格式**：Markdown 或 HTML（你的第 4 条需求）。 |
| R-10-06 | 技能声明它是否需要**读取代码仓**，以及需要哪个绑定（RP-09）。不声明需要代码仓的技能，执行时**不得**获得工作区访问。 |
| R-10-07 | 技能声明其**资源预期**：预计执行时长上限。超出时由 RP-12 终止。 |

### 生命周期

| ID | 需求 |
|---|---|
| R-10-08 | 技能状态至少包含：草稿、测试通过、已发布、已停用。 |
| R-10-09 | **上传不执行。** 处于草稿状态的技能不会被任何自动触发路径执行。 |
| R-10-10 | 技能必须经过至少一次成功的**测试执行**才能发布。测试执行由作者手动发起，在与正式执行相同的沙箱中进行。 |
| R-10-11 | 发布需要项目成员权限即可，**不经过审批流程**。 |
| R-10-12 | 已发布的技能可以停用；停用后不再被自动触发，但历史执行记录完整保留。 |
| R-10-13 | 技能的创建、发版、发布、停用全部产生审计事件（RP-04）。 |

### 安全

| ID | 需求 |
|---|---|
| R-10-14 | 技能内容是**不可信输入**（G7）。平台不解析其语义、不因其内容改变控制流，只负责把它交给执行环境。 |
| R-10-15 | 技能不得声明或获取超出其所属项目范围的任何资源——不能读别的项目的代码仓、缺陷、执行记录。 |
| R-10-16 | 技能不得通过任何方式写入确定性平面（G8）：不能创建缺陷之外的业务对象、不能改变审批状态、不能修改项目成员或角色（R-02-11）。 |

## 数据与不变量

- **I-10-1**：已发布的技能版本不可变。
- **I-10-2**：未经测试执行的技能不可发布。
- **I-10-3**：技能能触及的资源范围完全由其项目归属与显式声明决定，不存在隐式扩权路径。
- **I-10-4**：历史执行记录始终能追溯到它当时用的技能版本。

## 接口面

**MCP tools**

| 意图 | 说明 |
|---|---|
| 创建技能 | 含内容与声明 |
| 更新技能 | 产生新版本 |
| 发起测试执行 | 手动，作者可见结果 |
| 发布技能 | 需已有成功测试执行 |

**只读查询面**（供 RP-15）

- 项目技能列表与状态
- 技能版本历史与内容
- 技能的执行历史入口（跳转 RP-13）

## 验收标准

- 通过 MCP 创建一个技能，状态为草稿。
- 草稿技能无法被定时或事件触发执行（尝试触发时明确拒绝）。
- 未经测试执行直接发布被拒绝。
- 完成一次测试执行后发布成功。
- 发布 v1 后修改内容产生 v2，v1 内容不变，且已有的历史执行记录仍指向 v1。
- 一个未声明需要代码仓的技能，在执行时无法访问任何工作区。
- 技能试图访问其它项目的资源时失败。
- 停用技能后自动触发不再执行它，历史记录仍可查。

## MVP 子集

**以裁剪后的子集纳入 MVP。**

MVP 做到：
- 创建技能、声明输入契约与产出格式、声明是否需要代码仓
- 状态简化为两态：**草稿 / 已发布**，且保留"必须先测试执行成功才能发布"这条
- 版本化保留（R-10-03），但版本管理体验可以最朴素

MVP 可推迟：
- 停用（R-10-12）
- 资源预期声明（R-10-07）——MVP 用全局统一的执行时长上限
- 测试执行与正式执行的差异化（MVP 两者用同一条路径，只是不产生正式记录）

**不可裁剪**：R-10-09（上传不执行）、R-10-06（不声明就没有工作区）、R-10-14/15/16（安全三条）、R-10-10（发布前必须测试过）。

## 风险与待定

- **技能的内容形态未定**——是 Markdown 提示词、是结构化的步骤定义、还是 dsh 的插件形式？这与 Q2（dsh 集成形态）强耦合，属于设计选型，本需求文档不定。但需求侧有一条约束要传下去：**无论什么形态，R-10-04 的输入契约必须是可机读的**，否则 RP-11 的任务无法校验自己提供的输入是否匹配。

- **R-10-10 "必须测试执行成功"里的"成功"怎么判定？** 技能执行完成不代表结果有用。建议 MVP 只要求"执行完成且未报错"，由作者自己看产出决定是否发布——**不要试图自动判断产出质量**，那是判断题（G8）。

- **R-10-15/16 的强制点在哪里**是这个包最大的实现风险。这些约束不能靠"技能内容里没写坏话"来保证，必须由 RP-12 的执行环境从能力上封死——Agent 手里只有它该有的工具，没有别的。**这条要在 RP-12 的设计里兑现，本包只负责声明。**

- **技能与 XForge Skill 的关系**没有定义。XForge 也有 Skill 概念（投影到编程工具里的指导资产），两者同名但完全不同：XForge Skill 指导本地 Agent 怎么工作，XOps 技能是服务端执行的分析任务。**建议在术语上区分开**（例如 XOps 侧叫"分析技能"或"任务技能"），否则文档和对话里会持续混淆。
