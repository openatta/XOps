# RP-10 任务与执行策略

> 平台只有一种任务 · token 上限 · 终止时序 · 重叠策略 · onComplete 深度 1

## 归属与依赖

- **依赖**：RP-09 技能资产（任务引用一个已发布的技能）、RP-04 表引擎（任务声明写哪些表）、RP-03 MCP 基座。
- **被依赖**：RP-11 事件、触发与派工单 · RP-12 产出落地与保留期 · RP-16 脚本载体与插件（造插件任务是一种任务）。
- **里程碑**：M2。
- **独立性**：任务是一份**定义**——引用哪个技能、写哪些表、什么策略、完成后干嘛。**定义能不能建对、校验能不能挡住，不需要它真的跑起来。**

## Crate 归属

| crate | 本包是否新建 | 对外只经什么被用 |
|---|---|---|
| `xops-task` | **新建** | 任务定义的读写 · 执行策略 · onComplete 的挂点与深度校验 |

> ⚠️ **`xops-task` 会被 RP-12 再动一次**（写入路径与清理）。**两者是顺序的两次 Change，不并行。** 本包要把 crate 内部分成"定义 / 策略 / 写入路径"三块，让 RP-12 只动第三块。

## 背景与价值

**平台只有这一种任务。** 质量监管、审批、CI 触发、代码走读四种常见用法在平台看来完全一样：

```text
某个事件发生了 → 某个任务订阅了它 → 跑一次技能 → 往声明的表里写几行
```

**平台不认识这四个词。** 这是 P1「尽量简单」在执行面的兑现——一旦开始为"审批任务"和"检查任务"分别建模，就会长出两套对象、两套视图、两套权限。

**本包认领一条不能推迟的：**

| 条目 | 为什么不能推迟 |
|---|---|
| **`TSK-005` 单次 token 上限** | M3 一开定时触发，没有它就是**无上限烧钱**。这是自动化系统最常见的故障形态。引擎侧的单次预算给了落点，**但闸门的语义在本包** |

**两条形状很小、后果很大的：**

| 条 | 不做会怎样 |
|---|---|
| **`TSK-011` onComplete 深度硬限制 1** | **一层是"输出后处理"，两层就是任务编排 DAG**，随之而来的是依赖解析、失败传播、循环检测及其可视化。**创建时就校验，不满足直接拒绝** |
| **`TSK-008` 重叠策略默认跳过** | 定时任务最常见的故障是**执行变慢后堆积成雪崩**。默认排队等于默认雪崩 |

**还有一条时序是定死的**（`TSK-006`，超时与被取消走同一条路）：

```text
① 中止模型调用与会话（先停掉烧钱的那一头）
② 收敛并移交容器里已产生的行
③ **先落 `_runs`**（status / failureKind / tokensUsed），**再写产出行**
④ 销毁容器
```

③ 的顺序不是洁癖：`FLW-026⑥` 要读"这次执行是否正常完成"才能判断产出行算不算结算。**本包定义这个时序，RP-12 实现它的写入那一半。**

## 范围

### 包含

- 任务定义：引用**已发布**技能（默认固定版本）· 输入参数满足技能的输入契约 · **写哪些表**
- **执行策略**：超时 · **重叠策略** · 启停 · **单次 token 上限** · 两个保留期的**声明**
- **终止时序**的定义（`TSK-006`）与失败归类的对接
- **`onComplete`**（挂插件 / 挂任务 / 空）与**深度硬限制 1** 的创建时校验
- 后处理失败不影响主任务的记录
- 任务的**两种归属**（沿用 RP-09 的公共 / 私有规则）
- **造插件任务这一受限特例**的约束（只能手动触发、不能订阅任何事件）
- 执行历史与触发历史的查询（**含被拒绝与被跳过的**）
- 不做项目级额度与限流

### 明确不包含

- **技能本身**——归 RP-09。
- **事件订阅的分发与触发**——归 RP-11。**本包定义"这个任务订阅什么"，RP-11 决定"什么时候真的触发"。**
- **派工单装配**（`TSK-015`）——归 RP-11，它与 `EXE-001` 是同一件事的两半。
- **平台侧写入与保留期的实现**——归 RP-12。**本包只声明保留期，不实现清理作业。**
- **容器与执行**——归 RP-07。
- **插件本身**——归 RP-16。本包只提供 `onComplete` 的挂点。
- **流程相关的判定**——归 RP-15。本包写行，**不判断这一行算不算结算**。

## 关键不变量

`I-S`（onComplete 深度硬限制 1）· `I-V`（每次执行都有 token 上限，撞上即强制终止）· `I-C`（归属）· `I-I`（不扩权）。

## 接口面

**MCP tools**：创建 / 更新任务 · 启用 / 停用 · 声明订阅哪些事件、读哪些数据源、写哪张表、**onComplete 挂什么** · **配置单次 token 上限与两个保留期** · 查询执行历史与触发历史（含被拒绝与被跳过的）。

**对内提供给 RP-11 / RP-12 / RP-16**：

```text
resolve(task) -> 技能引用 + 订阅声明 + 写入目标 + 执行策略 + onComplete
```

## 验收标准

- **引用草稿技能被拒绝**；技能版本策略**默认固定版本**（跟随最新必须是明确选择）。
- **输入契约不满足时创建失败**，且**指明缺哪个参数**。
- **未声明的表写不了**：任务声明写 A 表，尝试写 B 表被拒绝。
- **token 上限**：撞上即强制终止，归入"超出 token 预算"；**已产生的行仍然写入，但标注来自未正常完成的执行**。
- **终止时序**：超时与取消**走同一条路**，且顺序是 ①②③④——**`_runs` 先于产出行**。
- **重叠策略三选一**且**默认跳过**；被跳过的触发**有痕迹可查**（这条要实际构造一次跳过并查到它）。
- **停用的任务不响应任何触发，包括手动**。
- **不提供删除任务**：执行记录不能因为任务没了就丢。
- **onComplete 深度 1**：给一个被挂在 onComplete 上的任务再挂一个 onComplete，**创建时被拒绝**。
- **后处理失败不影响主记录**：构造一次 onComplete 失败，`_runs` 那一行**完好**，且**通知任务所有者**。
- **造插件任务**：尝试给它订阅一个事件，**创建时被拒绝**。
- **项目级额度与限流不存在**：枚举代码，没有任何项目级配额判定。

## 内部工作包建议

一次 **Solid Change**：

```text
WP-A 任务定义（引用已发布技能、输入契约校验、写入目标声明、归属）
        │
        ├──► WP-B 执行策略（超时 / 重叠策略 / 启停 / token 上限 / 两个保留期的声明）
        │            + 终止时序的定义
        │
        └──► WP-C onComplete（挂插件 / 挂任务 / 空）+ 深度 1 的创建时校验
                    + 造插件任务的受限特例
                    + 执行历史与触发历史查询
```

**crate 内部要分成"定义 / 策略 / 写入路径"三块**——RP-12 只动第三块，分层错了它就会踩进本包的核心逻辑。

## 风险与待定

- **`TSK-005` token 上限的"闸门语义在本包、落点在引擎侧"这条接缝要早定。** 引擎有单次预算与对应的停止原因，**但"撞上之后怎么归类、已产生的行怎么标注"是本包的事**。两边对不齐的表现是：钱停了，但那次执行被记成了正常完成——**而正常完成的产出行是会结算流程节点的**。
- **`TSK-006` 的终止时序定义在本包、实现在 RP-12**。建议本包把时序写成一个可测试的状态机，**让 RP-12 去实现它而不是重新设计它**。
- **Q10（出网白名单由谁批准）**未定。本包实现"声明 + 默认拒绝"的机制，**自定义白名单在 Q10 定下来之前不开放**（`TSK-017`）。
- **"平台只有一种任务"是一条持续受压的边界。** 造插件任务已经是一个受限特例了；**第二个特例出现时，应当先问它是不是可以用声明表达**，而不是再加一种任务。
