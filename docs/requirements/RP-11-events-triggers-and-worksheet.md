# RP-11 事件、触发与派工单

> 事件白名单恰好五类 · 非阻塞/幂等/留痕 · 手动触发 · 派工单不扩权

## 归属与依赖

- **依赖**：RP-10 任务与执行策略（订阅声明由它持有）、RP-09 技能资产（声明由它持有）、**RP-07 执行运行时（只依赖它的契约**，契约一定型即可并行开发）。
- **增强来源**：RP-08 Git 仓绑定——做完之后，技能才多出"能读代码"这项能力。
- **被依赖**：RP-12 产出落地与保留期（执行由本包提交）、RP-13 自动触发（两类事件源接在本包的分发层上）、RP-14 流程定义与实例（「节点被激活」塞进本包的分发层）。
- **里程碑**：M2。
- **独立性**：RP-08 未就位时本包仍可完整验收——技能声明自己**不需要代码仓**、只吃任务的输入参数，链路一样跑得通。

## 背景与价值

这个包是"技能与任务"这三包里**唯一真的让东西跑起来**的一个。它管两件事：**什么时候跑**，和**跑的时候能看见什么**。

### 事件白名单恰好五类，且后两类不能自己订阅

```text
定时 · Git 事件 · 手动触发        ← 任务自己声明订阅，按载荷过滤
流程节点被激活                    ← 唯一订阅途径是**被某个节点指定为写入者**
上游任务完成                      ← 唯一订阅途径是**被某个任务挂在 onComplete 上**
```

> ⚠️ **白名单里永远不加"某张表被写入"。** 一旦任务能订阅表的变化，就有了**不受深度限制的回路**——A 写表触发 B，B 写表触发 A。需要串联就用 onComplete 那一层，或在一个技能内部做完多步。

**还有一条必须在实现上分很开的**（`TRG-005`）：

> **一行被写进表时，平台确实会去求值相关流程节点的插件。那是插件求值，不是触发任务**——插件跑在载体里、毫秒级、**不产生执行、不烧模型调用**。两条路混在一起的后果是：**一次写入变成一次模型调用。**

### 三条共同纪律

```text
非阻塞   触发的产出是"一次执行进了队列"，不是"任务跑完了"
幂等     同一个外部事件最多产生一次执行
留痕     被拒绝的、被重叠策略跳过的触发，同样留痕
         —— **一个静默被跳过的任务，会让人以为它在跑**
```

### 派工单：一次执行能看见什么，到此为止

```text
派工单（不可变）
  技能内容与版本 · 输入 · 数据源清单 · 写入目标 · 超时
  触发事件的完整载荷 · 触发者
  **不含任何凭据**；**只放技能实际声明的东西，不扩权**
```

`TSK-015` 与 `EXE-001` 是同一件事的两半（一个说"装配时不扩权"，一个说"派工单不可变、内容是这几样"），**所以两条都在本包**。

**两类数据源，一律显式声明，未声明的不提供**：代码（只读挂载，定位到确切修订）· 外部网络（默认拒绝 + 白名单）。**表数据不是数据源**（D44）——不给容器快照文件，也不给它到 XOps 的网络路径。

**最后一条容易漏的**：`TRG-017` **事件载荷覆盖任务定义里写死的目标修订**。少了这条，执行读的是"仓库现在长什么样"，不是"这次要它看的那一版"。

## 范围

### 包含

- **事件分发层**：白名单恰好五类、订阅规则、后两类的订阅途径
- **三条共同纪律**：非阻塞 · 幂等 · 留痕
- 触发前检查（任务存在、已启用、允许这种触发方式），任一不满足则拒绝并留痕
- **手动触发**（经 MCP，非阻塞，可带幂等键与目标修订）
- **事件载荷覆盖任务定义的目标修订**
- 「上游任务完成」的载荷
- **触发时不允许覆盖任务的输入参数**

- **产出行的落库与保留期**——归 RP-12。本包提交执行，**不负责结果怎么落**。

**MCP tools**：**手动触发（非阻塞，返回执行标识）** · 查询执行状态 · 取消执行。

## 验收标准

- **事件白名单恰好五类**：尝试订阅"某张表被写入"，**创建时被拒绝**；枚举分发层，**没有第六种事件源**。
- **后两类不能自己订阅**：直接声明订阅「流程节点被激活」或「上游任务完成」，**被拒绝**。
- **插件求值不是触发任务**：往一张结算表写一行，**不产生任何执行、不产生任何模型调用**（这条要实测计数，不是读代码）。
- **非阻塞**：手动触发**立即返回执行标识**，不等执行完成。
- **幂等**：同一幂等键 / 同一外部事件标识，**不产生第二次执行**。
- **留痕**：被拒绝的触发、被重叠策略跳过的触发，**都能查到**。这条要实际构造一次跳过并查到它。
- **触发前检查**：任务不存在 / 已停用 / 不允许这种触发方式——**三种都拒绝并留痕**。
- **载荷覆盖任务定义的修订**：任务里写死修订 A，事件带来修订 B，**执行读的是 B**。
- **触发不允许覆盖输入参数**（`TRG-020`）：尝试在触发时带参数，**被拒绝**。
- **派工单不可变**：装配之后不可改。
- **派工单不扩权**：**枚举它的每一个字段，逐个对得上某条声明**；含有任何未声明的东西即失败。
- **派工单不含凭据**：检查完整派工单内容，无任何凭据形状的值。
- **未声明代码数据源的执行**：容器中**确实没有任何工作区挂载**。
- **表不是数据源**：枚举派工单与容器环境，**没有任何表快照、也没有任何到 XOps 的网络路径**。
- **对着 RP-07 的桩实现可完整验收**：换成真实现后不改本包代码。
- **不依赖 RP-08 也能跑通**：声明"不需要代码仓"的技能，全链路正常。

## 风险与待定

- **`TRG-005`「写入触发的是插件求值，不是任务」要在 WP-A 的分发层就分开。** 等 RP-15/RP-16 接进来时才发现两条路混在一起，**代价是一次写入变成一次模型调用**——而这个错误在小数据量下测不出来。
- **分发层的形状是本包最要紧的一处设计。** RP-13 要往上接两类事件源，RP-14 要往里塞「节点被激活」。**形状定错，那两个包都要回头改本 crate**——而本 crate 到那时已经在跑了。
- **Q10（出网白名单由谁批准）**未定。本包实现"默认拒绝 + 声明白名单"的机制，**自定义白名单在 Q10 定下来之前不开放**。
- **`TSK-015` 与 `EXE-001` 必须一起做。** 它们是同一件事的两半，分开做的结果是"装配时检查了不扩权，但派工单结构里留了一个可以塞东西的口子"。
