# RP-11 任务定义

## 归属与依赖

- **依赖**：RP-10（任务引用技能）、RP-09（任务可声明目标代码仓）、RP-02、RP-03。
- **被依赖**：RP-12（执行任务）、RP-13（执行记录归属任务）、RP-14（触发任务）。
- **不做这个包会阻塞谁**：RP-12 与 RP-14。

## 背景与价值

你的第 3、4、6 条需求交汇在这里：**项目中创建任务** → **后台 AGENT 根据用户的任务来执行** → **触发有定时、手动、Git Hook、MCP 四种**。

技能（RP-10）是"怎么做"，任务是"对什么做、什么时候做、做完给谁看"。把两者分开的理由很实际：

> **同一个技能，会被用在不同的仓、不同的分支、不同的节奏上。**

一份"代码检视"技能，可能同时是"每天夜里跑一遍主干"和"每次 PR 触发跑一遍改动"两个任务。如果把触发与目标写死在技能里，技能就无法复用，每换一个用法就要复制一份内容——然后它们会各自演化，再也合不回去。

任务还有一个职责：**承载执行的历史。** 你的第 4 条明确要求"可以查看任务每次执行的输出"，所以执行记录必须挂在一个稳定的对象上，那就是任务。

## 范围

### 包含

- 任务的创建、更新、启用/停用
- 任务引用技能（含版本策略）
- 任务的输入参数（满足技能的输入契约）
- 任务的目标代码仓与修订范围
- 任务的触发方式声明（具体触发机制归 RP-14）
- 任务的并发与重叠策略
- 任务查询

### 不包含

- **实际执行**——归 RP-12。
- **触发机制的实现**——归 RP-14。本包只声明"这个任务允许被哪些方式触发"。
- **执行记录与产物**——归 RP-13。
- **任务之间的依赖编排**——明确不做，见"风险与待定"。

## 需求条目

### 定义

| ID | 需求 |
|---|---|
| R-11-01 | 任务归属项目，由项目成员通过 MCP 创建（G1）。 |
| R-11-02 | 任务引用一个**已发布**的技能。引用草稿技能被拒绝（R-10-09）。 |
| R-11-03 | 任务声明技能版本策略：**固定版本**（始终用某一版）或**跟随最新发布版**。默认固定版本——跟随最新意味着技能作者一次发布会改变所有引用它的任务的行为，这应当是明确选择而不是默认。 |
| R-11-04 | 任务提供的输入参数必须满足技能声明的输入契约（R-10-04）。不满足时创建失败并指明缺哪个参数。 |
| R-11-05 | 若技能声明需要代码仓（R-10-06），任务必须指定使用项目的哪个代码仓绑定，以及目标修订范围（分支、或"触发事件带来的修订"）。 |
| R-11-06 | 任务声明它允许的触发方式（手动、定时、Git Hook、MCP），可多选。未声明的触发方式对该任务无效。 |
| R-11-07 | 任务可以被启用与停用。停用的任务不响应任何触发，包括手动。 |

### 执行策略

| ID | 需求 |
|---|---|
| R-11-08 | 任务声明**重叠策略**：上一次执行尚未结束时又被触发，是**跳过本次**、**排队等待**、还是**终止上一次并重跑**。默认跳过——定时任务最常见的故障是执行变慢后堆积成雪崩。 |
| R-11-09 | 任务声明单次执行的**超时上限**；未声明时使用项目或平台默认值。 |
| R-11-10 | 任务可以声明失败重试次数与间隔。默认不重试——**一个会读代码、调模型、产出报告的任务，盲目重试的代价不小且很少有用**。 |
| R-11-11 | 任务的创建、更新、启停产生审计事件（RP-04）。 |

### 查询

| ID | 需求 |
|---|---|
| R-11-12 | 支持按项目、状态、引用技能、触发方式查询任务。 |
| R-11-13 | 任务详情包含其最近若干次执行的摘要（状态、时间、产物入口），完整历史归 RP-13。 |

## 数据与不变量

- **I-11-1**：任务始终引用一个确定的技能版本——即使版本策略是"跟随最新"，每次执行也必须记下当次实际用的版本。
- **I-11-2**：停用的任务不存在任何可被触发的路径。
- **I-11-3**：任务的输入参数在创建时已通过契约校验，执行时不再有"参数对不上"这类失败。
- **I-11-4**：任务的执行记录永不因任务被修改或删除而丢失。

## 验收标准

- 创建一个引用已发布技能的任务，参数校验通过。
- 引用草稿技能创建任务被拒绝。
- 缺少技能契约必填参数时创建失败，错误指明缺哪个。
- 技能声明需要代码仓但任务未指定绑定时，创建失败。
- 停用任务后，手动触发、定时触发、Git Hook 触发全部无效。
- 重叠策略为"跳过"时，上次执行未结束期间的触发被跳过且留痕。
- 版本策略为"固定版本"的任务，在技能发布新版后行为不变。
- 任务被修改后，此前的执行记录仍指向修改前的配置。

## MVP 子集

**以裁剪后的子集纳入 MVP。**

MVP 做到：
- 创建任务、引用技能（**只支持固定版本**）、提供输入参数、指定代码仓与分支
- 触发方式**只支持手动**（R-11-06 的其它三种随 RP-14 在 MVP 之后补）
- 启用/停用
- 超时上限（R-11-09）用平台统一默认值

MVP 可推迟：
- 重叠策略（R-11-08）——MVP 只有手动触发，堆积风险低，但**默认行为要是"跳过"**，不要留一个会堆积的默认
- 重试（R-11-10）
- 跟随最新版本策略（R-11-03 的另一半）

**不可裁剪**：R-11-02（只引用已发布技能）、R-11-04（契约校验）、I-11-1（记录实际使用的版本）、I-11-4（执行记录不随任务删除而丢失）。

## 风险与待定

- **任务编排明确不做。** 一旦支持"任务 A 完成后触发任务 B"，就需要 DAG、依赖解析、失败传播、循环检测，以及它们的可视化——这正是 §"不长成平台"那条边界要拦住的东西。如果真的需要串联，用一个技能内部完成多步，或者用 MCP 触发（RP-14）由外部编排方驱动。**这条建议写死。**

- **R-11-05 的"目标修订范围"在不同触发方式下语义不同**：定时触发是"当前分支头"，Git Hook 触发是"事件带来的那个提交"，手动触发可能是"用户指定的"。这三种需要在 RP-14 的设计里统一表达，否则技能拿到的上下文会不一致。**需求侧的约束是：无论哪种触发，执行记录必须记下确切修订（R-09-10）。**

- **任务的输入参数是否可以在触发时覆盖**没有定义。手动触发时想临时改个参数是很自然的需求，但一旦允许覆盖，R-11-04 的创建期校验就要在触发期再做一遍，而且执行记录要记下实际用的参数而非任务定义的参数。**建议 MVP 不允许覆盖**，需要不同参数就建不同任务；等真实需要出现再加。

- **删除任务的语义未定。** I-11-4 要求执行记录不丢，所以"删除"实际只能是停用+隐藏。建议直接不提供删除，只提供停用——少一个会让人误以为数据没了的操作。
