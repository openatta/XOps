# RP-12 Agent 执行运行时

## 归属与依赖

- **依赖**：RP-11（执行什么）、RP-10（技能内容与声明）、RP-09（代码工作区）、RP-04（留痕）。
- **被依赖**：RP-13（产出记录）、RP-14（触发后进入执行）。
- **不做这个包会阻塞谁**：整个执行域的价值。没有它，技能与任务都只是配置。

## 背景与价值

你的第 4 条需求：**后台运行 AGENT，可以根据用户的任务来执行，通过 AGENT + SKILLS，执行任务，输出 MD 或 HTML 数据。**

这个包是 XOps 里**唯一允许模型参与的地方**。全局约束 G8 把系统劈成两半：

| 平面 | 做什么 | 用什么 |
|---|---|---|
| **确定性平面** | 账本、审批、审计、权限、同步 | 确定性代码，不用模型 |
| **分析平面** | 代码与文档分析、报告生成 | **Agent + 技能（本包）** |

**两个平面之间的隔离是硬要求：分析平面不得写确定性平面的任何数据。** 否则模型就能写证据与缺陷账本，前面所有纪律在服务端被绕过。

这条隔离是本包**最重要**的需求，比"能跑起来"重要。一个能跑但能越界写账本的运行时，比一个跑不起来的运行时危险得多。

D3 已定：**集成 deepseek-harness（dsh）作为执行引擎**。但**集成形态属于设计选型（Q2），本文档不做决定**——需求条目因此全部写成对能力的要求，不对实现形态做任何假设。

## 范围

### 包含

- 执行的排队、调度、并发控制
- 执行环境的隔离与资源限制
- 技能与任务上下文的装配
- 代码工作区的挂载（消费 RP-09）
- 模型凭据的注入（平台级，D7）
- 执行的超时、终止、失败处理
- Agent 可用工具的边界控制
- 产出的收集与移交（给 RP-13）

### 不包含

- **产物的存储与查询**——归 RP-13。本包只负责产生并移交。
- **触发**——归 RP-14。本包从队列取任务，不关心它怎么进来的。
- **技能内容的语义**——归 RP-10。
- **判断产出质量**——不做。产出好不好由人看（G8）。

## 需求条目

### 隔离与边界（最高优先）

| ID | 需求 |
|---|---|
| R-12-01 | **执行中的 Agent 不得写入确定性平面的任何数据**（G8）：不得创建/修改项目、成员、角色、技能、任务、审批实例与决策、审计事件。 |
| R-12-02 | 这条边界必须由**能力封锁**实现，不得依赖技能内容中"没有要求做这些事"。Agent 手里只有本次执行该有的工具，没有别的。 |
| R-12-03 | Agent 可用的工具集由本次执行的技能声明决定（R-10-06），未声明的能力一律不提供。特别地：未声明需要代码仓的技能，其执行环境中不存在任何工作区。 |
| R-12-04 | 一次执行只能触及**一个项目**的资源（继承 I-09-3）。跨项目访问在环境层面不可能，而不是被检查后拒绝。 |
| R-12-05 | 执行环境之间相互隔离：一次执行不得读取、影响另一次执行的文件系统、进程或网络状态。 |
| R-12-06 | 模型凭据、代码仓凭据、平台令牌**不得进入 Agent 可读的上下文**（R-09-06）。凭据只在确定性代码控制的边界内使用。 |
| R-12-07 | 执行环境的对外网络访问受限。默认只允许访问模型服务与已绑定的代码仓地址，其余出站访问默认拒绝。 |
| R-12-08 | Agent 对工作区的写入不回流仓库，且执行结束后销毁（R-09-11）。 |

### 执行

| ID | 需求 |
|---|---|
| R-12-09 | 执行是**后台异步**的：触发方提交后立即得到执行标识，不阻塞等待完成。 |
| R-12-10 | 执行有明确状态：排队中、执行中、已完成、已失败、已超时、已取消。 |
| R-12-11 | 执行超过任务声明的超时上限（R-11-09）时被强制终止，状态为已超时，**已产生的部分输出仍被保留**——一份跑了一半的报告通常仍有诊断价值。 |
| R-12-12 | 执行可以被有权限的人手动取消，已产生的部分输出保留。 |
| R-12-13 | 并发执行数有上限，按平台与项目两级控制，防止单个项目耗尽全部算力。 |
| R-12-14 | 执行失败时，失败原因被分类记录：技能错误、凭据错误、仓库拉取失败、模型服务错误、超时、资源不足。**"失败了"不是一个可用的结论。** |
| R-12-15 | 执行过程产生可回看的过程记录（步骤、工具调用、耗时），移交 RP-13。 |

### 产出

| ID | 需求 |
|---|---|
| R-12-16 | 执行产出 Markdown 或 HTML（R-10-05），移交 RP-13 存储。 |
| R-12-17 | 产出内容是**不可信内容**：它由模型生成，可能包含任意文本与标记。呈现方（RP-15）必须按不可信内容处理，本包在移交时明确标注其性质。 |
| R-12-18 | 每次执行记录：任务标识、实际使用的技能版本、代码仓修订、输入参数、开始与结束时间、状态、失败分类（I-11-1、R-09-10）。 |

### 凭据

| ID | 需求 |
|---|---|
| R-12-19 | 模型凭据是**平台级统一配置**（D7），沿用 dsh 的凭据方案，一套配置服务全部项目。 |
| R-12-20 | 凭据配置变更不需要重启服务，且不影响在途执行。 |
| R-12-21 | 凭据的使用量可按项目归集，供后续的用量观察（不要求做计费）。 |

## 数据与不变量

- **I-12-1**：不存在任何从执行环境写入确定性平面的代码路径。
- **I-12-2**：Agent 上下文中不含任何凭据。
- **I-12-3**：一次执行的资源可见范围完全由其项目归属与技能声明决定。
- **I-12-4**：每次执行都能追溯到确切的技能版本与代码修订。
- **I-12-5**：执行环境在结束后被完整销毁，不留残留状态。

## 验收标准

**隔离必须被主动攻击验证，不能只做正向测试。**

- 写一个**故意越界**的技能：尝试创建缺陷之外的对象、修改项目成员、读另一个项目的代码仓、读环境变量里的凭据、访问未授权的外网地址。**每一项都必须失败**，且失败发生在能力层（工具不存在 / 网络不通），不是靠内容检查拦下的。
- 未声明需要代码仓的技能，其执行环境中确实没有任何工作区文件。
- 检查执行的完整上下文与日志：不含任何凭据原文。
- 两次并发执行互相不可见（各自写同名文件互不干扰）。
- 超时的执行被终止，状态为已超时，部分输出可查。
- 手动取消的执行立即停止，部分输出可查。
- 六类失败原因各构造一次，分类正确。
- 执行记录中的技能版本与代码修订，与实际使用的一致。
- 执行结束后检查宿主：无残留进程、无残留工作区。

## MVP 子集

**以裁剪后的子集纳入 MVP。**

MVP 做到：
- 单机、串行或低并发执行（R-12-13 用一个很小的固定上限）
- 一种触发来源（手动）进来的任务能跑完并产出 Markdown
- 超时终止、状态机、失败分类（R-12-14 可以先分三类：技能错误 / 基础设施错误 / 超时）
- 过程记录可以粗（保留原始输出即可，不做结构化步骤）

MVP 可推迟：
- HTML 产出（R-12-16 先只支持 Markdown）
- 项目级并发配额（R-12-13 的两级控制先做平台级）
- 用量归集（R-12-21）
- 结构化的过程记录（R-12-15）

**不可裁剪——这是全部需求包里"不可裁剪"最多的一个**：R-12-01 到 R-12-08 全部八条隔离需求，加上 R-12-11（超时终止）、R-12-18（可追溯）、I-12-5（环境销毁）。

理由很直接：**这些是安全边界，先跑起来再补隔离，等于在补之前一直是敞开的**，而这段时间里跑过的技能、读过的代码、泄过的凭据都无法追回。如果 MVP 的时间压力大到做不完隔离，正确的做法是**缩小 MVP 到只有缺陷闭环**（把整个执行域推迟），而不是做一个隔离不全的执行运行时。

## 风险与待定

- **Q2：dsh 的集成形态**——子进程调 headless profile、作为 Cordis 插件嵌入、还是用 ACP 协议驱动常驻进程。三者在隔离强度、可观测性、升级成本、以及被 dsh 破坏性变更波及的程度上差别很大（dsh 目前是 0.1.0-rc 阶段，README 明确写了"未来将出现破坏兼容性的变更"）。**这是本包最大的未决项，专项讨论。**

- **Q3：沙箱的隔离强度需要明确到可验收。** R-12-01～R-12-08 说的是"要隔离什么"，但没说"隔离到什么强度"。目录级、进程级、容器级、还是虚拟机级，取决于 Q5（实例上的用户是否互相信任）。**在 Q5 有答案之前，本包的验收标准里那条"主动攻击验证"是唯一能挡住偷工减料的东西，不要删。**

- **dsh 处于 rc 阶段**是一个真实的时间风险。它自带 Cordis 架构与代码生成构建流水线，深度绑定的代价在它稳定之前会反复付。这不改变 D3，但值得在 Q2 的专项讨论里作为一项权重。

- **R-12-07 的网络限制与技能的实际需要可能冲突**。一个"查询依赖库有没有已知漏洞"的技能需要访问外部数据源。建议在 RP-10 的技能声明里增加"需要访问哪些外部地址"，走白名单，而不是放开默认出站。**这条会反过来给 RP-10 加一条需求，等 Q3 定了一起加。**

- **成本没有约束机制。** 平台级统一凭据（D7）意味着任何项目成员创建的任务都在花同一份预算，而 Agent 执行的成本上限很难预估。R-12-21 只做归集不做限制。**建议在 MVP 之后尽早增加项目级的用量上限**，否则一个写错的定时任务可以在一夜之间花掉全部额度。
