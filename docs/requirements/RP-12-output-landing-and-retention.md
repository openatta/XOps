# RP-12 产出落地与保留期

> 平台在容器外写入 · 两层拒绝 · retainUntil · 到期清理与豁免清单

## 归属与依赖

- **依赖**：RP-11 事件、触发与派工单（执行由它提交）、RP-10 任务与执行策略（保留期与终止时序由它声明）、RP-04 表引擎（写入落在它的路径上）。
- **被依赖**：RP-15 结算判定与保护（`FLW-026⑥` 要读 `_runs.status`）、RP-16（`_plugins.generatedBy` 的悬空问题）。
- **里程碑**：M2。
- **独立性**：给定一份执行结果（若干待写入的行 + 状态 + 失败分类 + 过程记录），把它正确落进 `_runs` 与目标表，并让它到期时被清理掉——**用一份假的执行结果就能完整验收**。

## Crate 归属

| crate | 本包是否新建 | 对外只经什么被用 |
|---|---|---|
| `xops-task`（写入路径与清理模块） | **改，不新建** | 领取执行结果并落库 · 到期清理作业 |

> ⚠️ **本包改的是 RP-10 建的 `xops-task`。两者是顺序的两次 Change，不并行。** 本包只动"写入路径"与"清理"两块，**不碰任务定义、不碰技能资产、不碰事件分发**（后两者根本不在这个 crate 里）。

## 背景与价值

这个包被从任务那一组里单独拆出来，理由是它管的是一件独立的事：**执行结束之后，那些行怎么变成账本里的事实，以及它们什么时候消失。**

**它认领一块事后补等于回填全部历史行的东西：**

> **`RET-002` 保留期与 `retainUntil`。** 它是**写入时就要落的列**，值取自该任务**当时声明的**保留期。不靠"回查任务再取它的配置"，因为任务的保留期可以随时改，而**已经写下的行不应该因为任务改了配置就提前消失或延后清理**。

**两条容易做错的，都在这里：**

| 条 | 做错的样子 |
|---|---|
| **两层拒绝必须分清**（`EXE-024`） | schema 校验不过 → **整批行不入表**，执行归为技能错误类失败；schema 过、节点判定不过 → **行入表**，只是不结算。**两种情况都要通知**——把它们混成一种，自动化失灵就会变成静默的 |
| **豁免优先于任务保留期**（`RET-006`） | 一个还在进行中的流程实例，它的主体行或结算行被清理了**就等于实例被腰斩**。治理事实的生命周期跟着它治理的那件事，不跟着任务的保留期 |

**一处已知的悬空，说明白**：`_plugins.generatedBy` 指向生成它的那次执行，而那条 `_runs` 行会到期被清理。插件的源码、能力声明、用例、测试结果、安装人都在 `_plugins` 行内（豁免），安装那一刻也有审计事件——**丢的只是那次生成执行的 output 与 trace**。这是可接受的，**但不要以为全系统零悬空**。

## 范围

### 包含

- **平台在容器外写入**：领取执行结果、**校验每一行是否符合目标表的 schema**、写进 `_runs` 与任务声明的那些表
- 自动补齐来源字段（调用 RP-04 的写入点）
- **两层拒绝**的分清与各自的通知
- 产物的**体量上限**：超限时截断并明确标注，不静默丢弃
- `_runs` 行**永不被覆盖**；重跑产生新的一次
- **并发执行数上限**（平台与项目两级）
- **保留期**：任务分别声明输出保留期（默认 1 个月）与过程记录保留期（默认 7 天）
- **`retainUntil` 的写入时自动补齐**
- **到期清理作业**：整批按时间进行，**不得选择性删除个别行**，留清理痕迹
- **豁免清单**与"豁免优先"

### 明确不包含

- **技能与任务的定义**——归 RP-09 与 RP-10。
- **容器与执行**——归 RP-07。
- **列位的存在**（`retainUntil` 这一列）——归 RP-04。**本包负责它的取值与清理，不负责它存在**。
- **审计事件流的保留期**（`AUD-009`）——归 RP-02。**两条并存、互不取代**：一条全局管审计，一条挂在任务上管输出。
- **判断产出质量**——不做（G8）。

本包认领 [`requirements.md`](requirements.md) 的 **15 条**。**条目正文以 `requirements.md` 为准**，下表只是索引与一句话摘要。

### EXE 执行（5 条）

| ID | 摘要 |
|---|---|
| `EXE-023` | 平台在容器外写入时校验每一行是否符合目标表的 schema，然后写进 _runs 与任务声明的那些表，补上 writtenBy / at / revisio… |
| `EXE-024` | 两层拒绝必须分清：schema 校验不过 → 整批行不入表，执行归为技能错误类失败；schema 过、节点判定不过 → 行入表，只是不结算。 |
| `EXE-025` | 单次执行的产物有体量上限，超限时截断并明确标注，不静默丢弃。 |
| `EXE-026` | 每次执行产生一条 _runs 行，永不被后续执行覆盖；重跑产生新的一次。 |
| `EXE-027` | 并发执行数有上限，按平台与项目两级控制，防止单个项目耗尽全部算力。 |

### RET 保留期与清理（10 条）

| ID | 摘要 |
|---|---|
| `RET-001` | 任务分别声明输出保留多久（默认 1 个月）与过程记录保留多久（默认 7 天）。 |
| `RET-002` | retainUntil 与 writtenBy 一样是平台在写入时自动补的字段，值取自该任务当时声明的保留期。 |
| `RET-003` | 保留期作用于任务的输出：_runs 的行，以及任务写进用户表的那些行。 |
| `RET-004` | 过程记录（_runs.trace）到期只清这一列，行本身按输出保留期走。 |
| `RET-005` | 清理整批按时间进行，不得选择性删除个别行。 |
| `RET-006` | 豁免清单（豁免优先于任务保留期）：① 任何被 _flows.subject 引用过的行，或带 _instance 的行——不管它在结算表还是主体表、不管是谁… |
| `RET-007` | ① 写成"引用过"而不是"结算表的行"，是因为任务完全可以往主体表写行（FLW-018③），那批行两条规则都命中，必须有优先级。 |
| `RET-008` | _notices 有自己的保留期（平台级配置，默认 3 个月），与任务无关——否则通知会无限增长。 |
| `RET-009` | 已知悬空，必须显式承受：_plugins.generatedBy 指向的那条 _runs 行会到期被清理。 |
| `RET-010` | 除到期清理外，系统内不存在任何其它删行路径。 |

## 关键不变量

`I-X`（治理事实不受任务保留期约束）· `I-D`（事件不可变——**到期清理删的是行与它的历史事件，删除这件事本身留痕**，这与"不可变"不冲突：不可变说的是"不会被改写"，不是"永久保留"）· `I-B`（来源字段不来自请求体）。

**MCP tools**：查询执行历史（含产出与过程记录：`_runs.output` 与 `_runs.trace` 两列）。**保留期的配置 tool 在 RP-10**（它是任务定义的一部分）。

## 验收标准

- **写入顺序**：`_runs` 行**先于**产出行可见落定（`CON-011`）。构造一次两步之间的崩溃：**留下"`_runs` 行完整、产出行缺失"是可接受的**；**反过来必须不可能出现**。
- **两层拒绝分清**：
  - schema 不过 → **整批行不入表**，执行归为技能错误类失败，**有通知**；
  - schema 过、节点判定不过 → **行入表**，不结算，**有通知**。
  - 两种都要实际构造。
- **`retainUntil` 取写入当时的配置**：写一行 → 改任务的保留期 → 那一行的 `retainUntil` **不变**。
- **清理是整批按时间的**：不存在任何"删除某一行"的接口或代码路径。
- **豁免优先**：一个任务写进**主体表**的行（同时命中"任务输出"与"被 `_flows.subject` 引用"两条规则），**不被清理**。
- **豁免清单逐项验证**：带 `_instance` 的行 · 被 `subject` 引用过的行 · `_flows`/`_flow_nodes`/`_plugins` · 各类定义 · `_notices`（另有自己的保留期）。
- **过程记录先过期**：到期只清 `_runs.trace` 这一列，行本身按输出保留期走。
- **`_runs` 不被覆盖**：重跑产生新行，旧行完整保留（受 `RET-003` 约束）。
- **任务被修改或停用后**，它的执行记录仍完整保留。
- **产物超限**：截断并**明确标注**，不静默丢弃。
- **并发上限**：单个项目吃不掉全部算力。
- **清理留痕**：清理动作本身有事件可查。

## 内部工作包建议

一次 **Solid Change**：

```text
WP-A 平台侧写入（领取结果、schema 校验、_runs 与产出行、写入顺序、
     来源字段补齐、两层拒绝与各自的通知）
        │
        ├──► WP-B 体量上限与截断标注 + 并发上限
        │
        └──► WP-C 保留期与到期清理（retainUntil 的写入、清理作业、豁免清单）
```

**WP-A 的写入顺序与两层拒绝要一起做。** 它们共用同一段路径，分两次做会把这段路径写两遍。

## 风险与待定

- **豁免清单是本包最容易漏的一处。** 建议实现成"**先判豁免、再判保留期**"的显式两步，而不是在保留期判定里塞几个 if——后者在加新的系统表时一定会漏。
- **`RET-009` 的已知悬空**（`_plugins.generatedBy` 指向的 `_runs` 行会被清理）**要在 RP-16 的 WP-B 里落实自包含**，本包只负责把这条悬空写在文档里、不让它变成"以为追得到"。
- **清理作业跑在锁外**（`CON-006`），它与业务写并发。**建议在设计时就实测一次"清理与写入并发"的行为**，不要假设它们不会碰上。
- **"删除只有这一处"是一条全局属性**（`RET-010`）：除到期清理外系统内不存在任何其它删行路径。**建议写成 XForge Rule**——任何新增的删除路径都应当在评审阶段被拦下。
