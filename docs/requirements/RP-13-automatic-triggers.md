# RP-13 自动触发

> 定时 · Git webhook · 验签与幂等 · 错过的窗口不补跑

## 归属与依赖

- **依赖**：RP-11 事件、触发与派工单（事件分发层由它建）。
- **被依赖**：无。
- **里程碑**：M3。
- **独立性**：薄包。做完即可验收——配一个定时任务，夜里跑起来；配一个 webhook，推一次代码触发一次执行。

## Crate 归属

| crate | 本包是否新建 | 对外只经什么被用 |
|---|---|---|
| `xops-task`（调度与事件源模块） | **改，不新建** | 定时调度 · git 事件的产生 |
| `xops-web`（webhook 端点） | **改，不新建** | 一个非 MCP 的 POST 端点 |

> ⚠️ **本包改的是别的包建的两个 crate。两处都不并行**：`xops-dispatch` 在 RP-11 之后；`xops-web` 在 RP-05（M1）之后。这是本版拆分里的"同目录"风险点之二与之三（README §4）。

## 背景与价值

M2 结束时，XOps 已经能跑技能了，但要有人去按。这个包把"有人去按"换成"它自己会跑"：

> ★ **夜里跑，早上看。**

**它同时引入了 G1 的第二个非 MCP 入口**，而这个入口必须被削得只剩一件事可做：

```text
Git webhook 端点  只能产生一个 git 事件
                  **不能创建或修改任何对象**，只能让订阅了它的任务被触发
```

**三条容易做错的，都很具体：**

| 条 | 做错的样子 |
|---|---|
| **`TRG-010` 错过的窗口不补跑** | 服务重启后把错过的窗口补上——**补跑会在恢复瞬间产生一批并发执行，风险大于收益**。正确做法是只按下一个窗口正常触发，并对错过的窗口**留痕** |
| **`TRG-014` 端点必须快速返回** | 在请求内做拉取或执行——**平台的 webhook 都有超时并会因超时重投**，慢一次就会被放大成很多次 |
| **`TRG-012` 验签失败不泄露信息** | 返回"这个项目不存在"或"这个任务没订阅"——**那就成了探测工具** |

**还有一条是安全边界**：`TRG-015` 要求 webhook 载荷按 G7 当作不可信输入，**只从中提取结构化字段**（确切提交标识、分支、事件类型），**不解析其中任何自由文本**。

## 范围

### 包含

- **定时触发**：至少"每天某时"与"每隔 N 小时"两类表达，**明确的时区**
- 触发者记为系统，**但必须能追溯到配置该调度的人**
- 下次触发时间的查询
- **错过的窗口不补跑**，且对错过的窗口留痕
- **Git webhook 端点**：验签 · 按事件标识幂等 · 快速返回 · 只提取结构化字段
- 按分支与事件类型过滤

### 明确不包含

- **手动触发**——归 RP-11。
- **事件分发层本身**——归 RP-11。本包只往它上面接两类事件源。
- **三条共同纪律**（非阻塞/幂等/留痕）的机制——归 RP-11。**本包遵守它们，不重新实现。**
- **只读 Web 的路由与会话**——归 RP-05。本包只加一个端点。
- **git 仓的绑定与凭据**——归 RP-08。

本包认领 [`requirements.md`](requirements.md) 的 **7 条**。**条目正文以 `requirements.md` 为准**，下表只是索引与一句话摘要。

### TRG 事件与触发（7 条）

| ID | 摘要 |
|---|---|
| `TRG-009` | 定时：至少支持"每天某时"与"每隔 N 小时"两类表达，以及明确的时区。 |
| `TRG-010` | 服务重启或短暂不可用后恢复时，错过的定时窗口不补跑，只按下一个窗口正常触发，并对错过的窗口留痕。 |
| `TRG-011` | Git webhook 端点是 G1 的两个非 MCP 入口之一，它只能做一件事：产生一个 git 事件。 |
| `TRG-012` | webhook 必须验证签名/密钥；验证失败的请求被拒绝，且不泄露任何关于任务或项目是否存在的信息。 |
| `TRG-013` | webhook 按事件标识幂等：平台的重投机制会导致重复投递，同一事件重复投递不产生第二次执行。 |
| `TRG-014` | webhook 端点必须快速返回，不在请求内做任何拉取或执行——平台的 webhook 都有超时并会因超时重投，从而放大问题。 |
| `TRG-015` | webhook 载荷是不可信输入（G7）：只从中提取结构化字段（确切提交标识、分支、事件类型），不解析其中任何自由文本。 |

## 关键不变量

`G1`（webhook 是四个非 MCP 例外之一，只能做一件事）· `G7`（webhook 载荷是不可信输入）· `I-J`（不存在自触发回路）。

## 接口面

**MCP tools**：配置任务的定时调度 · 查询下次触发时间。

**非 MCP 端点**：Git webhook（POST）。**它只能产生一个 git 事件，不能创建或修改任何对象。**

**契约元素**（基线在 [`../contracts/`](../contracts/README.md)，正文由本包自己的变更逐条添加）：

```text
api:mcp.tool.schedule.*             配置定时调度 · 查询下次触发时间
api:http.paths./webhooks/git.post   **唯一一条被允许存在于 `api:http.*` 里的写方向端点**
                                    它只能产生一个 git 事件，不能创建或修改任何对象（TRG-011）。
                                    ⚠️ 登记它的时候要在元素正文里写清这一句——审 api.md 的人
                                    数"http 面有没有写路由"时，会数到它
rust:xops-dispatch#*  rust:xops-web#*   只加两类事件源与一个端点，形状由 RP-11 / RP-05 留好
```

## 验收标准

- **定时**：配一个"每天 02:00（指定时区）"的任务，到点触发一次，且**触发记录能追溯到配置它的人**。
- **错过的窗口不补跑**：停服跨过两个窗口再启动，**不产生两次补跑**，只按下一个窗口触发，且**两个错过的窗口各有一条痕迹**。
- **webhook 验签**：签名错误的请求被拒绝，且响应**不泄露任何关于任务或项目是否存在的信息**（与"项目不存在"表现一致）。
- **webhook 幂等**：同一事件标识重复投递，**不产生第二次执行**。
- **webhook 快速返回**：端点内不做任何拉取或执行；实测响应时间在平台的超时之内。
- **只提取结构化字段**：构造一个载荷，其自由文本字段里放攻击性内容，**验证它没有被解析、没有进入任何控制流**（G7、G9）。
- **过滤**：按分支与事件类型过滤生效。
- **端点不能改对象**：枚举端点的代码路径，**不存在任何创建或修改业务对象的调用**。
- **触发前检查**：任务不存在 / 已停用 / 不允许这种触发方式——三种都拒绝并留痕。

## 内部工作包建议

一次 **Solid Change**：

```text
WP-A 定时调度（表达、时区、下次触发查询、错过不补跑与留痕）
        │
        ▼
WP-B webhook 端点（验签、幂等、快速返回、只提结构化字段、过滤）
```

**两个 WP 动的是两个不同的 crate**（`xops-dispatch` 与 `xops-web`），可以并行开发，但要一起验收——它们共用 RP-11 的事件分发层。

## 风险与待定

- **本包一开，成本就不再有人盯着。** `TSK-005` 的单次 token 上限必须已经在（RP-10，M2）——**这是本包排在 M3 而不是更早的原因之一**。
- **"错过的窗口不补跑"是一条容易被"好心"推翻的规则。** 建议在代码里写下理由，而不只是不实现补跑——否则下一个人会以为是漏了。
- **不同 Git 托管方的 webhook 验签方式不同。** `RPO` 那边已经有多平台的问题，本包按"逐个平台交付"排期，不要假设一套验签通吃。
- **`xops-web` 的改动要落在 RP-05 预留的位置上；`xops-dispatch` 的改动要落在 RP-11 预留的"事件源可接入"形状上。** 如果发现没地方落，**回头修 RP-05 的路由分层，不要在本包里另起一个 HTTP 服务**。
