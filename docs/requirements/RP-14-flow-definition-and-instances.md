# RP-14 流程定义与实例

> 有序节点与并行组 · 结算表 ≠ 主体表 · 校验不落库 · 实例状态机

## 归属与依赖

- **依赖**：RP-04 表引擎（结算表与主体表是表）、RP-03 MCP 基座。
- **被依赖**：RP-15 结算判定与保护（**只依赖本包的状态机接口**，接口一定型即可并行）、RP-18 模板（三套模板的流程部分）、RP-19 XForge 适配（被适配物）。
- **里程碑**：M4。
- **独立性**：**定义一条流程、校验它、发起一个实例、看到第一个节点激活、取消它或让它过期、查它卡在哪。整条链路不需要任何一行结算行。** 这就是本包的验收面。

## Crate 归属

| crate | 本包是否新建 | 对外只经什么被用 |
|---|---|---|
| `xops-flow` | **新建** | 流程定义的读写与校验 · **实例与节点的状态机操作**（激活 / 通过 / 拒绝 / 取消 / 过期）· 实例查询 |

> **本包是 `xops-flow` 唯一的动刀方。** RP-15 建自己的 `xops-settle`，**经本包的状态机接口驱动迁移**，不进本 crate。

## 背景与价值

流程这一大块被拆成两个包，切口在这里：

```text
本包    流程**能表达什么**、实例**处在什么状态**
        —— 定义、校验、版本、发起、状态机、取消、过期、查询
RP-15   一行写进来**算不算数**、谁**能写**、状态列**谁能改**
        —— 允许写入者、_instance、七条判定、求值链、状态列保护
```

**这条缝之所以成立，是因为本包完全不需要"结算"这个概念就能自洽**：实例发起、第一个节点激活、取消、过期——四件事都不经过任何一行结算行。RP-15 接进来时，它调用的是本包已经存在的状态机操作。

### 本包守两条地基

| 地基 | 不做会怎样 |
|---|---|
| **`FLW-004` 结算表 ≠ 主体表，校验时就拒绝** | ① 若同表，人要推进流程就得往主体表插新行，而"插新行"正是随行发起实例的动作，**会开出第二个实例**；② 若靠 update 主体行推进，"数量 ≥ N"（会签）与"同一写入者只能结算一次"两条都失去意义。<br>分开之后模型是统一的：**主体表放"这件事本身"，结算表放"谁对它做了什么表态"** |
| **`FLW-007` 实例按发起时的版本走完** | 否则改一次流程定义，会改变所有在途实例的行为——而它们已经跑了一半 |

### 一处最难的：筛选不得重叠

`FLW-008` 的校验 tool 要抓三件事，其中第三件是本包最难的一处算法：

```text
把流程展开成一个**激活集合序列**
  —— 串行节点各自是一个集合，一个并行组整体是一个集合
则**同一集合内的节点两两之间**、以及**相邻两个集合之间**，筛选都不得重叠
```

**判定取保守口径：只要不能证明两个筛选互斥，就判为重叠并拒绝。宁可误拒**——误放的后果是运行时一行同时结算两个节点，**那是事后查不出来的**。

### 本版新增的一句

`FLW-003` 在第 11 版多了一条：**指定了流转插件的节点，还必须声明它求值时要用到哪些行**（哪张表、什么筛选、上限多少行）。

理由是 D53：流转插件读不到表，输入由平台在调用前查好喂进去。**这不是限制，是把一件本来就该做的事挑明了**——求值发生在写串行区间内，一次自由查询就是一次不确定的写时延。**声明写在本包（它是定义的一部分），预取发生在 RP-15。**

## 范围

### 包含

- 流程定义：**有序节点序列 + 并行组**；每个节点声明通过条件、拒绝条件、允许写入者、职责分离、求值方式
- **节点声明求值所需的行**（`FLW-003`，指定流转插件时必填）
- **结算表与可选的主体表**，且**两者不得相同**
- 定义的**版本化**、发布、停用
- **校验 tool（不落库）**，三件校验含**筛选重叠的保守口径**
- **实例**：两种发起方式（随行自动 / 显式）、主体 = (类型, 标识, 修订)
- `_flows` / `_flow_nodes` 的**状态机**：激活、通过、拒绝、作废、取消、过期
- **实例创建的同一步第一个节点随即激活**，并产生「流程节点被激活」事件（含它的载荷，`TRG-018`）
- 实例查询（**卡在哪**）与**跨项目聚合的"我待处理的节点"**
- **三条边界**：不做条件分支 / 不做退回循环 / 不做超时自动推进

### 明确不包含

- **一行算不算数**——归 RP-15。本包不知道"结算"这件事怎么判。
- **允许写入者的判定**——归 RP-15。**本包只存这个声明，不执行它**。
- **`_instance` 列与状态列的保护**——归 RP-15。
- **求值链与它接进写串行区间**——归 RP-15。
- **插件的生成、安装与执行**——归 RP-16。本包只定义"节点可以指定一个流转插件"这个字段。
- **通知的产生**——归 RP-17。
- **三套模板**——归 RP-18。

## 接口面

**MCP tools**：定义流程 / 发布新版本 / 停用 · 列出流程定义与各版本 · **校验（不落库）** · 发起实例 · 查询实例状态与**卡在哪** · 取消实例 · **查询我待处理的流程节点（跨项目聚合，注册位在 RP-03）**。

## 验收标准

- **结算表 = 主体表**：定义时就被**校验拒绝**。
- **无主体表却声明随行发起**：被校验拒绝。
- **筛选重叠**：按激活集合两两判定；**不能证明互斥即拒绝**。这条要构造几组"看起来不重叠但证不出互斥"的用例，验证它**误拒**而不是误放。
- **校验不落库**：调用校验 tool 之后，库里没有任何新对象。
- **两种发起都跑通**：随行自动（主体表插新行）与显式（经 MCP 调用）；**结算行的插入永远不会再开出一个实例**（随行发起只看主体表）。
- **实例创建的同一步第一个节点随即激活**，并产生「节点被激活」事件，**载荷含实例标识、流程与版本、哪个节点、发起者、主体标识与修订**。
- **版本冻结**：实例发起后发布新版本，**在途实例行为不变**。
- **停用**：停用后不能发起新实例，**在途实例继续执行完**。
- **拒绝即终态**：调用 `reject` → 实例立即进入拒绝终态，**其余节点转为"已作废"，不停在"未激活"**。
- **取消与过期**：各自进入对应终态。
- **同一张表可被多条流程引用**（"结算表 ≠ 主体表"是每条流程内部的约束）。
- **卡在哪**：查询一个多节点实例，能看出当前激活的是哪些节点（**并行组时可能是多个**——`_flows` 没有 `currentNode`，权威是 `_flow_nodes` 里 state=激活中的那些行）。
- **跨项目待办**：一个人在多个项目里待处理的节点，在一个地方查得到。
- **不需要任何结算行**：以上全部验收，**一行结算行都不用写**。

## 内部工作包建议

一次 **Solid Change**：

```text
WP-A 流程定义与版本化（节点序列、并行组、每节点的声明、结算表≠主体表）
        │
        ├──► WP-B 校验 tool（不落库；三件校验，含筛选重叠的保守口径）
        │            ← 这是本包最难的一处，建议尽早开始
        │
        └──► WP-C 实例与节点状态机（两种发起、激活、通过、拒绝、作废、
                   取消、过期、「节点被激活」事件与载荷）
                        │
                        ▼
                   WP-D 实例查询（卡在哪）+ 跨项目待办
```

**WP-C 的状态机接口是与 RP-15 的接缝，要先定型再实现**——定型之后 RP-15 就能对着它并行开工。

## 风险与待定

- **`FLW-008` 的筛选重叠判定是本包最难的一处算法。** 保守口径让它可实现，**但"宁可误拒"这条要写进错误信息里**，否则用户会以为是 bug——他会看到一个自己觉得没问题的流程被拒了。
- **状态机接口定小了，RP-15 会绕过它自己改 `_flows`。** 那样两个包就同时在写同一组系统表，而它们分属两个 crate——**这是本次拆分最可能失败的地方**。建议在 WP-C 定型时就与 RP-15 一起评审接口。
- **Q12（`expiresAt` 由谁设、默认多久）**未定，影响 `FLW-017` 与 RP-19 的 `XFG-013`。**不阻塞本包主体**——实例级的过期能做，节点结算的有效期留空。
- **Q23（归档项目与在途实例）的另一半在本包。** RP-02 只做了"新写入被拒绝"，**在途实例怎么办必须在这里关掉**——一个归档了但流程还在跑的项目，是一个没人负责的状态。
