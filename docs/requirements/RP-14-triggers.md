# RP-14 触发器

## 归属与依赖

- **依赖**：RP-11（触发的目标是任务）、RP-03（MCP 触发）、RP-09（Git Hook 依赖仓绑定）、RP-12（触发后进入执行）。
- **被依赖**：无。这是一个入口。
- **不做这个包会阻塞谁**：不阻塞执行本身（手动触发可以直接做在 RP-11 里），但不做它，任务就只能靠人一次次点。

## 背景与价值

你的第 6 条需求：**任务触发有定时、手动、GIT Hook、MCP 触发。**

四种触发方式看起来是四个功能，但它们真正的共同点是：**都要把一个外部事件，确定性地变成一次入队的执行请求。**

把它们收在一个包里的理由是共享同一套纪律：

1. **触发不等于执行。** 触发的产出是"一次执行请求进了队列"，不是"任务跑完了"。所有四种触发方式都必须是**非阻塞**的。
2. **触发要携带上下文。** 特别是 Git Hook——它带来的是一个具体的提交，那个提交标识必须原样传到执行，否则"这份报告针对哪版代码"就没有答案（R-09-10）。
3. **触发要防重与防洪。** 定时任务会堆积，webhook 会重投，MCP 触发会被循环调用。这三类问题的解法是同一套：幂等 + 重叠策略 + 速率限制。
4. **触发方的身份必须可追溯。** 每次执行都要能回答"谁/什么触发的"（R-13-02）。

## 范围

### 包含

- 手动触发
- 定时触发（周期性调度）
- Git Hook 触发（GitHub / Gitea / GitLab 的 webhook 接收）
- MCP 触发
- 触发的鉴权、幂等、去重、限流
- 触发上下文到执行的传递
- 触发失败与被跳过的留痕

### 不包含

- **执行**——归 RP-12。
- **任务的触发方式声明**——归 RP-11（R-11-06）。本包只负责在触发到达时检查该任务是否允许这种触发。
- **任务之间的编排**——明确不做（见 RP-11 的风险条）。
- **Git 仓库内容的读取**——归 RP-09。本包只接事件，不拉代码。

## 需求条目

### 通用

| ID | 需求 |
|---|---|
| R-14-01 | 所有触发方式都是**非阻塞**的：产出一个执行标识后立即返回，不等待执行完成。 |
| R-14-02 | 触发前检查：任务存在、任务已启用（R-11-07）、该任务允许这种触发方式（R-11-06）。任一不满足则拒绝并留痕。 |
| R-14-03 | 每次触发记录触发方式与触发者身份，传递给执行记录（R-13-02）。 |
| R-14-04 | 触发受任务的**重叠策略**约束（R-11-08）。被跳过的触发**必须留痕**——一个静默被跳过的定时任务，会让人以为它在跑。 |
| R-14-05 | 触发受速率限制。超限的触发被拒绝并留痕，不排进队列。 |
| R-14-06 | 触发本身产生审计事件（RP-04），包括被拒绝与被跳过的触发。 |

### 手动触发

| ID | 需求 |
|---|---|
| R-14-07 | 项目成员可通过 MCP 手动触发任务，立即得到执行标识。 |
| R-14-08 | 手动触发的触发者是令牌解析出的用户（G5）。 |

### 定时触发

| ID | 需求 |
|---|---|
| R-14-09 | 任务可配置周期性调度，支持至少"每天某时"与"每隔 N 小时"两类表达，以及明确的时区。 |
| R-14-10 | 定时触发的默认时段建议在业务低谷（夜间）。理由：分析是重活，而**质量结论不需要实时**。 |
| R-14-11 | 服务重启或短暂不可用后恢复时，**错过的定时窗口不补跑**，只按下一个窗口正常触发，并对错过的窗口留痕。补跑会在恢复瞬间产生一批并发执行，风险大于收益。 |
| R-14-12 | 定时触发的触发者记录为系统，但必须能追溯到配置该调度的人。 |

### Git Hook 触发

| ID | 需求 |
|---|---|
| R-14-13 | 支持接收 GitHub、Gitea、GitLab 三个平台的 webhook（D5）。 |
| R-14-14 | webhook 必须**验证签名/密钥**。验证失败的请求被拒绝，且不泄露任何关于任务或项目是否存在的信息。 |
| R-14-15 | webhook 按平台各自的重投机制可能重复投递，因此必须**按事件标识幂等**：同一事件重复投递不产生第二次执行。 |
| R-14-16 | 触发时把事件携带的**确切提交标识**传给执行，作为本次读取代码的修订（R-11-05、R-09-10）。 |
| R-14-17 | 支持按事件类型与分支过滤：任务可声明只对某些分支或某类事件（如推送、PR）响应。 |
| R-14-18 | webhook 端点的响应必须快速返回，不在请求内做任何拉取或执行——平台的 webhook 都有超时并会因超时重投，从而放大问题。 |
| R-14-19 | webhook 载荷是**不可信输入**（G7）：只从中提取结构化字段（提交标识、分支、事件类型），不解析其中任何自由文本，不因其内容改变控制流。 |

### MCP 触发

| ID | 需求 |
|---|---|
| R-14-20 | 任务可通过 MCP tool 触发，供 AI 编程工具中的 Skill 在需要时主动发起（例如"帮我对这次改动跑一遍代码检视"）。 |
| R-14-21 | MCP 触发支持幂等键（R-03-06），重复调用不产生第二次执行。 |
| R-14-22 | MCP 触发的调用方可以指定目标修订，但必须在任务绑定的代码仓范围内，越界被拒绝。 |
| R-14-23 | MCP 触发**不得形成回路**：由某次执行产生的动作不得再触发任务。执行环境中不提供触发能力（继承 R-12-02、R-12-03）。 |

## 数据与不变量

- **I-14-1**：触发永不同步执行任务。
- **I-14-2**：同一外部事件（webhook 事件标识 / MCP 幂等键）最多产生一次执行。
- **I-14-3**：每次执行都能追溯到确切的触发方式、触发者与触发上下文。
- **I-14-4**：被拒绝或被跳过的触发同样留痕。
- **I-14-5**：执行环境无法触发任务，不存在自触发回路。

## 接口面

**MCP tools**

| 意图 | 说明 |
|---|---|
| 手动触发任务 | 返回执行标识 |
| MCP 触发任务 | 可带幂等键与目标修订 |
| 配置任务的定时调度 | |
| 查询任务的触发历史 | 含被拒绝与被跳过的 |

**HTTP 端点**（非 MCP，G1 的必要例外）

- 各平台的 webhook 接收端点。**这是 G1 之外的第二个非 MCP 入口**，理由是 Git 平台只会发 HTTP webhook，无法要求它讲 MCP。但它不是一个通用写入面：它只能触发已配置的任务，不能创建或修改任何对象。

**只读查询面**（供 RP-15）

- 任务的触发历史（含被跳过/被拒绝）
- 定时调度配置与下次触发时间

## 验收标准

- 四种触发方式各触发一次任务，均返回执行标识且不阻塞。
- 停用的任务，四种方式全部触发失败并留痕。
- 任务只声明允许手动触发时，定时与 webhook 触发被拒绝。
- 同一 webhook 事件重复投递十次，只产生一次执行。
- 伪造签名的 webhook 被拒绝，且响应不泄露任务/项目是否存在。
- webhook 触发的执行，其记录中的代码修订与事件携带的提交一致。
- 上次执行未结束时的触发，按重叠策略被跳过，且跳过被留痕可查。
- 服务停机跨过一个定时窗口后重启，不补跑，且错过的窗口有留痕。
- 在技能里尝试触发任务：执行环境中不存在该能力。
- 超过速率限制的触发被拒绝且留痕。

## MVP 子集

**以裁剪后的子集纳入 MVP：只做手动触发。**

MVP 做到：R-14-01、R-14-02、R-14-03、R-14-06、R-14-07、R-14-08。

MVP 推迟：定时、Git Hook、MCP 触发三种方式全部。

理由：MVP 要验证的是"技能能跑通、产出能看"，手动触发已经足够验证这条链路。而另外三种触发各自带着独立的复杂度（调度器、三平台 webhook 适配与签名验证、回路防护），它们提升的是自动化程度，不是可行性。

**但有两条即使在 MVP 只做手动触发也不能省**：
- **R-14-04 的重叠策略**——哪怕只有手动触发，连点两次也会并发跑两次。
- **I-14-1 非阻塞**——如果 MVP 图省事做成同步等待，后面三种触发接进来时要全部重写。

## 风险与待定

- **webhook 端点是 G1（所有写操作经 MCP）的第二个例外**（第一个是 Q1 的令牌签发）。这是不可避免的——Git 平台不讲 MCP。但要守住它的边界：**webhook 只能触发已配置的任务，绝不能创建或修改任何对象**。建议把这条写成项目的 XForge Rule，因为"顺手让 webhook 也能自动建个缺陷"是一个非常自然、但会打开一个无认证写入面的想法。

- **三个平台的 webhook 差异不小**（签名算法、事件类型命名、载荷结构、重投策略）。需求上是一条，实现上是三份适配。**建议在 MVP 之后按平台逐个交付**，每个平台单独验收，而不是三个一起做。

- **R-14-11 不补跑**是一条有主张的取舍。有些场景（每日必须有一份报告）会希望补跑。我的理由写在条目里；如果你更倾向补跑，需要同时定义"最多补几次"和"补跑的并发上限"，否则一次长停机后的恢复会打垮执行队列。**这条你可以推翻，但推翻时要连带定这两个数。**

- **R-14-23 的回路防护**在 MVP 不做 MCP 触发时不构成风险，但等 MCP 触发上线后，它与 R-12-03 是同一条边界的两面。**注意不要在"让技能更强大"的动机下给执行环境开触发能力**——一个能触发自己的任务是无限循环，而它花的是真金白银的模型调用。
