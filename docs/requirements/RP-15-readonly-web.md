# RP-15 只读 Web 呈现

## 归属与依赖

- **依赖**：RP-01（登录身份）、RP-02（可见性边界）、以及各领域包的只读查询面（RP-04/05/07/09/10/11/12/13/14）。
- **被依赖**：无。这是一个出口。
- **不做这个包会阻塞谁**：不阻塞任何功能，但没有它，平台的一切只能通过 Agent 转述。

## 背景与价值

你的原话：**同时提供 WEB 呈现的方式（不在 WEB 上做增删改）。**

这条约束（G2）比它看起来重要得多。一个只读的 Web 面意味着：

1. **不需要第二套权限与审计。** 所有写入都经 MCP 基座（RP-03）那一道门，Web 面不构成新的攻击面，也不会出现"MCP 校验严格但页面上能绕过"这类经典问题。
2. **不需要表单、校验、乐观锁、冲突处理**这一整套前端复杂度。呈现层的工作量因此小一个数量级。
3. **产品定位是自洽的。** XOps 是给 AI 编程工具用的平台，人的角色是**看**——看缺陷账本、看待办审批、看执行结果、看趋势。人要做的**唯一**写操作是审批决策，而那件事也走 MCP。

这个包真正的技术难点只有一个，而且很尖锐：

> **执行产物是模型生成的、可能包含任意内容的不可信数据（R-13-10），而它要被渲染进浏览器。**

产物的内容部分来自被分析的代码仓，也就是说，**能往被分析的仓里提交代码的人，就能影响产物内容**。如果直接渲染，攻击链是完整的：往仓里提交一段构造过的内容 → 技能把它读进报告 → 质量负责人在 Web 上打开报告 → 脚本以查看者的身份在页面里执行。

## 范围

### 包含

- 登录与会话
- 各领域的只读视图
- 执行产物的安全渲染
- 审批待办的展示（决策动作本身走 MCP）

### 不包含

- **任何增删改**（G2）。没有表单、没有编辑、没有删除按钮。
- **报表引擎、看板、燃尽图、自定义仪表盘**——明确不做。这类东西会把 AI 化之后本已消失的重流程重造一遍。
- **跨项目的横向对比视图**——不做，理由同 RP-13 的风险条：想要趋势就写技能。
- **任何形式的写入 API**——Web 前端只消费只读查询面。

## 需求条目

### 通用

| ID | 需求 |
|---|---|
| R-15-01 | Web 面**不提供任何写入操作**。前端不存在调用写接口的代码路径，后端不为 Web 暴露任何写接口。 |
| R-15-02 | 可见性完全遵循项目成员边界（R-02-07）：非成员看不到项目的存在。 |
| R-15-03 | 登录后的会话与 MCP 令牌是**不同的凭据**，互不通用。Web 会话不能用于调用 MCP 写操作。 |
| R-15-04 | 页面上明确展示当前用户身份，避免"登错账号看错项目"。 |

### 视图

| ID | 需求 |
|---|---|
| R-15-05 | **项目视图**：我参与的项目列表、项目成员与各自角色。 |
| R-15-06 | **缺陷视图**：缺陷列表与筛选、单个缺陷详情与**完整时间线**（每一次状态变化、谁、何时、为什么）。时间线是追加式账本（G3）的直接体现，是这个视图的核心而非附属。 |
| R-15-07 | **审批视图**：我的待办、审批实例状态与"当前在等谁"（R-07-14）、单实例的完整决策时间线。**做决策的动作不在 Web 上**——页面告诉你该批什么，你去 Agent 里批。 |
| R-15-08 | **任务与执行视图**：任务列表、单任务的**每次执行历史**（R-13-05）、单次执行详情与产物。这是你第 4 条需求的直接落点。 |
| R-15-09 | **技能视图**：技能列表、状态、版本历史与内容。 |
| R-15-10 | **代码仓视图**：绑定列表与同步状态，**不含凭据任何形式的原文或可恢复片段**。 |
| R-15-11 | **活动视图**：项目的审计事件时间线（RP-04）。 |

### 产物渲染（安全关键）

| ID | 需求 |
|---|---|
| R-15-12 | 执行产物按**不可信内容**渲染（R-13-10）。 |
| R-15-13 | Markdown 产物渲染时，**禁用内联 HTML 与脚本**，只渲染受限的标记子集；外部资源引用（图片、链接）被明确标注为外部并且不自动加载。 |
| R-15-14 | HTML 产物（若支持）必须在**隔离环境**中渲染，与主页面不共享任何凭据、会话或 DOM 访问；隔离失败时拒绝渲染并提供纯文本下载。 |
| R-15-15 | 产物中的链接不得携带查看者的会话信息。 |
| R-15-16 | 来自未正常完成执行的产物（R-13-9）在页面上明确标注。 |
| R-15-17 | 提供产物的原始形式下载，供不信任渲染的人自行查看。 |

## 数据与不变量

- **I-15-1**：Web 面不存在写入路径。
- **I-15-2**：Web 会话凭据不能调用 MCP 写操作。
- **I-15-3**：产物内容在渲染前始终携带不可信标记（继承 I-13-3）。
- **I-15-4**：页面不泄露任何凭据。

## 验收标准

- 全站审查：不存在任何提交表单、编辑控件或写接口调用。
- 用 Web 会话凭据尝试调用 MCP 写操作，被拒绝。
- 非成员访问某项目的任意页面，得到与项目不存在一致的结果。
- **构造一份含恶意内容的产物**（内联脚本、事件处理属性、外部资源引用、伪装的链接），在页面上打开：**脚本不执行、外部资源不自动加载、会话不泄露**。这一条必须实际构造并验证，不能只做代码审查。
- 缺陷时间线展示全部历史记录，与 MCP 查询结果一致。
- 审批页面能看到待办，但页面上没有任何"批准/拒绝"按钮。
- 任务页面能看到每次执行及其产物。
- 代码仓页面不含凭据原文或可恢复片段。
- 产物可下载原始形式。

## MVP 子集

**以裁剪后的子集纳入 MVP。**

MVP 做到：
- 登录（依赖 Q1 的结论）
- 项目列表与详情（R-15-05）
- 缺陷列表 + 缺陷详情与时间线（R-15-06）——**MVP 的核心呈现价值**
- 任务的执行历史 + 单次执行的 Markdown 产物（R-15-08）
- 安全的 Markdown 渲染（R-15-12、R-15-13、R-15-17）

MVP 推迟：
- 审批视图（随审批域推迟）
- 技能、代码仓、活动视图
- HTML 产物渲染（R-15-14，随 RP-12 的 HTML 支持一起推迟）

**不可裁剪**：R-15-01（无写入）、R-15-03（会话与令牌分离）、R-15-12/R-15-13（不可信渲染）。

特别强调 **R-15-13**：MVP 只有 Markdown，很容易顺手用一个默认开启内联 HTML 的渲染库就上线。默认开启是绝大多数 Markdown 库的行为。**这一条要在 MVP 就做对**，因为它是产物渲染这条攻击链上唯一的那道门。

## 风险与待定

- **Q1 决定登录方式。** 如果走 Git 平台 OAuth，Web 登录与 MCP 令牌签发可以共用同一条身份链路，这是选择 OAuth 的一个附加收益。

- **R-15-07 的"看得到待办但不能批"会让人别扭。** 这是 G2 的直接后果，我认为是对的（决策必须经 MCP 才能保证 G5 的身份可信与 RP-04 的完整留痕），但用户体验上需要引导——页面应当直接给出"在你的 Agent 里跑这条命令"，就像 XForge 的 `nextActions` 那样。**建议把这条做成明确的产品行为，而不是让用户自己猜。**

- **HTML 产物的价值与风险不成比例**（详见 RP-13 的风险条）。R-15-14 写了隔离要求，但我的建议仍然是**先不做 HTML**。如果最终要做，隔离渲染方案要单独设计并单独验收。

- **移动端与响应式**未纳入需求。质量负责人多数在桌面上工作，但审批待办是典型的碎片时间场景。**这条需要你定优先级**，MVP 不做。
