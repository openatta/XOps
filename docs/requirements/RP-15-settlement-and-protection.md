## 背景与价值

这是整套设计**最大的一次简化**的落点：

> **流程吃掉审批。** 节点结算的唯一形式是"结算表上出现了满足条件、且写入者被允许的行"。

因为"人做决定"本来就是往那张表里写一行，于是不需要"审批实例""决策""质量门""代理任务"四个概念：

```text
人写这一行      → 这就是审批
任务写这一行    → 这就是自动化（agent 判断，费 token，能读代码）
插件判定        → 这也是自动化（确定性判断，不费 token，只吃平台喂的 JSON）
```

### 两条最容易被绕过、因而必须写死的地基

| 地基 | 不做会怎样 |
|---|---|
| **`FLW-023` `_instance` 是受保护列** | 两个并发实例会在同一张表上产生两条同样满足筛选的行，**节点判定无从区分**——这是整个流程模型的地基 |
| **`FLW-036` 状态列只有平台与流转插件能写** | 任何成员都能直接 `update bugs.status = closed` 绕过整条流程——**七条判定只管"这行算不算结算"，从不阻止写入** |

**第二条要读两遍。** 七条判定是一道**记账**的闸门，不是一道**写入**的闸门：不满足的行**照常留在表里**，只是不结算。所以"绕过流程"这件事拦不住在判定这一层——它必须由状态列的写保护来拦。

### 七条判定里，三条挡的是很具体的攻击

| 条 | 挡什么 |
|---|---|
| **② 写入这一刻判定，不是事先** | 名单表可以随时改：事件发出时 a 在名单里，任务跑了几分钟，期间 a 被移出——**② 正好挡住这一情形** |
| **③ 职责分离** | **闭环自批**：a 自己发起 → 触发 a 自己的任务 → 记为 a 的通过，**全程一个人**，审批唯一的价值（多一个人）当场归零。写入者是任务时比**任务所有者**——因为任务不是责任主体，人才是 |
| **⑥⑦ 产出异常** | 执行超时后部分产出仍被保留，**那些残片不能算数**；以及"执行读的是仓库当前 HEAD 而不是这次要它看的那一版" |

### 一条刻意的取舍

**`FLW-041` 一个总是失败的流转插件会让实例永久停住。** 超时与异常一律判为"未通过"，而既不做超时自动推进、也不做退回——所以实例就停在那儿。

**这是设计的一部分：卡死的东西应该被看见，不应该被绕过。** 出路是取消实例、修好插件、发起一个新实例。

## 范围

### 包含

- **允许写入者的三者并集**：项目角色集合 ∪ 名单表 ∪ 指定的私有任务
- **名单表是受保护表，只有所有者能写，保护级别不可降级**（它是审批权的元权限）
- **③ 只能指定私有任务**（公共任务没有"所有者这个人"）
- **`_instance` 受保护列**与它的**三种填法**（人写 / 任务写 / 流转插件写回）
- **主体行不带 `_instance`**；输出插件写不了结算表
- **七条结算判定**，以及"指定流转插件时 ②～⑦ 一条不减、且在调用插件之前判完"
- **任一不满足 → 行照常入表 + "未被采纳"痕迹 + 通知写入者**
- **只有 insert 参与求值**（update / delete 不触发、不结算、不撤销）
- **写入时的求值链**：接进 RP-01 的区间 ③，三条分支（不结算 / 通过 / 拒绝）
- **主体表状态列的保护**与"人写表态 → 节点结算 → 插件写状态列"这条闭环
- 一个总是失败的流转插件让实例永久停住这条取舍

### 明确不包含

- **流程定义与实例状态机**——归 RP-14。**本包调用它的接口，不自己迁移状态。**
- **插件的生成、安装与执行**——归 RP-16。本包只定义"节点可以指定一个流转插件"这个挂点的调用契约，以及"**超时与异常一律判为未通过**"这条要求。
- **平台代写插件交回的行**——机制在 RP-01 的区间 ④；**本包声明写回目标**（结算表与主体表），实现在 RP-16。
- **节点声明求值所需的行**——声明在 RP-14（它是定义的一部分），**本包负责按这份声明去预取**。
- **通知的产生**——归 RP-17。本包只声明哪些时刻**必须**通知。

## 验收标准

**七条判定逐条构造，一条都不能只看代码：**

- **自发自批**：a 自己发起 → 触发 a 名下的私有任务 → 它写的行**不结算**（③、`I-O`）。
- **名单竞态**：任务执行期间把人移出名单，**写入时**被 ② 挡下（**② 是写入这一刻判定，不是事先**）。
- **同一写入者重复结算**：④ 挡住第二次。
- **节点已不激活**：⑤ 挡住迟到的行。
- **执行未正常完成**：⑥ 挡住超时执行留下的残片。
- **修订不一致**：⑦ 挡住"读的是当前 HEAD 而不是主体修订"。
- **指定流转插件时**：**②～⑦ 在调用插件之前就判完**——不满足的行**根本不会被交给插件**（这条要用一个会记录自己被调用过的假插件来验）。

**保护与绕过：**

- **状态列绕过**：直接 `update` 主体表的状态列，**被拒绝**。
- **`_instance` 保护**：技能、用户、普通写入路径都**写不了**这一列；三种合法填法各验一次。
- **名单表**：非所有者写它被拒绝；尝试降低它的保护级别被拒绝。
- **公共任务不能当写入者**：定义时指定一个公共任务，**被拒绝**。
- **输出插件写结算表**：被拒绝。

**求值链：**

- **并发最后一票**：两个人同时往同一个结算表写"最后一票"，**只有一票被结算**（这条证明区间 ③ 真的在锁内）。
- **只有 insert 参与求值**：结算表上的 update/delete **不触发求值、不结算、也不撤销任何已有结算**。
- **未被采纳留痕**：不满足任一条的行**照常留在表里**，有痕迹，**且通知写入者**。
- **拒绝即终态**：一个节点拒绝 → 经 RP-14 的状态机让整个实例进拒绝终态。
- **触发任务在锁外**：「节点被激活」的派发与任务入队**不在串行区间内**（`CON-006`）。

**接缝：**

- **不改 RP-01 的写入路径**：求值接进区间 ③ 时，`xops-store` **一行不改**。
- **不改 RP-14 的 crate**：枚举本包代码，**没有任何一处直接写 `_flows` / `_flow_nodes`**，全部经状态机接口。
- **不依赖 RP-10 / RP-16 也能完整验收**：只用角色与名单表两种写入者、只用默认筛选判定，全链路跑通。

## 内部工作包建议

一次 **Major Change**：

```text
WP-A 允许写入者（三者并集、名单表的受保护性、③ 只能私有任务）
        │
        ▼
WP-B `_instance` 受保护列与三种填法 + 主体表状态列的保护
        │
        ▼
WP-C 求值链（接进 RP-01 区间 ③；按 RP-14 的声明预取相关行；
     插件挂点先留 no-op；三条分支；锁外入队）
        │
        ▼
WP-D 七条结算判定 + 未被采纳的留痕 + 必须通知的时刻
```

**WP-B 要early。** `_instance` 与状态列的保护是"流程不被绕过"的地基，**而它们是列上的闸门，不是判定逻辑**——晚做会让前面的判定测试都跑在一个可以被绕过的底座上。

**WP-C 是与 RP-01 的对接点**，它兑现的是 RP-01 预留的扩展点位——**如果这里需要改动 RP-01 的写入路径，说明扩展点位当初留错了**，应当回头修 RP-01 而不是在本包绕开。

## 风险与待定

- **本包与 RP-14 分属两个 crate，最可能的失败方式是本包绕过状态机接口直接改 `_flows`。** 那样两个包就同时在写同一组系统表。**验收里那条"枚举本包代码，没有直接写系统表的地方"要真的枚举。**
- **`FLW-041`（插件永久卡住实例）是刻意的，不是缺陷。** 出路是取消实例、修好插件、发起新实例。**这条要写在用户可见的地方**，否则它看起来像是系统坏了。
- **七条判定里 ⑥⑦ 依赖 `_runs` 的状态与修订**（RP-12 落的），**② 依赖名单表的当下内容**。这三处都是"判定时去读别的东西"，而判定在锁内——**要确认这几次读不会把写吞吐拖垮**，容量在设计阶段算一次。
- **`FLW-028`「插件判定替代 ① 的一半，②～⑦ 一条不减」是本包最容易做漏的一条。** 直觉写法是"有插件就交给插件判"，那样 ②～⑦ 就被跳过了——**而 ③ 一旦被跳过，自发自批的门当场消失**。
