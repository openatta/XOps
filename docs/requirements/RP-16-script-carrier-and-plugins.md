# RP-16 脚本载体与插件

> QuickJS 载体 · 能力默认为零 · 由技能生成 · 维护者安装并逐条披露

## 归属与依赖

- **依赖**：RP-10 任务与执行策略（造插件任务是一种受限的任务）、RP-15 结算判定与保护（流转插件的挂点）。
- **被依赖**：RP-18 模板（模板带插件）、RP-10 的 `onComplete` 挂输出插件这一半。
- **里程碑**：M4。

## Crate 归属

| crate | 本包是否新建 | 对外只经什么被用 |
|---|---|---|
| `xops-script` | **新建** | QuickJS 载体 · 能力解析与授予 · 两个调用位置 · 生成流水线 · `_plugins` 的写入 |

**本包不改 `xops-flow` 与 `xops-settle`**：流转插件的调用由 RP-15 的 WP-C 留出的挂点接进来。**本包也不改 `xops-store`**：插件交回的行由平台在区间 ④ 代写。

## 背景与价值

> **插件跑在 QuickJS 载体里，能力默认为零。载体管得了它碰什么，管不了它说什么——所以治理一条不减。**

上一版这个包的开篇是"安装一个插件 ≈ 授予这个人在 XOps 服务端执行任意代码的能力"。**D52 取代了那条结论**，但取代的方式是**收窄让渡**，不是解除让渡：

```text
让渡掉的，从   "由模型写的代码在服务端执行任意东西"
变成           "由模型写的代码替人做判断"
```

**后一半仍然在。** `G11` 的两半就是照着这个分的：

| 半 | 内容 | 拦得住什么 / 拦不住什么 |
|---|---|---|
| **载体** | 一次调用一个 runtime · 能力默认为零 · 字节码级中断 · 故障只花一次调用 | 拦得住"读别人的表""往外发数据""死循环拖垮平台"；**拦不住"永远返回通过"** |
| **治理** | 由技能生成 · 编译与用例 · **维护者安装并逐条披露能力** · 源码必须可读 · 每一步留痕 | 拦不住第一类（那是载体的活）；**这是第二类唯一的答案** |

**两条残留风险，写出来而不是假装没有：**

```text
① 载体本身是信任基。QuickJS 是一个 C 实现，它的内存安全是这套隔离的地基。
   版本要跟、CVE 要看 —— 它是依赖，不是免死金牌。
② 输出插件有出网与配置，就有外泄面。它拿得到的是喂给它的那份数据，
   能送到的是它声明过的那几台主机 —— 两者都在安装时披露过。
   **这是"可审查的外泄面"，不是"没有外泄面"。**
```

### 两类插件的能力，差别很大

```text
流转插件   能力为零，没有可声明项
           输入由平台预取（FLW-003 声明的那些行），输出交回平台代写
           在写串行区间内跑 —— 所以它必须是一次纯计算

输出插件   只能声明三样：出网白名单 · 读自己的配置 · 读声明过的表
           在 onComplete 上下文里跑，锁外
           "读表"那一项存在的唯一理由是接住 D44 的出路
```

## 范围

### 包含

- **QuickJS 载体**：一次调用一个 runtime · 内存上限 · **字节码级中断** · 故障只花一次调用
- **能力解析与授予**：默认为零；输出插件的三样；**未声明即那个函数不存在**
- 造插件任务这一受限特例的约束（只能手动触发、不能订阅任何事件）
- **生成流水线**：编译（字节码 + 入口导出检查）· 跑用例（**在真载体里，能力按声明给**）· 静态检查 · 产出候选
- 候选的查看（源码、**能力声明**、测试结果，成员可见）与**安装（维护者，逐条披露能力）**
- `_plugins` 表的写入、**版本不可变（能力声明是版本的一部分）**、停用、版本历史
- 两个调用位置：**流转插件**（接进 RP-15 的挂点）与**输出插件**（接进 RP-10 的 onComplete）
- 超时、错误隔离、不递归三件防故障的事
- **插件配置**：所有者写入、加密存储、任何接口读不出、**只在声明了该能力时注入给它自己**

### 明确不包含

- **代写插件交回的行**——机制在 RP-01 的区间 ④，写回目标由 RP-15 声明。**本包负责把插件的输出交出来，不负责写。**
- **流程节点的语义**——归 RP-14 与 RP-15。
- **插件内容的语义审查**——那是维护者安装前的人工职责（`PLG-010` 保证源码与能力声明必须可读）。**平台不用模型判断插件是否安全**（G8）。
- **给插件加第四种能力**——不做（`PLG-012`）。加第四样是一个要单独论证的决定。

## 关键不变量

`I-K`（未通过编译 + 用例的插件不可安装；已安装版本不可变）· `I-R`（交回的行由平台代写，不再触发求值；对主体表只能 update；输出插件写不了任何表）· `I-T`（源码与能力声明对成员可读；安装时逐条披露且不可跳过）· `I-Z`（能力默认为零，未声明即那条路不存在）· `I-A`（插件配置经任何 MCP 接口不可读出）。

## 验收标准

**能力测试是本包的核心验收，且必须失败在"函数不存在"而不是"被拒绝"：**

- **未声明出网的插件**发一次请求：失败，**且失败原因是那个绑定不存在**。
- **未声明读表的插件**查一次表：同上。
- **任何插件**读 `_notices`：失败——**它不在可声明之列**（`NTF-012`）。
- **流转插件**尝试任何 I/O：**它没有任何可声明项**，一律不存在。

**载体测试：**

- **死循环**（`while(true){}`）：被**字节码级中断**停下，表现为"这次求值超时"，节点**未通过**；**不是一个线程转死了**。
- **抛异常**：节点未通过并留痕，**平台不受影响**。
- **跨调用无状态**：第一次调用在全局上留下痕迹，第二次**读不到**。
- **内存上限**：一个吃内存的插件被限住，不拖垮进程。
- **故障只花一次调用**：一次失败不影响下一次正常调用。

**治理测试：**

- **非维护者安装候选插件**：被拒绝。**非所有者读写插件配置**：被拒绝。
- **编译失败 / 用例不过 / 静态检查不过**的产出：**不能成为候选**，更不能被安装。
- **安装时的能力披露不可跳过**：构造一次"不看披露直接装"的调用，**失败**。
- **改能力 = 新版本**：尝试给已安装的插件加一项能力，**不存在这条路径**。
- **已安装插件的源码与能力声明**：任何项目成员都读得到。
- **插件配置**：任何接口都读不出原文，**包括所有者自己**；它**不出现在 `_plugins` 表里**。
- **造插件任务尝试订阅一个事件**：**创建时被拒绝**。

**流程侧：**

- **流转插件交回的行**：由平台代写，**不再触发插件求值**；尝试往主体表 insert：**被拒绝**（只能 update）；尝试交回第三张表的行：**平台不代写**。
- **超时视为"节点未通过"，绝不视为通过。**
- **引用某个插件的流程节点用的是固定版本**，安装新版本后旧节点行为不变。

## 内部工作包建议

一次 **Major Change**：

```text
WP-A QuickJS 载体（一次一个 runtime、内存上限、字节码级中断、故障隔离）
     + 能力解析与授予（默认为零；三样的实现）
        │
        ▼
WP-B 造插件任务与生成流水线（编译 / 用例在真载体里跑 / 静态检查 / 候选）
        │
        ▼
WP-C 候选查看与安装（维护者 + 逐条披露）+ `_plugins` 表 + 版本不可变
        │
        ├──► WP-D 两个调用位置（流转接进 RP-15 挂点；输出接进 RP-10 onComplete）
        │
        └──► WP-E 插件配置（加密存储、只注入、不经查询面暴露）
```

**WP-A 必须最先，且能力面要一次定死。** 三样能力的边界（出网每跳重判、配置只读自己那份、读表只声明过的且排除 `_notices`）如果分几次加，会出现"这一样按新规矩、那一样按老规矩"。

## 风险与待定

- **`CON-009` 插件超时上限直接决定结算表的写吞吐**，因为求值在锁内。**QuickJS 让这个数字好看得多，但这不是把超时调大的理由**——默认值要小，容量要在设计阶段实算一次。
- **`RET-009` 的已知悬空**：`_plugins.generatedBy` 指向的 `_runs` 行会到期被清理。所以源码、能力声明、用例、测试结果、安装人**必须都在 `_plugins` 行内自包含**——**这条在 WP-C 里就要落实**，不能等清理真的发生时才发现追不回来。
- **载体是信任基**：把 QuickJS 的版本跟踪与 CVE 关注列为**持续责任**，不是一次性选型。建议写进项目的依赖策略。
- **`PLG-018`「能用技能解决的，不要用插件」是纪律，不是机器可验证的条目。** 它必须进评审清单。理由已经从"插件不可隔离"换成"插件本来就做不了多少事"——**两个正当理由仍然只有省 token 与平台做不到的对接**。
- **"给插件加第四种能力"会是一个持续的请求。** 建议把 `PLG-012` 的三样写成 XForge Rule：第四样出现在能力表里，评审阶段必须有单独论证。
