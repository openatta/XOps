# RP-17 通知

> 通知就是 `_notices` 上属于我的那些行 · 从事件派生 · 锁外追加 · 无渠道无重试

## 归属与依赖

- **依赖**：RP-04 表引擎（`_notices` 的 schema）、RP-05 读模型与 Web 后端（个人看板长在它的读模型上）。
- **被依赖**：无——**但 RP-15、RP-12、RP-19 都声明了"这些时刻必须通知"**，本包是那些声明的兑现方。
- **里程碑**：M4。
- **独立性**：薄包。做完即可验收——构造几类事件，验证对应的通知行出现在正确的人的个人看板上。

## Crate 归属

| crate | 本包是否新建 | 对外只经什么被用 |
|---|---|---|
| `xops-notice` | **新建** | 从事件派生通知行 · 两个平台专属 tool |

**个人看板的呈现落在 RP-05 的读模型与 RP-06 的前端上**——本包提供数据，**但它是平台内建的固定视图，不是用户能配的看板**。

## 背景与价值

**通知不是一条投递管道，是 `_notices` 表上属于我的那些行。**

这个设计省掉了三样东西：**投递渠道 · 重试策略 · 聚合窗口**。要把消息送出 XOps（邮件、IM），用**输出插件**（RP-16）——**平台侧不存在任何一条能承载任意内容、发给任意人的通路**（`I-W`）。

**两条结构性保证，不是概率话术：**

| 保证 | 怎么做到的 |
|---|---|
| **通知的失败绝不影响业务操作** | 通知行在业务写的**串行区间之外**追加（`CON-006`）。写失败只留痕，**绝不回滚业务写** |
| **不会出现"发了通知但账本里没有对应事实"** | 通知**只从事件派生**，不引入独立的产生路径（`I-W`） |

**它还带着全系统唯一的两处例外，两处都必须写死：**

```text
① `_notices` 是行级可见性的唯一例外
   读写被平台硬限定为 `user = 令牌持有人`
   立这个例外而不是做通用行级权限，理由是它**只有一张表、只有一条规则、平台自己写死**

② `readAt` 是全系统唯一一个用户可改的系统表列
   只能改自己那一行、只能改这一列，由平台专属 tool 代写，**照样追加事件**（I-N）
```

**为什么通知必须在 M4 而不是更晚**：`FLW-027` 与 `XFG-006` 都写着"必须通知"。**没有通知，自动化失灵就是静默的**——一个写了行却没被采纳的人，不会知道自己白写了。

## 范围

### 包含

- `_notices` 行的产生：**只从事件派生**，内容由**确定性代码**生成（不经模型）
- 自由文本**原样引用或截断**，不改写、不摘要、不翻译
- 只发给对该事件所属项目**有可见权限**的用户
- **不含凭据、令牌或产物原文，只含指针**
- 值得通知的五类：有节点在等我处理 · 流程实例已决定 · 我写的行未被采纳 · 执行完成或失败 · 表里的某行指派给我
- **锁外追加**与它的失败处理
- 两个平台专属 tool：查我的未读 · 标记已读
- **行级限定**（`user = 令牌持有人`）与 `readAt` 这一处例外
- `_notices` 的独立保留期（平台级配置，默认 3 个月）
- 跨项目聚合（它是平台全局表）

### 明确不包含

- **投递渠道、订阅偏好、去重聚合窗口、重试**——不做（`NTF-013`）。
- **个人看板的渲染**——归 RP-06。本包提供数据与那两个 tool。
- **把消息送出 XOps**——用输出插件（RP-16）。**平台不提供这个能力，也不定义"通道"。**
- **通用查询 tool 与自由看板**——`_notices` **不派发**（`NTF-009`、`BRD-004`）。

## 关键不变量

`I-W`（只从事件派生；锁外追加，失败绝不回滚业务写；平台侧无任意内容任意收件人的通路）· `I-Y`（读写硬限定为 `user = 令牌持有人`；不派发通用查询 tool）· `I-N`（`readAt` 照样追加事件）· `G8`（内容由确定性代码生成，不经模型）· `G7`（自由文本原样引用或截断）。

## 接口面

**MCP tools**：**只有两个**——查我的未读 · 标记已读。

> **这两个之外不派发任何 `_notices` 的 tool。** 这不是"暂时没做"，是 `NTF-009`。

**对内**：从事件流派生通知行（被 RP-12、RP-15、RP-19 声明的那些时刻触发）。

## 验收标准

- **锁外追加**：构造一次通知写入失败，**业务写不回滚**、照常成功，且失败**有痕迹**。
- **只从事件派生**：枚举全部产生通知的代码路径，**每一条都对应一个已存在的事件**；不存在"直接发一条通知"的接口。
- **不经模型**：枚举内容生成路径，**不含任何模型调用**。
- **自由文本原样或截断**：构造一条含特殊内容的自由文本，通知里**原样出现或被截断**，**没有被改写、摘要或翻译**。
- **不含凭据与产物原文**：构造一次含凭据形状内容的事件，通知里**只有指针**。
- **可见权限**：非项目成员**收不到**该项目的任何通知。
- **行级限定**：用 a 的令牌去查 b 的通知，**查不到**；用 a 的令牌去标记 b 的通知已读，**失败**。
- **`readAt` 的边界**：只能改自己那一行、只能改这一列；改别的列或别人的行都失败；**改动照样追加事件**。
- **不派发通用 tool**：枚举 `_notices` 相关的 tool，**恰好两个**。
- **建不了自由看板**：尝试为 `_notices` 定义看板，被拒绝。
- **五类都要实际触发一遍**，尤其"我写的行未被采纳"——它是自动化失灵时唯一的信号。
- **跨项目聚合**：一个人在多个项目里的待办，**在一个地方看得到**。
- **独立保留期**：`_notices` 按自己的保留期清理，**与任务保留期无关**。

## 内部工作包建议

一次 **Solid Change**：

```text
WP-A `_notices` 的产生（事件派生、确定性生成、五类、锁外追加与失败留痕）
        │
        ▼
WP-B 两个平台专属 tool + 行级限定 + `readAt` 这一处例外
        │
        ▼
WP-C 独立保留期 + 跨项目聚合
```

## 风险与待定

- **"顺手加一个渠道"是这个包最可能的走样方向。** 一旦加了邮件或 IM，就会跟着来重试、去重、聚合窗口三样。**这三样明确不做**（`NTF-013`）——要送出去用输出插件。
- **行级可见性的例外只有这一处。** 它之所以能立，是因为"只有一张表、只有一条规则、平台自己写死"。**任何"给别的表也加一点行级可见性"的请求，都不属于这个例外的射程。**
- **`readAt` 是全系统唯一一个用户可改的系统表列。** 实现时要走平台专属 tool 代写，**不要为它开一条通用的系统表写入路径**——那条路一开，`I-P` 与 `I-N` 都会跟着松。
- **本包是别人声明的兑现方。** RP-12、RP-15、RP-19 里每一处"必须通知"都要在本包有对应实现，**建议在验收时逐条对照那三个包的声明**，而不是只测本包自己列的五类。
