# RP-18 模板

> 一套表 + 可选流程 + 可选插件 · 一步实例化 · 实例化之后就是普通对象

## 归属与依赖

- **依赖**：RP-04 表引擎（建表）、RP-14 流程定义与实例（建流程）、RP-15 结算判定与保护、RP-16 脚本载体与插件（装插件）。
- **被依赖**：RP-19 XForge 适配（approvals 模板是它的被适配物）。
- **里程碑**：M4。
- **独立性**：薄包但**依赖面最宽**——它要同时用到表、流程、插件三样。做完即可验收：在一个空项目里实例化 bugs 模板，一条 bug 走完全程。

## Crate 归属

| crate | 本包是否新建 | 对外只经什么被用 |
|---|---|---|
| `xops-template` | **新建** | 列出模板 · 查看模板内容 · 在本项目实例化 |

**本包只调用别人**：`xops-table` 建表、`xops-flow` 建流程、`xops-script` 装插件。**它不新增任何机制。**

## 背景与价值

```text
模板 = 一套表 schema + 可选的流程定义 + 可选的插件
```

平台自带三个：

| 模板 | 建什么 |
|---|---|
| **bugs** | `bugs`（主体表：状态列、自增序号列、派生的可读 ID 列）+ `bug_events`（结算表）+ 一条随行自动发起的流程 + `bugs` 流转插件 |
| **issues** | `issues` + `issue_events` + 一条流程 + `issues` 插件 |
| **approvals** | `approvals`（结算表，**无主体表**）+ 一条用于审批的流程骨架 + `approvals` 插件 |

**实例化之后它们就是普通的表、流程和插件**，用户想怎么改就怎么改。**模板是起点，不是约束。**

**这个包最重要的性质是它什么都不新增：**

> **关于缺陷 ID**：`<项目短名>-<序号>` 由 bugs 模板声明的一个**派生文本列**生成，模板是 `{project.slug}-{seq}`。平台只提供"自增序号"与"派生文本"两个通用列类型和"项目短名"这个项目属性，**不认识"缺陷 ID"这个概念**。
>
> 用派生列而不是让写入方 agent 自己拼字符串，是因为这个 ID 会被手写进提交历史——**它必须简单到不可能出错**。派生列由平台在写入时算一次、之后不变；也**不需要为它开第三个插件调用位置**。

**还有一条落在 approvals 模板上的重要职责**：

> **理由必填。** 决策必须附带理由，空理由被拒。**这条由 approvals 模板的插件承接**——它校验 reason 列非空，空的不结算。**平台本身不认识"理由"这个概念。**

> ⚠️ **上一版模板的表部分排在 M1**（跟着表引擎走），流程与插件部分在 M4。**本版整个挪到 M4**，理由是：模板要建的是"表 + 流程 + 插件"三样，**只有表的那半个模板不值得单独交付一次**，而且它会让 M1 多背一个依赖。

## 范围

### 包含

- 模板的表示形式与三个 tool：列出 · 查看内容 · **在本项目实例化（一步完成）**
- **三套模板的内容**：bugs · issues · approvals（各自的表、流程、插件）

### 明确不包含

- **任何新机制**——本包只组合 RP-04 / RP-14 / RP-15 / RP-16 已有的能力。**如果实例化需要一个新机制，说明那几个包里有一个缺东西，回头补它。**

- **模板的版本化与升级**——不做。实例化之后是普通对象，模板改了不影响已实例化的项目。
- **XForge 的登记与两个 tool**——归 RP-19。本包只提供 approvals 这套被适配物。

## 验收标准

- **一步实例化**：在一个空项目里实例化 bugs 模板，**建表、建流程、装插件一次完成**；中途失败不留下半套东西。
- **实例化之后就是普通对象**：给 `bugs` 加一列、改流程、换插件（换插件仍需维护者），**都能做**。
- **bugs 全程**：插一条 bug（主体表）→ 流程实例自动发起 → 人往 `bug_events` 写一行表态 → 节点结算 → **流转插件把 `bugs.status` 写成新状态**。这条链路要完整跑通。
- **缺陷 ID**：`<项目短名>-<序号>`，**insert 时生成一次、之后 update 写不了它**；两条 bug 的序号连续且项目内独立。
- **approvals 无主体表**：它的流程校验通过（无主体表时**不得声明随行发起**，`FLW-008②`）。
- **理由必填**：往 approvals 的结算表写一行**空 reason**，**不结算**，且写入者被通知。
- **模板带的插件走正常流程**：它是候选 → 维护者安装（含能力披露），**不存在绕过安装的路径**。
- **三套模板互不干扰**：同一个项目里实例化两套，表名与流程不冲突（冲突时**明确失败**，不覆盖）。
- **不新增机制**：枚举本包代码，**没有任何一处在 RP-04/RP-14/RP-15/RP-16 之外实现表、流程或插件的能力**。

## 内部工作包建议

一次 **Solid Change**：

```text
WP-A 模板的表示形式 + 三个 tool（列出 / 查看 / 实例化）
        │
        ├──► WP-B bugs 模板（表 + 流程 + 流转插件）  ← 先做这一套，它最全
        │
        ├──► WP-C issues 模板（bugs 的同构简化）
        │
        └──► WP-D approvals 模板（无主体表 + 理由必填的插件）
                    ← 它是 RP-19 的被适配物，形状要与 XFG 的结果列映射对齐
```

**WP-B 先做**：bugs 是三套里最全的（主体表 + 结算表 + 状态列 + 派生 ID + 流转插件），它跑通了，另外两套是它的子集或变体。

**WP-D 要与 RP-19 一起评审**：approvals 的结算表列名直接决定 XForge 那边的**结果列映射**能不能拼出 `poll_approval` 的返回值。

## 风险与待定

- **本包依赖面最宽（四个包），但自己没有机制。** 这意味着它的风险不在实现，在**发现依赖的包缺东西**。建议在 Proposal 阶段就把三套模板需要的能力逐条对照 RP-04/RP-14/RP-15/RP-16 的接口面，**缺的回头补那几个包**，不要在本包里补。
- **Q15（用户自定义模板的导出与提交）**未定，M6。本包的模板表示形式**要为它留出可能**——如果表示形式是硬编码在 Rust 里的结构体，将来导出会很难。**建议用一种可序列化的声明式表示**，即使首版三个模板随平台发行。
- **"理由必填"是平台不认识的概念，靠插件承接。** 这条要在文档里写清楚，否则将来有人会想在平台层加一个"reason 非空"的通用校验——**那就是平台开始认识业务语义的第一步**。
