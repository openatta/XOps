### 1.1 一个前提

本文**只以概念与架构为根**，不以任何既有实现为约束。

**本仓是空的**——除了这套文档，没有代码、没有已归档的 Specs、没有可承接的实现。第 11 版把实现语言定为 Rust（D49）之后，这一条从"我们选择不受既有实现约束"变成了一个事实陈述：**十九个包全部是新建，没有"只做改造"的包**。估交付体量时这一点很要紧，见 [`README.md` §3](README.md)。

## 2. 定位与四条设计原则

**XOps 不是开箱可用的 AI 编程运营平台，是一个基础框架。**

> 由 skill 赋能、agent 执行的 task；数据源是 Git 仓和表；输出落表，可查询、可看板、可驱动流程、可交给插件继续处理。

> ⚠️ 这句里的"数据源是……表"要按 `EXE-013`（D44）读：**表是产出侧与查询侧的数据形状，不是执行的输入侧数据源**。技能读不到表；需要表数据就经 MCP 查好放进任务输入。

**一切业务写入经 MCP，一切围绕项目转。Web 只读。可本地部署。**

不以替代任何现有工具为目标——与 GitHub Actions / Issues / Projects 特性重叠是正常的。差异只在三处：**MCP 是唯一写入面**（为 agent 而不是为人设计）· **执行与数据共用一本账** · **能力用自然语言扩展**。

| # | 原则 | 它约束什么 |
|---|---|---|
| **P1** | 尽量简单。功能有了就行，不对用户怎么用做过多猜想 | 只有一种任务、一种数据形状（表）、一种流程 |
| **P2** | 规则由用户定，我们只按用户的规则做事 | 平台不预置任何业务表、流程、质量标准、看板内容 |
| **P3** | 一切经 MCP，一切围绕项目 | 没有 Web 写入面、没有管理后台、没有流程设计器 |
| **P4** | 扩展点是技能、插件与模板，不是配置项 | 想要新能力就写技能或让 agent 生成插件，不是等平台加开关 |

> P1 的反面是这套系统最容易走岔的方向：**只要开始为"缺陷"和"审批"分别建模，平台就会长出两套对象、两套视图、两套权限**——而它们本来是同一件事：一张表，加一条流程。

### 2.1 三个扩展点

| 扩展点 | 谁写 | 跑在哪 | 它够得到什么 |
|---|---|---|---|
| **技能** | 任何项目成员，自然语言 | 一次性容器 | 只有声明过的代码与出网。无凭据、无写表路径 |
| **插件** | 由技能生成的 JS 代码 | **QuickJS 载体**，一次调用一个 runtime | **默认为零**；输出插件另有声明出来的三样（`PLG-012`） |
| **模板** | 一套表 + 流程 + 插件绑定 | —— | 取决于它带的插件声明了什么 |

> 上一版这张表的第三列叫「信任级别」，插件那格写的是"高——与平台同权限"。**D52 之后不再是这样**：能力从"全部"变成"声明出来的那几样"。但换掉的只是**执行**这一半——**判断**那一半没换，见 `G11`。

### 2.2 全局约束

横跨全部域，任何条目的实现都不得违反。G1～G8 沿用既有（**G7、G8 在第 10 版被修订，第 11 版随 D52 再改一次措辞**），G9～G11 由概念文档第 10 版新增（**G11 被 D52 改写**），**G12 由第 11 版新增**。

| # | 约束 | 一句话 |
|---|---|---|
| **G1** | 所有写操作经 MCP | 两个非 MCP 入口（OAuth 回调、Git webhook）都被削得只剩一件事可做；另有两个凭据类例外（会话面、令牌管理面），四个例外一并见 `MCP-013` |
| **G2** | Web 只读 | 前端不存在调用写接口的代码路径，后端不为 Web 暴露写接口 |
| **G3** | 账本追加式 | 表对外是 CRUD，对内每次写都追加事件 |
| **G4** | 权限一律按项目判定 | 无跨项目全局角色，无组织级继承 |
| **G5** | 身份来自凭据 | MCP 不认证调用者，只认证令牌 |
| **G6** | XOps 不进入开发的关键路径 | XForge 的 Gate 只读仓内文件，不查询 XOps |
| **G7** | 所有外部自由文本是不可信输入 | 表里的文本、技能内容、任务输入、webhook 载荷、模型产出。**插件源码是唯一例外**：安装前是不可信输入且必须经维护者人工审查，安装后它是**被载体约束的**平台扩展 |
| **G8** | 确定性平面与分析平面隔离 | 账本、审计、权限判定、节点结算判定、schema 校验都不经模型；Agent 只在容器内工作，**没有任何写表的路径**。**插件是分析平面产物在确定性平面运行的唯一入口**——它的**执行**被载体约束，它的**判断**不被 |
| **G9** | **任何自动判定只看结构化列** | 从不读长文本列，从不因自由文本改变控制流 |
| **G10** | **每一次节点结算都归属一个具名的人** | 人直接写、他名下的私有任务代写、或维护者装的插件判定 |
| **G11** | **插件的执行由载体隔离，插件的判断由治理兜底** | 载体：一次调用一个 runtime · 能力默认为零 · 字节码级中断 · 故障只花一次调用（`PLG-012` `PLG-013`）<br>治理：生成+测试流水线 · **维护者安装并逐条披露能力** · 源码必须可读 · 每一步留痕（`PLG-005`～`PLG-011`）<br>**两半缺一不可**——载体拦不住"永远返回通过"，治理拦不住"装完之后源码没人看" |
| **G12** | **执行引擎与存储都在契约后面，且各有一次换实现的硬验收** | 引擎换成桩实现（`EXE-014`）· 存储换成内存实现（`CON-012`）。两次都**不改上面的任何代码** |

> **G9 是一条一破就全盘作废的约束。** "让它读一下报告里有没有写 PASS"是一个非常自然的想法，而它会一次性推翻本文全部设计。这条应当写成项目的 XForge Rule。

## 3. 十个核心对象

其余概念都是这十个的派生物或属性。本文 §4～§12 按它们组织。

```text
1  项目        边界                        → PRJ
2  成员与角色   谁能做什么                   → PRJ · IDN · TOK
3  Git 仓绑定   代码从哪来                   → RPO
4  表（行）     一切数据的形状 —— 缺陷、待办、审批记录、任务输出，全是它   → TBL · CON · RET
5  技能        自然语言写的指令，跑在容器里    → SKL
6  任务        技能 + 何时跑 + 读什么 + 写哪 + 完成后干嘛   → TSK · TRG
7  执行        一次实际发生，落进 `_runs`     → EXE
8  插件        JS 代码，QuickJS 载体里跑，能力默认为零     → PLG
9  流程（实例） 有序节点；节点结算 = 表上出现被允许的行     → FLW
10 看板        表的一个视图                  → BRD · NTF
```

配套两域：`TPL` 模板（表 + 流程 + 插件的一步实例化）· `XFG` XForge 适配（两个形状定死的 tool）。

## 4. 项目、身份与操作面

### 4.1 项目与成员（`PRJ`）

**项目是唯一的归属边界、权限边界、数据边界。它不是团队，也不是仓库。**

| ID | 需求 |
|---|---|
| PRJ-001 | 任何用户都可以创建项目，无需申请或审批。创建者自动成为**所有者**。 |
| PRJ-002 | 项目有稳定的、创建后不可变的标识；显示名可变，且**不得作为关联键使用**。 |
| PRJ-003 | 项目另有一个**短名**：全平台唯一、创建后**不可变**、限定为便于手写的字符集。平台自己不认识"缺陷 ID"这种概念，但模板会用短名去组合可被手写引用的标识（`TPL-005`）。**一旦分配就再也改不了**——创建项目时必须让人清楚这一点。 |
| PRJ-004 | 项目内恰好三个角色：**所有者**（管理成员与项目本身、写受保护表、写插件配置）、**维护者**（管理项目内业务对象、安装插件）、**成员**（建表、写表、写技能与任务、参与流程）。**角色集合固定，不做可配置角色系统**（D15 的代价见 `XFG-018`）。 |
| PRJ-005 | 所有者可把其他用户加入项目并指定角色、变更角色、移除成员。 |
| PRJ-006 | 一个项目必须始终至少有一个所有者。移除最后一个所有者被拒绝。 |
| PRJ-007 | 同一用户在不同项目中的角色互相独立。不存在跨项目全局角色，不存在组织级继承（G4）。 |
| PRJ-008 | **非项目成员看不到项目的存在。** 查询一个自己不是成员的项目，得到的响应与查询一个真正不存在的项目**完全一致**——不是"无权限"，是"不存在"。否则错误码本身就成了探测他人项目的工具。 |
| PRJ-009 | 项目可被归档。归档后转为只读：不再接受任何写操作，历史内容完整保留、可查询。**在途流程实例与在途执行在归档时的处置见 Q23。** |
| PRJ-010 | 权限判定是确定性纯函数：相同的（用户，项目，动作）在角色未变时永远得到相同结果，不受任何模型或外部服务影响（G8）。 |
| PRJ-011 | 项目角色不得由受治理路径之外的任何自动化改变——**特别地，执行中的任务不得提升自己或他人的角色**。 |
| PRJ-012 | **每个对象恰好有一个归属方**：项目（公共技能、公共任务、表、流程、插件、模板实例）或**用户**（私有技能、私有任务）。且每个对象恰好在**一个项目的上下文**中被使用。执行产生的行归属**项目**（I-C）。 |

### 4.2 身份与令牌（`IDN` / `TOK`）

| ID | 需求 |
|---|---|
| IDN-001 | 全部登录经同一个**身份提供方接口**完成。新增一个提供方只需实现该接口，不改动用户模型、令牌模型与权限判定。 |
| IDN-002 | 身份提供方至少包含：**预置账号**（部署自测用）与**第三方 Git 平台 OAuth**（先做 GitHub）。两者产生的用户在系统内是同一种主体，不构成第二套身份模型。 |
| IDN-003 | **不开放自注册。** 自注册存在开关且**默认关闭**。关闭时，未被预置或未被邀请的账号登录后被拒绝，且**不创建任何用户记录**。 |
| IDN-004 | 用户是平台的顶层主体，用户之间地位平等，不存在任何上下级或分组关系。 |
| IDN-005 | 每个用户有稳定的、创建后不可变的用户标识；显示名与邮箱可变，**不得作为关联键使用**。 |
| IDN-006 | 用户记录保存其来源身份提供方与在该平台上的账号标识，使"XOps 里的这个人"与"代码仓里提交的那个人"能够对上。 |
| IDN-007 | **OAuth 登录回调是 G1 的两个非 MCP 入口之一，它只能做一件事**：完成身份验证、建立会话。**不能创建或修改任何业务对象。** |
| TOK-001 | 令牌一律**按人签发**，不存在按服务、按项目或按团队共享的令牌。一个用户可持有多个并存的令牌，用于区分不同工具、机器与自动化。 |
| TOK-002 | 令牌签发时**只呈现一次**，之后系统只保存不可逆摘要，任何位置都无法再次读出原文（I-A）。 |
| TOK-003 | 令牌可被其所有者随时撤销，撤销后**立即失效，无生效延迟窗口**。 |
| TOK-004 | 令牌可设过期时间；已过期与已撤销的行为**完全一致**。 |
| TOK-005 | 令牌解析失败（不存在、已撤销、已过期、格式非法）时，错误**不得泄露具体原因**，也不得泄露该令牌是否曾经存在。 |
| TOK-006 | 每个令牌记录最后一次成功使用的时间，供所有者识别不再使用的令牌。 |
| TOK-007 | **行为人一律由令牌解析得出。** 系统在任何位置都不接受"调用方声明的身份"——参数中的 `actor`/`user`/`author` 之类字段一律被**静默忽略**（不报错，但绝不生效）（G5、I-B）。 |

### 4.3 MCP：唯一操作面（`MCP`）

| ID | 需求 |
|---|---|
| MCP-001 | XOps 对外暴露标准 MCP server，任何符合 MCP 的客户端都能接入，不需要 XOps 专属 SDK。 |
| MCP-002 | 每次调用必须携带令牌；无令牌或令牌无效时拒绝，且**不执行任何副作用**。 |
| MCP-003 | 所有 tool 有明确输入 schema，**未在 schema 中声明的字段一律拒绝**，不静默丢弃——静默丢弃会让调用方以为自己传的东西生效了。 |
| MCP-004 | tool 的输入 schema 必须是**固定形状的窄接口**。**不提供任何接受任意结构、任意上下文或自由指令的通用 tool**，不存在"把这段上下文一起发过去"这种口子。 |
| MCP-005 | **"任意表 CRUD"不构成对 `MCP-004` 的破例**：每张表建好之后，平台为它**派发一组专属的读写 tool**，各自带由该表 schema 生成的固定形状输入 schema。**不存在 `{table, values: 任意形状}` 的通用写 tool**——列名与类型在协议层是被声明过的，不是运行时随便塞的。 |
| MCP-006 | 产生副作用的 tool 支持幂等：调用方提供幂等键时，重复调用不产生第二次副作用，并返回与首次相同的结果。 |
| MCP-007 | 错误响应使用统一契约：稳定错误码、可读消息、以及"该重试还是该改参数"的明确区分。 |
| MCP-008 | **权限不足与对象不存在返回相同的错误**（呼应 `PRJ-008`）。 |
| MCP-009 | 能力发现按调用者的项目角色裁剪，**表专属 tool 一并参与发现**。 |
| MCP-010 | 所有自由文本参数视为不可信输入（G7）：只做 schema 与长度校验并原样存储，**不解析、不执行、不依据其内容改变控制流**。 |
| MCP-011 | 对外的 tool 域：**身份**（查询当前身份 · 能力发现 · **查询我待处理的流程节点，跨项目聚合**）· **项目** · **Git 仓** · **表** · **模板** · **技能** · **任务** · **调度** · **执行** · **插件** · **流程** · **看板** · **XForge 登记** · **通知** · **XForge 适配** · **审计**。各域的具体意图由本文对应域的条目声明；**tool 目录本身是可扩展的，扩展方式必须统一**，否则每加一域都要改这一条。 |
| MCP-012 | 对内提供给各域的接口面四件：tool 注册（声明 schema、所需权限、是否幂等）· 已认证的调用上下文（调用者、目标项目、角色）· 统一错误构造 · 与业务写入处于同一原子边界内的审计事件写入。**注册一个 tool 即自动获得全套纪律**，不需要各域自行编写认证、鉴权、schema 校验、幂等或留痕代码。 |
| MCP-013 | **不存在绕过 MCP 的业务写入路径。** 已声明的例外只有四个，且每个都被削得只剩一件事可做：OAuth 登录回调（`IDN-007`）· Git webhook 端点（`TRG-011`）· 会话面（登录与注销）· 令牌管理面。后两个是**凭据类**例外，不写任何项目内的业务对象。 |
| MCP-014 | 长文本类参数有明确体量上限，超限拒绝而不是截断——截断会让调用方以为写进去的是完整内容。 |
| MCP-015 | **不做速率限制**（D48）。平台不提供按用户或按 tool 的限流。挡住重复调用的是别的机制：`MCP-006` 幂等键 · `TRG-013` webhook 按事件标识幂等 · `TSK-008` 重叠策略；挡住成本失控的是 `TSK-005` 单次 token 上限与 `EXE-027` 并发上限。**剩下的"高频但各不相同的调用"是部署侧的事**——XOps 可本地部署、单实例，限流交给它前面的反向代理。**这是明写的不做，不是"以后再说"。** |

### 4.4 审计（`AUD`）

审计事件是**账本的底层形态**：§5 的"表对内追加"与本域是同一套事件流的两个视角。

| ID | 需求 |
|---|---|
| AUD-001 | 事件日志**只追加**。系统不提供任何就地修改或删除单条事件的能力——是没有这个能力，不是有但被拒绝。纠正错误的方式是追加一条纠正事件。 |
| AUD-002 | 每条事件至少包含：稳定事件标识、发生时间、行为人、所属项目、事件类型、目标对象标识、结构化载荷。**载荷是结构化数据，不是一段自由文本。** |
| AUD-003 | 事件按所属项目分区，非成员查询不到该项目的任何事件。不属于任何项目的平台级事件只有其主体本人可读。 |
| AUD-004 | **对任意给定时刻，可以仅凭事件流重建当时的业务状态快照**，不依赖任何当前视图。表的当前视图是缓存，不是权威（I-D）。重建是一个**受支持的运维操作**，有对外入口与文档，可对全量或指定截止时刻执行。 |
| AUD-005 | 事件写入与其对应的业务副作用在**同一次操作**中完成——不存在"业务成功但没留痕"或"留了痕但业务没生效"的中间态。 |
| AUD-006 | 事件的写入路径**不经过任何模型**（G8）。 |
| AUD-007 | 失败的 MCP 调用也留痕，但与成功事件区分——失败留痕用于排查与滥用检测，不进入业务账本。 |
| AUD-008 | 支持按项目、时间范围、事件类型、行为人、目标对象查询；并支持查询**某个对象的完整历史**。 |
| AUD-009 | 事件类型有统一目录与扩展方式。 |
| AUD-010 | 审计事件流的保留期可配置，保留期内不可删除，到期清理只能**整批按时间**进行，不得选择性删除个别事件。**这条管的是审计事件流，与 `RET-001`（任务输出的保留期，挂在任务上）并存，互不取代——两者的作用对象必须在实现上分清。** |
| AUD-011 | 以下动作一律留痕，缺一条就有一处黑箱：项目与成员变更 · 建表与加列 · 仓绑定与凭据轮换 · 技能发布 · 任务启停 · 每次触发（**含被拒绝与被跳过的**）· 每次执行 · 插件生成与安装 · 流程定义与发布 · 实例发起与每次节点结算 · 到期清理 · 标记已读。 |

## 5. 表：一切数据的形状

### 5.1 表与行（`TBL`）

| ID | 需求 |
|---|---|
| TBL-001 | 项目下可经 MCP 创建**命名的表**：声明它有哪些列、每列什么类型、**保护级别**，然后对它做增删改查。表名在项目内唯一。 |
| TBL-002 | **平台一张业务表都不预置。** 用户想记缺陷就建 `bugs`，想记待办就建 `issues`，想记什么就建什么——或者用模板（§10）。 |
| TBL-003 | 表分三种：**系统表**（平台自动建，schema 固定且不受用户列类型集合限制，只有平台能写）· **用户表**（用户建，schema 用户定义，按项目角色写）· **受保护表**（用户建时声明，schema 用户定义，**只有项目所有者能写**）。 |
| TBL-004 | **保护级别建表时声明，之后不可降级**（I-Q）。 |
| TBL-005 | 系统表恰好五张，schema 固定：`_runs` · `_flows` · `_flow_nodes` · `_plugins` · `_notices`。字段清单见 `TBL-006`～`TBL-010`。**除 `_notices` 外，系统表按项目存在。** |
| TBL-006 | **`_runs`**（每次任务执行一行）：`run` · `task` · `skill`（含版本）· `trigger` · `triggeredBy` · `inputs`（文本）· `revision`（读的哪个代码修订）· `startedAt` · `finishedAt` · `status` · `failureKind` · **`tokensUsed`** · **`tokenBudget`** · **`retainUntil`** · **`traceRetainUntil`** · `output`（技能产出的 Markdown 正文）· **`trace`**（过程记录，blob 列）。**它是默认的任务输出表**——"任务跑完就有记录可查"开箱就有，不需要用户先建表。 |
| TBL-007 | **`_flows`**（每个流程实例一行）：`instance` · `flow`（含版本）· `subject`（主体表与行 ID，或外部主体标识）· `subjectRevision` · `startedBy` · `state`（进行中/已通过/已拒绝/已取消/已过期）· `startedAt` · `endedAt`。**没有 `currentNode`**——当前激活的节点可能有多个（并行组），权威是 `_flow_nodes` 里 `state=激活中` 的那些行。 |
| TBL-008 | **`_flow_nodes`**（每个实例的每个节点一行）：`instance` · `node` · `state`（未激活/激活中/已通过/已拒绝/已作废）· `activatedAt` · `settledAt` · `settledBy`（结算它的那些行的 ID）。实例被拒绝或取消时，其余节点转为**已作废**，不停在"未激活"。 |
| TBL-009 | **`_plugins`**（每个插件的每个版本一行）：`plugin` · `version` · `state`（候选/已安装/已停用）· **`position`**（流转/输出）· **`entry`**（入口函数名）· `source`（JS 源码）· **`capabilities`**（能力声明）· `tests`（用例）· `testResult` · `generatedBy`（执行标识 + 技能版本）· `installedBy` · `installedAt`。<br>⚠️ **`position` `entry` `capabilities` 三列是 D59 补的**：D52 把插件改成载体里跑的东西之后，「在哪调用」「入口叫什么」「声明了哪几样」成了这一行必须自己回答的事——`PLG-009` 说能力声明是版本的一部分，`I-T` 说它对成员可读，`RET-009` 说这一行必须自包含，三条都落在这里。**配置仍然不在这张表里**（`PLG-015`）。 |
| TBL-010 | **`_notices`**（每条通知一行，属于一个用户，**平台全局表**）：`notice` · `user` · `project` · `kind` · `subject` · `text` · `createdAt` · `readAt`。详见 §11。 |
| TBL-011 | `_runs` / `_flows` / `_flow_nodes` / `_plugins` 与别的表一样**可查询、可看板、可被插件读到**；**`_notices` 是例外**（`NTF-009`）。 |
| TBL-012 | **对外 CRUD，对内追加**：用起来就是普通的表（增删改查），底层每一次写都**追加一条事件**再投影到当前视图；删除是**软删除**；**任何一行都能查出它的完整历史**（I-D、I-N）。 |
| TBL-013 | 每一行有稳定的行标识，写入后不变、不被复用。 |
| TBL-014 | 平台在写入时自动补下列字段，**任何列声明都不能覆盖它们**：`writtenBy` · `at` · `revision`（若来自读仓的执行）· `_instance`（若这张表是某条流程的结算表）· `retainUntil`（若这一行由任务写入）。 |
| TBL-015 | **`writtenBy` 恰好四种取值，且必须自包含**：① 某个人——用户标识；② 某次执行——执行标识 **+ 任务标识 + 任务所有者 + 技能版本 + 代码修订 + 该执行的最终状态**；③ 某次插件求值——插件标识与版本 + 安装它的人 + 流程实例；④ 平台自身。**②③ 必须内联那几项，不能只存一个指针**——`_runs` 的行有保留期而结算行没有，一个月后还要能回答"这一票是谁的"，靠的就是这里内联的任务所有者（I-B、G10）。 |
| TBL-016 | **"不可信内容"不再是一个特殊标记，而是 `writtenBy` 的自然结果**：责任归属、看板上的来源标识、流程节点的写入者判定，全都读它。 |
| TBL-017 | 列类型是**穷举的**：文本 · 长文本(Markdown) · 整数 · 小数 · 布尔 · 时间 · 枚举（取值集合由用户声明）· 自增序号 · 行引用 · 二进制(blob) · 派生文本。 |
| TBL-018 | **自增序号**：项目内、每表独立，不跨项目共享计数器。 |
| TBL-019 | **行引用**：存另一张表的行 ID，**平台不校验、不级联**。 |
| TBL-020 | **派生文本**：按声明的模板，从**同一行的其它列与项目属性**计算（例：`{project.slug}-{seq}`）；**insert 时生成一次、之后不变，update 写不了它**。 |
| TBL-021 | **不提供 `json` / 任意对象列类型。** 一旦有，`MCP-005` 那套表专属 tool 的派发机制就退化成通用透传，窄接口纪律当场破掉。 |
| TBL-022 | **可以加列**（新列对历史行为空）。**改列类型、删列、改列名——不做。** 需要就新建一张表，用 MCP 把旧表读出来写进新表。**不做 schema 迁移。** |
| TBL-023 | **不做表之间的关联 / 外键 / 级联。** 行引用列只是存一个 ID，要关联是用户自己的事。流程的主体表与结算表的关系记在**流程定义**与 `_flows.subject` / `_instance` 上，是运行时事实，**不是 schema 层的外键**——不做级联、不做 join 查询、删一边不影响另一边。 |
| TBL-024 | **不做行级权限，表级足够。唯一例外是 `_notices`**（`NTF-010`）。做通用行级权限就要为每张表设计可见性规则，那是猜想。 |
| TBL-025 | 表的读写权限按项目角色判定；受保护表只有所有者能写。表结构可查询，项目的表可列出。 |
| TBL-026 | **删表是软删除**（D42）：表从列出结果中消失、其专属 tool 停止派发，**已有的行与事件一律保留、单行历史仍可查**——`RET-010` 说得很清楚，除到期清理外系统内不存在任何硬删除路径。**表名不可复用。** 被任何流程引用为结算表或主体表的表**不能删**，先停用那条流程。 |

### 5.2 写入的一致性：一张表同时只有一个写（`CON`）

| ID | 需求 |
|---|---|
| CON-001 | **一张表在同一时刻只允许一个写操作（insert / update / delete）在进行。** 第二个写排队等待，前一个结束才轮到它。不同的表互不影响——这是**表级**串行，不是全局锁。 |
| CON-002 | 一次"写"的边界包含四件事，它们在**同一个串行区间内**完成：① schema 校验 → ② 追加事件 + 投影 → ③ 流程节点求值（含流转插件）→ ④ 插件写回。**把 ③④ 圈进来是这条规则的全部意义**：否则求值读到的表可能已被另一个写改过，`_flows` 的状态迁移就不是原子的，两条并发的结算行会同时被判为"该节点的最后一票"。 |
| CON-003 | 串行区间**归属被写的那张表**。**流转插件自己不写任何表**——它把要写的行交回平台，**由平台在同一区间内代写**（`PLG-002`），且平台只肯代写**两张表**：本流程的结算表与主体表；**对主体表只能 update，不能 insert**（否则等于让它开出新实例，I-R 挡不住）。 |
| CON-004 | 这两张表的锁**一次性按表名全序获取**（全序即无循环等待，构造不出死锁）；写回结算表本身时锁**可重入**；`_flows` / `_flow_nodes` 的状态迁移随同一区间落定。 |
| CON-005 | **第三张表，平台不代写。** 真要写，用一个任务。<br>⚠️ 上一版这条写的是"`ctx` 不提供"，并附一句"进程内的插件绕过 `ctx` 是平凡的，所以这条防的是正常代码写出死锁、不防恶意"。**D52 之后那句注解删掉了**：插件根本没有写表的路，锁集合因此是结构性有界的，不再依赖插件自觉。 |
| CON-006 | **三件事明确在锁外**：「节点被激活」事件的派发与任务入队（非阻塞入队，**模型调用绝不在锁内**）· 通知行的写入 · 到期清理（整批离线进行）。 |
| CON-007 | **除该区间外，任何跨表写都没有原子性**——这是明确不承诺的事，不得在别处依赖它。 |
| CON-008 | **不做行级锁、不做多表事务、不做 MVCC。** 那是数据库的活。 |
| CON-009 | 插件求值有**硬超时**，且该超时上限**直接决定它所在结算表的最大写吞吐**（求值在锁内）。超时上限必须可配置，且默认值必须小到不会把一张表压死。<br>⚠️ QuickJS 载体让一次求值退化成毫秒级的纯计算（输入由平台预取，`PLG-002`），**这让这个数字好看得多，但不构成把超时调大的理由**——它仍然在锁内。容量必须在设计阶段实算一次。 |
| CON-010 | 容量规划必须把 **`_runs` 是全系统最热的表**这件事算进去（每次执行至少写一次）。它不被任何流程绑定，所以它的写没有 ③④ 两步。 |
| CON-012 | **存储层只使用基本的增删改查，不依赖任何数据库特有能力**（触发器、存储过程、行锁、事务隔离级别、MVCC、外键、级联、JSON 列）。表级写串行（`CON-001`）与写入区间（`CON-002`）由**应用层**实现，因而换一个数据库不需要改写入路径（D46）。<br>**落法**：存储层是一层只有基本 CRUD 的契约，SQLite 是它的第一个实现（D56）。**硬验收**：换一个内存实现进去，写入路径与它上面的一切不改一行——这与 `EXE-014` 是同一种验收放在两个接缝上（G12）。<br>⚠️ **D60 加了第二条平级的缝**：`Relations`（带索引的当前视图，五个方法）。需要按别的列找的表**独立成一张真表**，索引交给数据库；**不在键值里手写二级索引**——那是在重新实现数据库已经做好的事。它**是缓存不是账**（账在事件流里，漂了清空重放），因而 `I-N` 不受影响；`CREATE TABLE` / `CREATE INDEX` 不在本条的禁用清单里，且三个目标库上是同一个东西。第二条缝同样有两个实现跑同一组一致性测试。<br>⚠️ **应用层的表级串行只在单实例部署下成立。** 多实例需要一把进程外的锁，那是另一个决定，现在不做。 |
| CON-011 | **跨表写的原子性不做**（D43，`CON-007` 的直接后果）。`_runs` 行与产出行之间因此只有**可见性顺序保证**：**先落 `_runs`（`status` / `failureKind` / `tokensUsed`），再写产出行**——因为 `FLW-026⑥` 要读 `_runs.status` 才能判断产出行算不算结算。**两者之间崩溃是一种可接受的失败形态**：`_runs` 行完整、产出行可能缺失；**反过来（产出行在、执行状态未定）是不可接受的**，顺序就是为了排除它。 |

### 5.3 保留期与清理（`RET`）

| ID | 需求 |
|---|---|
| RET-001 | 任务分别声明**输出保留多久**（默认 **1 个月**）与**过程记录保留多久**（默认 **7 天**）。理由：过程用于排查，结论用于回看，价值衰减速度不同。 |
| RET-002 | `retainUntil` 与 `writtenBy` 一样是**平台在写入时自动补的字段**，值取自该任务**当时**声明的保留期。**不靠回查任务再取配置**——任务的保留期可以随时改，而已经写下的行不应该因为任务改了配置就提前消失或延后清理。 |
| RET-003 | 保留期作用于**任务的输出**：`_runs` 的行，以及任务写进用户表的那些行。到期后**整行删除**，并留一条清理留痕。 |
| RET-004 | 过程记录（`_runs.trace`）到期**只清这一列**，行本身按输出保留期走。 |
| RET-005 | 清理**整批按时间进行，不得选择性删除个别行**。 |
| RET-006 | **豁免清单（豁免优先于任务保留期）**：① 任何被 `_flows.subject` 引用过的行，或带 `_instance` 的行——不管它在结算表还是主体表、不管是谁写的；② `_flows` / `_flow_nodes` / `_plugins`；③ 项目 / 成员 / 技能 / 任务 / 流程 / 表 的定义；④ `_notices`（另有自己的保留期）。**一个还在进行中的流程实例，它的主体行或结算行被清理了就等于实例被腰斩**（I-X）。 |
| RET-007 | ① 写成"引用**过**"而不是"结算表的行"，是因为**任务完全可以往主体表写行**（`FLW-018③`），那批行两条规则都命中，必须有优先级。 |
| RET-008 | `_notices` 有自己的保留期（**平台级配置，默认 3 个月**），与任务无关——否则通知会无限增长。 |
| RET-009 | **已知悬空，必须显式承受**：`_plugins.generatedBy` 指向的那条 `_runs` 行会到期被清理。因此插件的源码、用例、测试结果、安装人**必须都在 `_plugins` 行内自包含**（`TBL-009`），丢的只是那次生成执行的 `output` 与 `trace`。 |
| RET-010 | **除到期清理外，系统内不存在任何其它删行路径。** 这是全系统唯一一处硬删除，理由只有一条：存储不是无限的。它与 I-D 不冲突——不可变说的是"不会被改写"，不是"永久保留"，且删除这件事本身留痕。 |

## 6. Git 仓绑定（`RPO`）

核心问题不是"怎么 clone"，而是：**让服务端 agent 能读到代码，同时让源码不落到任何个人的机器上**；以及**只读**——XOps 不需要任何仓库写权限，这个域不应该把它加回来。

| ID | 需求 |
|---|---|
| RPO-001 | 项目**当前绑一个** Git 仓。绑定经 MCP 建立，需所有者或维护者权限。（多仓见 **Q11**——多仓会让"一次执行只持有一个项目的代码"细化成"只持有本次声明的那几个仓"，隔离判定复杂一档。） |
| RPO-002 | 凭据**必须是只读的**。绑定生效前**实际验证一次**它确实能读、且**确实不能写**。若目标平台无法确认写权限，必须**明确告警**，不得静默放行（I-G）。 |
| RPO-003 | 凭据加密存储，**任何接口都不能读出原文，包括项目所有者自己**。展示时只给可识别片段与来源说明。 |
| RPO-004 | 凭据可轮换与撤销。撤销后依赖它的执行立即失败，**不使用任何缓存凭据**。 |
| RPO-005 | 凭据只注入到**容器外**实际需要它的那一次拉取动作，**不进入容器、不进入 agent 可读的上下文、不进入环境变量、不进入过程记录**（I-F）。 |
| RPO-006 | 每次使用凭据访问仓库产生审计事件：哪个项目、哪个仓、哪次执行、拉取了什么修订。 |
| RPO-007 | 平台差异必须收在一个**可适配的接口**后面（认证、克隆、权限元数据校验、webhook 签名验证）。**先做 GitHub**，新增一个平台只实现该接口，不改动绑定模型、工作区管理与执行链路。 |
| RPO-008 | 工作区在**容器外**准备：定位到**确切修订**，**只读**挂载进容器，容器内的任何写入不回流仓库，且随容器一并销毁。 |
| RPO-009 | 一次执行的工作区**只包含一个项目**的代码。跨项目访问在容器层面不可能，而不是被检查后拒绝。 |
| RPO-010 | 每次读取**记下确切修订**——否则"这份报告针对哪版代码"无法回答。 |
| RPO-011 | 拉取有容量与时间上限，超限时失败并明确报告，不允许无限制占用。 |
| RPO-012 | 提供绑定与同步状态查询（上次拉取时间、当前修订）、凭据轮换、解绑。查询结果中**不含凭据任何形式的原文或可恢复片段**。 |
| RPO-013 | **XOps 在任何代码路径上都不持有、不请求仓库的写权限**：不推分支、不提 PR、不打 tag、不改任何仓库内容（I-G）。 |
| RPO-014 | XForge 的登记（`XFG-002`）**挂在仓绑定上**，不另开一套对象。 |

## 7. 技能、任务与触发

### 7.1 技能（`SKL`）

**技能跑在一次性容器里，无凭据、只读挂载、默认拒绝出网、用完销毁——它越界了也做不到什么。这是为什么"任何成员都能写技能"是安全的。**

| ID | 需求 |
|---|---|
| SKL-001 | 技能是**用自然语言写的一份指令 + 几项声明**，经 MCP 创建；更新产生**新版本**。 |
| SKL-002 | **已发布的技能版本不可变**（I-K）。 |
| SKL-003 | 技能必须经过至少一次**成功的测试执行**才能发布。测试执行由作者手动发起，**在与正式执行相同的隔离环境中进行**（I-K）。 |
| SKL-004 | **上传不执行。** 草稿状态的技能不会被任何自动触发路径执行。这条防的不主要是别人，是作者自己。 |
| SKL-005 | 技能状态至少包含草稿、已发布、已停用。停用后不再被触发，历史执行记录完整保留。 |
| SKL-006 | 技能内容是**不可信输入**（G7）。平台不解析其语义、不因其内容改变控制流，只负责交给执行运行时。 |
| SKL-007 | 技能声明：**输入契约**（可机读：哪些参数、类型、是否必填）· **产出形态** · 是否需要**读代码仓** · **出网白名单** · 预计时长上限。**未声明的一律不提供**（I-I）。 |
| SKL-008 | 技能有两种归属：**项目公共**（归项目所有，成员都能看、能用、能触发）与**个人私有**（归创建它的人所有，同项目的其他成员看不到、也用不了）。私有技能**在项目中执行，用项目的数据源**。 |
| SKL-009 | **私有技能能读项目数据，是因为它的所有者是项目成员。权限来自人，不来自技能**——一个人退出项目，他挂在这个项目里的私有任务**立刻失去数据源，不能再执行**。 |
| SKL-010 | 可从一份技能**派生一份私有副本**（同项目内公共 → 私有，是一次**拷贝**而不是引用）。 |
| SKL-011 | **一条例外**：一旦某个私有技能的某个版本被用于满足某个流程节点，**该版本的内容、以及那个任务的定义（订阅什么、写哪张表）对项目成员转为可读**。私有是为了不打扰别人，不是为了让自动决策不可审查。 |
| SKL-012 | 跨项目复用技能**不做**（**Q14**）。技能内容的导出/导入若要支持，也只能是一次拷贝，不是引用。 |

### 7.2 任务（`TSK`）

```text
任务 = 一个技能 + 订阅哪些事件 + 读哪些数据源 + 写哪些表 + onComplete + 执行策略
执行策略 = 超时 · 重叠策略 · 启停 · 单次 token 上限 · 输出保留多久 · 过程记录保留多久
```

| ID | 需求 |
|---|---|
| TSK-001 | **平台只有这一种任务。** 质量监管、审批、CI 触发、代码走读四种常见用法在平台看来完全一样：某个事件发生了，某个任务订阅了它，于是跑一次技能，往声明的表里写几行。**平台不认识这四个词。** |
| TSK-002 | 任务引用一个**已发布**的技能。引用草稿技能被拒绝。技能版本策略**默认固定版本**——跟随最新意味着技能作者一次发布会改变所有引用它的任务的行为，这应当是明确选择而不是默认。 |
| TSK-003 | 任务提供的输入参数必须满足技能的输入契约；不满足时创建失败并**指明缺哪个参数**。 |
| TSK-004 | 任务声明**写哪些表**。写入由平台在容器外按该声明执行，**未声明的表写不了**。 |
| TSK-005 | 任务声明**单次 token 上限**（未声明用平台默认值）：一次执行消耗的模型 token 撞上这个数，**强制终止**——销毁容器、中止会话、归入"超出 token 预算"这一类失败。已产生的行仍然写入，但**标注来自未正常完成的执行**，因而不结算任何流程节点（`FLW-017⑥`）。实际用量记进 `_runs.tokensUsed`（I-V）。 |
| TSK-006 | **终止的时序是定死的**（超时与被取消走同一条路）：① 中止模型调用与会话（先停掉烧钱的那一头）→ ② 收敛并移交容器里已产生的行 → ③ **先落 `_runs`**（`status` / `failureKind` / `tokensUsed`），**再写产出行**——顺序定死，但**不是跨表事务**（`CON-011`、D43）→ ④ 销毁容器。 |
| TSK-007 | **项目级额度与限流不做。** 单次执行的上限就够了；项目级配额需要计费模型、配额分配与超额策略，现在没有支撑它的真实需求。 |
| TSK-008 | 任务声明**重叠策略**：上次执行未结束时又被触发，是**跳过本次**、**排队等待**、还是**终止上次并重跑**。**默认跳过**——定时任务最常见的故障是执行变慢后堆积成雪崩。 |
| TSK-009 | 任务可被启用与停用。停用的任务不响应任何触发，**包括手动**。**不提供删除**——执行记录不能因为任务没了就丢。 |
| TSK-010 | 任务可声明 **`onComplete`**，在它**正常完成、行已写入之后**执行一步：**一个插件入口** 或 **另一个任务** 或 **空**。挂插件时平台调用该插件的入口并把本次执行的 `_runs` 行交给它；挂任务时被挂的任务被触发，事件载荷带上本次执行的标识与产出行。 |
| TSK-011 | **深度硬限制 1**：被 `onComplete` 挂上的那个任务，它自己的 `onComplete` **必须为空**——**创建时就校验，不满足直接拒绝**（I-S）。一层是"输出后处理"，两层就是任务编排 DAG，随之而来的是依赖解析、失败传播、循环检测及其可视化。 |
| TSK-012 | **后处理失败不影响主任务的记录。** `_runs` 那一行已经写好了；onComplete 失败只留自己的痕迹并通知任务所有者。 |
| TSK-013 | 任务与技能一样有两种归属：项目公共 / 个人私有（`SKL-008`、`SKL-009`、`SKL-011` 同样适用）。 |
| TSK-014 | **造插件任务是本域的一个受限特例**：只能手动触发、不能订阅任何事件，见 `PLG-005`。 |
| TSK-015 | 装配派工单时，**只把技能实际声明的东西放进去，不扩权**；派工单**不含任何凭据**（I-I、I-F）。 |
| TSK-016 | 提供查询任务的**执行历史**与**触发历史**（含被拒绝与被跳过的）。 |
| TSK-017 | 〔纪律〕**CI 触发这一类用法需要自定义出网白名单**，而"白名单由谁批准、能不能由技能作者自己填"未定义（**Q10**）。在 Q10 定下来之前，自定义白名单不开放。 |

### 7.3 事件与触发（`TRG`）

| ID | 需求 |
|---|---|
| TRG-001 | **事件白名单恰好五类，仅此五类**：定时 · Git 事件 · 手动触发 · 流程节点被激活 · 上游任务完成。 |
| TRG-002 | 前三类由任务**自己声明订阅**并按载荷过滤。 |
| TRG-003 | 后两类**不是任务能自己声明订阅的**：「流程节点被激活」的唯一订阅途径是**被某个节点指定为写入者**；「上游任务完成」的唯一订阅途径是**被某个任务挂在 onComplete 上**。 |
| TRG-004 | **白名单里永远不加"某张表被写入"。** 一旦任务能订阅表的变化，就有了不受深度限制的回路——A 写表触发 B，B 写表触发 A。需要串联就用 onComplete 那一层，或在一个技能内部做完多步。 |
| TRG-005 | **写入触发的是插件求值，不是任务。** 插件求值跑在进程内、毫秒级、不产生执行、不烧模型调用。**这两件事必须在实现上分得很开。** |
| TRG-006 | **容器内不提供任何触发能力**，不存在自触发回路（I-J）。 |
| TRG-007 | 三条共同纪律：**非阻塞**（触发的产出是"一次执行进了队列"，不是"任务跑完了"）· **幂等**（同一个外部事件最多产生一次执行）· **留痕**（被拒绝的、被重叠策略跳过的触发同样留痕——一个静默被跳过的任务，会让人以为它在跑）。 |
| TRG-008 | 触发前检查：任务存在、已启用、**该任务允许这种触发方式**。任一不满足则拒绝并留痕。 |
| TRG-009 | **定时**：至少支持"每天某时"与"每隔 N 小时"两类表达，以及**明确的时区**。触发者记为系统，但**必须能追溯到配置该调度的人**。提供下次触发时间的查询。 |
| TRG-010 | 服务重启或短暂不可用后恢复时，**错过的定时窗口不补跑**，只按下一个窗口正常触发，并对错过的窗口留痕。补跑会在恢复瞬间产生一批并发执行，风险大于收益。 |
| TRG-011 | **Git webhook 端点是 G1 的两个非 MCP 入口之一，它只能做一件事**：产生一个 git 事件。**不能创建或修改任何对象**，只能让订阅了它的任务被触发。 |
| TRG-012 | webhook 必须**验证签名/密钥**；验证失败的请求被拒绝，且**不泄露任何关于任务或项目是否存在的信息**。 |
| TRG-013 | webhook 按**事件标识幂等**：平台的重投机制会导致重复投递，同一事件重复投递不产生第二次执行。 |
| TRG-014 | webhook 端点**必须快速返回**，不在请求内做任何拉取或执行——平台的 webhook 都有超时并会因超时重投，从而放大问题。 |
| TRG-015 | webhook 载荷是不可信输入（G7）：只从中提取**结构化字段**（确切提交标识、分支、事件类型），**不解析其中任何自由文本**。支持按分支与事件类型过滤。 |
| TRG-016 | **手动触发**：项目成员经 MCP 发起，**非阻塞**返回执行标识；可带幂等键与可选的目标修订。 |
| TRG-017 | **事件载荷覆盖任务定义里写死的目标修订**：git 事件带来的提交标识、流程事件带来的主体修订，都覆盖任务定义。少了这条，执行读的是"仓库现在长什么样"，不是"这次要它看的那一版"。 |
| TRG-018 | 「流程节点被激活」的载荷含：**实例标识** · 流程与版本 · **哪个节点** · **发起者** · **主体标识与修订**。 |
| TRG-019 | 「上游任务完成」的载荷含：上游执行标识 · 它写的那些行。 |
| TRG-020 | 〔纪律〕触发时**不允许覆盖任务的输入参数**——一旦允许，创建期的契约校验就要在触发期再做一遍，执行记录也要记下实际用的参数而非任务定义的参数。需要不同参数就建不同任务。 |

## 8. 执行（`EXE`）

```text
事件 → 任务被触发 → 装配派工单（不可变） → 容器外准备（只读工作区）
     → 一次性容器里跑（全部工具执行在此发生） → 移交（行 + 状态 + 失败分类 + 过程记录）
     → 平台在容器外写入 → onComplete
```

| ID | 需求 |
|---|---|
| EXE-001 | 派工单**不可变**，内容为：技能内容与版本 · 输入 · 数据源清单 · 写入目标 · 超时 · **触发事件的完整载荷** · 触发者。**不含任何凭据**，且只放技能实际声明的东西（I-I）。 |
| EXE-002 | 每次执行使用**独立的一次性容器**。容器不复用、不共享、不池化。 |
| EXE-003 | **全部文件与进程操作都在容器内发生。** 容器外的常驻编排进程只做编排与模型调用，不直接触碰工作区、宿主文件系统或宿主进程。 |
| EXE-004 | **容器里没有任何写表的路径。** 任务"写表"的实际含义是：容器产出待写入的行，**平台在容器外按任务的声明写入**（I-E）。 |
| EXE-005 | 这条边界必须由**能力封锁**实现——容器里根本没有通往确定性平面的凭据与网络路径——**不得依赖"技能内容里没有要求做这些事"**。 |
| EXE-006 | 容器内可用的能力由派工单的数据源清单决定，**未声明的一律不提供**。未声明需要代码的执行，容器中**不存在任何工作区挂载**。 |
| EXE-007 | 容器的对外网络**默认拒绝**，只放行声明的白名单。**模型服务不在此列**——模型调用发生在容器外。 |
| EXE-008 | 容器有明确的 CPU、内存、磁盘上限，超限时被终止并归入**资源不足**类失败。<br>⚠️ **硬上限由 D64 转交部署侧**（2026-09-05）：`setrlimit` 是进程级的、会把 xopsd 自己一起限住且要 `unsafe`（本仓 forbid），cgroups 要 Linux 加权限，两者粒度都不是「一次执行」——**在进程内做不到，不是没做**。<br>**责任转移不是消失**：实际在拦着的六道（token 上限 · 看门狗 · 并发上限 · 上游的工具回话上界 · 产物截断 · 产出行上限）逐条列在 `IsolationLevel::bounds()` 里、上启动横幅、有测试盯着一条都不能少。剩下的是**一个上界不是一道墙**，那道墙由部署方建。 |
| EXE-009 | 容器之间相互隔离：一次执行不得读取或影响另一次执行的文件系统、进程或网络状态。 |
| EXE-010 | 容器内**不含任何凭据**，**不提供触发能力**（I-F、I-J）。 |
| EXE-011 | 执行结束后容器被**完整销毁**，不留残留进程、文件、挂载或网络状态。 |
| EXE-012 | **两类数据源，一律显式声明，未声明的不提供**：**代码**（只读挂载项目的 Git 仓，定位到确切修订，一次执行只有一个项目的代码）· **外部网络**（默认拒绝，只放行声明的地址，模型服务不在此列）。 |
| EXE-013 | **表数据不是执行的数据源**（D44）。平台**不把表导出成快照文件**，也**不给容器任何到 XOps 的网络路径**。"让容器里的 agent 自己调 MCP 读表"这条路**不存在**——那要往容器里放一个令牌，`I-F` 与 `EXE-005` 当场破掉。需要表数据的技能，由创建任务的人或 agent **经 MCP 查好，作为任务的输入参数传进去**。<br>⚠️ **这条收窄了「数据源是 Git 仓和表」这句定位：技能读不到表。** 表是产出侧与查询侧的数据形状，不是执行的输入侧数据源。 |
| EXE-014 | **XOps 与执行引擎之间只有一条执行契约这一个接缝。引擎的概念不得泄漏进契约。** 硬验收：**把引擎换成一个最简桩实现，契约与其余部分无需修改。**<br>**兑现方式**（D50 → **D61 改**）：引擎是 **AttaCore**，**以库的形式嵌在 XOps 进程里**（`runtime::agent::Builder`），源码以 git 子模块固定在一个 tag 上。<br>⚠️ **这是兑现，不是取代**：XOps 侧仍然有自己的执行契约，**AttaCore 的数据结构不得直接流进它**，桩实现验收照做。**最容易破坏本条的，正是图省事让引擎的数据结构直接流进契约**——有一条枚举源码的测试守着它。<br>⚠️ **第 11 版这条原本写的是"两个分立的进程"，D61 把它改成一个。** 换来的代价与仍然成立的部分逐条记在 D61 里，**其中 `EXE-017` 的一半是真的拿不到了**，不是被绕过去了。 |
| ~~EXE-029~~ | **由 D62 关闭：XOps 不实现容器后端。** 隔离是部署侧的事——**责任转移，不是消失**：需要那道墙的部署自己去建，XOps 负责把边界在哪儿说清楚。<br>没有容器之后边界改由这几样兑现（都可跑可测）：工具集只有 `Read`/`Glob`/`Grep`/`EmitRow`（`I-I`）· 路径锁在只读工作区里、没声明代码仓就一个文件都不准碰 · 派工单不含凭据也不含到 XOps 的网络路径 · 唯一的写向是 `EmitRow` 且只通向已声明的表（`EXE-031`）。<br>⚠️ **`EXE-008` 资源上限是剩下的主要风险**：一个跑飞的技能能吃满这台机器，那是部署侧最该先补的一条。<br>原文见 §20 与 `D51`。
| EXE-030 | **引擎不可用时，执行失败并如实归入引擎错误类，绝不在 XOps 进程里就地跑一遍。**<br>这与"沙箱不可用就不沙箱"是同一个错误：一个配置成"在别处执行"的部署，如果在别处连不上时悄悄在本地执行了，**它的隔离承诺恰好在最需要的时刻不成立**。<br>⚠️ **D61 之后引擎就在本进程里，所以这条在嵌入路径上是空的**——没有"别处"可连，也就没有"连不上就在本地跑"这个降级。它对任何**走进程外引擎**的实现仍然成立，`Engine::healthy` 那个口子因此保留着。 |
| EXE-015 | **模型凭据只存在于容器外**，从结构上进不了容器。凭据是平台级统一配置，变更不需重启服务，且不影响在途执行。 |
| EXE-016 | **跨执行的会话隔离由常驻编排进程负责**，必须**显式实现并实测**：一次执行一个会话、用完即销毁；第一次执行在会话里留下可识别痕迹，第二次读不到（I-M）。**失效时通常没有任何报错**，表现只是产出变得莫名其妙——光看代码发现不了。<br>⚠️ 引擎侧另有会话池与空闲淘汰，**"看起来干净"比没有池子时更容易骗过人**——这条必须实测，不能看代码。 |
| EXE-017 | **编排进程崩溃、卡死或异常退出时，全部在途执行**必须在有限时间内被归入明确的失败分类**并可重跑**，**不得无限期挂起**。常驻进程被全部在途执行共享，一次崩溃就是一批执行同时失败。<br>⚠️ **D61 之后这一条只兑现了一半**：引擎嵌在 XOps 进程里，所以 panic 由 `Runtime` 的 `catch_unwind` 接住并归类（这半边还在），而 **abort / OOM 会把 XOps 一起带走——那时没有一个活着的进程去做归类**。卡死那一半由看门狗兜住（`EXE-019`），它与引擎在不在同一个进程无关。**这是 D61 明写的代价，不是疏漏。** |
| EXE-018 | 编排进程重启与恢复不得丢失已经完成并移交的执行结果。 |
| EXE-019 | **超时强制终止时不得留下孤儿会话继续消耗模型额度。** |
| EXE-020 | **失败必须分类**：技能错误 / 凭据错误 / 工作区错误 / 模型服务错误 / 引擎错误 / 超时 / **超出 token 预算** / 资源不足。**"失败了"不是一个可用的结论。** |
| EXE-021 | 执行是**异步**的：提交后立即返回执行标识，不阻塞等待完成。执行可被取消，取消后立即终止，部分输出保留。 |
| EXE-022 | 保留**过程记录**（至少含原始输出流），存 `_runs.trace`。**过程记录中不得出现任何凭据**（I-F）。 |
| EXE-023 | 平台在容器外写入时**校验每一行是否符合目标表的 schema**，然后写进 `_runs` 与任务声明的那些表，补上 `writtenBy` / `at` / `revision` / `_instance` / `retainUntil`。 |
| EXE-024 | **两层拒绝必须分清**：schema 校验不过 → **整批行不入表**，执行归为技能错误类失败；schema 过、节点判定不过 → **行入表**，只是不结算。**两种情况都要通知**——自动化失灵不能是静默的。 |
| EXE-025 | 单次执行的产物有体量上限，超限时**截断并明确标注**，不静默丢弃。 |
| EXE-026 | 每次执行产生一条 `_runs` 行，**永不被后续执行覆盖**；重跑产生新的一次。执行记录在其任务被修改或停用后仍完整保留（受 `RET-003` 约束）。 |
| EXE-027 | 并发执行数有上限，按平台与项目两级控制，防止单个项目耗尽全部算力。 |
| EXE-028 | **隔离必须被主动攻击验证，不能只做正向测试**（⚠️ **D62 之后被攻击的对象从"我们的容器"变成"部署那道墙"，验证的责任跟着一起走**）：写一个故意越界的技能，尝试写表、读另一个项目的工作区、读凭据、访问白名单外地址、触发另一个任务、逃逸宿主文件系统——**每一项都必须在容器与能力层失败**（路径不存在／网络不通），**不是靠内容检查拦下的**。 |
| EXE-031 | **技能交回产出行的路径由平台提供，且只通向任务已声明的那张表。**<br>`EXE-023` 说的是"平台在容器外写入"，`TSK-006` ② 说的是"收敛并移交容器里已产生的行"——两条都指着同一个缺口:**行怎么从执行里出来，此前没有一条需求说过**，于是声明了 `output: rows` 的技能产不出任何行。<br>落法有两条硬约束:<br>① **入口由平台给，不是技能自己找**。技能没有到 XOps 的网络路径（`EXE-004`、`I-F`），也不该有——入口是执行方在本地收下，随执行结果一并交回。<br>② **权威校验在执行之外**（`EXE-023`）。入口那一侧可以先做形状检查，**那是给模型改的机会，不是判定**；判定留在 `EXE-024` 的两层拒绝里。把权威移进去等于让技能自己判自己。<br>⚠️ **`_instance` 一律拒**（`I-P`）:技能与用户都不能自己写它，它由平台按流程上下文填。<br>⚠️ 未声明的表写不了（`TSK-004`）；本版**一次执行只写一张表**——就是任务声明的第一张，多表留到有真需求时再说。 |

> **这个拓扑的两笔代价必须正面应对，不能因为图上画着"一次性容器"就以为它们不存在**：`EXE-016`（会话隔离原本由"一次执行一个容器"免费提供，编排进程常驻之后变成它自己的责任）与 `EXE-017`（崩溃影响面从单次执行扩大到全部在途执行）。

## 9. 插件（`PLG`）

> **插件跑在 QuickJS 载体里，能力默认为零。载体管得了它碰什么，管不了它说什么——所以治理一条不减。**

上一版这里的开篇是"安装一个插件 ≈ 授予这个人在 XOps 服务端执行任意代码的能力"。**D52 取代了那条结论**，但取代的方式是**收窄让渡**，不是解除让渡：让渡掉的从"由模型写的代码在服务端执行任意东西"变成"**由模型写的代码替人做判断**"。后一半仍然在，`G11` 的两半就是照着这个分的。

| ID | 需求 |
|---|---|
| PLG-001 | 插件是一段 **JS 代码**，装在项目里，被平台在**两个位置**调用：**流转插件**（流程节点求值时）与**输出插件**（任务 onComplete 时）。**不存在第三个调用位置。**<br>它跑在 **QuickJS 载体**里：**一次调用新建一个 runtime，调用结束整个扔掉**——调用之间不共享任何状态。 |
| PLG-002 | **流转插件**：输入是实例状态 · 刚写入的那一行 · **节点声明的相关行**（`FLW-003`）——**三样都由平台在调用前查好，按 JSON 喂进去**；输出是这个节点**过 / 不过 / 拒绝**，以及**要写回哪些行**，那些行**由平台在同一串行区间内代写**（`CON-003`）。<br>**流转插件的能力为零，没有可声明项**：没有文件、没有网络、没有表、没有时钟（除 `Date`）、没有任何宿主绑定。 |
| PLG-003 | **输出插件**：输入是本次执行的 `_runs` 行与它写的那些行；输出由插件自己决定——发邮件、发 IM、推到别的系统，**都是插件的事**。它的能力见 `PLG-012`。**它写不了任何表**（I-R）。 |
| PLG-004 | **平台不提供"发消息"这种能力，也不定义"通道"这个概念。** 它只负责在正确的时机调用插件入口、把该给的数据给它，并按它声明过的能力放行它要用的那几样。插件要连什么系统、用什么凭据，是插件自己的事。 |
| PLG-005 | **插件不是上传的，是生成的。** 造插件任务是一种**受限的任务**：**只能手动触发，不能订阅任何事件**；技能产出 **JS 源码 + 一份能力声明 + 一组测试用例**（输入 → 期望输出）。 |
| PLG-006 | 平台确定性地做三件事：**编译**（QuickJS 字节码编译 + 入口导出检查）· **跑用例**（在**真载体**里跑，能力**按声明**给，不多给）· **静态检查**。三样全过 → 产出一个**候选插件**（还没生效）（I-K）。 |
| PLG-007 | **维护者**经 MCP **安装**候选插件，它才成为项目的插件，才能被流程节点或 onComplete 引用。**安装时必须逐条披露它声明了哪些能力，披露不可跳过。** |
| PLG-008 | 权限分层：造插件任务的创建与手动触发、看测试结果 = **项目成员**；把候选插件安装进项目 = **维护者及以上**；读写插件的配置 = **所有者**。 |
| PLG-009 | **已安装的插件版本不可变**（I-K），**能力声明是版本的一部分**。改就是生成一个新候选、再装一次——**改能力也是**，不存在"给已安装的插件加一项能力"这条路径。引用它的流程节点用**固定版本，不跟随最新**。 |
| PLG-010 | **已安装插件的源码与它的能力声明，对全体项目成员必须可读**（I-T）。<br>⚠️ **理由变了，结论一个字没变**：上一版的理由是"它有完全权限"，现在它没有了，但**它的判断仍然能结算流程节点**——一个不可审查的、由模型生成的东西替人做决定，没人能对它负责。**隔离管的是它能碰什么，管不到它说什么。**<br>成员还可列出候选插件、查看其源码、能力声明与测试结果。 |
| PLG-011 | 安装是一条审计事件，记下**谁装的、哪个技能的哪个版本生成的、哪次执行产出的、声明了哪些能力、测试用例是什么、结果如何**。 |
| PLG-012 | **能力默认为零，未声明即没有**——不是"调用时被拒绝"，是**那个函数不存在**（I-Z）。<br>**流转插件没有可声明项**（`PLG-002`）。**输出插件只能声明三样，仅此三样**：<br>① **出网**——一张主机白名单。未声明的主机连不上；**重定向每一跳重新判定**，否则白名单只对第一跳成立。<br>② **读自己的配置**——只能读到**它自己**那一份（`PLG-015`），读不到别的插件的、读不到平台的。<br>③ **读表**——声明的那几张、**本项目的**。**`_notices` 不在可声明之列**（`NTF-012`）。<br>⚠️ ③ 存在的唯一理由是接住 **D44** 的那条出路：技能读不到表，需要表数据就"经 MCP 查好放进任务输入，**或用 onComplete 挂一个输出插件去读**"。后一条路必须还在。 |
| PLG-013 | 平台仍要做**三件防故障（不是防恶意）的事**：**超时**（插件求值有硬超时，**超时视为"节点未通过"，绝不视为通过**）· **错误隔离**（插件抛异常不能拖垮平台；异常视为"节点未通过"并留痕；**故障只花一次调用**，不是一个 runtime 的持续降级）· **不递归**（流转插件交回、由平台代写的行**不再触发插件求值**，避免自激）（I-R）。<br>**死循环由载体的字节码级中断兜住**——光靠 future 超时停不下一个不让出的循环；它的表现必须是"这次求值超时"，不是"一个线程转死了"。 |
| PLG-014 | **`I-S`（onComplete 深度限制）与 `I-J`（执行环境无法触发任务）对插件同样成立**：插件没有触发任务的能力，也没有自己的 onComplete——那两条路不在它能声明的三样里。<br>⚠️ 上一版这条写的是"它们不约束插件，绕过是平凡的，这属于 G11 的治理范围"。**D52 之后前半句反过来了**；但 `G11` 的治理那一半**没有因此作废**，它现在负责的是**判断**而不是**执行**（`PLG-010`）。 |
| PLG-015 | 每个插件有一份自己的配置（键值对），**由项目所有者经 MCP 写入，加密存储，任何接口都读不出原文**；调用时只注入给该插件，**且只在它声明了 `PLG-012` ② 时注入**。**配置不落在 `_plugins` 表里**——那张表可查询，把凭据放进去等于公开。**这是全系统唯一一份不以表的形式存在的状态**（I-A）。 |
| PLG-016 | 提供：列出已安装插件 · 列出候选插件 · **查看候选的源码、能力声明与测试结果** · **读已安装插件的源码与能力声明** · **安装候选插件（含能力披露）** · 停用 · 查询版本历史 · 读写插件配置。 |
| PLG-017 | **静态检查的范围由载体回答**（D54，原 **Q16** 由此关闭）：**够不到的东西不需要禁**——载体不给绑定，脚本就没有那条路，所以不必再讨论"要不要禁某些 import、禁 `process.env`"。剩下的静态检查只有两件确定性的事：**① 入口导出在不在；② 声明的能力与安装时披露的是否一致。** |
| PLG-018 | 〔纪律〕**能用技能解决的，不要用插件。**<br>理由从"插件不可隔离"换成了更朴素的一条：**插件读不到代码、读不到任务的输入、只吃平台喂的那点 JSON，它能做的事本来就少。** 正当理由仍然只有两个：**省 token**（流程流转这种高频、确定性的判断不该每次调模型）和**平台做不到的对接**。**"JS 写起来顺手"不是理由。** |

> **两条残留风险，写出来而不是假装没有**（对应概念文档 §11.2）：
>
> ① **载体本身是信任基。** QuickJS 是一个 C 实现，它的内存安全是这套隔离的地基——**版本要跟、CVE 要看**。它是依赖，不是免死金牌。
>
> ② **输出插件的外泄面是可审查的，不是不存在的。** 它拿得到喂给它的数据，送得到它声明过的主机，两者在安装时都披露过（`PLG-007`）。

## 10. 流程：吃掉审批（`FLW`）

```text
流程 = 有序的节点序列（可含并行组）
     + 结算表：节点的结算行写在这里
     + 主体表（可选）：流程在治理哪张表的行
     + 何时发起实例
```

**节点结算的形式只有一种：结算表上出现了满足条件、且写入者被允许的行。**

```text
人写这一行      → 这就是审批
任务写这一行    → 这就是自动化（agent 判断，费 token，能读代码）
插件判定        → 这也是自动化（确定性判断，不费 token，读表）
```

因为"人做决定"本来就是往那张表里写一行，所以**不需要"审批实例""决策""质量门""代理任务"四个概念**。

### 10.1 定义与实例

| ID | 需求 |
|---|---|
| FLW-001 | 流程定义归属项目，经 MCP 创建（G1）。**不存在流程设计器界面。** |
| FLW-002 | 一条流程由**有序的节点序列**组成，可含**并行组**（同时激活，全部通过后才推进）。 |
| FLW-003 | 每个节点声明：**通过条件**（结算表上出现满足〈筛选 A〉的行，且数量 ≥ N）· **拒绝条件**（出现满足〈筛选 B〉的行，可选）· **允许写入者** · **职责分离**（是否要求写入者 ≠ 实例发起人）· **求值方式**（默认按筛选判定，或指定一个**流转插件**）。<br>**指定了流转插件时，节点还必须声明它求值时要用到哪些行**（哪张表、什么筛选、上限多少行）。理由是流转插件读不到表（`PLG-002`）：它的输入由平台在调用前查好喂进去。**这不是限制，是把一件本来就该做的事挑明了**——求值发生在写串行区间内（`CON-002` ③），一次自由查询就是一次不确定的写时延。 |
| FLW-004 | 流程声明一张**结算表**与可选的**主体表**。**两者不得是同一张，校验流程定义时就拒绝。** |
| FLW-005 | `FLW-004` 这一刀避开两个死结：① 若同表，人要推进流程就得往主体表插新行，而"插新行"正是随行发起实例的动作，会开出第二个实例；② 若靠 update 主体行来推进，那么"数量 ≥ N"（会签）与"同一写入者只能结算一次"两条都失去意义。分开之后模型是统一的：**主体表放"这件事本身"，结算表放"谁对它做了什么表态"**。 |
| FLW-006 | 流程定义**版本化**：发布新版本、可停用；停用后不能发起新实例，在途实例继续执行完。 |
| FLW-007 | **实例始终按发起时的流程定义版本走完**，不受后续版本变更影响。 |
| FLW-008 | 提供**校验** tool（**不落库**），至少抓三件事：① 结算表 ≠ 主体表；② 无主体表时不得声明随行发起；③ **筛选不得重叠**。<br>**③ 的判定口径**（D47）：把流程展开成一个**激活集合序列**——串行节点各自是一个集合，一个并行组整体是一个集合——则**同一集合内的节点两两之间**、以及**相邻两个集合之间**，筛选都不得重叠。同一集合内同时激活，一行落进来会被多个节点同时求值；相邻集合之间则会在前一个通过的瞬间被同一行结算。<br>**判定取保守口径：只要不能证明两个筛选互斥，就判为重叠并拒绝。宁可误拒**——误放的后果是运行时一行同时结算两个节点，而那是事后查不出来的。 |
| FLW-009 | **实例发起二选一，在流程定义里声明**：**随行自动发起**（**主体表**插入一条新行时，主体就是那一行）或 **显式发起**（有人经 MCP 调"发起实例"，主体由调用方给）。 |
| FLW-010 | **结算行的插入永远不会再开出一个实例**——随行发起只看主体表。 |
| FLW-011 | 两种方式都一样：**实例创建的同一步，第一个节点随即激活**并产生「流程节点被激活」事件。 |
| FLW-012 | 主体 = (类型, 标识, 修订)。**类型开放，平台不解释。** |
| FLW-013 | 实例落在 `_flows`，每个节点在 `_flow_nodes` 有一行（`TBL-007`、`TBL-008`）。 |
| FLW-014 | 同一张表**可以被多条流程引用**（"结算表 ≠ 主体表"是每条流程内部的约束）。锁按表名全序取，因而仍构造不出死锁（`CON-004`）。 |
| FLW-015 | 提供：发起实例 · 查询实例状态与**卡在哪** · 取消实例 · **为某实例的某节点写入一行**。 |
| FLW-016 | 提供**跨项目聚合**的"查询我待处理的流程节点"。 |
| FLW-017 | 实例可设**过期时间**，过期进入"已过期"终态。节点结算的**有效期**（`expiresAt`）由谁设、默认多久待定（**Q12**）。 |

### 10.2 谁被允许写

| ID | 需求 |
|---|---|
| FLW-018 | 节点的**允许写入者**是三者的并集：① **项目角色集合**（所有者/维护者/成员）· ② **某张名单表里的人** · ③ **某个指定的私有任务**（该任务写入的行才算数）。**这就是"由创建流程的人决定谁来做"的落法**，三种写法在同一个字段里，不新增概念。 |
| FLW-019 | **名单表是受保护表，只有项目所有者能写，保护级别不可降级**（I-Q）。**名单表的写权限就是审批权的元权限**——谁能改名单，谁就能给自己发审批权。 |
| FLW-020 | 名单表可以独立于流程定义变更——**人员变动改名单，不改流程**。 |
| FLW-021 | **③ 只能指定私有任务。** 项目公共任务没有"所有者这个人"，一旦它写的行被算作节点通过，"每一次通过都归属一个具名的人"当场落空（G10、I-H）。 |

### 10.3 一行怎么知道自己属于哪个实例

| ID | 需求 |
|---|---|
| FLW-022 | 流程的**结算表**上，平台自动加一个**受保护的系统列 `_instance`**。三种填法：人写行 → 用"为某实例的某节点写入一行"这个 tool，实例标识作为参数；任务写行 → 由「节点被激活」事件载荷里的实例标识自动填；流转插件写回 → 由求值上下文自动填。 |
| FLW-023 | **技能与用户都不能自己写 `_instance` 这一列**（I-P）。没有它，两个并发的流程实例会在同一张表上产生两条同样满足筛选的行，节点判定无从区分——**这是整个流程模型的地基**。 |
| FLW-024 | **主体行不带 `_instance`**——主体与实例的关联记在 `_flows.subject` 上。主体表的插入只负责开实例，**主体行本身不参与任何节点的求值**。 |
| FLW-025 | **输出插件对结算表只读，不能写**（I-R）。它跑在 onComplete 的上下文里，没有流程求值上下文，`_instance` 无从填；让它写结算表等于开一条绕过 `FLW-026` 的旁路。 |

### 10.4 一行要算数，必须同时满足

| ID | 需求 |
|---|---|
| FLW-026 | **七条判定，缺一不可**：<br>① 该行写进了节点的**结算表**，`_instance` 指向本实例，且满足节点的筛选；<br>② 写入者在节点的**允许写入者集合内**——**写入这一刻**判定，不是事先；<br>③ 若节点要求职责分离：**写入者 ≠ 实例发起人**（写入者是任务时，比的是**任务所有者**）；<br>④ **同一写入者在同一节点尚未贡献过结算行**；<br>⑤ 该节点此刻处于**激活**状态（实例未终结、未被别处的拒绝终止）；<br>⑥ 若写入来自执行：该执行**正常完成**（非超时/取消/失败）；<br>⑦ 若写入来自执行且该执行声明了代码数据源：其**实际读取的修订 == 事件载荷里的主体修订**（未声明代码数据源的执行不适用本项）。 |
| FLW-027 | **任一不满足 → 这一行照常留在表里**（它是一条正常数据），只是不结算该节点，并**留一条"未被采纳"的痕迹 + 通知写入者**。 |
| FLW-028 | **节点指定了流转插件时**：① 里的"满足筛选"这一半由**插件的判定替代**，**②～⑦ 一条不减**，且由平台在**调用插件之前**先判完——不满足的行根本不会被交给插件。 |
| FLW-029 | ② 之所以是**写入这一刻**判定：名单表可以随时改——事件发出时 a 在名单里，任务跑了几分钟，期间 a 被移出，② 正好挡住这一情形。 |
| FLW-030 | ③ 挡的是**闭环自批**：a 自己发起 → 触发 a 自己的任务 → 记为 a 的通过，全程一个人，审批唯一的价值（多一个人）当场归零。**写入者是任务时比任务所有者，因为任务不是责任主体，人才是**（I-O）。 |
| FLW-031 | ⑥⑦ 挡的是**产出异常**：执行超时后部分产出仍被保留，那些残片不能算数；以及"执行读的是仓库当前 HEAD 而不是这次要它看的那一版"。 |
| FLW-032 | **只有 insert 参与节点求值**（D45）。结算表上的 **update 与 delete 不触发求值、不结算、也不撤销任何已有的结算**——一次表态一旦被采纳就是既成事实，改写或删掉那一行不会把它收回去（`_flow_nodes.settledBy` 记的是结算它的那些行的 ID，那条记录不因原行被改而变）。要改变结论，只能在节点仍激活时再写一行，或按 `FLW-039` 发起一个新实例。 |

### 10.5 一行写入时发生什么

| ID | 需求 |
|---|---|
| FLW-033 | 一行被写进表 → 追加事件、投影（总是发生）；**若这张表是某条流程的结算表且这一行带 `_instance`** → 定位该实例**当前激活的节点** → 求值（默认按筛选，或调用节点指定的流转插件）。 |
| FLW-034 | 求值三条分支：**不结算** → 行照常留在表里，留"未被采纳"痕迹 + 通知写入者；**通过** → 节点标记已通过、写回流转插件要求的行，串行时下一个节点激活、并行组全部通过后才推进，并产生「流程节点被激活」事件；若已是最后一个节点 → **实例进入"已通过"终态**；**拒绝** → **整个实例立即进入拒绝终态**，其余节点转为"已作废"。 |
| FLW-035 | 整段发生在**这张表的写入串行区间内**（`CON-002`）——**除了最后的"触发任务"那一步，它在锁外入队**。 |
| FLW-036 | **流程可以声明主体表上的哪些列是状态列**（比如 `bugs.status`）。**状态列只有平台与流转插件能写，用户的 update 写不了它**（I-P）。不这么做，任何成员都能直接 `update bugs.status = closed` 绕过整条流程——七条判定只管"这行算不算结算"，**从不阻止写入**。 |
| FLW-037 | 于是一个主体的流转是这样闭环的：**人往结算表写一行表态 → 节点结算 → 流转插件把主体表的状态列写成新状态**。 |

### 10.6 三条边界

| ID | 需求 |
|---|---|
| FLW-038 | **不做条件分支 / 表达式引擎。** 用"不同流程 + 发起时选择"表达；需要条件逻辑就写进流转插件。 |
| FLW-039 | **不做退回 / 驳回循环。** 被拒绝的实例进入拒绝终态；重走一遍是**发起一个新实例**。 |
| FLW-040 | **不做超时自动通过 / 自动推进。** 实例可设过期，过期走"已过期"终态。**一个会自动放行的关卡比没有关卡更糟——它看起来像有。** |
| FLW-041 | **一个总是失败的流转插件会让实例永久停住，这是刻意的**：超时与异常一律判为"未通过"，而既不做超时自动推进、也不做退回，所以实例就停在那儿。**卡死的东西应该被看见，不应该被绕过。** 出路是**取消实例**，修好插件之后发起一个新实例。 |

## 11. 模板、看板与通知

### 11.1 模板（`TPL`）

| ID | 需求 |
|---|---|
| TPL-001 | 模板 = **一套表 schema + 可选的流程定义 + 可选的插件**。 |
| TPL-002 | 提供：列出可用模板 · 查看模板内容 · **在本项目实例化**（建表、建流程、装插件，一步完成）。 |
| TPL-003 | 平台自带三个：**bugs**（`bugs` 主体表：状态列、自增序号列、派生的可读 ID 列 + `bug-events` 结算表 + 一条随行自动发起的流程 + 流转插件）<br>⚠️ 结算表名写成连字符而不是下划线，是与 `TBL-001` 的表名规则对齐（小写字母开头，只含小写字母、数字与单个连字符）——**差一个字符，但下划线那种建不出来**。· **issues**（同构，`issues` + `issue-events`）· **approvals**（`approvals` 结算表，**无主体表** + 一条用于审批的流程骨架 + 插件）。 |
| TPL-004 | **实例化之后它们就是普通的表、流程和插件**，用户想怎么改就怎么改——加列、改流程、换插件（换插件仍需维护者）。**模板是起点，不是约束。** |
| TPL-005 | 缺陷 ID `<项目短名>-<序号>` 由 **bugs 模板声明的一个派生文本列**生成（模板 `{project.slug}-{seq}`）。**平台只提供"自增序号"与"派生文本"两个通用列类型和"项目短名"这个项目属性，不认识"缺陷 ID"这个概念。** 用派生列而不是让写入方 agent 自己拼字符串，是因为这个 ID 会被**手写进提交历史**——它必须简单到不可能出错。 |
| TPL-006 | **"决策必须附带理由"由 approvals 模板的插件承接**：它校验 `reason` 列非空，空的不结算。**平台本身不认识"理由"这个概念。** |
| TPL-007 | 模板建议在结算表上加一个**行引用列指回主体行**，方便人和 agent 各自把完整时间线拼起来（`BRD-006`）。 |
| TPL-008 | 首版三个模板随平台发行。**用户自定义模板的导出与提交路径待定（Q15）。** |

### 11.2 看板与 Web（`BRD`）

| ID | 需求 |
|---|---|
| BRD-001 | **看板 = 一张表的一个视图**：显示哪张表、按什么筛选、按什么排序、显示哪几列。看板的定义**经 MCP** 创建与修改。 |
| BRD-002 | **平台不内建任何报表**——没有燃尽图、没有趋势图、没有跨项目对比、没有执行结果对比视图。想要趋势，就写一个技能，读历史行、往一张趋势表里写行，然后给那张表建个看板。 |
| BRD-003 | 判断标准：**如果有一天需要在平台代码里写"什么是缺陷密度"，那就越界了。** |
| BRD-004 | `_notices` **不允许建自由看板**（`NTF-009`）。**个人看板是平台内建的固定视图**，不是用户能配的那种看板。 |
| BRD-005 | **Web 只读**（G2），**由两道兑现且顺序不能反**：<br>**① 后端不存在写路由**——不是"有但不给 Web 用"，是不存在。这道是**结构性**的：前端就算想写也没有地方可发。<br>**② 前端不存在调用写接口的代码路径**，并用 CI 检查兜住"就加一个按钮"这种持续压力。这道是**纪律性**的，作用是让越界在**评审阶段**被看见，而不是等它撞上 404。<br>**看板上没有任何直接写库的按钮**——个人看板上的「标记已读」也是发一次 MCP 调用，走平台专属 tool。页面应当直接给出"在你的 Agent 里跑这条命令"。<br>**只有 ② 没有 ①，等于把一条安全属性交给前端自觉。** |
| BRD-006 | **一个主体的"完整时间线"横跨两张表**：状态怎么变的、谁改的、什么时候，在主体行的**单行历史**里；为什么这么变、谁表的态，在同实例的**全部结算行**里。**看板上是两个视图，MCP 上是两次查询——平台不做 join**（`TBL-023`）。 |
| BRD-007 | **Web 会话凭据与 MCP 令牌互不通用**；Web 会话不能用于任何写操作（I-L）。 |
| BRD-008 | **长文本（Markdown）列渲染时必须禁用内联 HTML 与脚本**，只渲染受限标记子集，外部资源不自动加载。**绝大多数 Markdown 渲染库默认开启内联 HTML**，而这些内容部分来自被分析的代码仓——**能往那个仓提交代码的人，就能影响它**。这是渲染这条攻击链上唯一的门。 |
| BRD-009 | `BRD-008` 必须**实际构造恶意内容验证**（内联脚本、事件处理属性、外部资源引用），不能只做代码审查。 |
| BRD-010 | 提供长文本的**原始形式下载**，供不信任渲染的人自行查看。 |
| BRD-011 | Web 的可见性完全遵循项目成员边界，并明确展示当前用户身份。 |

### 11.3 通知（`NTF`）

**通知不是一条投递管道，是 `_notices` 表上属于我的那些行。**

| ID | 需求 |
|---|---|
| NTF-001 | 每个用户有一个**个人看板**，显示的就是 `_notices` 按自己过滤后的视图。 |
| NTF-002 | 通知**只从事件派生**，不引入独立的产生路径——否则会出现"发了通知但账本里没有对应事实"（I-W）。 |
| NTF-003 | 内容由**确定性代码**从结构化事件生成，**不经模型**（G8）。 |
| NTF-004 | 内容中的自由文本**原样引用或截断**，不改写、不摘要、不翻译（G7）。 |
| NTF-005 | 只发给对该事件所属项目**有可见权限**的用户。 |
| NTF-006 | **不含凭据、令牌或产物原文，只含指针。** |
| NTF-007 | 值得通知的五类：**有节点在等我处理** · 流程实例已决定 · **我写的行未被采纳** · 执行完成或失败（尤其定时任务）· 表里的某行指派给我。 |
| NTF-008 | **通知行在业务写的串行区间之外追加**（`CON-006`）：写失败**只留痕，绝不回滚业务写**。这让"通知的失败绝不影响产生该事件的业务操作"成为**结构保证**，而不是"几乎不会失败"这种概率话术（I-W）。 |
| NTF-009 | `_notices` **只有两个平台专属 tool**：查我的未读 · 标记已读。**不派发通用查询 tool，不允许对它建自由看板**（I-Y）。 |
| NTF-010 | 读写都被平台**硬限定为 `user = 令牌持有人`**——这是行级可见性的**唯一例外**。立这个例外而不是做通用行级权限，理由是它**只有一张表、只有一条规则、平台自己写死**。 |
| NTF-011 | `readAt` 是**全系统唯一一个用户可改的系统表列**：只能改自己那一行、只能改这一列，由平台专属 tool 代写，**照样追加事件**（I-N）。 |
| NTF-012 | **插件读不到 `_notices`。** 流转插件根本不读表；输出插件的读表能力按声明授予，而 **`_notices` 不在可声明之列**（`PLG-012`）。<br>⚠️ 上一版这条写的是"ctx 层的收窄，不是隔离——进程内的插件绕过 ctx 读它是平凡的"。**D52 之后它是隔离**：载体不给别的路。 |
| NTF-013 | **不做投递渠道、订阅偏好、去重聚合窗口、重试。** 要把消息送出 XOps（邮件、IM），用**输出插件**。**平台侧不存在任何一条能承载任意内容、发给任意人的通路**（I-W）。 |
| NTF-014 | `_notices` 是**平台全局表**，因而能跨项目聚合"我在 N 个项目里的待办"。它不破项目数据边界——**边界由 `NTF-010` 那条行级限定守住**：一个人只能读到属于自己的行，而属于他的行只会来自他有权见的项目。 |

## 12. 与 XForge 的配合（`XFG`）

**这是配合关系，不是绑定关系**：XForge 可单独用（它的 local 审批在真实终端里完成）· XOps 可单独用（表、技能、任务、插件、流程都不需要 XForge 存在）· 两者一起用时 XOps 作为 XForge 的 **MCP 审批 provider**。

**XOps 挂了，XForge 侧的表现是"这一轮审批失败、可重试"，不是"变更被卡死"，更不是"变更被放行"。**

### 12.1 前提与登记

| ID | 需求 |
|---|---|
| XFG-001 | 链路成立需要五件事：① 在 XOps 建一个项目；② 绑定 XForge 所在的那个仓库；③ 登记 **policyId → 哪条流程**并声明**结果列映射**；④ **每个开发者用自己的 XOps 令牌**跑 `xforge approve`；⑤ 被审对象的 **gitHead 必须已推送到绑定的那个仓**。 |
| XFG-002 | **②③ 任一找不到时明确失败，绝不静默创建。** ③ 挂在 ② 的仓绑定上，不另开一套对象。 |
| XFG-003 | **结果列映射**声明：结算表的哪一列是 `decision`（approve/reject）、哪一列是 `reason`。**没有它，适配层拼不出 `poll_approval` 的返回值。** |
| XFG-004 | `approver` 由结算行的 `writtenBy` 解析：是人 → 就是他；是执行 → 取那个**私有任务的所有者**；是插件求值 → 取**安装该插件的维护者**。`role` 取该人在本项目的角色。 |
| XFG-005 | **④ 不是运维建议，是一条安全前提。** 职责分离（`FLW-026③`）整个压在"事件载荷里的发起者就是那个真人"上，而发起者 = 调用 `submit_approval_request` 所用令牌的持有人。**一旦团队共用一个令牌，这条会整体失效且无声**。`TOK-001` 因此必须被当作本链路的前置条件在文档与实例化流程中显式提示。 |
| XFG-006 | **⑤ 只影响自动化，不影响人。** gitHead 还没推上去时，任务的工作区准备会失败 → `FLW-026⑥` 不过 → 不结算、归为工作区错误、通知写入者；**人工写入不受影响**。调用方那边只会看到 `pending`，**所以这条失败必须真的发出通知**。 |

### 12.2 两个形状定死的 tool

| ID | 需求 |
|---|---|
| XFG-007 | 实现名为 **`submit_approval_request`** 的 tool，参数与 XForge 规格完全一致：`change` · `flow` · `stage` · `transition` · `policyId` · `revision`（含 `stateRevision`/`contentRevision`/`policySnapshotDigest`/`gitBase`/`gitHead`）· `governingDigest` · `roles` · `reason`。 |
| XFG-008 | 实现名为 **`poll_approval`** 的 tool，参数**只有** `governingDigest`。 |
| XFG-009 | 两个 tool 的返回值是**一个 `text` 类型的 content item，其 `text` 是一段 JSON 字符串**——**不使用 `structuredContent`**。 |
| XFG-010 | **两个 tool 的名字与参数由 XForge 定死，XOps 没有任何设计自由度，只有实现义务**（`MCP-004` 的窄接口纪律方向一致但来源不同）。 |
| XFG-011 | `submit_approval_request` 的处理：由仓绑定定位 XOps 项目（找不到 → 明确失败）→ 由 `policyId` + `roles` 映射到本项目的流程（找不到 → 明确失败）→ 按 **`governingDigest` 幂等**发起流程实例（**主体 = `governingDigest`**），第一个节点激活，**立即返回**。**不得重复开单**（`governingDigest` 到实例是一一映射）。 |
| XFG-012 | **原样保存 `revision` 各字段**（人做决定时要看清"我批的是哪一版"）。其中 **`gitHead` 同时作为事件载荷里的主体修订**喂给任务（`TRG-017`、`FLW-026⑦`）。 |
| XFG-013 | `poll_approval` **必须立即返回，绝不阻塞**：未决 → `pending`；已决 → `decided` + `decision` + `approver{id, role}` + `reason`（+ 可选 `expiresAt`），取自 `XFG-003` 声明的结果列映射；**从未提交过 → 明确的未知状态，不是报错**（XForge 会整轮重试：连接+提交+轮询，**必须对重试安全**）。 |
| XFG-014 | `poll_approval` 是**纯读操作，无副作用，可安全重复调用**。 |
| XFG-015 | `approver.role` 必须是 XForge 侧认得的角色名，且同时在 provider 条目与被满足的 policy 角色列表内。**XOps 侧应当自己先校验**——让角色配错在"告诉人类他的批准生效了"之前就失败。 |
| XFG-016 | `reason` 是不可信自由文本（G7），原样保存与展示，不解析。 |

### 12.3 三条必须记住的边界

| ID | 需求 |
|---|---|
| XFG-017 | **XOps 从不写任何仓库。** 回执由 XForge CLI 自己写进仓里，并在同一次运行里追加一条审计事件。回执不带签名，可信的是"项目自己的审计链里有一条匹配事件"（I-G）。 |
| XFG-018 | **Gate 拿不到凭据**：XForge 的 Gate 子进程会过滤掉一切凭据形状的环境变量。所以**绝不能**把归档前的校验设计成"Gate 去查 XOps"——它没有能力认证。**本域不提供任何供 Gate 调用的查询接口**（G6）。**这也是 XOps 挂了不影响开发的原因。** |
| XFG-019 | **角色以 XOps 为准**：XOps 返回自己的项目角色名，XForge 侧去对齐。**代价**：XOps 的角色固定为所有者/维护者/成员，若 XForge 侧某条 policy 要求 `verifier`，校验将永远失败且无法绕过。两条出路：约定 XForge 侧只用这三个名字，或日后在绑定上加一张三五行的映射表——**不要为此把 XOps 改成可配置角色系统**。 |
| XFG-020 | **不可用时可重试，不是放行。** 关停 XOps 之后跑 `xforge approve`，必须报连接失败可重试。**任何"连不上就跳过"的降级逻辑都会让变更被静默放行——这条必须实际断网测一次。** |

### 12.4 XForge 侧的配套是 XOps 的持续交付物

| ID | 需求 |
|---|---|
| XFG-021 | **四样，缺一样门就不存在**，由 XOps 提供并维护：① 一份 `McpServer` 资源（`transport: http` · `url` · `authTokenEnv` · `timeoutSeconds`）；② 它在 `manifest.yaml` 的 `scaffold.mcpServers` 里的登记；③ 一条 `approvals.providers[]` 条目（`roles` 与 XOps 实际返回的角色对齐）；④ 某条 Flow 的 `approvalPolicies[].providers` 里**引用这个 provider id**。 |
| XFG-022 | **①② 缺了会加载失败，③④ 缺了会静默失效**——后者更危险：`xforge doctor` 对未被引用的扩展资源**只警告、从不阻塞**，于是 provider 装好了、连得上、却没有任何一条 Flow 引用它，**这道审批门等于不存在，而一切看起来都正常**。因此必须提供一个**能检出 ③④ 缺失**的检查手段。 |
| XFG-023 | **两侧的版本对齐责任在 XOps 这边。** 这是一个**持续交付物**，不是一次性配置说明。 |
| XFG-024 | 验收必须用**真实的 `xforge approve --provider xops` 跑通**，不能只做孤立单测。 |

## 13. 两件必须诚实面对的事

这一节不是需求，是**验收时的解释框架**。它防的是把"可追溯"读成"正确"。

### 13.1 平台知道的是"可追溯"，不是"正确"

**平台不执行任何验证命令。** 所以：

> **XOps 的一切自动判定，可信度上限等于「写这个技能/插件的人 + 那次执行」的可信度。**

```text
平台真的知道的：
  哪个技能的哪个版本 · 哪个插件的哪个版本 · 哪次执行 · 读的哪个代码修订
  什么时候 · 谁授权的 · 被哪个事件触发 · 往哪张表写了几行、什么值
平台不知道的：
  这些行对不对
```

**审批不保证正确。它保证的是：多了一个具名的人为这件事负责。** 任务或插件代人写结算行之后，这个价值发生了一次**部分让渡**：保留的是"结算仍归属一个具名的人，且这个人不能是发起请求的那个人"；让渡的是"那个人不再逐次亲自看内容"。

**这是一次真实的取舍，不是一次免费的自动化。** 值得做，因为逐次人工点通过在高频场景下退化成橡皮图章——一个不看内容的人和一个不看内容的技能，可信度差不多，而技能与插件至少是**可复现、可审查、有版本**的。

对策不是加机制，是把它标清楚（这五条都已落成条目）：

```text
每一行都有 writtenBy，人/执行/插件/平台永不混同        → TBL-015
用于结算节点的私有技能版本与任务定义对项目成员可读        → SKL-011
已安装插件的源码对项目成员必须可读                      → PLG-010
未正常完成的执行，其产出的行明确标注来源且不结算任何节点   → TSK-005 / FLW-026⑥
产物超过体量上限时截断并明确标注，不静默丢弃             → EXE-025
```

**一条硬纪律**：**任何自动判定只看结构化列，从不读长文本列**（G9）。

### 13.2 插件是这套设计里唯一没有隔离的地方

> **技能跑在容器里，越界了也做不到什么；插件跑在进程内，越界了什么都做得到。**
> 前者靠隔离，后者只能靠治理（生成+测试流水线、维护者安装、源码必须可读、每一步留痕）。
> **能用技能解决的，不要用插件。**

| **给流转插件任何 I/O** | 输入由平台预取、输出交回平台。求值在写串行区间内 | `PLG-002` `FLW-003` |

## 16. 交付顺序

概念文档 §14 的演进路线。**需求包的边界与这条顺序对齐，而不是与本文的域划分一一对应**——域是为了编号稳定，包是为了能独立进流程、独立验收。各里程碑对应的包见 [`README.md` §5](README.md)。

```text
M0  工程地基　【RP-01 存储与写串行】
    Rust workspace 起架；**存储契约 + SQLite 实现**（CON-012）；
    **表级写串行的四步区间骨架**（CON-001～011，③④ 先留 no-op 扩展点位）
    ★ 硬验收：换一个内存实现进去，写入路径与它上面的一切不改一行
    ⚠️ 单独立出来的理由：串行区间与存储契约事后补等于重写写入路径，
       而它们与身份、项目、表都无关 —— 没有理由等在它们后面

M1  项目 + 表　【RP-02 身份项目审计 · RP-03 MCP 基座 · RP-04 表引擎
                · RP-05 读模型与只读 Web 后端 · RP-06 Web 前端】
    身份与令牌 · 项目与成员 · MCP 基座 · 追加式事件 · 只读 Web（后端 + 前端）
    + 表：建表（含保护级别）、加列、每张表的专属增删改查 tool、查单行历史
    + 平台自动补的列位（TBL-014）
    ★ 这本身就是个能用的东西 —— 一个 agent 友好的、可审计的记录系统

M2  技能跑起来　【RP-07 执行运行时 · RP-08 Git 仓绑定 · RP-09 技能资产
                · RP-10 任务与执行策略 · RP-11 事件、触发与派工单
                · RP-12 产出落地与保留期】
    执行运行时 —— 隔离是这一步的全部难点，五件事一件都不能少：
       ① 容器隔离全部条目（EXE-002～011）  ⚠️ **D62 之后归部署侧，见下**
       ② 分立进程 + XOps 自己的执行契约这一个接缝
          （硬验收：换成桩实现，契约不改；引擎的数据结构不得流进契约）
       ③ ~~容器后端的四个执行契约实现（EXE-029）~~ —— **D62 取消**：
          不做容器，隔离归部署侧；边界改由工具集、路径边界与派工单内容兑现
       ④ 跨执行的会话隔离（EXE-016，失效时没有报错）
       ⑤ 崩溃时在途执行不挂起、可重跑；超时不留孤儿会话；失败必须分类；
          **引擎不可用时绝不就地跑**（EXE-030）
    + Git 仓绑定（只读）+ 技能（含公共/私有与派生）+ 任务 + 手动触发
    + `_runs` + 平台在容器外写入
    + 单次 token 上限与用量记录 + 输出保留期与到期清理
      ⚠️ 两条都必须在 M2，不能推迟：token 上限——M3 一开定时触发就是无上限烧钱；
         retainUntil 是写入时就要落的列，事后补等于回填全部历史行
    ★ 主动攻击测试：每一项越界都必须在容器与能力层失败

M3  自动跑起来　【RP-13 自动触发】
    + 定时触发 → git webhook 触发（按平台逐个交付）
    ★ 夜里跑，早上看

M4  流程 + 插件 + 通知 + 模板　【RP-14 流程定义与实例 · RP-15 结算判定与保护
                              · RP-16 脚本载体与插件 · RP-17 通知 · RP-18 模板】
    + `_flows` / `_flow_nodes` · `_instance` 与状态列的保护
    + 流程定义与实例 · **节点声明求值所需的行**（FLW-003）
    + **QuickJS 载体**：能力解析、一次调用一个 runtime、字节码级中断、故障隔离
    + 造插件任务 · 插件安装（含能力披露）与配置 · 流转插件求值 · onComplete
    + bugs / issues / approvals 三套模板与插件
    + `_notices` + 个人看板
    ★ 七个测试一个都不能少：自发自批 · 多节点激活 · 修订一致 · 名单竞态
      · 状态列绕过 · 插件故障（含死循环） · 并发最后一票
    ★ 第八个：**插件能力测试**——没声明就够不到（未声明出网的发请求、
      未声明读表的查表、任何插件读 `_notices`），三项都必须失败在
      "函数不存在"，不是失败在"被拒绝"
    ⚠️ 通知在这一步而不是更晚：FLW-027 与 XFG-006 都写着"必须通知"，
       没有通知，自动化失灵就是静默的
    ⚠️ 模板从 M1 挪到这里：模板要建"表 + 流程 + 插件"三样，
       只有表的那半个模板不值得单独交付一次

M5  XForge 适配　【RP-19 XForge 适配】
    + 两个固定 tool + 一次绑仓 + 一条登记（含结果列映射）+ 两条约定
    + XForge 侧配套四样的交付与维护（缺后两样是静默失效）
    ★ 断网测试：关停 XOps 后 xforge approve 报可重试，不是放行

M6  多仓 · 独立对象存储 · 用户自定义模板的导出与提交 · 多实例部署
```

> **一条不能被时间压力推翻的顺序**：如果 M2 的隔离做不完，正确的做法是**整个推迟 M2、在 M1 停下**，而不是先上一个隔离不全的运行时。先跑起来再补隔离，等于在补上之前一直敞开，而这段时间里跑过的技能、读过的代码、泄过的凭据都追不回来。

## 18. 术语

| 术语 | 一句话 |
|---|---|
| **项目** | 唯一的归属、权限与数据边界。有不可变短名，当前绑一个 Git 仓 |
| **表 / 行** | 项目下命名的数据表与其中的记录。对外 CRUD，对内追加 |
| **系统表** | 平台维护、schema 固定：`_runs` · `_flows` · `_flow_nodes` · `_plugins` · `_notices` |
| **受保护表** | 建表时声明、不可降级。名单表是其一，只有所有者能写 |
| **结算表** | 流程节点的结算行写在这里。带受保护的 `_instance` 列 |
| **主体表** | 流程在治理哪张表的行（可选）。**不得与结算表相同**；它的状态列只有平台与流转插件能写 |
| **技能** | 用自然语言写的一份指令 + 几项声明。归属项目（公共）或用户（私有） |
| **任务** | 一个技能 + 订阅哪些事件 + 读哪些数据源 + 写哪些表 + onComplete + 执行策略 |
| **造插件任务** | 一种受限任务：只能手动触发，产出插件源码 + 测试用例 |
| **事件** | 定时 / Git / 手动 / 流程节点被激活 / 上游任务完成（白名单，仅此五类） |
| **执行** | 一次一次性容器的完整生命周期。永不覆盖，重跑产生新的一次 |
| **插件** | 由技能生成、维护者安装、**在 QuickJS 载体里执行**的 JS 代码。流转插件（零能力）/ 输出插件（三样声明出来的能力） |
| **能力声明** | 插件随源码一起产出的一份清单，说明它要用哪几样宿主绑定。**是版本的一部分**，安装时逐条披露，未声明即没有 |
| **载体** | 跑插件的那层东西。它管的是"插件能碰到什么"，管不到"插件会说什么"（`G11`） |
| **执行契约** | XOps 与执行引擎之间唯一的接缝。引擎的概念不得泄漏进它（`EXE-014`） |
| **存储契约** | 只有基本 CRUD 的一层 trait。换一个实现进去，写入路径与它上面的一切不改（`CON-012`） |
| **流程** | 有序节点序列 + 一张**结算表** + 可选的**主体表**（两者不得相同）+ 何时发起实例 |
| **流程实例** | 一条流程的一次运行，绑一个主体，落在 `_flows` 表 |
| **节点结算** | **结算表**上出现了满足条件、且写入者被允许的行 |
| **名单表** | 一种受保护表，行是人。**只有项目所有者能写**——它是审批权的元权限 |
| **模板** | 一套表 + 可选流程 + 可选插件，可一步实例化到项目里 |
| **看板** | 一张表的一个视图。个人看板 = `_notices` 里属于我的那些行 |
| **token 上限** | 一次执行的模型消耗上限，撞上即强制终止。项目级额度不做 |
| **保留期** | 任务分别声明输出（默认 1 个月）与过程记录（默认 7 天）保留多久。治理事实豁免，且豁免优先 |
| **表级写串行** | 一张表同时只有一个写；校验、追加、节点求值、插件写回在同一区间内，锁集合限于结算表与主体表 |

## 19. 需求化阶段定下的决策（D42～D48）

接概念文档 §16 的 D1～D41 续号。这七条是在需求化过程中由人定下的，**已在第 10.1 版并入概念文档 §16**，本节保留为详细版（带落点条目）。**第 11 版新增的 D49～D56 见 §20。**

| # | 决策 | 落点 |
|---|---|---|
| **D42** | **删表是软删除。** 表从列出结果中消失、专属 tool 停止派发，行与事件一律保留、单行历史仍可查；**表名不可复用**；被任何流程引用为结算表或主体表的表**不能删** | `TBL-026` |
| **D43** | **不做跨表写的原子性。** `_runs` 行与产出行之间只有**可见性顺序保证**——先落 `_runs`，再写产出行。两者之间崩溃是可接受的失败形态；反过来不可接受 | `CON-007` `CON-011` `TSK-006` |
| **D44** | **表数据不是执行的数据源，平台不做表导出。** 不给容器快照文件，也不给它到 XOps 的网络路径。需要表数据就经 MCP 查好，作为**任务的输入参数**传进去。**代价：技能读不到表**——这收窄了「数据源是 Git 仓和表」这句定位 | `EXE-012` `EXE-013` `SKL-007` |
| **D45** | **只有 insert 参与节点求值。** 结算表上的 update 与 delete 不触发求值、不结算、也不撤销任何已有结算。要改变结论只能再写一行或发起新实例 | `FLW-032` |
| **D46** | **存储层只使用基本增删改查，不依赖任何数据库特有能力**（触发器、存储过程、行锁、事务隔离级别、MVCC、外键、级联、JSON 列），因而**可更换**；表级写串行由**应用层**实现。**初始实现选 SQLite**（这一条是实现选型，记在这里只为说明 D46 的由来）| `CON-001` `CON-002` `CON-008` `CON-012` |
| **D47** | **筛选重叠按"激活集合"判定**：把流程展开成激活集合序列（串行节点各一个集合，并行组整体是一个集合），同一集合内两两、相邻集合之间都不得重叠；**判定取保守口径**，不能证明互斥即判为重叠并拒绝 | `FLW-008` |
| **D48** | **不做速率限制。** 既有 `R-01-33` 就此关闭。挡重复靠幂等（`MCP-006`、`TRG-013`）与重叠策略（`TSK-008`），挡成本靠单次 token 上限（`TSK-005`）与并发上限（`EXE-027`）；剩下的交给部署侧的反向代理 | `MCP-015` |

> **D46 有一个连带前提要认下来**：应用层的表级串行**只在单实例部署下成立**。多实例需要一把进程外的锁——那是另一个决定，现在不做。
>
> **D44 是本轮射程最大的一条**，它不只是"少一个功能"：`RP-06` 里"技能可以只读表、不碰代码仓"那类用法（例如"读账本生成周报"）**不再成立**。这类需求的新出路是：由 agent 经 MCP 查好放进任务输入，或者干脆用 `onComplete` 挂一个输出插件在进程内读表。
