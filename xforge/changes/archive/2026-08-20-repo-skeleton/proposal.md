# 仓库骨架

## Why

XOps 的需求已拆成 9 个包（`docs/requirements/`），架构已定（`xforge/architecture.md`）：`apps/{api,worker,web}` 与 `packages/{core,defects,repos,tasks,approvals,triggers,notify,runtime,store}`，外加 dsh 侧的 `dsh-bridge/`。

但**这些模块目前一个都不存在，仓库里也没有任何可以承载它们的结构**——没有 workspace、没有 TypeScript 编译基线、没有测试与 lint 的运行方式、没有 CI。

第一批要开工的两个需求包 RP-01（平台基座）与 RP-02（容器化执行运行时）**互不依赖、路径不重叠，本可以并行**。但它们都需要同一套根配置。谁先开工谁就得顺手把骨架建起来，另一个要么等、要么在同一批文件上冲突——而项目宪法明确要求「只并行化共享资源可被隔离的工作」。

**这个 Change 的全部意义，就是把那份共享资源先隔离出来。** 它自己不交付任何产品行为。

## Scope

仅限仓库根一级的工程基线：

- pnpm workspace 结构，声明 `apps/*` 与 `packages/*` 两个 glob
- TypeScript 编译基线（供各包继承的基础配置）
- 统一的类型检查、lint、测试三条命令，可在仓库根一次跑全量
- Node 版本的显式声明
- CI：在推送与 Pull Request 上执行上述三条命令
- `.gitignore` 补充构建与依赖产物

## Non-goals

- **不创建任何 `apps/*` 或 `packages/*` 的实现**。骨架只声明 workspace 能容纳它们，不预先铺出空目录树——那会把这个 Change 变成跨模块变更，也会留下一批没有内容的包。
- **不引入任何运行时依赖**：不配置数据库、对象存储、容器运行时，也不引入 dsh。
- **不写任何业务代码**，不新增任何 MCP tool、HTTP 端点或数据模型。
- **不做部署与发布**。
- **不选定业务技术栈中尚未决定的部分**（队列、关系库、容器编排均属后续 Change 的设计选型）。

## Actors

- **实现者**：后续每个需求包 Change 的开工者。骨架的唯一消费者就是他们。
- **CI**：在无人参与的情况下执行同一套命令，因此命令必须不依赖任何本地状态或交互。

## Success criteria

1. 在干净 clone 上安装依赖后，类型检查、lint、测试三条命令均可执行并通过。
2. 新增一个空的 workspace 包时，**无需修改任何根配置**即被纳入上述三条命令的覆盖范围。
3. CI 在推送与 Pull Request 上执行这三条命令，任一失败即判定失败。
4. 仓库中不存在任何业务代码与运行时依赖。

## Flow 选择

**本 Change 覆盖了 manifest 默认的 `solid`，改用 `quick`。**

理由是它精确落在 Quick 的适用范围上：`risk: low`、单模块（`root`）、边界清晰、且完全可逆——骨架配置写错了删掉重来即可，不产生任何需要迁移的数据、不定义任何对外契约、不承载任何安全或隐私影响。

Quick 没有 Check Stage，因而不带 Constitution 台账。这对本 Change 是恰当的，而不是绕开：它**没有任何原则级风险可供逐条认证**——它不交付行为、不触碰信任边界、不产生可观测的对外需求。相反，让它走 Solid 会为一份"全部内容都是工程基线"的变更套上设计与检查两道流程，成本落在真正需要这两道的 RP-01 与 RP-02 之前。

需要说明的是：**后续每一个需求包的 Change 都不适用这条理由**，它们将回到默认的 `solid`。
